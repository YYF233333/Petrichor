## Language

- `f.bind(x)` where `f` has a parameter with a default. Spec §3.11 types it by dropping the last parameters. The engine passes bound arguments after the caller's (`core/variant/callable_bind.cpp:141-150`), so `x` lands where the caller's arguments end.
  - So `pressed.connect(f.bind("Deck"))` with `func f(title: String, randomized := false)` is refused, though it runs (deck_builder_tutorial `scenes/run/run.gd:148`).
  - In corpus v2, 27 such binds of a class's own methods leave the defaults to the caller, and 17 fill them. Scene connections already follow the engine (`checker_scenes.cpp`).
- A track naming an engine property that ClassDB does not list is refused, as `current` of AudioListener2D (spec §7.7). The engine takes such a name through `_set`. The check could ask an instance of the class for its properties.
- `Array[PackedScene[T]]` cannot be written, though `[preload(...)]` infers it and spec §7.4 lists container elements.
- `find_key()` of `Dictionary[T?, V]` for an object `T`. The engine gives null for a missing key and for a None key.
- Scenes used as roots that the checks do not know as such (spec §7.2, §7.3, §7.5):
  - autoloads that are scenes, and the paths that `change_scene_to_file()` and a MultiplayerSpawner name. The spec does not list them;
  - for the node paths of a script, all but the main scene. The script check does not ask how a scene is used (architecture §6.4). So a scene also inherited may lack a node without an error, which the run-time check catches.
- The root of a scene that only GDScript uses as a root (spec §7.5). Is it a compile error when it lacks a must-assign export? GDScript can assign one after `instantiate()`. Now only the check at ready looks.
- A track or synchronized property whose path leads to no node: a warning (spec §7.7). It goes with the warnings of spec §7.2.
- Members that animation tracks and synchronized properties name, unchecked for `pub` and existence (spec §7.7, §10.5):
  - through a path that leaves the scene storing it, as from an AnimationPlayer at its root;
  - after the first subname, on a resource of this language, as `health` in `Body:stats:health`.
- Animation tracks in an inherited scene. The checks read the `root_node` and the libraries of the scene's own layer only (`src/adapter/editor/scene_index.cpp:240-245, 295-307`). So a derived scene can miss an error or get a false one.
- Types of a C# class's members that are narrower than what is seen (spec §11.1):
  - an exported object property is `Object?`, as its class is only in the hint string;
  - a method's parameters and results have their native class, as the engine's generator drops the script class.
- An assignment inside a branch forgets the `None` narrowing of every level, the outer ones and sibling branches included (`Checker::forget()`). An `if` keeps one branch's narrowing only when the other must leave. So legal code that relies on narrowing after branches meet can be refused. The fix keeps the outer state per branch and intersects it where they meet.
- Whether GDScript should see a `pub` function's containers whose elements exist only in this language (spec §3.14). Overrides of engine virtuals returning `Variant` and `pub` static variables do not apply that rule now. A foreign element is a program error when read, with no memory problem.
- In an inner class, a bare value naming an outer class's instance function is refused for want of an outer object. That holds even when the inner class's engine base has a method of the name. Bare-name resolution looks up engine members first (spec §4.1), and GDScript takes the engine method.
- A script without a path cannot take a method of its own struct as a value. The value names its class by the script's path. The verifier then rejects the module as an internal compiler error (`src/compiler/lower.cpp`, `struct_method_call`). A script made at run time in the editor, as by `PetScript.new()`, has no path.
- An index of a vector constant, as `V[0]` of `const V := Vector3(1, 2, 3)`, is refused in a constant expression, though spec §4.5 lists indexes of constants. The engine computes the vector when the class loads, and a stored constant has no index to apply then (`fold_subscript` in `src/compiler/constant.cpp`). The same holds for `Color`, `Basis` and the other values the engine indexes.

## Runtime

- A struct method taken as a value binds the class image of its creation (`src/runtime/method_callable.h`, `StructMethodCallable`). After a hot reload it still runs the old body, unlike spec §12.4.
- An inner class that extends the class around it makes their images hold each other, through `base` and `inner_classes` (`src/runtime/class_image.h`). So the images are never freed, nor their static variables, even after the script unloads.
- Comparing and hashing a struct, a payload enum or `T??` uses the raw object id of a nested `T?` field. A freed object there does not compare equal to `None`, though it does at the top level (`src/runtime/values.cpp`).
- A Task of another result type is described by its class alone, as in "expected CoroutineTask, found CoroutineTask".
- Messages name an inner class by its path, as `res://a.pet::Plain`, where the script writes `A.Plain`.
- GDScript can pass an `async func() -> String` where `func() -> Task[int]` is expected. `.call()` then reports the mismatch only at the `await`, while `callv()` refuses at once. Read from the code, not run.
- `call()` by a name that is not pub fails without naming the method or the cause. It only says that calling `call()` failed.
- Double-precision builds of the engine (`precision=double`), whose constants spec §4.5 provides for. The bytecode lays out built-in values at their sizes in standard builds. So initialization and loading refuse such builds (`check_value_sizes()`). The 0.1 release notes promise them before 1.0.
  - With them, the format id must cover the value sizes. It is computed when SConstruct runs, before `gen/` exists.
- Ordering of arrays of engine types as spec §5.2 says. It differs from the engine's operators only with NaN, so it waits for the open question on NaN.
- Range checks of ints passed through an engine method's value, as `f.call(x)` (spec §10.6). The value is the engine's Callable, which converts without them.
- A Callable of another language after `bind()`, called through a function type, is taken for a function value of this language (spec §8.1). A program error in this language's code that it calls then ends the caller's run silently. The engine does not show what a bound Callable wraps.
- Destruction order of `LambdaCallable` at exit when `WorkerThreadPool` holds unclaimed tasks (`main/main.cpp:5268, 5295`, `core/object/worker_thread_pool.cpp:855-880`, `ed1daf0`). Add an engine test and verify teardown.
- Before the bytecode format gets its version, with Mod (architecture §6.1), settle these decisions of the format:
  - static variables of other scripts are referenced by index;
  - the format id does not cover the value sizes;
  - the await instructions do not carry the type of their result;
  - `Task[T]` holds T as a key string in the type table and as a type index in instructions;
  - opcodes are numbered by their position in the X macro, so inserting one renumbers the rest;
  - `Function::params` repeats a prefix of `slots`, and `CALL_AWAIT_BUILTIN` is recognized by its method name;
  - hot reload compares declarations by a list kept by hand beside the serializer's fields. Driven by those fields, a new field would count by default.

## Performance

Engine methods with a MethodBind, also the accessors of engine properties, are called through its ptrcall (architecture §2.2). Vararg methods and other languages' methods and properties still go by name with Variant arguments.

- Engine singletons and autoloads resolved once. Now GET_SINGLETON looks the name up at every run, and GET_AUTOLOAD calls get_node_or_null. A singleton's pointer can be kept, and an autoload's ObjectID with a liveness check.
- Engine callbacks such as `_process(delta)`: no entry check of value-type arguments, whose types the engine guarantees.
- Calls between classes of this language: the method found by name once per call site. A run keeps one version of each class, which allows this (spec §12.4). Now these are loaded through ResourceLoader at every use:
  - a static method's script;
  - the script `Class.new()` sets;
  - the class of a static variable that another class or an inner class uses (spec §4.8).
- Calls within a class: since inheritance, they pass arguments the general way of calls between classes. They also repeat checks that loading made. The calls benchmark went from 18 to 22 ms (architecture §4).
- Function values that still go through the engine, with Variant arguments: struct method values and `async` functions. A struct is encoded and decoded on the way.
- Calls by name: every object result is asked whether it is a `GDScriptFunctionState`, by a call into the engine. Only methods of GDScript classes return one (spec §9.8).
- Default values built anew. Each call constructs every slot whose default is not zero, such as an Array's. CLEAR builds such a default again for each register it clears (spec §6.8). Two remedies:
  - registers whose scopes do not overlap share slots, as GDScript pools its temporaries (`modules/gdscript/gdscript_byte_codegen.cpp:122-131`, `ed1daf0`);
  - CLEAR copies one shared empty container instead of making one.
- Optimizations from what static analysis knows, keeping the meaning. Lowering does not know which classes are RefCounted, so CLEAR clears every object register (spec §6.8). An object whose static type is not RefCounted, such as a Node, holds no reference, and its clear can go.
- Containers. Reading, writing and iterating over an Array's elements call the engine once each (architecture §2.2).
  - Built-in methods with a Variant result, such as `pop_back()`, take the general way of a call. So do methods that handle elements or keys. It costs about 11 ns more than a plain call.
  - A Dictionary read calls the engine twice, for `has()` and the lookup, after the key is made a Variant.
  - The check that a container is not read-only before each change is a call into the engine (spec §3.8).
  - Escape analysis can give containers that do not escape a private representation (architecture §2.2). The engine container stays the reference semantics.
  - A private representation supports some operations. A container that uses others keeps the engine's. Each private operation is tested against the engine's.
- An interpreter whose speed does not depend on code layout. The compute benchmarks could then gate changes again (architecture §4).
  - Placing `run` first in `.text` (`__declspec(code_seg(".text$a"))`) steadied float_loop, members and vectors, but not int_loop.
  - Candidates:
    - dispatch without one shared indirect jump, as computed goto or tail calls do (architecture §2.2);
    - placing the hot handlers.
- Instructions left in compute code, which already beats GDScript by 1.2 to 3.5 times.
  - Each evaluation of a String literal copies it with an instruction. Other literals are preset in the frame or read from the constant table.
  - Each statement starts with a LINE instruction, one of six per iteration of int_loop. GDScript debug builds also emit one per statement (`modules/gdscript/gdscript.cpp:2871-2875`, `ed1daf0`). Release builds emit none.
    - A table from code positions to lines would replace it.
    - An error would look its line up by position. The handler calls that pass a line would drop it.
    - Every engine error captures the backtraces of all languages (`core/error/error_macros.cpp:126`, `ed1daf0`). So a frame would save its position before each instruction that can call the engine. Lua saves it only before such instructions. CPython 3.11 and later save it at every instruction.
    - Under the debugger, breakpoints, stepping and the editor's break button need a call at each line (`core/debugger/engine_debugger.h:128-134`, `ed1daf0`). The debugger is on or off for the whole process. When it is off, the runtime would drop LINE as it loads the code.
    - The compiler could record each instruction's statement in the table. Such a table would also fix a wrong line. From the second pass on, an error in a `while` condition is reported at the body's last statement. GDScript does the same (`modules/gdscript/gdscript_compiler.cpp:1903`, `ed1daf0`).
- Large projects, before teams bring real ones in 0.3. A generated project of 1000 scripts, 300 scenes and 60 `.gd` files, on the official 4.7.2 editor, headless:
  - opening it takes 80 to 150 s, and the headless build about 80 s in all. Most of it reads each scene once.
    - Reading a scene loads the scenes it instances, and compiles their scripts anew, as nothing keeps them loaded (`SceneIndex::read`).
    - Instances nest about 30 deep there, likely deeper than in real projects.
    - Ways out, to choose with the owner:
      - keep loaded scripts alive in the scene index;
      - compile scripts lazily on load, as GDScript's cache does;
      - read the structure from the scene text;
  - renaming a `pub` member that every script and scene uses takes 9 to 16 s to its preview at first, 5 to 10 s after. Each checks every script twice, before and after the edits;
  - applying it takes about 100 s. Two thirds of it reload the open scene, which reads every rewritten scene again;
  - `EditorFileSystem::update_file` takes 15 ms for each script there. It saves the whole list of global classes, and `update_files` is not bound (`editor/file_system/editor_file_system.cpp:2160-2197, 3730`, `ed1daf0`);
  - renaming a local takes 0.4 to 0.6 s. The script editor's check of a script on a node takes 10 ms unchanged and 0.45 to 0.65 s after a keystroke.
    - Each pass lists every scene and parses the header of each script on a node.
    - After a keystroke a check makes two such passes: compiling the script, and collecting the scenes' errors in it (`Analysis::placed_errors`).
  - Once fixed, CI holds these times to a budget (architecture §5, step 11).
- Benchmarks of real workloads; optimizations of the IR and code generation after those. In the init function, instructions that can run other code are barriers to them.
- Liveness of the IR's registers (`src/compiler/ir.h`), one analysis on the IR before any optimization.
  - It serves the warning `modified_copy` (spec §3.6), which is off until then.
  - It also serves native code's register allocation (architecture §5).
  - One table states each opcode's operands and whether each is read, written or both. It replaces the two schema strings, `stores_last` and the verifier's per-instruction rules. Writing a View writes part of its root.
  - With this first IR lint, lowering gets a warning channel, and `@warning_ignore` filters after lowering. Each instruction records its statement's token range, where the warning shows.
  - The warning takes a write to a field of a struct loop variable, after which the variable is not live. The write may also go through a value type's subscript, as `h.pos[0] = 1.0`.
  - A read in an inner loop's next iteration keeps the variable live, as `while h.count > 0: h.count -= 1`. So does a lambda's capture.
  - `continue`, `break` and `return` end its paths.
  - The warning shows only for files without errors, which have IR. The checker's former cases are in `git show 3e63b1c:tests/compiler/test_warnings.cpp`.

## Upstream

- List the gaps and workarounds hit in `ScriptLanguageExtension`, with citations, for the owner's reply on [#14652](https://github.com/godotengine/godot-proposals/issues/14652).
- Godot: three defects in `ScriptInstanceExtension` (`core/object/script_language_extension.h:870-892, 909-926`, `core/extension/gdextension_interface.cpp:1589`, `ed1daf0`):
  - missing fallback callbacks leave `*r_valid` uninitialized;
  - `object_get_script_instance` casts a placeholder instance to `ScriptInstanceExtension`;
  - an unset `refcount_decremented` returns `false`, leaking `RefCounted` owners.
- Godot: two defects in the GDScript VM (`modules/gdscript/gdscript_vm.cpp:1675-1681, 2667-2668`, `ed1daf0`):
  - resuming an `await` writes `null` unchecked into a typed value register, crashing on a cancelled coroutine;
  - in release builds, `as` copies a non-object value into a typed object slot.
- Godot: `ClassDB` leaves return and parameter metadata empty on `MethodInfo` (`core/object/method_info.h:55-56`, `core/object/class_db.cpp:955-974`, `ed1daf0`). Filling and exporting them exposes `RequiredResult` and integer widths at runtime.
- Godot: GDScript cannot call static methods of non-GDScript scripts or read the member types of non-GDScript autoloads (`core/object/object.cpp:800-826`, `modules/gdscript/gdscript_analyzer.cpp:806-826`, `ed1daf0`; [#14614](https://github.com/godotengine/godot-proposals/issues/14614)).
- Objects that an extension creates have no signal mutex. `_postinitialize` does not run for them (`core/extension/gdextension_interface.cpp:1669-1672`, `core/object/object.cpp:226-231`, `ed1daf0`; godot#125308). So a task's `completed` and `cancelled` are unguarded when GDScript awaits it from another thread.
- GDScript's per-iteration clearing of loop-body locals, left as commented-out TODOs (engine facts). It would match spec §6.8. The owner may contribute it.
- Store-forwarding stalls in moves of Variant, found while profiling arrays (d516c08). A wide load reads a Variant just written by narrower stores. It then waits for those stores to reach the cache. The owner may contribute both fixes once the current work is done.
  - godot-cpp: the move constructor and assignment are out of line and swap the bytes (`src/variant/variant.cpp:90-92, 551-554`, `8070599`).
    - MSVC builds have no LTO by default, so no caller can inline them (`tools/windows.py:214-217`).
    - Every moved Variant therefore goes through memory. In one profile of Array element writes, 38% of the time was in the move.
    - Inline in the header, they could copy the bytes and set the source to NIL.
  - Godot: `Array::set()` copies the value, validates the copy and moves it into place (`core/variant/array.cpp:517-523`, `ed1daf0`).
    - For an int, the copy writes 8 bytes of `_data`, and the move reads all 16 (`core/variant/variant.cpp:1148-1150`, `core/variant/variant.h:853-861`, `ed1daf0`).
    - GDScript spends 54% of a loop writing `Array[int]` elements stalled there. `push_back()` has the same shape (`core/variant/array.cpp:282-287`, `ed1daf0`).
    - A candidate fix: `reference()` copies the whole `_data` for types that need no deinit.
  - Each patch needs a benchmark that shows its gain. `docs/development.md` describes the profiling.
- Godot: a script's `_get` and `_set` take engine property names in GDScript's `.` access, not in calls of their methods. On 4.7.2, `label.text = s` goes to a `_set` that takes `text`, and `label.set_text(s)` does not. Object's docs say these methods are not called for built-in properties (engine facts). The owner may report it as an issue, or contribute a PR that makes the docs and the behavior agree.
  - [#99828](https://github.com/godotengine/godot/issues/99828) is about a script's own properties, which these methods do not see. It likely led to the note in the docs.
- Godot: in the official Windows builds, each read of a `thread_local` goes through GCC's emulated TLS. The owner may report it as an issue.
  - Each read calls winpthreads' `pthread_getspecific`, as disassembly of the official 4.7.2 binary shows. That call saves the last error, takes a spin lock and restores the error.
  - Node's thread guards make such reads in each guarded method of debug builds (`scene/main/node.h:694-716, 934-948`, `core/os/thread_safe.cpp:36-38`, `ed1daf0`).
  - In the engine_method benchmark, each `Node3D.translate()` makes about four such reads. They take about two thirds of each iteration, in GDScript as in this language.
  - Candidate fixes: native TLS in the official builds, or guards that read fewer thread-locals.
- godot-cpp: each object an extension constructs makes a StringName from its engine class's name. The owner may contribute a fix.
  - The default constructor of an engine class passes its name as a C string (`include/godot_cpp/classes/wrapped.hpp:436, 516`, `8070599`).
  - Wrapped's constructor takes a StringName, so each construction converts it (`wrapped.hpp:133`, `8070599`). The engine then looks the name up under a lock.
  - In coroutines.pet, when each call made a CoroutineTask, this took 1.8% of the loop. The whole construction took 14.5%.
  - A candidate fix: pass the class's cached `get_class_static()` instead.
- Godot: objects record no creation site. The owner may contribute an option for debug builds that records one, which would serve GDScript too.
  - `ObjectDB::cleanup` lists leaked objects only with `--verbose`, by class, ID and path (`core/object/object.cpp:2532-2568`, `ed1daf0`).
  - Script backtraces can be captured at any point (`core/object/script_language.h:103`, `ed1daf0`). Capturing one as an object is made would give its site.
  - With it, this language's table of the engine objects it makes could go.
- Godot: the open [#124220](https://github.com/godotengine/godot/pull/124220) changes how the script editor takes an extension's errors and warnings. The owner may comment before it merges; nothing here changes until then.
  - It groups every error that names a path into one diagnostic on the last line. The editor does not underline it (`core/object/script_language_extension.h:425-436`, `editor/script/script_text_editor.cpp:756-758`, `05ee117`).
  - On 4.7 an extension must name its own script there, as this one does (`editor/script/script_text_editor.cpp:859-860`, `ed1daf0`; `PetLanguage::_validate`).
  - It also puts the extension's one-based lines and columns into zero-based ranges, so errors and warnings move down a line (`core/object/script_language_extension.h:429, 459`, `4febb8d`). GDScript's own conversion subtracts one (`modules/gdscript/gdscript_editor.cpp:161-164`, `4febb8d`).
  - Once it merges, one build would need different output per engine version. A fix in the wrapper keeps the contract: take the script's own path as its own, and subtract one.
- Views of the enums, inner classes and static variables of GDScript classes, a later addition (spec §11.1, §14.2). They need a change in Godot first, which the owner may contribute.
- Godot: String has no method that replaces the character at a position. The owner may contribute one.
  - Its methods replace by content, insert or erase (`core/variant/variant_call.cpp:2039-2048`, `ed1daf0`).
  - Here `s[i] = c` is a compile error, and its fix uses `erase()` and `insert()` (spec §5.1).

## Open questions

- Whether the migration's inference counts the `null` that GDScript gives a variable declared without a value (architecture §6.6). Counted, a member assigned in `_ready` becomes `T?`, and an `int` counter `int?`. Not counted, they become `T` and `int`. A member of type `T` must then be assigned, which the checker takes an ancestor to do (spec §6.2). The inference does not count it yet. Starter-Kit-FPS and deck_builder_tutorial have no such variable.
- Whether a method that overrides a `pub` method of a base class is `pub` without writing it (spec §4.2). Now the override must repeat `pub`, though an exported variable and an `@rpc` function need not write it. Kotlin keeps the overridden member's visibility, as its docs state for `protected` and `internal`. The owner finds that object-oriented languages have not settled it.
- Whether a C# property without `[Export]` is a known limitation (spec §11.1). The editor lists only exported ones, so `c.Hits` is a compile error.
- Whether `reduce()` types its lambda from the start value, as `func(A, T) -> A` (spec §3.8). Now the lambda's types must be written. A `None` start would need a rule of its own.
- Whether a function value turned into a Callable has only its result checked for `T??` and `Variant?` (spec §10.1). Parameters cannot lose a `None`: the engine passes null or a boxed value. Now `Array[int??].filter(func(x): ...)` is refused. `bind()`, `callv()` and a function type that holds `T??` are not checked, and turn `Some(None)` into `None`.
- Design questions from the third coverage rerun, which the spec leaves open:
  - engine classes as values, as gdUnit4 passes `[InputEventMouseButton, …]` (0.7% of the files; spec §2.6). They would also let `is_instance_of(v, T)` take a native class held in a variable. Decide them before 0.9, with the type patterns of `match` (spec §14.2). An identifier is a value pattern (spec §5.6), so a class that is a value takes the spelling of a type pattern;
  - `Array[T](a)` as a typed copy, which the corpus does not use.
- For 0.4: the rules of `@tool` in the editor, with their implementation (spec §2.3, §14.3; architecture §5, 0.9). They cover keeping edited state across declaration changes via entry checks, and folding repeated per-frame errors.
  - When the work starts, gather into one check the about ten branches on `Engine::is_editor_hint()` that mean no code runs in the editor.
  - `PetScript::set_image` swaps every instance's image without comparing declarations. Under `@tool` a changed layout would then corrupt memory, so it must compare them first.
- Before 0.9: how `NaN` behaves in containers, which GDScript handles inconsistently (spec §5.2, engine facts). NaN rarely stands for a legal state in game logic. Candidates:
  - forbid `NaN` from entering containers;
  - warn wherever a `NaN` is detected.
  A survey of the corpus decides. Until then, spec §5.2 marks it a known limitation.
- Whether setters that run before ready wait for ready on their own after the first version (spec §6.5, §14.2). The alternative is writing the behavior in the setter. The owner suspects that the implicit suspension makes setters hard to understand.
- Before 0.9: whether a container that holds itself is a program error as a `Dictionary` key (spec §3.8). The engine stops hashing it at a depth of 100 with an error. One that holds itself twice takes about 2^100 steps, in GDScript too (`core/variant/array.cpp:195-208`, `ed1daf0`).
- Whether a nesting depth limit is a compile error. Very deep code overflows the compiler's stack and crashes the editor. On Windows' 8 MB main thread that takes 3,000 levels of `[[…]]`, or about 2,000–4,000 `elif` branches or operands of one chain. Corpus v2's longest `elif` chain has 77 branches. Decide when compiling runs on a thread with a small stack, or when someone hits the limit.
- The long-term boundary of compatibility with GDScript and Godot: which agreements are promises and which merely hold today. How semantics may change is settled (architecture §5, 0.9).
- Before 0.9: the text that `str`, `print` and `%` give for values of this language (spec §5.1). Showing them as written is a later addition (spec §14.2). After the freeze it would change what legal code does.
- Before 0.9: a design on paper for the cleanup code of a cancelled task, a later addition (spec §9.4, §14.2). It must fit `cancel()` releasing the frame at once (spec §9.3).
- After 0.3 and before 0.9: user-defined generics (spec §3.10, §14.3, design-notes §1.1). Their definitions stay in their own modules (architecture §6.1).
- After 0.3 and before 0.9: tuples for multi-parameter signal `await` (spec §9.6, §14.3). Decide then whether `await Task.all([...])` also returns a tuple of heterogeneous results (§9.5).
  - About half of the uses in corpus v2 await `HTTPRequest.request_completed`, often reading `[3]`. Fields named by the signal's parameters, as `.body`, are a candidate besides tuples.
  - Before them, `AWAIT_TASK` and `AWAIT_SIGNAL` must carry the type of their result, as other instructions with a result do. Now the VM searches the frame's slots on each resume.
- After 0.3 and before 0.9: default values of lambda parameters and of interface method parameters, with optional parameters in function types (spec §3.9, §3.11, §14.3).
  - Before them, one `Signature` value should serve overriding, implementing, signal handlers and function-type conversion. Now each repeats the rules of compatibility and argument counts.
  - Before them, hot reload must tell function types apart. `type_key` erases them, so a change from `Callable` to `func() -> void` counts as a body change.
- Before the migration tool of 0.3: how many GDScript files migrating one class drags along in the games of corpus v2. GDScript cannot call this language's static methods or use its enums in types (spec §11.3). If the number is large, the tool generates forwarding shells in 0.3.
  - The proper fix is upstream: [godot#118595](https://github.com/godotengine/godot/pull/118595) for static methods has waited for review since July. Enums in types need a change of their own.
  - Engines older than the fix keep the restriction, back to 4.4 (architecture §6.3).
- The differences from GDScript that spec §1.2 names stay open for public comment until 0.9, literals typed by their elements above all (design-notes). Revisit one only on feedback with real code.
- A cycle of static initialization whose two classes load on two loader threads deadlocks, instead of being a program error (`initialize_class` in `src/runtime/vm.cpp`). The cycle is a program error anyway. Whether GDScript deadlocks too is unchecked.
- Whether the spec gives a spelling of GDScript's truthiness for a `Variant` condition. `v != None` misses 0, "" and empty values, and the exact `bool(type_convert(v, TYPE_BOOL))` is no idiom. The second paper migration has no such condition.
- Whether a class may be named as a standard type of this language, as `class_name Result` (spec §4.1). It is a compile error for now. Corpus v1 has no such class name. Inner classes may take these names, as godot-tiny-mmo's `class Result` does.
- Whether a member may have the name of a member of another kind in a base class of this language (spec §4.1). It is a compile error, as in GDScript (`modules/gdscript/gdscript_analyzer.cpp:234-253`, `ed1daf0`). An example is a function named as an inherited enum.
- Whether the scene index finds an inherited scene's overrides by `unique_id`, as the engine does since 4.6. After a base scene renames a node, the engine finds them by id (`scene/resources/packed_scene.cpp:286-299`, `ed1daf0`). The index merges them by path (`read_scene` in `src/adapter/editor/scene_index.cpp`). So a check may report a false error until the inherited scene is saved again.
- The rule that keeps a member's old name in its declaration (architecture §6.4). It is proposed when a team that edits scenes in parallel needs it. Until then renaming rewrites scenes.
- A constant named as an autoload, written in a type: a compile error for now (spec §11.1). Allow it later as the nearer name, or as the autoload as GDScript does?
- Members that are non-null only once the node is ready, which need a design of their own. The owner likens it to linear types. It covers these (spec §6.2, §6.4):
  - members that must be assigned, and where the compiler looks for the assignment;
  - assignments by ancestors, which the checker now assumes without looking for them:
    - it takes a must-assign member of a node with an owner as one they assign, unless it is exported or `_init` assigns it;
    - the spec requires `$Child.target = v` or an `@onready` reference in their `_ready`, or else `T?`. It marks the check a known limitation;
  - members assigned after ready, which now must be `T?`.
- How third-party C++ extensions declare non-null results and narrower types once a project in 0.3 needs them (spec §10.2, §10.3). Candidates are an external metadata file and upstream `ClassDB` metadata.
- How to test the gain in maintenance. Use the language in a real project through several rounds of changing requirements. See how many problems it points out ahead of renames, interface changes and refactorings across files. The cost of adoption includes migrating in step by step, mixing and leaving. With cross-language inheritance restricted, the unit of migration may be an inheritance cluster or a subsystem.
  - Record the share of edits that the compiler locates during a change. Also record how defects fall across editing, instantiation, runtime and silent wrong behavior.
- After 1.0: how this language coexists with Godot's shading language, which is statically typed itself. The gap is where a script names a uniform by a string, as `material.set_shader_parameter("tint", c)`. An unknown name is stored without an error (`scene/resources/material.cpp:419-433`, `ed1daf0`). Corpus v2 has 1651 such calls with a literal name, in 318 files of 72 projects. Candidates, smallest first:
  - check the name and the value's type against the shader's uniforms, as literal names are checked (spec §10.4). The material's shader comes from scenes or `preload`, as for `PackedScene[T]`;
  - a typed handle generated from the shader, as `material.params.tint`;
  - shaders written in a language of this toolchain.
