# Petrichor 实现架构

**草案 · 2026-10-29**

本文记录实现层面的决定：组件划分、值的表示、测试和推进顺序。语言规则以[语言规范](language-spec.zh.md)为准。实现中发现规范有问题时，单独提交修改规范，不在实现中放宽规则。引擎事实对照 Godot 4.7.2-stable（提交 `ed1daf0`）核对，汇总见[引擎事实](engine-facts.md)。

## 1. 已定的选择

- **C++17、godot-cpp、SCons。** 解释器要在 iOS 和主机上运行（规范 §12.2），以后还可能改为引擎模块（§1.3）。引擎用 C++17 编译（`SConstruct:916, 921`），引擎模块只能用 SCons 构建。godot-cpp 固定在某个提交，以 `api_version=4.7` 构建。引擎提高 C++ 标准之前本项目也不提高：C++20 只带来方便，强制尾调用是编译器扩展。
- **目标引擎是 Godot 4.7。** 引擎加载最低版本不高于自身的扩展，所以声明 4.7 的构建也能在之后的引擎上加载（`core/extension/gdextension_library_loader.cpp:315-329`）。但只对照 4.7.2 核对过。在之后的引擎上运行，还要求引擎的值保持本构建依赖的布局（`src/runtime/values.h`）：
  - Variant 先存类型，数据从第 8 字节起，对象存为 ObjectID 和指针；
  - 各内置类型不超过字节码为它预留的大小，运行时在加载时检查。
- **导出的游戏只含字节码**（规范 §1.3）。`.gdextension` 按功能标签为编辑器和导出模板选择不同的库（`gdextension_library_loader.cpp:82-96`）。编辑器用的库含编译器，导出模板用的库只含运行时。
- **寄存器按静态类型存放原生值。** GDScript 即使静态类型已知，寄存器也是 Variant，运算和引擎调用都经 Variant（`modules/gdscript/gdscript_vm.cpp:536, 848-862, 2273-2313`）。本语言省掉这些开销，这是“明显快于 GDScript”（规范 §12.2）的主要来源。
- **从编辑器运行时，游戏读取编辑器写好的字节码，自己不编译**（§2.4）。

## 2. 组件

| 组件 | 依赖 | 内容 |
|---|---|---|
| compiler | 不依赖 Godot | 词法和语法分析、语义分析、场景检查、带类型的 IR、字节码生成、诊断、符号索引 |
| bytecode | 不依赖 Godot | 编译结果的格式、序列化和校验，compiler 与 runtime 共用 |
| runtime | godot-cpp | 字节码加载、虚拟机、值和类型描述、任务、程序错误、引擎边界上的检查和转换 |
| adapter | godot-cpp、runtime；编辑器用的库还依赖 compiler | 脚本语言、脚本和脚本实例三个扩展接口，资源的加载和保存，导出插件，编辑器插件，无界面命令 |

### 2.1 compiler

- 不含 Godot 的头文件，构建时也不给它 godot-cpp 的头文件路径。所以它的测试是不启动引擎的普通 C++ 程序，改为引擎模块时也能原样使用。
- 外部信息经接口取得：
  - 引擎 API：类、方法、属性、信号、enum、内置类型的运算符表；
  - 项目：场景、资源、autoload、全局类；
  - GDScript 类的静态视图（规范 §11.1）；
  - 绑定审核的数据（§10.3），放在 `src/compiler/binding_metadata.txt`。
- adapter 实现这些接口时，引擎类取自 ClassDB，场景取自引擎读出的 SceneState，GDScript 类取自 Script 的反射接口。这样其他扩展的类、更新版本引擎的 API 和二进制场景都按引擎的理解读到。
- 内置类型、工具函数和引擎的可空性元数据（规范 §10.2），ClassDB 不提供（`core/object/method_info.cpp:37-51`）。它们取自构建时从 `extension_api-4-7.json` 生成的表，可空性再与审核数据合并。这些表不随扩展变化；其他扩展的类按 §10.2 的默认规则处理。
- 流程：词法 → 语法树 → 语义分析 → 场景检查（§7）→ 带类型的 IR → 字节码、调试信息和类的元数据。语义分析处理名字、类型、收窄、match、泛型、接口和可见性。
- IR 由显式的基本块和虚拟寄存器组成，不是 SSA；每条指令带类型和源码位置。字节码与 IR 基本一一对应。语法糖（`?`、链式赋值的写回、await、match、就绪前的 setter）在生成 IR 时展开。
- struct 的字段是 struct 字节上的视图寄存器，没有自己的槽位，读写不需复制。推理寄存器的处理（复用槽位、协程保留的槽位）把视图算作所视寄存器的一部分。struct 在所有字段求值后才构造到新寄存器中，以免读取的字段先被覆盖。
- 常量表达式（规范 §4.5）在类型检查时求出。编译器算出标量和容器的结构；引擎类型的部分写进常量表，由运行时在类加载时算（§2.2）。编译期按虚拟机指令的算法计算（如 int 回绕），因为同一表达式在函数体中由虚拟机计算。
- 分析（`src/compiler/analysis.h`）保留每个脚本完整检查的结果：诊断、引用表和字节码。结果用到它读过的输入改变为止：自己的源码、其他脚本的声明，和项目对它所问问题的答案。
  - 其他脚本的声明按函数体之外的 token 求哈希，所以只改函数体不会使用到它的脚本重新检查。
  - 再用之前逐项重读输入比较，而不监听文件变化：重读命中缓存，编辑器和无界面命令行为一致。检查只经接口读取输入（§6.4），所以不会用到过时的结果。
  - 一次分析（一次构建或校验）把项目当作不变：场景只列举一次，其他脚本只解析一次。检查过的声明指向其他文件的语法树，只在一次分析内共享；分析之间只保留结果。否则一次检查会混用同一文件的两个版本。
  - 编辑器校验未保存的文本；其他脚本在保存后才看到改动。
  - 引擎的类只在扩展加载、卸载或重载时改变，这时清空所有结果（`core/extension/gdextension_manager.cpp:483-485`）。
- 一个文件中的每个类（含内部类，规范 §4.1）各有一个检查器，检查函数体之前所有类先完成声明。同文件的类经彼此的检查器读取声明，常量和 enum 在第一次用到时检查。裸名由近及远到外层类中查找。每个类生成自己的模块，文件的模块包含其内部类的模块。
- 语法树建在无损的 token 流上。语法 token 和 trivia（注释、续行的 `\`、非法字符）分成两列，按字节偏移合并即是原文。
  - 注释不在语法 token 中，所以解析器的前瞻不必跳过它们。格式化和 `##` 文档注释按偏移找注释；GDScript 也把注释另存为按行号的表（`modules/gdscript/gdscript_parser.cpp:4066-4106`）。
  - 行列只在报告时由行首表换算，列按码点计。
  - 每个节点记下首尾 token 的下标。名字和运算符另记自己的 token 下标，因为引用表需要每个名字的位置。
  - 诊断是字节区间；Godot 的接口只取起点的行列（`core/object/script_language_extension.h:322-330`）。快速修复和格式化以 token 为单位编辑。
  - 不采用无损的具体语法树（Roslyn 的 red-green 树），它要重写解析器和检查器。格式化器大多建在 AST 和 token 上（gofmt、Ruff）。
  - GDScript 的解析器只留与执行有关的 token，给它写的格式化器因此丢了字面量的写法和括号（[godotengine/godot#76211](https://github.com/godotengine/godot/pull/76211)）。
- 名字的解析记在引用表中。每解析一个名字记一条：位置、所指声明的标识和角色（声明或引用）。
  - 位置在 `.pet` 中是字节区间，因为字面量里的方法名和 `$"Head/Camera"` 的各段只是字符串 token 的一部分。场景中的位置是场景路径、节点路径、种类和键。
  - 声明的标识由种类、作用域和名字组成，按值比较，跨文件稳定，如 `Hit.damage`。一处源码可有多条，如挂在两个场景中的脚本的 `$Head/Camera`。解析不出的名字记为只有名字的未解析标识。
  - 覆盖或实现另一声明的条目带上被覆盖者的标识，供重命名找全相关声明（clangd 亦然）。
  - 表属于一个 `.pet` 文件的检查，重新检查时整份替换。场景中的引用（信号连接的方法、节点路径、导出属性的键）写入挂载该场景的脚本的表。
  - 跳转和悬停按位置查表，查找引用和重命名按声明反查；补全不用这张表。重命名执行时按当前文本核对每一处，对不上就放弃；未解析的同名候选只列出供确认（规范 §13.3）。
  - GDScript 的语言服务器没有这张表，按文本搜索名字再逐处解析，找不到字面量和场景中的引用（`modules/gdscript/language_server/gdscript_workspace.cpp:434-500`）。
- 有语法错误时，诊断只报语法错误（GDScript 亦然，`modules/gdscript/gdscript_editor.cpp:150-153`）。补全、悬停和跳转在恢复后的语法树上运行检查。编译也运行检查器，只是丢弃诊断、不生成 IR，使恢复的路径始终受检验。
- 补全只列出在光标处能通过检查的名字（规范 §13.2）。
  - 编辑器在光标处放一个 U+FFFF，它读作名字的一部分（`scene/gui/code_edit.cpp:2390-2400`）。检查器只检查声明和光标所在的函数体。
  - 候选取自各处的列举，多于能写的。每个候选换到光标处，由检查器自己的查找判断。所以规则只写在查找一处。
  - TypeScript 同样用检查器的可访问性判断过滤成员（`isValidPropertyAccessForCompletions`）。
  - 全局类按项目列出的名字给出，不逐个解析，因为解析要读每个脚本。
  - 列表总是完整的。退格后编辑器只在已有列表中筛选，不再询问（`editor/gui/code_editor.cpp:1008-1012`）。
  - 实参提示由检查器在检查调用时给出，所以显示的参数类型就是检查所用的。光标在嵌套的调用中时，取最内层的。
  - 注解名由解析器判断。它报告读到注解的位置，补全列出该处接受的名字。
  - 字符串按所在的参数补全，如路径、输入动作和本类的方法名。除 preload 的路径外，字符串所指的名字尚未检查，所以列出全部（规范 §10.4）。
- 恢复以行为单位：出错时丢弃本行余下的 token，缺少的部分由错误节点填补。行后的块照常解析（GDScript 亦然，`modules/gdscript/gdscript_parser.cpp:2366-2373`）。
  - 未闭合的括号会吞掉其后的行结构，而这是边输入边编辑时最常见的状态。所以词法分析把未闭合的括号视为在其后第一个合适的换行处闭合。合适指下一行缩进不深于括号所在行，且不以闭括号开头。
  - 这样 `print("a",` 后同一缩进的 `set_process(true)` 仍是下一条语句；只凭语法决定的做法（Ruff）会把它读成实参。
  - 解析器在括号内出错时，本行止于括号内的下一个换行，词法和解析各重做一遍。
- 一个原因只报一条错误，报在错处（参照 CPython 3.10 和 rustc）：
  - 未闭合的括号在开括号处报一次，它闭合前发现的问题不再报；
  - 词法分析已报错的行，解析器不再报；
  - 漏掉的逗号报在应有逗号处，多出的闭括号报为不匹配。
- 检查器把错误节点当作类型 Error，不再因它报错；格式化器不处理有语法错误的文件。
- 已保存的脚本有语法错误时，其他脚本看到恢复出的声明。没有错误（语法或检查）的声明照常可用，函数只看签名。
  - 用到有错误的声明时报在使用处，如 `Partly.bad has errors (res://partly.pet, line 4).`。
  - 缺少的块是开启它那一行的错误，报在冒号处（GDScript 亦然，`modules/gdscript/gdscript_parser.cpp:238-240、1956`）。
  - 【已知限制】报错中的行号是使用者上次检查时的；只移动声明的修改不会让使用者重新检查。
  - 实现接口有错误的类仍可使用，但不能当作该接口，如 `Half implements Combat.Damageable with errors (res://half.pet, line 1).`。子类要求基类的声明全都没有错误。
  - 找不到的名字所在的类或其本语言基类的文件有语法错误时，报错附上第一处，如 `A has no method "hit()"; res://a.pet has syntax errors (line 4).`。
- lint 是检查器中的检查，作为警告给出，与编译器的警告共用诊断和 `@warning_ignore`（规范 §13.2）。警告经 `@warning_ignore` 过滤后显示在脚本编辑器的警告列表中。快速修复是 token 区间上的文本替换，标明能否自动应用。一起应用时跳过区间重叠的修复，应用后重新检查。
- 格式化器（`src/compiler/formatter.h`）只改 token 之间的空白和空行（规范 §13.2）。输出再词法分析一遍，token 或注释与原文不同就放弃（Black 亦然），所以语法树不变由构造保证。验收：编译器测试格式化全部测试源码和 `tests/engine`、`benchmarks/project` 的脚本，再格式化一次不应再改动。FPS 和 Ring 用格式化后的脚本构建和运行。

### 2.2 runtime

- 值：int、float 各 8 字节；引擎的内置值类型就地存放，按引擎的规则复制和析构；String、Array、Dictionary 用引擎的类型。Option 和带载荷的 enum 有带判别字段的布局。struct 依次存放各字段，字段就是 struct 槽位内的槽位，verifier 从类型表得出它们。struct 的 `==` 是一条按类型表逐字段比较的指令。
- 元素是本语言独有类型的容器（规范 §3.8）及其嵌套的容器存为引擎容器，元素装在不可变的盒子里。
  - 盒子是用本库的 token 创建的自定义 Callable，数据是元素的类型和值，不能调用（`core/extension/gdextension_interface.cpp:1617-1631`）。
  - 引擎经盒子的 equal 回调比较 Callable，`has`、`find`、`erase`、容器的 `==` 和 Dictionary 查找都经 `hash_compare` 走到这里（`core/variant/callable.cpp:265-288`，`core/variant/variant.cpp:3351-3355`）。所以这些操作和只移动元素的操作，由构造保证按本语言的语义进行。
  - Callable 的哈希在创建时算一次（`gdextension_interface.cpp:221-227`），所以只有键的盒子在创建时哈希内容。键的内容只读（规范 §3.8）；引擎类型的值用引擎的哈希，它把所有 NaN 和正负零各视为相等（`core/templates/hashfuncs.cpp:39-64`）。
  - 运算表不比较 Callable 的大小（`core/variant/variant_op.cpp:731-791`）。所以 `sort`、`bsearch`、`min`、`max` 和容器的 `<` 由运行时用本语言的 `<` 完成。`hash`、`has_all` 和深复制也由运行时经盒子完成。
  - `resize` 后编译器生成的代码把新元素设为默认值，因为只有编译器知道 struct 字段的默认值。
  - 插入的键是逐层只读的副本，交出的键就地设为只读。虚拟机在修改容器前检查 `is_read_only()`，因为引擎在这里只报错或写进临时值（`core/variant/array.cpp:104-108, 518`）。
  - `Array(hits)`、`Dictionary(d)` 按规范 §10.1 编码。代价是每个元素一个盒子；不逃逸的容器以后可由逃逸分析换成私有表示。
- 不是 RefCounted 的对象存为 ObjectID 和指针，访问时检查存活（规范 §3.3）；RefCounted 持强引用，`weak` 不持（§3.12）。实例的成员由实例和其上运行的调用共同持有。方法运行中实例被删除时（`free()`、`set_script`），成员只标记为已释放；之后访问成员或 self 是程序错误。
- 每种类型有类型描述，提供复制、移动、析构和与 Variant 的转换（§10.1）。编译器为每个栈帧生成槽位类型表，供析构、协程搬移栈帧和调试器使用。
- 常量表在类加载时经引擎的接口求值一次，标量写回表中，容器逐层只读、每次使用读到同一个。加载资源的常量在按名字读取时才加载（规范 §4.5）。
- 编译好的函数不可修改，带版本。只改函数体的热重载替换函数表，运行中和挂起的栈帧继续用旧版本（§12.4）。
- 静态变量（规范 §4.8）存在类的镜像创建的存储中，只改函数体的热重载把它交给新镜像。
  - 适配层在脚本加载时初始化它们，编辑器中除外。另一个类的静态初始化先用到的类，在那时初始化。
  - 使用未初始化的静态变量和初始化之间的环，都由初始化状态和本线程上进行中的初始化发现。
  - 有静态变量的脚本整个运行中保持加载，除非带 `@static_unload`。
- 协程的栈帧在堆上，按归属成树，取消沿树传递（§9.3）。释放通知来自运行时自己的实例绑定，它与 godot-cpp 的绑定并存（`core/object/object.cpp:2167-2201`）；是否报错在每帧回调中判定（§9.7）。
- 等待 `GDScriptFunctionState` 时，运行时持有第一个状态直到 `completed` 发出，并监听接收者或 Callable 目标的释放和 `script_changed`（§9.8）。
  - 协程再次挂起后，内层状态只以 ObjectID 记住第一个状态，后者又已离开待处理列表（`modules/gdscript/gdscript_vm.cpp:2634-2639`，`modules/gdscript/gdscript_function.cpp:329-330`）。
  - 实例析构时引擎不发出 `completed`（`modules/gdscript/gdscript.cpp:2069-2079`，`gdscript_function.cpp:343-362`），状态也不暴露所属实例（`gdscript_function.cpp:288-307, 337, 364-370`，`modules/gdscript/register_types.cpp:140`，`object.cpp:995`）。
- 程序错误沿本语言的调用栈展开，释放局部变量，回到引擎的调用入口。入口返回该类型的默认值（§8.1）。
- 对本语言类的方法的调用不经过引擎（§8.1）。虚拟机找到实例或类的当前镜像，按名字找到方法并核对签名，再按槽位的原生布局传参。一次运行中的脚本总是一起编译（§12.4）。签名不同只出自不是一起构建的字节码，这时调用是程序错误。
- 引擎方法的调用要把原生值的指针直接传给 ptrcall（BACKLOG 的性能部分）；从引擎进入的调用做入口检查（§10.1）。
- 虚拟机可以在任意线程上运行，不使用没有锁保护的全局可变状态（§12.3）。
- 运行时直接用 godot-cpp 的类型，它们对应引擎内部的同名类型。改为引擎模块时，运行时换用引擎的头文件，adapter 重写，编译器和字节码原样使用（§2.1、§2.3）。
- 第一版只用 switch 分派，各平台只有一条代码路径要测试。本语言的优势在按类型存放的寄存器，不在分派（GDScript 在 GCC、Clang 上用 computed goto，`modules/gdscript/gdscript_vm.cpp:254-450`）。每条指令的处理只写一次，以后可从同一份定义生成 computed goto 或尾调用分派。是否加入由 §4 的基准决定。switch 分派始终保留，因为并非所有工具链都保证尾调用（如 MSVC 的 debug 构建）。
- 原生代码由一个多后端的代码生成模块按函数生成，运行时生成和事先生成共用它。生成时机暂不决定（§7）。CPython 的 JIT 因维护、评估和调试支持说不清而将被移除（[PEP 836](https://peps.python.org/pep-0836/)）。所以本语言的原生代码从一开始就要支持调试器、程序错误的位置和性能剖析。动手之前先定好基准和目标。

### 2.3 adapter

- 实现 ScriptLanguageExtension、ScriptExtension 和 ScriptInstanceExtension，把实例的属性读写、方法调用和通知转给 runtime。
- Script 类绑定 `new`，并把 `pub` 的 `_init` 报告为返回该类的静态方法，供 GDScript 检查 `Player.new(...)`（`modules/gdscript/gdscript.cpp:1078`，`modules/gdscript/gdscript_analyzer.cpp:5958-5961`）。不带 `pub` 的 `_init` 不报告，GDScript 视其为无参构造（`:6005-6031`，规范 §10.1）。
- async 方法在反射中报告为无类型的 Variant（`PROPERTY_USAGE_NIL_IS_VARIANT`，§9.8）。反射没有协程标记（`core/object/method_info.h:37-44`），而报告为 T 有两个问题：
  - GDScript 会给出多余 await 的警告（`gdscript_analyzer.cpp:3102-3107`）；
  - 取消时的 `completed(null)` 不经检查写进 T 类型的临时变量，Transform3D 等值类型因此崩溃（`modules/gdscript/gdscript_vm.cpp:2667-2668`，`modules/gdscript/gdscript_byte_codegen.cpp:998-1001`）。
- `.pet` 源码和字节码文件的加载与保存。
- 内部类的脚本（规范 §4.1）没有资源路径，由所在文件的脚本持有并一并取得镜像。运行时以文件路径后接 `::` 和各级名字指称它。
- 导出插件用字节码替换 `.pet`，经 `add_file(..., true)` 生成重映射，与 GDScript 换成 `.gdc` 时一样（`modules/gdscript/register_types.cpp:99-116`）。
- 编辑器插件提供：
  - 分析服务（§13.1）和场景编辑器中的错误标记；
  - 带场景部分的重命名和撤销（§13.3）；
  - 运行前的编译；
  - 右键菜单中的格式化（§13.2），作为一步撤销替换全文。
- 场景编辑器中给节点改名或移动节点时，改动并入编辑器刚提交的动作：
  - 在提交后发出的 `history_changed` 中，以场景根为上下文，创建同名、`MERGE_ALL` 的动作（`editor/editor_undo_redo_manager.cpp:63-105, 149-156, 298`，`core/object/undo_redo.cpp:97, 116-117`）；
  - 不能在动作执行中追加操作：移动节点时动作内不发出信号，提交时又先退出动作再执行（`editor/docks/scene_tree_dock.cpp:2535-2677`，`undo_redo.cpp:313-332`）。
- 无界面命令：
  - `--petrichor-build` 运行同一套分析，有编译错误时以非零退出（§13.1）。警告和提示只打印，不使它以非零退出；
  - `--petrichor-format` 格式化项目的脚本，加 `--check` 时只列出未格式化的。有这样的脚本或语法错误时以非零退出（§13.2）。

### 2.4 编辑、运行、导出和热重载

- 分析服务在编辑器进程中持有整个项目的编译结果，诊断显示在脚本编辑器和场景编辑器中。
- 编辑器中本语言脚本的实例是自己的占位实例（`src/adapter/pet_placeholder.h`）。它像引擎的占位实例一样保存导出的属性，脚本有错时保留场景设的值（`core/object/script_language.cpp:680-923`）。它还回答 `_get_configuration_warnings`，场景面板由此把错误标在节点上；引擎的占位实例不回答任何调用（`scene/main/node.cpp:3522-3532`，`editor/scene/scene_tree_editor.cpp:493-519`，`core/object/script_language.cpp:793-804`）。
- 场景用错脚本的诊断记下场景和节点，信号连接的错误记在连接的目标上。节点的位置是它所属场景中的路径，实例化的场景根记为 `.`。
- 错误按保存后的场景计算。保存资源或场景、文件系统变化时，节点重新取错误，分析只重新检查输入变了的脚本（`editor/plugins/editor_plugin.cpp:284-289`）。
- 编辑器加载脚本时只编译声明，足以提供反射信息，但不能运行。
  - 这时不能加载用到这个脚本的场景，引擎会当作循环加载拒绝（`core/io/resource_loader.cpp:1049-1056`）。
  - 所以完整编译在加载之外进行：编辑时的检查、保存、运行前的构建和导出。
  - 只编译声明时不读场景，由场景定型的成员（如 `@onready var camera = $Head/Camera`）这时是 Variant。
  - 支持 tool 脚本时，它们在加载后补一次完整编译。
- 跳转到定义和悬停经 `_lookup_code`，按光标处的引用表条目（§2.1）：
  - 本语言的声明跳到所在的行，局部变量和参数悬停显示类型；
  - 引擎的声明打开它的文档页，GDScript 类的成员跳到声明它的行；
  - 各种声明悬停时显示自己的文档。
- 本语言的类经 `_get_documentation` 提供文档，取自声明的检查，命名同 GDScript，类型按本语言的写法（`modules/gdscript/editor/gdscript_docgen.cpp:40-46, 339-347, 594-598`）。
  - 文档也列出没有 pub 的成员，因为悬停与帮助页共用文档，而类里悬停的多是自己的成员。
  - `##` 注释（规范 §2.2）按 GDScript 的读法成为说明（`modules/gdscript/gdscript_parser.cpp:3938-4243`）；局部变量的注释在悬停时显示。
- 从编辑器运行时，运行前编译（`_build`），字节码写入 `.godot/petrichor/`，游戏只读取。因为 `$X` 等的类型取决于场景（规范 §7）。游戏自己编译要重新分析全部场景，启动更慢，结果也可能与编辑器不同。
- 无界面命令同样写出字节码，供测试和 CI 使用；导出插件把字节码放进导出包。
- 首次发布前字节码不设版本号，只带格式标识，即构建时对 `src/bytecode/` 的哈希；标识不同的构建不读它。带着源码加载的脚本还按源码的哈希确认字节码由它编译，否则要求重新构建。
- 热重载：保存脚本后编辑器重新编译，经调试连接通知游戏重新加载。只改函数体时实例换用新代码。声明有变化时，游戏保留原代码，此后不再应用任何重载，直到重新运行（规范 §12.4）。

## 3. 测试

测试来自规范、引擎和真实代码三个方面，不从实现反推：

- **规范一致性**：按规范各节的规则编写测试。编译期的检查放在不启动引擎的 compiler 测试中，运行时的行为放在引擎测试中。
- **引擎兼容**：无界面运行的 Godot 测试项目，检查脚本的挂载、保存和重载，以及 GDScript 与本语言的双向调用。生命周期方面检查：
  - await 期间所属对象被释放，或信号源被释放；
  - 信号同步发出后再次挂起，同一个挂起点被恢复两次；
  - GDScript 调用本语言后，本语言再等待外部信号。
- **真实代码**：[第二次纸面迁移](surveys/paper-migration-2.md)中的 FPS 和 Ring 代码真正运行起来。
  - 迁移测试复制原项目，换入迁移后的脚本，尚未迁移的仍是 GDScript。迁移后的运行只能报告原项目也报告的错误，退出时也只能占用原项目占用的资源。
  - Ring 的测试不需要 .NET：`tests/engine/ring/ring_check.tscn` 代替 `Root.cs`，发出 Ring 的 `main.md` 构造的消息。C# 的 `Call()` 与 GDScript 的动态调用一样，都经引擎按名字调用。

编译器测试经同一个辅助函数编译源码，它检查 §2.1 的约定：

- token 流无损；
- 节点的范围依次嵌套；
- 每个解析出的名字都有引用，且原文相符。

对没有错误的源码，它还把每一行从中间截断后再编译。要求不崩溃、只报语法错误，其他行的语句仍在语法树上；未闭合括号之后缩进更深的行除外。这样每个新特性的测试同时检验这些约定。语法错误的报错另有一组用例，取边输入边编辑时的典型错误，写明位置和措辞。`tests/engine` 中的 `.pet` 文件没有真实的引擎 API，只检查 token 流、节点的范围和截断后的解析。

每个引擎测试写明它预期的错误，出现其他任何错误都算失败。运行器启动的导入不做检查：Godot 4.7.2 的编辑器在导入后立即退出时可能崩溃（Godot issue #111048）。

## 4. 性能

| 基准 | 测量内容 |
|---|---|
| 启动与编译 | 冷启动、重复运行、修改代码后重新运行 |
| 纯计算 | 整数和浮点循环、数组、函数调用、泛型 |
| 引擎边界 | 属性读写、调用引擎方法、Callable、信号 |
| 分配 | 带载荷的 enum、闭包、协程挂起、创建对象 |

比较使用优化过的构建，不用 `dev_build`。是否生成原生代码、优化哪些路径，由这些数据决定。

`benchmarks/` 中有 14 对运行时用例，以及一个 32 脚本项目的启动与编译基准。

- 运行时用例预热一次，再交替语言顺序采样五次，逐次检查结果一致。

- 启动时间是编辑器准备加游戏进程。编辑器准备在本语言是 `--petrichor-build`，在 GDScript 是等待编辑器扫描。

## 5. 推进顺序

1. **引擎接入**：不含语言，`.pet` 脚本能挂到节点上，在编辑器中和导出后都能运行。已完成。
2. **探针**：在运行的引擎上验证规范中只由源码推出的几处。已完成。
3. **最小编译链**：语言的一个子集挂进场景运行，GDScript 能调用它，断点能停，函数体能热重载。已完成。
4. **第一个里程碑**：第二次纸面迁移中的 FPS 代码真正运行。已完成。
5. **偿还技术债**：处理第一版实现留下的与规范不符的行为、重复的规则和不实的测试与文档。已完成。
6. **第二个里程碑**：第二次纸面迁移中 Ring 的 breakout 以迁移后的脚本运行。已完成。
7. **补齐第一版的语言**：第 4、6 步只覆盖了两个项目用到的写法。这一步实现规范第一版其余的特性，对应的规则同时写成测试。
   - 每个特性都满足 §2.1 的约定，第 8 步的工具建在其上。
   - 改动热路径的特性各跑一次基准（§4），把代价记进提交说明，但不为它优化。写进规范的运行时检查是以后的约束，定下之前要知道它的代价。
   - 这一步其余的部分放到第 8 步之后，主要是带载荷的 enum 与 Result、必须赋值的成员。

   验收：[实现覆盖调查](surveys/implementation-coverage.md)表中的写法都得到支持，重跑调查。
8. **工具链**：规范 §13.2 的第一版工具，包括带场景部分的重命名（§13.3）。
   - 它放在第 7 步其余部分之前，因为之后的特性都满足 §2.1，只给工具增加内容。只有用户定义的泛型会改变工具显示类型的方式，而它已移出第一版（规范 §14.2）。
   - 大项目和多人协作中的重命名按 §6.4。
   - 先做 Godot 自带的编辑器，LSP 最后。Godot 只给语言留了诊断、补全、跳转和自动缩进的回调，其余由编辑器插件提供（`core/object/script_language_extension.h:304, 391, 441, 475`）。场景只能经引擎读取，所以分析服务和 LSP 都在 Godot 进程中。

   按依赖分为：
   - 常驻的分析服务，构建和无界面命令共用它的缓存。验收：Ring 的构建不再重复编译基类和列举场景，只改函数体时只重新检查一个文件；
   - 诊断和 lint：场景中的错误标在节点上，lint、`@warning_ignore` 及其失效时的提示，无界面命令给出同样的诊断；
   - 格式化：在全部测试脚本和 FPS、Ring 上，语法树不变，第二次格式化不再改动，注释全部保留；
   - 导航：悬停的类型、跳转到定义、包括场景的查找引用、补全；引用表补上场景中导出属性的键；
   - 带场景部分的重命名，这时提出 §6.4 中写明旧名的语言规则；
   - 快速修复；
   - LSP：编辑器进程中的服务器，把同一组查询映射为 LSP 请求，也可由无界面的编辑器启动。

   内置的测试运行器是否在第一版中，留在 `BACKLOG.md` 的待定问题，最后决定。验收：§13.2 所列的每项工具。
9. **性能**：§4 的四组基准与 GDScript 比较，再按数据优化，包括是否生成原生代码（§7）。放在最后，因为先满足约束才谈得上快。验收：明显快于 GDScript（规范 §12.2）。
10. **首次公开发布**：由 CI 为 §6.3 所列的平台构建编辑器用的库和两种导出模板用的库。导出的游戏用官方导出模板运行。

    - 字节码格式定下版本号（§2.4、§6.1）。

    验收：不装 C++ 工具链，一个项目导出到每个平台都能运行。
11. **第一版之后**：Mod（§6.1）、struct 与带载荷 enum 的导出（§6.2），以及规范 §14.2 所列的其他内容。

## 6. 以后必须能做到的事

下面四件事排在第 8 步或更晚。做不到时，真实项目要么无法选用本语言，要么用到中途无法继续。本节说明现有设计允许以后做到它们，以及在那之前不能打破的约束。

### 6.1 Mod

用本语言写的游戏在运行时加载 Mod 的包。Mod 的类继承、调用和实现游戏的类，使用游戏的场景，而 Mod 的作者拿不到游戏的源码。

- 加载：Mod 的包由 `ProjectSettings.load_resource_pack` 载入，包中的 `.remap` 同样生效（`core/config/project_settings.cpp:581-585`，`core/io/resource_loader.cpp:1491-1519`）。所以 Mod 的脚本与游戏的脚本经同一条路径到达运行时。字节码按路径指称类，不必登记全局类名（`src/bytecode/module.h:76-82`）。
- 链接：脚本之间按路径和名字引用。运行时做三项检查：
  - 加载时检查基类的成员布局和签名（`src/runtime/class_image.cpp:50-54, 101`）；
  - 调用时检查方法的签名（`src/runtime/vm.cpp:1102-1103`）；
  - 使用处检查场景中节点的类（`vm.cpp:800-813, 879-889`）。

  所以版本不符或替换了场景的 Mod 得到加载错误或程序错误，不会读错内存。C# 和 Java 的 Mod 也建在这种带检查的动态链接上。
- 格式：首次发布前，Mod 须用与游戏相同的构建编译（§2.4）。首次发布时格式定下版本号，此后可读取兼容版本编译的 Mod。
- 声明：编译器对其他脚本只检查声明（`src/compiler/project_api.h:109`，`src/compiler/script_classes.cpp:331`）。所以游戏随 Mod 工具附上去掉函数体的脚本，Mod 就有完整的检查和补全。这些脚本可以按节点的 token 范围生成（§2.1）；游戏包中的场景经 SceneState 直接可读。
- 信任：verifier 拒绝损坏和过时的文件，但信任表中的引擎签名，伪造的文件可以使游戏崩溃（`module.h:419-427`）。GDScript 写的 Mod 本就能做任何事，加载 Mod 本身是信任的决定。要防不受信任的字节码，有两条增加的路（规范 §14.2）：
  - 加载时对照引擎核对签名；
  - 改用含编译器的运行时库，由游戏编译 Mod 的源码。
- 在此之前要守住：
  - 脚本之间的引用保持按路径和名字，在加载或调用时检查。跨脚本的优化（BACKLOG 的性能部分）在加载或首次调用时完成。它不把别的脚本的下标或布局不经检查地编进字节码。
  - 泛型（规范 §3.10）的定义留在自己的模块中，例如加载时按类型实参特化，不在使用处按源码单态化。这样别的模块无需泛型的源码就能实例化它，寄存器仍存原生值（§1）。
  - 编译器只经接口读取其他脚本，构建已保证这一点（`SConstruct:76-82`）。

### 6.2 struct 与带载荷 enum 的导出

struct 和带载荷 enum 的成员可以 `@export`，在检查器中编辑，存进场景和 `.tres`（规范 §14.2）。

- 存储：两者在引擎边界上编码为按字段名的 Dictionary，带载荷的 enum 以 `"$variant"` 记分支名（规范 §10.1）。场景保存时经 `get` 读出它们，实例化时经 `set` 先交给脚本实例的入口检查解码，引擎无需改动（`scene/resources/packed_scene.cpp:494, 861-883`，`core/object/object.cpp:239-246`）。
- 编辑：检查器的通用字典编辑器已能编辑它们，只是不按类型（`editor/inspector/editor_properties.cpp:4280-4287`）。按类型的面板由本扩展注册的 EditorInspectorPlugin 提供，属性的提示字符串写明类型（`editor/inspector/editor_inspector.h:356, 360`，`editor/plugins/editor_plugin.cpp:674`）。
- 加入时要定的规则：
  - 旧数据缺少新加的字段时，现在解码是程序错误（规范 §3.6）。存下的数据应改取字段的默认值，这是兼容的放宽。
  - 重命名字段要改写场景中嵌套的键，与第 8 步重命名导出成员是同一项工作（BACKLOG 的编辑器部分）。
- 在此之前要守住：可以导出之后，§10.1 的编码就是存储格式。它按字段名和分支名编码，加字段、调顺序都不影响旧数据。带载荷的 enum 按这个编码实现，首次发布后不再以丢失旧数据的方式修改它。

### 6.3 全平台的预编译库

用户不装 C++ 工具链就能导出到 Windows、Linux、macOS、Android、iOS 和 Web；之后的 Godot 4.x 版本继续可用。

- 分发：`.gdextension` 按功能标签为每个平台和架构列出库，导出插件取相符的那个（`core/extension/gdextension_library_loader.cpp:82-96`，`editor/export/gdextension_export_plugin.h:107-117`）。
  - iOS 的静态库由导出插件生成注册代码（`:119-137`，`editor/export/editor_export_platform_apple_embedded.cpp:1233-1325`）；
  - Android 把库放进 `lib/<abi>/`（`platform/android/export/export_plugin.cpp:800-822`）；
  - Web 要用带扩展支持的导出模板（`platform/web/export/export_plugin.cpp:362-374`，规范 §1.3）。

  所以发布就是为每个平台构建一份库，godot-cpp 带有这些平台的构建脚本。
- 代码：编译器和字节码是普通 C++17，运行时和 adapter 只用 godot-cpp，`src/` 没有按平台的条件编译（`SConstruct:14`）。解释器不生成机器码，所以能在禁止运行时生成代码的 iOS 和主机上运行（规范 §12.2）。
- 主机：扩展能否加载取决于移植方；退路是构建为引擎模块，编进每个平台的导出模板（Godot 的 `SConstruct:1237`、`modules/SCsub:32-42`）。C++17、SCons 和与引擎同名的类型都是为保留这条路选的（§1、§2.2）。
- 引擎版本：之后的版本加载同一个构建（§1）。引擎行为的变化，靠[引擎事实](engine-facts.md)在换提交时逐条复核。API 的变化在运行时按名字和哈希查找方法时暴露，不会悄悄调错方法（`src/bytecode/module.h:425-426`）。
- 在此之前要守住：平台相关的代码只经 godot-cpp；正确性不依赖生成机器码；导出用的库不含编译器（`SConstruct:84-89`）。

### 6.4 大项目和多人协作中的重命名

在上千个脚本、数百个场景、多人在分支上并行修改的项目中，重命名成员、方法或节点要响应快。它也不应迫使人一次改写别人正在编辑的场景。

- 为什么改写场景：场景按名字存导出属性的值和信号连接的方法，名字不存在时值被悄悄丢弃（`scene/resources/packed_scene.cpp:494, 666, 682`）。所以重命名要改写这些键（规范 §13.3）。改写是 token 区间上的文本替换，只动用到名字的行，只在别人改了同一行时冲突。
- 不改写场景的做法：设置属性和按名字调用连接的方法，都先经脚本实例（`core/object/object.cpp:239-246, 800-816`）。所以运行时可以接受成员声明里写明的旧名。
  - 场景下次保存时写成新名字，于是在有人本来就要编辑时迁移。引用表列出仍用旧名的场景（§2.1），都迁移后删去旧名。
  - 占位实例已是本语言自己的（§2.4）。它像引擎的一样拒绝属性列表之外的名字，接受旧名也在这里处理（`core/object/script_language.cpp:680-707`）。
  - 写明旧名是语言规则，在第 8 步做重命名时提出。
- 响应：检查一个脚本只依赖它的源码、所用脚本的声明、挂载它的场景，以及 `@owner` 涉及的场景（`src/compiler/script_classes.cpp:331`，`src/compiler/checker.cpp:5256`）。只改函数体时声明不变，依赖它的脚本无需重新检查（热重载同样比较声明，`src/runtime/class_image.cpp:584`）。分析按这些依赖保留结果（§2.1）。
- 在此之前要守住：检查只依赖经接口传入的输入，不读接口之外的状态；引用表按文件（§2.1）。
