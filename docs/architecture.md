# Petrichor 实现架构

本文记录 Petrichor 在实现层面的关键决策，涵盖组件边界、值的布局、测试基准与推进顺序。语言规则一律以[语言规范](language-spec.zh.md)为准；实现中若暴露规范问题，单独提交修改规范，不在实现层放宽规则。文中涉及的引擎行为均已对照 Godot 4.7.2-stable（提交 `ed1daf0`）核对，汇总见[引擎事实](engine-facts.md)。

## 1. 已定的选择

**C++17、godot-cpp 与 SCons**：解释器要能在 iOS 和主机上运行（规范 §12.2），将来也保留改为引擎模块的退路（§1.3）。Godot 自身以 C++17 编译（`SConstruct:916, 921`），引擎模块也只能经 SCons 构建，这套工具链与引擎保持一致。godot-cpp 固定在指定提交，以 `api_version=4.7` 构建；在引擎提高 C++ 标准之前，本项目同样不升级：C++20 只带来便利，强制尾调用仍是编译器扩展。

**以 Godot 4.7 为目标版本**：引擎允许加载最低版本不高于自身的扩展，声明 4.7 的构建也能在更新的引擎上加载（`core/extension/gdextension_library_loader.cpp:315-329`）。全部引擎行为目前只对照 4.7.2 核对过；要在后续引擎上运行，引擎的值还须满足 `src/runtime/values.h` 依赖的两项布局前提：

- Variant 先存类型，数据从第 8 字节起始，对象存为 ObjectID 与指针；
- 各内置类型不超过字节码为其预留的大小，运行时在加载阶段校验这一点。

**导出的游戏只含字节码**（规范 §1.3）。`.gdextension` 按功能标签为编辑器和导出模板挑选对应的库（`gdextension_library_loader.cpp:82-96`）：编辑器库内置编译器，导出模板库只含运行时。

**寄存器按静态类型存放原生值**：GDScript 哪怕已知静态类型，寄存器仍是 Variant，运算和引擎调用都要绕行 Variant（`modules/gdscript/gdscript_vm.cpp:536, 848-862, 2273-2313`）。本语言省去这层装箱与分发开销，这是“明显快于 GDScript”（规范 §12.2）的主要来源。

**游戏直接读取预编译字节码**：从编辑器启动游戏时，游戏读取编辑器写好的字节码，自己不再编译（§2.4）。

## 2. 组件

整个实现拆成四个边界清晰的组件，其中编译侧与字节码格式完全不依赖 Godot：

| 组件 | 依赖 | 内容 |
|---|---|---|
| compiler | 不依赖 Godot | 词法和语法分析、语义分析、场景检查、带类型的 IR、字节码生成、诊断、符号索引 |
| bytecode | 不依赖 Godot | 编译结果的格式、序列化和校验，compiler 与 runtime 共用 |
| runtime | godot-cpp | 字节码加载、虚拟机、值和类型描述、任务、程序错误、引擎边界上的检查和转换 |
| adapter | godot-cpp、runtime；编辑器用的库还依赖 compiler | 脚本语言、脚本和脚本实例三个扩展接口，资源的加载和保存，导出插件，编辑器插件，无界面命令 |

### 2.1 compiler

#### 引擎无关边界与外部接口

compiler 不含 Godot 头文件，构建时也不传入 godot-cpp 的头文件路径。它的单元测试是免启动引擎的普通 C++ 程序，将来改为引擎模块也能原样复用。外部信息统一经接口注入：

- 引擎 API：类、方法、属性、信号、enum 与内置类型的运算符表；
- 项目信息：场景、资源、autoload 与全局类；
- GDScript 类的静态视图（规范 §11.1）；
- 绑定审核数据（§10.3），保存在 `src/compiler/binding_metadata.txt`。

adapter 实现这些接口时，引擎类取自 ClassDB，场景取自引擎读出的 SceneState，GDScript 类取自 Script 反射接口。其他扩展的类、更新版本引擎的 API 与二进制场景，都能由此按引擎自身的理解读到。内置类型、工具函数和引擎可空性元数据（规范 §10.2）不由 ClassDB 提供（`core/object/method_info.cpp:37-51`）。它们在构建时从 `extension_api-4-7.json` 生成静态表，可空性再与审核数据合并。这些表不随扩展变化，其他扩展的类按 §10.2 的默认规则处理。

#### 编译管线、IR 与代码生成

编译管线依次经过词法、语法树、语义分析、场景检查（规范 §7）与带类型 IR，产出字节码、调试信息和类元数据。语义分析负责名字、类型、收窄、match、泛型、接口和可见性。IR 由显式基本块与带类型虚拟寄存器组成，不采用 SSA，行号指令标出源码位置，与字节码基本一一对应。语法糖（`?`、链式赋值写回、await 与 match）都在生成 IR 时展开。

- **遵循检查器决策**：IR 生成照检查器的决定执行，不从寄存器表示反推语义。
  - 转换种类只由源类型与目标类型决定，检查器判断能否赋值，IR 生成据此转换，两者调用同一个 `conversion()`。
  - 比较时的目标转换类型、Variant 比较方式与特殊内置方法由检查器记在节点上。
  - 收窄由节点类型与局部变量声明类型的差异得出。
- **struct 视图与构造**：struct 的字段是 struct 字节上的视图寄存器，没有独立槽位，读写无需复制。寄存器复用与协程保留槽位分析都把视图算作所视寄存器的一部分。struct 在所有字段求值后才构造到新寄存器中，以免读取的字段先被覆盖。
- **默认参数与字段默认值**：参数默认值在函数开头计算（规范 §4.6），lambda 的也一样，其捕获排在参数之后。调用方把实参个数写进帧中槽位，函数入口据此跳过已传入的参数。IR 由此保持单一入口，而 GDScript 会直接跳进函数中段（`modules/gdscript/gdscript_vm.cpp:2781-2784`）。非常量的 struct 字段默认值由声明类中的函数计算。别的类构造时按名调用该函数，避免把另一个脚本的代码编进自己的字节码（§6.1）。
- **签名与兼容**：覆盖、接口实现、信号连接和函数类型的赋值共用一种签名表示（`Signature`，`src/compiler/types.h`）。兼容只由 `misfit()` 判断，它比较实参个数、逐个实参、结果和 `async`。覆盖按不经转换的赋值比较类型，其余按普通赋值。函数值的 `call()` 带上函数类型的整个签名和可省略的个数。签名与被调函数相同时虚拟机直调并信任类型，少传的实参由被调方补默认值。
- **作用域引用释放**：引用按作用域由 IR 生成阶段插入的 `CLEAR` 完成（规范 §6.8），将一组能持有引用的寄存器放回默认值。
  - 插入处位于语句结束、复合语句头部判定之后以及离开块时；
  - `break` 和 `continue` 负责清空所离开各块的局部变量；
  - 函数体的局部变量随栈帧释放，不另行清空。
- **就地写回与计数循环**：对于先读完操作数再写结果的指令，赋给局部变量时直接写入该变量，省去临时寄存器。引擎运算对数学类型先算出值再写入，数组相加则不然（`core/variant/variant_op.h:50-83, 659-673`）。计数型 `for` 循环中，只要循环体不给循环变量赋值，就以循环变量本身计数。
- **常量求值**：常量表达式（规范 §4.5）在类型检查阶段求值。编译器算出标量和容器结构，其余由它生成的常量函数在类加载时计算（§2.2）。常量函数用函数体计算同一表达式的指令，常量表对这些条目只记计算式的哈希。编译期沿用虚拟机指令的算法（如 int 回绕），因为同一表达式在函数体中由虚拟机执行。
- **多类文件与默认参数推断**：同一文件中的每个类（含内部类，规范 §4.1）各有检查器，检查函数体前所有类先完成声明。同文件类经彼此检查器读取声明，常量和 enum 在首次用到时检查，裸名由近及远向外层类查找。每个类生成各自的模块，文件模块包含其内部类模块。
  - 写作 `name := value` 的参数在检查成员前从默认值得到类型（规范 §4.6），默认值只在这时检查一次，看得到 self 和前面的参数。
  - 默认值读到尚未检查的成员时先检查它；更早用到该参数（如成员初始值调用它）则先推断所在函数。若推断过程又用到自身，报错并要求写出类型。

#### 增量分析、工作区与缓存失效

分析缓存（`src/compiler/analysis.h`）保留每个脚本完整检查后的诊断、引用表与字节码。缓存持续有效，直到它读过的输入（自身源码、其他脚本声明或项目查询回答）发生变化。

- **声明哈希与场景结构隔离**：其他脚本的声明按函数体之外的 token 求哈希，只改函数体不会让依赖脚本重新检查。`_init` 函数体除外，其他脚本依赖它的赋值摘要（§6.4）。为 `$X` 定型时，脚本检查只读场景的结构（节点路径、类、脚本与实例），改存值或信号连接不会触发重检。
- **revision 验证与单次快照**：每份结果记下验证时的工作区 revision，未变则直接沿用，与 salsa 的 verified_at 相同。revision 变化后才逐项重读输入比对；检查只经接口读取输入（§6.4）。一次分析（一次构建或校验）把项目当作不变快照：场景只列举一次，其他脚本只解析一次，项目问题只问一次。检查过的声明指向其他文件的语法树，仅在单次分析内共享，分析之间只保留结果，以免混用同一文件的两个版本。分析进行中禁止写入工作区，嵌套分析也不得另给项目，违规直接终止。
  - 一次分析读场景时载入的场景和资源留到分析结束（`ProjectApi::hold()`），它们的依赖留在引擎缓存中，各场景共用的文件只载入一次（`doc/classes/ResourceLoader.xml:168-173`）。分析之间编辑器什么都不持有，改动的文件下次照常重读。代价是一次分析期间的内存：tanks-of-freedom-ii 带素材最多多占约 176 MB，大半是模型。
- **双视图缓存与扩展变更**：读磁盘的分析（构建与磁盘视图会话）与其他分析分开缓存结果（§6.5）。两视图中有文件不同时，交替请求不会互相挤掉缓存，也不会反复重检。LSP 会话读自己所见的项目，即自身视图叠上打开的文档（§2.4，`Analysis::View`）。会话文本与视图不同时，沿用视图结果并按读取记录重新核对。引擎类只在扩展加载、卸载或重载时变化，此时清空全部缓存（`core/extension/gdextension_manager.cpp:483-485`）。
- **场景检查缓存**：场景检查（§6.4）沿用同一套缓存，输入包括场景、节点脚本全文、其他脚本声明和项目回答。它的错误可能落在这些脚本的任一行（记在 `Diagnostic::file` 中），按全文比对可让行号随脚本同步更新。
  - 对节点和所实例化场景根上的脚本，只检查声明再核验场景如何放置它们（`CompileOptions::scene`），基类也一并检查（如基类的 `@parent` 要求）。
  - 只要场景对所实例化场景中的节点存了值，或包含指向它们的轨道、同步属性或信号连接，就一并检查那些场景中的脚本。
  - 当作根使用的场景同样检查这些脚本，因为规范 §7.5 要求逐层每个节点都满足必须赋值的导出。
  - 资源文件是没有节点的场景，场景检查同样覆盖它所含资源的脚本。资源没有就绪阶段，文件须给出它必须赋值的成员（规范 §6.2）。
- **工作区（人的视图）**：编辑器的各项检查统一读工作区（`src/compiler/workspace.h`），确保各功能看到同一份文本。工作区作为人的视图（§6.5），把三类未保存文本叠在磁盘之上：
  - 打开的脚本缓冲区；
  - 有未保存修改的场景；
  - 人的视图上 LSP 会话打开的文档（§2.4）。
  - 适配层在每次分析前同步打开的脚本。代码编辑器版本号随编辑递增，撤销与重做还原对应版本号，不变则免取文本（`scene/gui/text_edit.cpp:4784-4848, 9193, 9233`）。
  - 未保存的场景在编辑停下后打包写入（§2.4），查找引用和重命名之前也会重新打包。
  - 写入内容与原内容相同时 revision 不变，与 rust-analyzer 的 VFS 一致。文件版本取最后一次改动时的 revision，关闭再打开不会复用旧版本（同 TypeScript）。文件打开期间不受磁盘改动影响，与 rust-analyzer、gopls 和 TypeScript 相同。
- **磁盘变化追踪**：磁盘改动在得知时立即处理，不在每次使用前重读。
  - 编辑器自身写入经保存资源或场景、`filesystem_changed` 和 `settings_changed` 事件让 revision 加一（`editor/plugins/editor_plugin.cpp:284-289`，`core/config/project_settings.cpp:575`）。
  - 本语言保存器写入文件后先通知，再编译依赖它的脚本。
  - 其他程序的写入由项目服务比对文件得知（§6.5），编辑器自身只在窗口重获焦点时扫描（`editor/editor_node.cpp:1049-1058`）。
  - 场景索引在两次变化间沿用已读场景，变化后按修改时间和大小判定失效。修改时间取文件系统精度（NTFS 为 100 纳秒），不用只精确到秒的引擎接口（`drivers/windows/file_access_windows.cpp:444-448`）。
  - 服务察觉外部改动后，场景索引丢弃读过它的结果；读取中途被改的文件，事后取的修改时间也会与读到的内容不符。
  - 【已知限制】FAT32 和 exFAT 的修改时间只精确到 2 秒，同一时间单位内大小不变的改动无法察觉。
- **构建视图与延迟结果的戳**：构建和导出读磁盘而非工作区。运行前编辑器默认保存所有脚本和场景，两者通常一致（`editor/editor_node.cpp:2590-2603`）；无界面构建只运行一遍。延后使用的结果附带戳，记录算出时的 revision 及含位置的文件列表；分析沿用缓存时取当初算出时的 revision。只要其中任一文件版本晚于该 revision，结果即已过时；只用于显示的结果按 revision 变动直接重算。

#### 无损语法树与引用表

语法树建在无损的 token 流之上：语法 token 与 trivia（注释、续行的 `\`、非法字符）分作两列，按字节偏移合并即可还原原文。注释不进入语法 token，解析器前瞻无需跳过它们。格式化和 `##` 文档注释按偏移查找注释，GDScript 同样把注释另存为按行号索引的表（`modules/gdscript/gdscript_parser.cpp:4066-4106`）。

- **位置与 token 策略**：行列只在报告时由行首表换算，列按码点计。每个节点记下首尾 token 下标，名字和运算符另记自身 token 下标供引用表定位。诊断以字节区间表示（Godot 接口只取起点行列，`core/object/script_language_extension.h:322-330`），快速修复和格式化以 token 为单位编辑。本项目不采用 Roslyn 式的 red-green 无损具体语法树，以免重写解析器和检查器。格式化器与 gofmt、Ruff 一样建在 AST 和 token 之上。相比之下，GDScript 解析器只留与执行有关的 token，给它写的格式化器因此丢了字面量写法和括号（[godotengine/godot#76211](https://github.com/godotengine/godot/pull/76211)）。
- **引用表结构**：名字的每次解析在引用表中记为一条，包含位置、声明标识和角色（声明或引用）。
  - `.pet` 中的位置是字节区间，因为字面量里的方法名和 `$"Head/Camera"` 的各段只是字符串 token 的一部分。场景中的位置是场景路径、节点路径、种类和键，还带着改写所需的结构路径（§6.4）：
    - struct 字段和 enum 分支：从所存值到该名字逐层的元素或键值下标；
    - 轨道和同步属性：所在 Animation 或 SceneReplicationConfig 的路径、轨道或属性序号，以及方法轨道中键的序号；
    - 信号连接：存它的场景（继承的场景也列出基场景存的连接）。
  - 声明标识由种类、作用域和名字组成（如 `Hit.damage`），按值比较且跨文件稳定。一处源码可对应多条（如挂在两个场景中的脚本里的 `$Head/Camera`）；解析不出的名字记为只带名字的未解析标识。覆盖或实现另一声明的条目会带上被覆盖者标识，供重命名找全相关声明（clangd 亦然）。
  - 引用表归属单个文件的检查，重检时整份替换。场景中的引用（信号连接的信号和方法、节点路径、导出属性键）写入该场景检查的表（§6.4）。
- **内存占用与查询方式**：分析保留每个脚本的引用表，单条占 680 字节，其中 480 字节是脚本条目也带着的场景位置字段。字符串大多存在自身之内，另分配的不到 5%。
  - 在官方 4.7.2 编辑器中查找引用并检查全部脚本和场景后，实测占用如下：
    - 生成的大项目（1000 个脚本、300 个场景）有 1.9 万条，约 15 MB，占无界面编辑器进程私有内存的 2.4%；
    - 演示项目有 778 条，约 0.7 MB。
  - 每 KB 源码约 60 到 80 条、占约 60 KB，源码到约 1.7 MB 时表才到 100 MB。到那时先把场景位置字段移出条目。
  - 跳转和悬停按位置查表，查找引用和重命名按声明反查，补全不用这张表。重命名执行时按当前文本逐处核对，对不上则放弃；未解析的同名候选只列出供确认（规范 §13.3）。
  - 字面量节点路径另记它在各场景中从哪个节点走到哪个节点，供节点改名或移动时重写路径（§2.3）。GDScript 语言服务器没有引用表，只能按文本搜索名字再逐处解析，找不到字面量和场景中的引用（`modules/gdscript/language_server/gdscript_workspace.cpp:434-500`）。

#### 语法恢复、补全与错误隔离

文件存在语法错误时，诊断只报语法错误（GDScript 亦然，`modules/gdscript/gdscript_editor.cpp:150-153`），但补全、悬停和跳转仍会在恢复后的语法树上运行检查。普通编译也会对恢复后的树运行检查器，只是丢弃诊断、不生成 IR，让恢复路径始终受检验。检查器将错误节点视作类型 Error 而不再连锁报错，格式化器则不处理有语法错误的文件。经 `T?` 读成员或调用方法报错后，表达式取解包后所得的类型，其后照常检查，迁移推断也由此看到流出的值（§6.6）。

- **按行恢复与未闭合括号**：恢复以行为单位，出错时丢弃本行余下 token 并由错误节点填补缺失部分，行后的块照常解析（GDScript 亦然，`modules/gdscript/gdscript_parser.cpp:2366-2373`）。
  - 未闭合的括号会吞掉后续行结构，又是边输入边编辑时最常见的状态。词法分析将其视为在之后第一个合适换行处闭合（即下一行缩进不深于括号所在行，且不以闭括号开头）。
  - 这样 `print("a",` 后同缩进的 `set_process(true)` 仍是下一条语句，而纯语法恢复（如 Ruff）会把它读成实参。
  - 解析器在括号内出错时，本行止于括号内的下一个换行，词法和解析各重做一遍。
- **单因单报**：参照 CPython 3.10 与 rustc，一个原因只在错处报一条错误。未闭合括号只在开括号处报一次，闭合前发现的问题不再重复报。词法已报错的行解析器不再报，漏掉的逗号报在应有逗号处，多出的闭括号报为不匹配。
- **精确补全**：补全只列出在光标处能通过检查的名字（规范 §13.2）。
  - 编辑器在光标处放入 U+FFFF 并将其读作名字的一部分（`scene/gui/code_edit.cpp:2390-2400`），检查器只检查声明和光标所在函数体。
  - 候选取自各处列举（多于实际可写），每个候选换到光标处由检查器自身的查找验证，规则只写在一处。TypeScript 同样用检查器的可访问性判断过滤成员（`isValidPropertyAccessForCompletions`）。
  - 全局类直接按项目列出的名字给出，不逐个解析脚本。补全列表总是完整的，因为退格后编辑器只在已有列表中筛选而不再询问（`editor/gui/code_editor.cpp:1008-1012`）。
  - 实参提示由检查器在检查调用时直接产出，保证显示的参数类型与检查所用一致；光标在嵌套调用中时取最内层。
  - 注解名由解析器报告位置并列出该处接受的名字；字符串按所在参数位置补全路径、输入动作和本类 `pub` 方法名（规范 §10.4、§10.5）。
- **跨文件错误隔离**：已保存脚本有语法错误时，其他脚本看到恢复出的声明，没有错误（语法或检查）的声明照常可用，函数只看签名。
  - 用到有错误的声明时报在使用处（如 `Partly.bad has errors (res://partly.pet, line 4).`），缺少的块算作开启它那一行的错误并报在冒号处（GDScript 亦然，`modules/gdscript/gdscript_parser.cpp:238-240、1956`）。
  - 【已知限制】报错中的行号取自使用者上次检查时，只移动声明的修改不会让使用者重新检查。
  - 实现接口有错误的类仍可使用，但不能当作该接口（如 `Half implements Combat.Damageable with errors (res://half.pet, line 1).`）。
  - 基类有错误时，子类照常检查并按上述规则使用基类声明，防止迁移时子类错误被基类遮住。同时子类在 `extends` 处另报一条（如 `Base script res://base.pet has errors (line 3).`），阻止生成字节码。
  - 找不到名字时，若该类或其本语言基类文件有语法错误，报错附上第一处位置（如 `A has no method "hit()"; res://a.pet has syntax errors (line 4).`）。
- **跨文件未知类型**：其他脚本读到的声明不读场景和资源，只有基类的读。由场景或资源定型的声明在那里类型未知，用到时报错要求写出类型：
  - 成员、静态变量和常量，报在读取处（如 `The type of Visuals.STYLE is not known here`）；
  - 以 `:=` 由默认值定型的参数，报在调用处和取函数值处；
  - struct 字段，报在需要 struct 布局的语句或声明处（凡是该 struct 的值都需要布局，由代码生成报出）。

#### 警告、快速修复与格式化

- **警告与 lint**：警告经 `@warning_ignore` 过滤后显示在脚本编辑器的警告列表中。第 8 步加入的 lint 是检查器中的检查，与编译器警告共用诊断和 `@warning_ignore`（规范 §13.2）。它们不另设 pass，检查器因此难以维护时再考虑拆出。
- **快速修复**：快速修复（第 8 步）是 token 区间上的文本替换，由检查器在报错处生成并随诊断进入 `CompileResult`（`Diagnostic::fixes`），每处编辑自带原文供应用前核对。每个修复属于一个种类，能否自动应用按种类定，不在报错处零散判断。
  - 参照 Clang 和 Swift 对错误 fix-it 的要求（[设计说明](design-notes.md)），自动种类须同时满足四条：
    - 只有一种明显的改法；
    - 只改报错的表达式或语句，或只在一个声明前补上 `pub`；
    - 保持 GDScript 中的含义；
    - 检查器报出错误后，按已经应用了修复继续检查。
  - 自动种类包括：
    - 真值改写、`float` 实参和 `is_instance_valid`。setter 和 getter 判断 `@onready` 成员时先判 `is_node_ready()`：它们可能在就绪前运行，这时 GDScript 读到 null，本语言则报程序错误（规范 §6.5）。`is_node_ready()` 在 `_ready` 之前变真，GDScript 在 `_ready` 开头初始化这些成员（`scene/main/node.cpp:279, 334-336, 3555-3557`，`modules/gdscript/gdscript.cpp:1950-1952`，`ed1daf0`）；
    - 两层 Option 当作 GDScript 的 null（如与 null 比较和传给 `Variant`）；
    - `.detach()`，以及字面量名字改用方法或信号本身；
    - 从根到 autoload 的字面量路径改用它的名字（§6.6）；
    - packed 数组位置上不是字面量的 `Array` 套上该类型构造（如 `PackedVector2Array(points)`），GDScript 也接受它并逐个元素转换（`core/variant/variant.cpp:814-819, 2076-2084, 2185-2191`，`core/variant/variant_construct.h:637-655`，`ed1daf0`）。字面量在这里本就是该 packed 数组（规范 §3.13），无需修复；
    - 多参信号结果的字面量下标改为它所指的字段，`Array` 位置上的结果套上 `Array(r)`，写作 `Array` 的局部变量去掉类型而取得字段（§6.6）。检查器按去掉类型后的局部变量继续检查；
    - 位置期望的正是 `as` 所转的容器类型时，去掉字面量上的 `as`。字面量本就取位置的类型，GDScript 也把它定为所转类型（`modules/gdscript/gdscript_analyzer.cpp:3808-3815`，`ed1daf0`）；
    - 期望 enum 处的 `int` 套上 `E(x)`。引擎的 enum 开放，转换不查范围；本语言的 enum 只在 `int` 是它某个值的常量时提供（规范 §3.7）。GDScript 照收 `int`（`modules/gdscript/gdscript_analyzer.cpp:6397-6400`，`ed1daf0`），两种都与它同值；
    - 静态代码中裸写的 `new()` 前补上类名，内部类补它自己的名字（deck_builder_tutorial 的 `scenes/modifier_handler/modifier_value.gd:13`）。GDScript 在运行它的脚本上调用裸写的 `new()`，静态代码经类调用时即是本类（`modules/gdscript/gdscript_compiler.cpp:654-661`，`modules/gdscript/gdscript_vm.cpp:656-666`，`modules/gdscript/gdscript.cpp:928-947`，`ed1daf0`）。经子类实例调用静态函数时 GDScript 取实例的脚本，它对这种调用给出警告（`modules/gdscript/gdscript_analyzer.cpp:3699-3703`）。方法中裸写的 `new()` 取 `self` 的脚本，可能是子类，因此不提供；无 `class_name` 的文件类没有名字可写，同样不提供；
    - 补上 `pub`（若声明会因此露出不带 `pub` 的类型，则不提供）。
  - 其余种类（如 `.unwrap()`、改为 `T?`、补上 `async`、`await`、null 模式、写 `as`、检查所转值的 `E(x)`、无类型容器和 `@owner(T)`）只作备选；自动修复排在首位且无需输入。
  - `int` 位置上的 `float` 套上 `int(x)` 也只作备选，因为本语言写的代码在这里更常是该把变量写成 `float`。GDScript 在它写了类型（含 `:=`）的位置向零取整转换并给出警告（`modules/gdscript/gdscript_analyzer.cpp:3062-3064, 6370-6374`，`modules/gdscript/gdscript_byte_codegen.cpp:934-939, 992-997`，`modules/gdscript/gdscript_vm.cpp:1433-1438`，`core/variant/variant_construct.cpp:69`，`ed1daf0`），迁移因此直接应用它（§6.6）。检查器同样按已经套上继续检查。复合赋值不提供：GDScript 转换的是运算结果（`modules/gdscript/gdscript_compiler.cpp:1346-1381`）。以值定型、没写 `:=` 的变量也不提供，它在 GDScript 中是 `Variant`，照存 `float`。
  - 一键修复（`compiler::fix_all()`）每次只应用本脚本中的一种自动修复。同种修复区间重叠或起点相同时跳过后者留给下次，两个错误给出的同一修复只应用一次；跨种类批量修复属于迁移工具（§6.6）。
  - 改写会给操作数加括号（名字、成员、调用、下标、字面量和已在括号中的除外）。检查器在原树上暂时改写并重检来判断改写能否通过（如加上 `.unwrap()` 后成员能否找到），通不过就不提供。这次检查的报错、引用和警告随即撤回，补全时不做这种验证。
  - 修复也可编辑其他脚本（如给另一文件的声明补上 `pub` 或给被覆盖方法补上 `async`），这处编辑带上目标脚本的 `res://` 路径，原文从关键字取到名字。
- **格式化器**：格式化器（`src/compiler/formatter.h`）只改 token 之间的空白和空行（规范 §13.2）。输出会再词法分析一遍，只要 token 或注释与原文不同就放弃（Black 亦然），以此从构造上保证语法树不变。因为 token 和注释分开比较看不出交错次序，去掉空白后与原文不同同样放弃。验收要求编译器测试格式化全部测试源码和 `tests/engine`、`benchmarks/project` 的脚本，二次格式化不再改动；FPS 和 Ring 用格式化后的脚本构建并运行。

### 2.2 runtime

#### 值表示与复合类型布局

运行时按静态类型在槽位中存放原生值：int 与 float 各占 8 字节，引擎内置值类型就地存放并按引擎规则复制和析构。String、Array、Dictionary 直接使用引擎类型，Option 采用带判别字段的布局。

- **struct 布局与方法**：struct 依次存放各字段，字段即 struct 槽位内的子槽位，由 verifier 从类型表得出。struct 的 `==` 是一条按类型表逐字段比较的指令。struct 方法编为声明类的静态函数（如 `Hit.total`），实例方法首参为 struct 本身即 `self`，lambda 像捕获局部变量一样捕获其副本。名字中的点避免与类函数同名，且它们不是 pub、引擎找不到。本类和子类经 `CALL` 调用，其他类经 `CALL_METHOD` 按名调用，运行时无需新指令。
- **带载荷 enum 与 `Result`**：带载荷 enum 按 struct 布局存放，先放分支序号，再依次排列每个分支的字段。未激活分支的字段保持默认值，复制和析构与 struct 相同。构造先读入该分支的常量（各字段均为默认值）再写入实参；相等、排序、哈希和编码只看序号与该分支字段。不重叠存放的代价是槽位较大，以后可改为按最大分支共用。
  - `Result[T, E]` 是名为 `Result` 的带载荷 enum，分支为 `Ok(value: T)` 和 `Err(error: E)`。类型键含字段类型，不同的 T、E 是不同的类型。它的方法和后缀 `?` 编译为按序号跳转，`unwrap` 和 `expect` 另用一条指令，失败时报出错误值。
- **`T.try_from(v)` 与引擎 `try_`**：`T.try_from(v)` 对应单条指令，与 struct 字段共用解码函数，两者规则由构造保持一致。解码失败时，`Err` 中的 `ConversionError` 记下入口检查报错；`ConversionError` 由编译器声明，没有脚本，字节码中名为 `::ConversionError`。引擎 API 的 `try_` 版本在每个调用处展开：先调原方法，再调读取错误的 getter（规范 §10.3）。作为值时，检查器将其改写成调用它的 lambda（如 `func(path, flags): return FileAccess.try_open(path, flags)`），降级与运行时无需新路径。
- **多参信号的结果**：`await` 多参信号得到编译器声明的 struct（规范 §9.6），没有脚本，按参数的名字和类型命名，如 `await Signal(result: int, body: PackedByteArray)`。参数名字和类型都相同的信号共用这一类型，`Task.of(信号)` 的结果也是它。
  - 字节码中它名为 `::await Signal(...)`，运行时据此把它编码为按参数顺序的 Array，也从这样的 Array 解码。信号恢复 `await` 时交来的正是这个 Array，GDScript 的 `await` 也给出它（`modules/gdscript/gdscript_function.cpp:256-274`，`ed1daf0`）。
  - 字段没有默认值，因为非空对象参数本就没有默认值，所以 `resize()` 等需要默认值的操作不接受它。
- **必须赋值的成员标记**：必须赋值的成员（规范 §6.2）和 `@late` 的成员与静态变量（§6.3）在槽位后紧跟 8 字节标记，赋值后非零。本语言写入后跟一条置位指令（静态变量由读写指令自己置位），引擎经 `set` 写入时由运行时置位，读取前检查该标记。引擎写入 null 时，未赋值的 `@late` 成员保持未赋值，与场景未存值相同。这套标记对所有类型一致，因为 struct 和带载荷 enum 没有可表示"未赋值"的值。节点就绪时，运行时检查本类必须赋值的成员（规范 §6.4），`@late` 成员只在读取时检查。

#### 装箱容器与循环引用防护

元素是本语言独有类型的容器（规范 §3.8）及其嵌套容器存为引擎容器，元素装入不可变盒子。盒子是用本库 token 创建的不可调用自定义 Callable，数据是元素的类型和值（`core/extension/gdextension_interface.cpp:1617-1631`）。

- **语义对齐与操作分工**：引擎经盒子的 equal 回调比较 Callable，`has`、`find`、`erase`、容器 `==` 和 Dictionary 查找都经 `hash_compare` 走到这里（`core/variant/callable.cpp:265-288`，`core/variant/variant.cpp:3351-3355`）。这些操作与只移动元素的操作由此按本语言语义进行。
  - Callable 哈希在创建时只算一次（`gdextension_interface.cpp:221-227`），只有键的盒子在创建时哈希内容。键内容只读（规范 §3.8）；引擎类型值用引擎哈希，将所有 NaN 与正负零各视为相等（`core/templates/hashfuncs.cpp:39-64`）。
  - 引擎运算表不比较 Callable 大小（`core/variant/variant_op.cpp:731-791`），`sort`、`bsearch`、`min`、`max`、容器 `<` 以及 `hash`、`has_all` 和深复制改由运行时经盒子完成。
  - `resize` 后由编译器生成代码把新元素设为默认值，因为只有编译器知道 struct 字段的默认值。
  - 插入的键是逐层只读副本，交出的键就地设为只读。虚拟机修改容器前检查 `is_read_only()`，避免引擎只报错或写进临时值（`core/variant/array.cpp:104-108, 518`）。
  - `Array(hits)` 与 `Dictionary(d)` 按规范 §10.1 编码。代价是每个元素一个盒子，不逃逸的容器以后可由逃逸分析换成私有表示。
  - 引擎检查不了 Callable 签名和 Task 结果类型，函数值与 `Task[T]` 也装盒。各函数类型共用一种盒子，调用时再检查签名（规范 §3.11）。类型键则按写法区分函数类型，热重载和跨类读写成员据此比较。
- **自包含与循环遍历保护**：struct 经容器包含自己时（规范 §3.6），类型表中容器元素可排在容器之后，而字段和 `T?` 的 `T` 仍排在前面，大小仍可算出。
  - 这类值可能经共享容器包含自己。比较、哈希、打印、编码、解码和深复制进入盒子超过 100 层即停下，深复制遇到正在复制的容器也停下。
  - 本线程运行着本语言函数时，停下的遍历留下标记，后续遍历立即结束；其他程序错误结束调用链时一并清掉标记。
  - 可能遍历的指令在辅助函数中取走标记，并在该语句报程序错误（规范 §3.6）。把检查放进分派循环会让不遍历的基准也慢 5–10%。
  - 引擎运算符指令在循环内直接调引擎，无法遍历盒子，容器 `==` 由此改用 struct 的比较指令。
  - 本线程没有本语言函数时，遍历由引擎发起，停下时报引擎错误并给出引擎在同一深度给出的结果（`core/variant/array.cpp:149-153`，`ed1daf0`）。调试器显示变量时同样停下，不算程序错误。

#### 对象生命周期与调试追踪

非 RefCounted 对象存为 ObjectID 和指针，访问时检查存活（规范 §3.3）；RefCounted 持强引用。实例成员由实例和其上运行的调用共同持有。方法运行中实例若被删除（`free()`、`set_script`），成员只标记为已释放，此后访问成员或 self 是程序错误。

- **RefCounted 的 `PREDELETE` 保护**：`PREDELETE` 期间引用计数已归零，由它构造的 Variant 为 null（规范 §6.6）。调用自身引擎方法和属性时，接收者直接取实例指针，不经 self 的 Variant。此时把 self 当作值使用或用 lambda 捕获 self 都是程序错误；`PREDELETE` 分支中的写法在编译期被拒绝，辅助函数中的在运行时发现。
- **debug 释放位置环**：debug 构建记下释放时本线程正在执行的本语言语句（规范 §3.3），来源有三种：本语言实例的 `PREDELETE`、本语言调用的 `free()` 以及 `queue_free()`。
  - 位置存入本线程 4096 项的环形缓冲，记录时不分配内存也不等待。各线程的环登记在一张表中，线程结束后环仍保留给下一个新线程使用。
  - 报对象已释放的程序错误时，按 ObjectID 在每个环中从新到旧查找。查找逐个锁住环，记录遇到锁时跳过本次。更早的释放不再有位置，与 AddressSanitizer 的隔离区相同。
- **debug 泄漏追踪**：debug 构建同时记下创建位置，退出时列出泄漏（规范 §6.7）。本语言实例在自身存储中记下创建语句，退出时列出全部存活实例（引擎或其他语言创建的实例无位置，按类列出）。本语言 `new()` 创建的引擎对象记入本线程表，表长翻倍时删去已释放对象。位置指向类镜像的路径和函数名，镜像首次记录时复制并保留到退出。清单在扩展的 CORE 级反初始化时打印，此前场景树和各服务器已释放所持对象（`main/main.cpp:5259, 5295-5391`，`ed1daf0`）。

#### 常量表、静态变量与热重载状态

每种类型有类型描述，提供复制、移动、析构和与 Variant 的转换（§10.1）。编译器为每个栈帧生成槽位类型表，供析构、协程搬移栈帧和调试器使用。

- **常量表与 `preload`**：编译器知道的条目在类加载时直接写入常量表，包括标量、字符串、None、带载荷 enum 的分支和内置类型常量。引擎计算的条目由模块的常量函数 `@constants` 在类加载时算出一次。它用函数体同样的指令计算，再由 `INIT_CONSTANT` 写入条目并逐层设为只读，此后每次读到同一个容器。函数体中的 int、float 和 bool 常量作为栈帧预设值随清零一并写入，读取无需指令。引擎算出的值（如 `Vector2(1, 2)`、`sin(1.0)`）存为原生布局，读常量表原样复制。容器字面量则每次求值新建。packed 数组字面量（规范 §3.13）逐个 `append()` 建成，作常量时也一样。
  - 每个 `preload`（含函数体中的）都是常量表条目，由 `@constants` 经 `LOAD_RESOURCE` 加载。资源随类加载，与 GDScript 在编译脚本时加载一致，使用处不再加载。构建后文件改了类型时，程序错误报在常量所在行，类加载失败。
  - 常量函数运行时调试器不单步，因为 GDScript 编译时就存下常量的值，不运行它的行（`modules/gdscript/gdscript_compiler.cpp:2919-2924`，`ed1daf0`）。
  - 只当类型用的脚本常量（规范 §2.1）例外：它另占一个条目，没有代码读写它，类加载时也不求值。本文件任一表达式以名字、成员或调用读到这个名字就算值用，被同名声明遮住的也算（`names_read()`，`src/compiler/ast.h`）。局部常量照常加载。
  - 热重载按值和计算式的哈希比较条目，不看它是否只当类型用，所以函数体里加一处值用只是函数体改动（规范 §12.4）。新镜像加载时求值，脚本随之加载。
  - `preload` 不能成环，否则类会等待正在加载自身的文件（规范 §7.6）。GDScript 经引擎内部接口取得加载中的资源，GDExtension 没有该接口。
  - 环检查的边由各文件的语法树算出（`load_edges()`，`src/compiler/script_classes.h`），函数体也算在内，其他文件只解析不检查。边包括值用的 `preload`、复制自另一文件常量的 `preload`（只看一层，如 `const P = Board.Piece`），以及类加载时建的带类型容器的元素与键类型。后者只看常量、静态变量和 `_static_init()` 里写出的类型。
  - 本文件的类建的容器都不算边（规范 §7.6）。静态初始化时本文件的脚本已经登记。元素或键是本文件类的容器常量在建镜像时留空，由另一个常量函数计算。它等文件脚本连同内部类脚本都拿到镜像后，在加载登记下运行一次（`finish_constants()`）。热重载时实例先换到新镜像，其他线程这时可能已在运行新代码，所以只有这类常量等待。这类常量经容器指回脚本，脚本因此像含静态变量的一样保持加载，退出时清空。GDScript 文件仍按词法扫描 `preload`，另加它写到的其他语言全局类，GDScript 编译时会加载它们（`modules/gdscript/gdscript_analyzer.cpp:802-803`）。
  - 编辑器加载脚本只检查声明，这样的模块没有常量函数，加载时不运行代码，也不加载资源。引擎计算的 pub 常量在每次按名读取时由反射函数重新计算，GDScript 按名读取含 `preload` 的常量时同样才求值。
- **反射值**：反射读到成员初始值、方法列表的默认参数和仅编声明时引擎计算的 pub 常量。模块的反射函数 `@reflected` 按序号每次新建它们，并按规范 §10.1 编码。带载荷 enum 的默认参数由此显示为 `{"$variant": "STOP"}`。这些值不在类加载时计算，以免 `Array[B]` 这样的值给加载添上规范 §7.6 没有的边。仅编声明的模块也运行这个函数，它只含计算常量表达式的指令。
- **函数版本与静态变量**：编译后的函数不可修改且带版本，只改函数体的热重载直接替换函数表，运行中和挂起的栈帧继续用旧版本（§12.4）。静态变量（规范 §4.8）存在类镜像创建的存储中，只改函数体的热重载把它移交给新镜像。
  - 适配层在脚本加载时初始化静态变量（编辑器中除外），被另一类静态初始化先行用到的类在当时触发初始化。使用未初始化静态变量与初始化成环，都由初始化状态和本线程进行中的初始化发现。
  - 含静态变量的脚本在整个运行中保持加载，带 `@static_unload` 的也不例外（规范 §4.8），其他类读写静态变量时持有的存储指针靠这一点保持有效。
  - 引擎对本线程正在加载的文件只给空值（`core/io/resource_loader.cpp:1046-1056`），而静态初始化可能要建本类的对象或带类型容器。这时脚本取自本线程的加载登记；仍取不到就报程序错误，不建只按原生类定型的容器（`core/variant/array.cpp:885-897`）。
  - 退出时每个仍加载的脚本的静态变量和常量都清回默认值，与 GDScript 一样（`modules/gdscript/gdscript.cpp:1343, 1453, 1471, 2239-2265`）。这打破经本类对象或容器指回脚本的环，也放开泄漏对象的脚本所 `preload` 的资源。Ring 泄漏的 `old_model` 节点由此不再占着它 `preload` 的 `new_model.tres`（`breakout/scenes/consumables/old_model/old_model.gd:42-43`）。

#### 协程栈帧与 Task 运行时

协程栈帧分配在堆上，按归属关系成树，取消沿树向下传递（§9.3）。对象释放通知来自运行时自己的实例绑定，与 godot-cpp 绑定并存（`core/object/object.cpp:2167-2201`）；是否报错留到每帧回调中判定（§9.7）。挂起期间，栈帧放下槽位中指向 self 的引用，恢复时再放回（规范 §9.4）。self 在此期间释放时协程已被取消（§9.7），临时值和局部变量中的 self 不会让它保持存活。

- **轻量 `Task` 句柄与延迟装箱**：`Task` 值是运行时自有引用计数句柄，槽位直存其指针（`ValueType::Task`）。引擎侧的 `CoroutineTask` 直到任务首次进入引擎（如传给 GDScript、存入 Variant 或容器）才建出。每次调用协程都建扩展类对象曾占 coroutines 用例约 22% 的时间，延迟创建省掉了这笔开销。
  - `CoroutineTask` 存活期间与同一任务一一对应，任务运行期间持有它，保证连到其信号的代码能收到信号（§9.8）。
  - 本语言内部等待任务不经引擎信号，任务结束时直接通知等待方，再发出 `completed`。
  - 未结束任务按所属对象成表，释放对象时只遍历自身任务；每帧回调只检查所等对象已释放的任务。
- **组合与定时任务**：`Task.of` 和 `Task.delay` 不运行函数，只等单个信号（§9.5），等待、取消和释放监听与其他协程共用。信号源释放同样延后到每帧回调判定再取消；`Task.delay` 复用 `SceneTree.create_timer` 的 `timeout`，暂停和时间缩放按引擎默认值。
  - `t.settled()`、`Task.any` 和 `Task.all` 也不运行函数，只等目标任务结束（§9.2、§9.5）。它拥有为它启动的任务并在自己结束时取消，对已有任务只停止等待；所等任务因所属对象释放取消时，同样推迟到每帧回调判定。`Settled` 与 `Result` 同为无脚本带载荷 enum，`CancelReason` 为无脚本 enum。
- **等待 GDScript 协程**：等待 `GDScriptFunctionState` 时，运行时持有第一个状态直到 `completed` 发出，并监听接收者或 Callable 目标的释放与 `script_changed`（§9.8）。协程再次挂起后，内层状态只按 ObjectID 记住第一个状态，而后者已离开待处理列表（`modules/gdscript/gdscript_vm.cpp:2634-2639`，`modules/gdscript/gdscript_function.cpp:329-330`）。另外，实例析构时引擎不发 `completed`（`modules/gdscript/gdscript.cpp:2069-2079`，`gdscript_function.cpp:343-362`），状态也不暴露所属实例（`gdscript_function.cpp:288-307, 337, 364-370`，`modules/gdscript/register_types.cpp:140`，`object.cpp:995`）。

#### 调用分派、引擎边界与迭代路径

从引擎进入的调用须做入口检查（§10.1）。程序错误沿本语言调用栈展开并释放局部变量，回到引擎入口后返回该类型的默认值（§8.1）。本语言内部的方法调用、成员读写以及多数引擎交互均绕开 Variant 分发。

- **本语言直调与成员访问**：调用本语言类方法不经过引擎（§8.1）。虚拟机找到实例或类的当前镜像，按名找到方法并核对签名，再按槽位原生布局传参。一次运行中的脚本总是一起编译（§12.4），签名不同只出自不同构建的字节码，此时调用是程序错误。
  - 函数类型 `f.call(x)` 遇到本语言 lambda 或方法值时同样直调，其他 Callable、`async` 函数与签名不同的方法值走引擎。lambda 捕获值依次存于对象内，放得下时不另分配；直调不复制镜像和上下文，由调用方寄存器保证存活。无类型 `Callable` 的 `call()` 遇到它们也按槽位直调，但按引擎入口语义处理：被调方出错后调用方得默认值继续（规范 §8.1）。
  - 其他实例成员同样不经引擎读写：虚拟机按名查当前镜像、核对类型后直接读写槽位，有访问器的成员经 `CALL_METHOD` 调用访问器。非 `pub` 成员由此按规范 §4.2 访问，装箱容器也不必经反射暴露（§10.5）。
- **引擎方法与属性 ptrcall**：有 MethodBind 的引擎方法（含 `$Path`）经 ptrcall 调用，与 GDScript 调用已知类方法相同，不经脚本实例（`modules/gdscript/gdscript_vm.cpp:2273-2313`）。参数和结果按原生槽位传指针，对象传其指针。
  - 编辑器按引擎算法从 ClassDB 方法信息算出 hash 写入字节码（`core/object/method_info.cpp:87-116`），类加载时按 hash 取 MethodBind，算法不一致会在加载期直接失败。可省略参数的默认值按引擎 `var_to_str` 文本记下，加载时转成原生值。
  - `free()` 没有 MethodBind，可变参数方法不支持 ptrcall，它们和其他语言类的方法仍按名走 Variant 调用。
  - 引擎属性读写是对 getter 和 setter 的 ptrcall 调用（规范 §10.5）。带下标属性先传下标，ClassDB 不向脚本提供下标（`core/object/class_db.h:478`），构建时从 godot-cpp 的 `extension_api` 取得。其他扩展的这类属性、其他语言类的属性和接口属性仍按名读写。
- **内置类型方法与容器快路径**：内置类型方法同样走 ptrcall。签名固定、结果非 Variant 且不处理元素和键的方法只做只读检查，参数直取槽位；其余走通用调用以检查元素、键和结果（规范 §3.8）。可变参数方法（如 `emit()`、`bind()`）经 Variant 按名调用，与 GDScript 相同（`modules/gdscript/gdscript_byte_codegen.cpp:1191-1192`），因为其 ptrcall 每次在堆上复制参数（`core/variant/variant_call.cpp:561-578`）。
  - Array 元素的读写和每次 `for` 迭代只调用引擎一次。读取越界时，引擎给出空指针而不报错（`core/extension/gdextension_interface.cpp:1289-1295`）。
  - 标量类型化 Array 的元素都不持有资源，由引擎写入检查保证（`core/variant/variant.h:268-272`）。写入直接替换元素数据，不经 `Array::set` 的复制和检查（`core/variant/array.cpp:517-523`）。
  - Packed 数组元素经引擎指针 getter 和 setter 按元素槽位布局读写（`core/variant/variant_setget.cpp:348-354, 421-428`）。
- **`for` 迭代**：`for` 每次迭代对应一条 ITERATE 和一条 JUMP，与 GDScript 相同（`modules/gdscript/gdscript_vm.cpp:3471-3492, 3661-3681`），计数 `for` 用 ITERATE_INT。遍历对象的 `for` 由检查器展开为对 `_iter_*` 的三次普通调用，本语言类直接走直调（§8.1）。对象、Array 和状态放在无名局部变量中，调试器不显示它们。每次调用 `_iter_init` 或 `_iter_next` 前新建单元素 Array，调用后由 ITER_STATE 核对长度并取回状态（规范 §5.7）。

#### 并发模型、分派策略与原生代码预留

虚拟机可在任意线程上运行，不使用无锁保护的全局可变状态（§12.3）。运行时直接使用 godot-cpp 的类型，它们与引擎内部同名类型一一对应；改为引擎模块时，运行时换用引擎头文件，adapter 重写，编译器和字节码原样使用（§2.1、§2.3）。

第一版只用 switch 分派，各平台只有一条代码路径要测试。本语言的优势在于按类型存放的寄存器而非分派（GDScript 在 GCC、Clang 上用 computed goto，`modules/gdscript/gdscript_vm.cpp:254-450`）。每条指令的处理只写一次，以后可从同一定义生成 computed goto 或尾调用分派，是否加入由 §4 的基准决定。switch 分派始终保留，因为并非所有工具链都保证尾调用（如 MSVC 的 debug 构建）。

原生代码规划由一个多后端的代码生成模块按函数生成，运行时生成和事先生成共用它，生成时机暂不决定（§7）。CPython 的 JIT 因维护、评估和调试支持说不清而将被移除（[PEP 836](https://peps.python.org/pep-0836/)）。本语言的原生代码从一开始就要支持调试器、程序错误位置和性能剖析，动手前先定好基准和目标。

### 2.3 adapter

#### 扩展接口、反射与编辑器集成

adapter 实现 ScriptLanguageExtension、ScriptExtension 和 ScriptInstanceExtension，将实例属性读写、方法调用和通知转给 runtime，并负责 `.pet` 源码与字节码文件的加载保存。内部类脚本（规范 §4.1）没有资源路径，由所在文件脚本持有并一并取得镜像，运行时以文件路径后接 `::` 和各级名字指称它。

- **构造与反射暴露**：Script 类绑定 `new`，并把 `pub` 的 `_init` 报告为返回该类的静态方法，供 GDScript 检查 `Player.new(...)`（`modules/gdscript/gdscript.cpp:1078`，`modules/gdscript/gdscript_analyzer.cpp:5958-5961`）。非 `pub` 的 `_init` 不报告，GDScript 视其为无参构造（`:6005-6031`，规范 §10.1）。`Class.new` 作为值是名为 `new` 的静态函数值（规范 §3.11），与 Script 的 `new` 共用构造，可见性由检查器在取值处检查（§4.2）。
- **导出提示**：检查器按类名挑选导出的对象。脚本的类名由编译器写进字节码（`Member::export_class`），取沿基类最近的有全局名的类，否则取引擎类，与 GDScript 相同（`modules/gdscript/gdscript_parser.cpp:4601-4650, 4808-4819`）。列出属性时因此不加载脚本，只当类型用的常量在导出中也不加载（规范 §2.1）。
- **async 方法的反射**：反射接口没有协程标记（`core/object/method_info.h:37-44`），async 方法统一报告为无类型 Variant（`PROPERTY_USAGE_NIL_IS_VARIANT`，§9.8）。若报告为 T，GDScript 一方面会给出多余 await 警告（`gdscript_analyzer.cpp:3102-3107`）。另一方面，取消时的 `completed(null)` 不经检查写进 T 类型临时变量，会让 Transform3D 等值类型崩溃（`modules/gdscript/gdscript_vm.cpp:2667-2668`，`modules/gdscript/gdscript_byte_codegen.cpp:998-1001`）。
- **导出插件**：导出插件用字节码替换 `.pet`，经 `add_file(..., true)` 生成重映射，与 GDScript 换成 `.gdc` 相同（`modules/gdscript/register_types.cpp:99-116`）。同时它检查导出的每个场景，有错误即报告导出失败。
- **编辑器插件**：提供分析服务（§13.1）、场景编辑器错误标记、运行前编译，以及两项脚本编辑器扩展：
  - 右键菜单格式化（§13.2）：作为一步撤销只改动空白，断点和书签由此留在原行；改动超出撤销栈容量时退回替换全文，这些标记随之丢失。所有改动脚本编辑器文本的功能经同一个函数应用编辑。
  - 语法高亮：按词法分析的 token 着色，颜色取自 GDScript 高亮器所读的编辑器设置，因为引擎标准高亮器不对扩展开放（`editor/register_editor_types.cpp:175`）。

#### 带场景重命名与跨文件写盘

带场景部分的重命名（§13.3）读取工作区（§2.1），确保预览准确且取消不留改动。有未保存修改的场景经 `PackedScene.pack()` 得到 SceneState，与磁盘场景经同一接口读取（`editor/editor_node.cpp:2505`）。文本定位器读取这类场景时，引擎按文本格式将其写到 `.godot/` 下的绝对路径临时文件，编辑器既不当它是项目文件也不给它 uid（`core/io/resource_saver.cpp:146-147`，`editor/file_system/editor_file_system.cpp:3672-3676`）。

- **预览与前提拒绝**：改动涉及场景或资源文件，或包含候选时，先在引用面板按文件预览（与 JetBrains IDE 相同）。确定的引用默认勾选且不能取消，候选起初不勾选。若已打开、还没有文件的场景中有节点用到声明成员的脚本或其子类，则拒绝给成员改名并提示先保存，因为它不在工作区中，按名存的值改不到。
- **应用主流程**：重命名按以下顺序落地，确保脚本先于场景重载，避免旧脚本丢弃新名存值：
  1. 切换并保存受影响且有未保存修改的已打开场景（含实例化或继承它们的场景），再按标签页位置切回原标签页；
  2. 按保存后状态重新计算改名结果（与预览不同则只刷新预览、不应用），并逐文件核对现有文本，有一处对不上就什么都不改；
  3. 按字节写入所有改动文件（保留换行，脚本见下文），任一写失败则把已写文件写回原字节，标签页也不改；
  4. 全部写完后，已加载的所改脚本先换新文本并在一次分析中重载，再让场景索引重读依赖资源，避免中途按旧脚本读到旧成员；
  5. 通知编辑器文件系统重新读取已加载的资源和场景，重载显示它们且无未保存改动的已打开场景；
  6. 最后查找新名字的引用，与所改之处不符时给出警告。
- **引擎与文件系统防坑细节**：上述步骤绕开了编辑器的多处内部约束：
  - 编辑器只保存当前场景（`editor/editor_interface.cpp:699-704, 775-777`）；标签页是按序排列的已打开场景，按位置切回兼容没有路径的场景（`editor/scene/editor_scene_tabs.cpp:263-292`，`editor/editor_node.cpp:8847`）。
  - 每次切换标签页后，余下步骤延后执行：显示场景时场景面板的延后调用持有面板项，同一帧再切换或重载会释放它们并令编辑器崩溃（`editor/editor_node.cpp:4651-4675`，`editor/scene/scene_tree_editor.cpp:995-1004, 1131-1140`）。
  - 编辑器默认启用安全保存，写入失败可能到关闭文件时才发生，写后必须读回比对（`drivers/windows/file_access_windows.cpp:197-216, 245-277`）。
  - 脚本重载必须先于通知文件系统（`editor/editor_node.cpp:1291-1323`）：按旧脚本读回场景会丢弃按新名存的值，并在之后保存时写掉。
  - 已加载场景同样需要重读：显示标签页时，编辑器若发现实例化或继承的文件变了，会从已加载场景重建它（`editor/editor_data.cpp:722-771`，`scene/resources/packed_scene.cpp:848`）。重读会就地改动已加载场景状态，无未保存改动的已打开场景须随之重载，有未保存改动的不重载以免丢改动（`core/io/resource.cpp:234`，`scene/resources/packed_scene.cpp:2477, 2610`）。
- **跨文件脚本写盘**：重构（含重命名和改他脚本的快速修复）直接把改动脚本写盘，服务不持有未保存文本（§6.5）。读磁盘的构建、导出和运行中游戏由此看到全部改动（§2.1）。
  - 未打开的脚本按字节写入，保留字节顺序标记和换行。已打开的脚本经同一函数在标签页中作为一步撤销改动，保留原有历史并一并保存未保存改动。写入文本与编辑器保存时一致，去掉回车、保留字节顺序标记。
  - 写完后标签页标为已保存，插件发出 `resource_saved`（`editor/editor_node.cpp:1774, 8664-8665`），让脚本编辑器记下新修改时间（`editor/script/script_editor_plugin.cpp:723-742`，`editor/script/script_editor_base.cpp:91-93, 570-573`）。否则它在重获焦点或保存时误以为文件在别处改过，会按磁盘重载并多出撤销步或弹窗询问（`editor/script/script_editor_plugin.cpp:803-850, 2535-2588`）。
  - 写入脚本走保存后热重载（§2.4）：标签页的由脚本编辑器在 `resource_saved` 时发出，其余由插件发出（`editor/script/script_editor_plugin.cpp:738-741`）。
  - LSP 客户端打开且无未保存改动的脚本照常写盘，由客户端自行重读。在客户端发来新文本前，工作区取文件文本，直到人的视图上有会话改动或关闭它。读回、引用核对和撤销记录由此都按写入文本计算。
- **冲突拒绝条件**：重构不写掉编辑器没读到的外部改动，遇以下情况整批拒绝并提示文件名：
  - 打开的脚本文件与编辑器上次读写时不同（如在别处改过，§2.4），标签页有未保存改动时提示冲突（§6.5）。此条最先核对，客户端文本因此与标签页不同时仍按冲突提示。
  - 要先保存的已打开场景与磁盘冲突（§6.5），服务还没读回的改动也算（修改时间或大小变化且内容异于编辑器上次所见）。
  - 人的视图上有 LSP 会话对所改脚本有未保存改动（服务器存不了客户端文本，【待定】是否另有做法）。未打开的脚本按应用时现读文本改动，不必这样核对。

#### 重构的撤销与重做联动

全部改动落在单个已打开脚本中时（如局部变量和仅本文件用到的私有成员），改动只是该脚本的一步撤销，不写磁盘。跨文件或涉及场景的重构则进入全局历史，不把全局历史标为未保存（文件已写盘；只改单个标签页时该标签页标为未保存）。

- **语义重算与历史对齐**：撤销和重做按同一套规则改动并写盘，只剩单个已打开脚本时只改其标签页。重命名撤销按声明 id 找到声明并基于当时文本改回，保留后续编辑，旧名已被占用则拒绝。前一步改过的候选按改后位置找回，位置变了则拒绝。声明已是目标名字时视作已完成（用于菜单撤销被拒、全局历史已回退一步后让重做重新对齐）。
- **标签页与场景历史衔接**：若标签页最后一步正是重构改动，撤销就撤掉该步以接回先前历史。撤掉后文本与重算不符时，重做回去并另加一步。其余情况下撤销是新一步，重做总是新一步并清掉先前撤掉的那步；文本回到文件内容时标签页标为已保存。重载受影响场景会清空其历史，与引擎给文件改名相同（`editor/editor_node.cpp:7151`）；编辑器重建关联场景亦然（`editor/editor_node.cpp:4747-4753`）。整个动作推迟到编辑器撤销或重做返回后运行，避免在全局历史只改了一半时触发编辑器检查各历史（`core/object/undo_redo.cpp:432-434`，`editor/editor_undo_redo_manager.cpp:321-325, 402-407`）。
- **脚本内快捷键接管**：在脚本中按撤销键时，若脚本已无可撤销内容或最后一步正是这次重构，插件接管并改撤全局重构。重做键同理：脚本已无可重做内容，或下一步是要重做撤销重构时撤掉的那一步。
  - 插件在 `_input` 中早于代码编辑器收到 `ui_undo` 和 `ui_redo`（`scene/main/viewport.cpp:3537`，`scene/gui/text_edit.cpp:2737-2746`）。只有重做才看得出还原后的版本号（`scene/gui/text_edit.cpp:4840, 4848`），插件先在脚本中重做，确认为撤掉的那步再撤回并转而重做重构。撤掉的那步不在脚本中单独重做，不接管或重做被拒时按键什么都不改。
  - 接管前插件按当时文本试算一遍，会被拒绝则吞掉按键并提示，各历史不动。通过时经主菜单撤销项执行以保持各历史一致（主菜单收起成一个按钮时不接管）。编辑器按时间在全局和当前场景历史间选一步撤销（`editor/editor_undo_redo_manager.cpp:136, 340-367, 509-538`），重命名后若别的历史有过步骤就不接管。关闭场景只丢弃历史，不算步骤（`editor/editor_data.cpp:674-699`）。
  - 【已知限制】经脚本编辑器的"编辑"菜单撤销时，插件不接管，只撤掉该脚本改动而与场景中新名脱节（`editor/script/script_editor_base.cpp:385-387`）。经该菜单重做时，撤掉的那步也只在脚本中重做，标签页标为未保存（`editor/script/script_editor_base.cpp:390-391`）。

#### 场景节点移动与路径同步

在场景编辑器中给节点改名或移动时，脚本中的字面量路径随之改写，并并入编辑器刚提交的动作（规范 §13.3）。删除节点不改写脚本，到它的路径报编译错误。改动按重构规则应用（只改一个已打开脚本时只改标签页，否则写盘），输出面板逐处列出文件、行、旧路径和新路径。

- **变动捕捉与过滤**：插件按对象 id 记下当前场景所拥有节点的路径，在切换场景、撤销、重做和处理完改名后重记。只有提交动作期间改名或重新入树且路径变化的节点及其子孙才算移动，撤销、重做和 `@tool` 代码在动作之外的改名都不算（`scene/main/node.cpp:366, 1472`，`editor/editor_undo_redo_manager.cpp:252-260, 298`）。把节点设为场景根时其余节点随之移动（新根原为场景中节点，`editor/docks/scene_tree_dock.cpp:1111-1135`），计入移动。删除和剪切只移走节点，粘贴的是新副本，都不算移动（`editor/docks/scene_tree_dock.cpp:709-769, 2887-2983`）。
- **与编辑器撤销动作合并**：在提交后的 `history_changed` 中，插件以场景根为上下文创建同名、`MERGE_ALL` 的动作。移动节点在动作内不发信号且提交先退出动作再执行，无法在动作执行中追加。合并要求距编辑器建动作不到 800 毫秒，插件先提交动作、将改写推迟到之后计算（`core/object/undo_redo.cpp:97`）。多选和批量改名带 `backward_undo_ops` 合并不成，改写退为同场景历史中紧随其后的一步（`editor/scene/scene_tree_editor.cpp:1678`，`editor/scene/rename_dialog.cpp:601`）。执行与撤销调用插件同一方法，分别带上正反向路径对应，均在编辑器撤销或重做返回后按当时文本重算。
- **路径重算与安全回退**：改名前检查覆盖所有脚本，未读相关场景的沿用缓存；改名前的场景由当前场景按反向对应还原。若该步连带增删父节点（如 Reparent to New Node 及其撤销），还原缺父节点时补上一个 Node 让路径走通（`editor/docks/scene_tree_dock.cpp:3223-3274`）。
  - 路径从起点新位置重算到目标新位置，与编辑器改写 NodePath 属性一致（`editor/docks/scene_tree_dock.cpp:2077-2120`）。含 `%Name` 的路径保留到最后一个 `%Name` 为止并从该节点重算，该节点改名则换上新名。
  - 改写后在移动后的场景中再检一遍：只要某个放置脚本的场景中路径会指向别的节点或不再指向节点，就不改写，只列在输出面板中。非字面量 `get_node()` 中以整段写出目标节点名的字符串同样只列出。
- **继承场景与已知限制**：继承场景按基场景存盘结构读取，可能是改名前也可能是改名后的样子，按两方向改写可兼顾两种状态。根换了时每个继承场景都有根、分不出哪一样，不改写其脚本。
  - 【已知限制】基场景改名后保存前，继承场景上改写过的路径在检查中报找不到节点。连续改名而不保存时，第二次起不再改写这些脚本。
  - 【已知限制】在脚本标签页中按撤销键只撤销该脚本中的改写，场景历史不动。之后在场景中撤销这一步时按当时文本重算，两边仍会一致。

#### 无界面命令行入口

- `--petrichor-build` 运行同一套分析并检查每个场景，警告和提示只打印（§13.1）。
- `--petrichor-format` 格式化项目脚本（§13.2），加 `--check` 时只列出未格式化的文件；有未格式化脚本或语法错误时以非零退出。

### 2.4 编辑、运行、导出和热重载

#### 编辑器分析、占位实例与按需重算

分析服务常驻编辑器进程并持有整个项目的编译结果，诊断同步显示在脚本编辑器和场景编辑器中。编辑器中本语言脚本使用自有占位实例（`src/adapter/pet_placeholder.h`）：它像引擎占位实例一样保存导出属性，脚本有错时保留场景设的值（`core/object/script_language.cpp:680-923`）。它还回答 `_get_configuration_warnings` 让场景面板把错误标在节点上，而引擎占位实例不回答任何调用（`scene/main/node.cpp:3522-3532`，`editor/scene/scene_tree_editor.cpp:493-519`，`core/object/script_language.cpp:793-804`）。

- **错误降级与诊断定位**：脚本有错时，默认值和信号取上次编译成功的声明（与 GDScript 相同，`modules/gdscript/gdscript.cpp:546-548, 575-578`），避免保存场景时把未存导出写成 null 或丢掉信号连接。场景用错脚本的诊断记下场景和节点（实例化的场景根记为 `.`），信号连接错误记在目标上，动画轨道与同步属性错误记在所指节点上。节点错误合并自其脚本检查与沿 owner 链向上找到的各场景检查（`scene/resources/packed_scene.cpp:567-573`），在每个场景中以该场景根到节点的路径定位。脚本编辑器列出挂载脚本的场景报在脚本中的错误，但仍判脚本有效并照常应用其源码（`editor/script/script_text_editor.cpp:841-886`）。
- **可见项按需重算**：节点错误和脚本编辑器列出的场景错误均读工作区（§2.1），行号与错误都按未保存缓冲计算。只有可见结果会主动重算（节点错误与当前显示的本语言标签页），其余按需重算，且每个 revision 只重算一次。
  - 场景编辑、撤销与重做停下后，先打包未保存场景再重算两者（`editor/editor_node.cpp:8406-8409`）。一次重算要重检该场景放置的脚本、耗时远超一帧，因此在编辑停下 `text_editor/completion/idle_parse_delay` 秒后再触发（与脚本编辑器一致，`editor/gui/code_editor.cpp:1014, 1166, 1696-1699`）。
  - 标签页检查完脚本后节点重取错误；磁盘变化（§2.1）后同样重算两者，分析只重检输入变了的脚本。
  - 隐藏标签页不检查，各标签页记下上次检查时的 revision。切换标签页时由编辑器重检新显示的标签页（`editor/script/script_editor_plugin.cpp:410`，`editor/gui/code_editor.cpp:1701-1702`）；回到脚本画面时引擎不主动重检（`editor/script/script_editor_plugin.cpp:4318-4325`），工作区已变则由插件补检。
- **加载期仅编声明与文件重载**：编辑器加载脚本时只编译声明以提供反射信息（不可运行），避免加载期读场景被引擎当作循环加载拒绝（`core/io/resource_loader.cpp:1049-1056`）。完整编译留到编辑检查、保存、运行前构建和导出；仅编声明时不读场景，场景定型成员（如 `@onready var camera = $Head/Camera`）暂为 Variant。支持 tool 脚本时会在加载后补一次完整编译。
  - 脚本编辑器检查通过后把标签页文本交给脚本并要它的导出（`editor/script/script_text_editor.cpp:874-878`）。该文本没编过时同样只编声明，占位实例在保存前就有新导出（同 GDScript），不写文件也不重载游戏。
  - 编辑器发现已加载脚本文件变化时经 `reload_from_file()` 重载（`editor/editor_node.cpp:1291-1323`）。脚本先换上工作区文本（优先未保存的标签页或客户端文本，否则读文件；GDScript 也先读文件，`modules/gdscript/gdscript.cpp:2556-2559`）。否则无标签页脚本停在旧声明，重读场景会丢掉新导出值并被下次保存写掉。

#### 导航、重命名与快速修复

跳转到定义、悬停文档、查找引用、重命名与快速修复均建在编译器查询与引用表之上，编辑器插件负责快捷键接入、面板交互与撤销联动。

- **跳转、悬停与文档**：跳转与悬停经 `_lookup_code` 查询光标处的引用表条目（§2.1）。本语言声明按工作区文本跳到对应行，局部变量与参数悬停显示类型；引擎声明打开文档页，GDScript 成员跳到声明行，各类声明悬停均显示自身文档。本语言类的文档经 `_get_documentation` 由声明检查生成（命名同 GDScript、类型按本语言写法，`modules/gdscript/editor/gdscript_docgen.cpp:40-46, 339-347, 594-598`），同时列出非 `pub` 成员供类内悬停查阅。`##` 注释按 GDScript 规则成为说明（规范 §2.2，`modules/gdscript/gdscript_parser.cpp:3938-4243`），局部变量注释在悬停时显示。
- **查找引用**：由编译器 `find_references`（`src/compiler/navigation.h`）完成，LSP 直接沿用。它在单次分析中编译所有本语言脚本并检查场景与资源（未变结果沿用缓存），读工作区并按声明反查引用表（§2.1、§2.3），输出与重命名预览一致。
  - 经覆盖或实现相连的本语言声明一起查出供同步改名，连接不经不可改名的引擎声明。所查的本语言声明能被引擎按名找到时才列出候选（规范 §10.5），局部变量和不带 `pub` 的成员没有候选。检查器把目标为 `Object` 或 `Variant` 的字面量名字记为未解析引用以取同名候选，`.gd` 和 `.cs` 按整词文本匹配。
  - 引用面板记下查找时的 revision，点击处的文件若已改动则先重查再跳转。重查按声明 id 找到声明并跳到同文件同序位置，找不到则清空面板并提示项目已变。局部变量 id 含声明偏移，声明前改动即找不到。重新查找推迟到选中之后，因为 Tree 遍历条目期间发出 `item_selected`，立即重填会释放正在遍历的条目（`scene/gui/tree.cpp:3006-3074`）。
- **重命名计算与冲突校验**：打开改名框前先经 `renamed_name` 做不依赖新名字的检查（`rename` 也先做这些检查）。光标无名、指向节点或引擎声明、或覆盖引擎及其他语言方法时提示原因且不弹框，否则填入该名字。`rename`（`src/compiler/rename.h`）对查找引用的每一处生成字节区间、现有文本与新文本（应用前先核对原文），场景和资源文件交由文本定位器定位（§6.4）。
  - 新名字须是一个标识符 token（排除关键字）；覆盖引擎或其他语言方法的声明不能改名，因为调用方按原名调用。按名匹配字段的模式中 `var x` 是 `x = var x` 简写（规范 §5.6），只改其中之一时写成完整形式（如 `amount = var damage`）。
  - 冲突直接交给检查器判断：将改后源码投入独立分析重检（改局部变量时只检所在脚本），若多出错误或某处改指另一声明（如局部遮蔽成员）即拒绝。改前结果取自查找引用，缓存未变的脚本跳过比较；本遍结果照常留存，应用后即成新缓存，取消则下次按读取记录重检。
  - 【已知限制】新名字原有的按名用法改后可能开始指向该声明（如 GDScript 的 `o.has_method("take_damage")`），接收者为 `Object`/`Variant` 的字面量、`.gd`/`.cs` 及场景中的这类用法均不检查。成熟重命名都只按旧名找动态用法，Roslyn 还有意不报改前解析不到、改后解析到的引用（`src/Workspaces/Core/Portable/Rename/ConflictEngine/ConflictResolver.Session.cs:546-550`，roslyn `644d001`）。
- **快捷键接入**：代码编辑器上下文菜单插件的快捷键只在菜单打开时生效（`editor/inspector/editor_context_menu_plugin.cpp:155-176`，`editor/script/script_editor_plugin.cpp:3111`，`ed1daf0`），查找引用由编辑器插件 `_shortcut_input` 接收。重命名快捷键 F2 同样由它接收，但只在焦点位于当前代码编辑器时生效，以免与场景面板和文件系统面板的 F2 冲突（`editor/docks/scene_tree_dock.cpp:181-184`，`editor/docks/filesystem_dock.cpp:2780, 3885`）。
- **快速修复与跨文件应用**：快速修复（规范 §13.2）取自脚本编辑器刚完成的分析缓存，保存时不做修复。
  - 本语言标签页在折叠边栏右侧紧挨文本增设边栏，光标行有带修复错误时画出灯泡。工作区变动（含其他标签页）后灯泡隐去，打开列表前重检。点击灯泡、按 Alt+Enter 或选右键 Quick Fix 打开列表（Ctrl+. 已是转到下一个断点，`editor/script/script_text_editor.cpp:2672`）。
  - 列表先列含光标的错误、再按位置去重列出本行修复；分隔线后为本脚本检查中出现两个以上的纯本脚本自动种类各列一项（如 `Fix all 'Write the truth test' in file`），由 `compiler::fix_all()` 得出编辑。场景检查报在脚本中的错误只提供只改本脚本的修复。
  - 列表带戳（§2.1），包含修复涉及的文件。戳未变时按错误和标题找回修复；戳变了就不用缓存单独重检，以免沿用缓存中已偏移的其他文件位置。找不到修复则不应用，提示项目已变并刷新灯泡。只改本脚本的单项或批量修复均为本脚本一步撤销。
  - 改动其他脚本的修复（如补上 `pub`）保持当前标签页，应用前按工作区核对目标原文，再按重命名规则落地（§2.3）。它记入全局历史，撤销重做按当时文本核对，编辑已在文本中时视作完成。应用后插件发出代码编辑器的 `validate_script` 信号触发当前标签页立即重检（`editor/gui/code_editor.cpp:1696-1699`，`editor/script/script_editor_base.cpp:653`）。

#### 内置 LSP 服务器与连接管理

LSP 服务器位于编辑器进程内（`src/adapter/editor/lsp_server.cpp`），与编辑器共用分析缓存和工作区（§2.1）。成熟语言服务器通常由客户端经 stdio 启动，但本语言检查依赖运行中的 ClassDB 和场景，故驻留在编辑器内。扩展也不另启无界面编辑器，因为 Windows 上同一项目的第二个编辑器进程加载不了扩展（`core/extension/gdextension_library_loader.cpp:196`，`platform/windows/os_windows.cpp:488-504`）。有界面的编辑器总是开启服务器；无界面编辑器只在 `--petrichor-lsp` 下开启，构建、测试和 godot-tools 启动的实例都不开。

- **监听与发现**：插件仅监听 127.0.0.1 上由系统分配的端口，将端口和进程号写进 `.godot/petrichor/lsp.json`，避开 godot-tools 视作 GDScript 服务器的 6005 和 6008 端口。扩展按项目根读该文件，同时打开的多个项目各自连到对应编辑器；GDScript 用固定端口，第二个编辑器绑不上（`modules/gdscript/language_server/gdscript_language_server.cpp:95-99`）。
- **主线程调度与防重入**：插件在主线程的 `process_frame` 中轮询服务器，分析同样跑在主线程。编辑器失焦时每帧睡 100 毫秒，请求最多因此多等 100 毫秒（`editor/editor_node.cpp:1064-1073`，GDScript 服务器亦然）。分析进行中不轮询且禁止重入，因为进度框会在调用中途跑一帧（`editor/gui/progress_dialog.cpp:148-154`）。
- **多会话与视图选择**：服务器同时服务多个会话，各自维护生命周期、客户端能力、打开文档及其版本和诊断。每帧每会话至少处理一条消息，其余在帧预算内处理，避免一个会话阻塞其他会话。会话默认处于人的视图（§6.5），`initialize` 带 `initializationOptions: {"view": "disk"}` 时切到磁盘视图，其他 `view` 值直接拒绝并说明原因。连接后 10 秒内未发 `initialize` 则断开。`window/showMessage` 只发给引起请求的会话，冲突提示除外，它会发给每个会话（§6.5）。
- **协议解析与边界防护**：消息头按行只认 `Content-Length`，缺少可用长度时跳到下一个 `Content-Length` 续读。正文不是 UTF-8 的 JSON 时回复 ParseError，字段不合要求的通知整条忽略，回复消息（含无 id 者）永不回答。正文中的 `\u0000` 换成等 UTF-16 长度的 U+FFFD，避免引擎 String 每遇 NUL 打印一条错误（`core/string/ustring.cpp:202-206`）。单条消息限 16 MB，超过的跳过正文并经 `window/showMessage` 告知；不读取导致待发内容超过 128 MB 的客户端直接断开。

#### 文本同步、外部改动读回与路径归一化

LSP 文本同步是增量的，编辑应用到全文。按 LSP 对 `didOpen` 的要求，会话的请求与诊断总是基于“自身视图叠上自己打开的文档”计算；人的视图上只有一个会话时，这正是工作区。工作区中脚本的文本依次取自人的视图会话、Godot 标签页和磁盘（`src/adapter/editor/scene_index.cpp`）。

- **多端视图仲裁**：人的视图上会话打开或改动文件后，工作区改取其文本，Godot 标签页仍检查自己的文本。同一文件在两个会话各有未保存文本时，各自诊断按各自文本算、两份文本不同步。对其他各方（Godot、其他文件检查和另一会话的其他文件），取最后改动它的会话。
  - Godot 经重构或格式化写入会话打开的脚本后，对其他各方改取写入文本，直到会话再次改动（§2.3）。重构写盘不向客户端推送文本，客户端之后打开读到的就是写入文本。
  - 会话关闭文件或断开时，工作区依次退回人的视图上另一最后改动的会话、Godot 标签页或磁盘。已加载脚本取过会话未保存文本的（如读回资源后），交还时换回工作区文本重载，同 Godot 丢弃标签页改动（`editor/script/script_editor_plugin.cpp:607-611`）。
  - 磁盘视图会话只看文件和自己打开的文档，不受 Godot 和其他会话未保存内容影响，其文档也不进入工作区。
  - 人的视图会话改动与编辑器自身改动等价：停止变化 `idle_parse_delay` 秒后重检显示的标签页与节点错误（每 revision 一次），会话断开交还文件时立即重检。
  - Godot 标签页去掉回车而客户端可能保留（`scene/gui/text_edit.cpp:9253-9254`），因为回车只在行尾，行列依然一致。标签页光标与改动按行列与工作区偏移互转。
- **外部写入读回与热重载**：服务察觉外部改动或新增脚本、场景或文本资源时（§6.5），按重构写盘后的步骤读回（§2.3）。已加载脚本先换上工作区文本（含客户端打开且改名未保存的脚本）并在一次分析中重载。随后通知文件系统重读已加载资源与场景，重载无未保存改动的已打开场景（含二进制场景）。改名文件无论何种顺序写入，资源和场景总按新脚本读回。文件系统同时记下新修改时间，避免重获焦点扫描时误按旧脚本重读。
  - 读不出的资源不读回也不重载其已打开场景，避免重载先关场景再读文件导致场景被关掉（`editor/editor_node.cpp:7143-7146`）。空资源文件不交给引擎加载、等写入后再读，避免先截断再写引发引擎语法报错（`core/variant/variant_parser.cpp:1879-1880`，`scene/resources/resource_format_text.cpp:1143-1147`）。已载入的文件为空时，服务让文件系统做的扫描也等它写入后再做。扫描会重读改过的已载入文件，Godot 4.8 起打开的场景也一直载入（`editor/file_system/editor_file_system.cpp:1018-1026, 1060-1063`，`ed1daf0`；`editor/editor_node.cpp:5081`，`c51ff06e8`）。
  - 【已知限制】外部写入后、服务察觉前若 Godot 重获焦点，扫描会先按旧脚本读回一次。服务察觉后再读回一次结果正确，但在此之间按 Ctrl+S 会写掉这些值。
  - 保存的脚本继续走热重载：按磁盘文件编译字节码（保证可由磁盘源码重现），再经调试会话发出 `reload_scripts`（重构写盘同理，§2.3）。条件是脚本无错且调试菜单开着 Synchronize Script Changes（`editor/script/script_editor_plugin.cpp:776-801`，`editor/debugger/debugger_editor_plugin.cpp:238`）。
  - 其他文件增删改由服务通知工作区并让文件系统扫描（同编辑器重获焦点，`editor/editor_node.cpp:1049-1058, 1291-1323`，`editor/file_system/editor_file_system.cpp:1597-1607, 1018-1025`）。Godot 未改过的标签页换上保存文本，改过的不动、留待重获焦点时询问是否重载（`editor/script/script_editor_plugin.cpp:803-850`）。GDScript 服务器保存时直接换掉标签页文本，未保存改动会丢失（`modules/gdscript/language_server/gdscript_text_document.cpp:95-124`，`editor/script/script_editor_plugin.cpp:2535-2588`）。
- **MD5 识别自身写入**：文件与编辑器上次写入或读回内容相同时不触发读回，避免把 Godot 自身保存当作外部改动而重载场景、清空撤销历史（`editor/editor_node.cpp:7143-7151`）。编辑器保存场景、资源与脚本（`editor/plugins/editor_plugin.cpp:284-289`）、每次读回、重构写盘以及无未保存改动标签页同步文件时（`editor/script/script_text_editor.cpp:248-251`，`editor/script/script_editor_plugin.cpp:723-728`，`editor/script/script_editor_base.cpp:575-604`）都会记下 MD5。重构也按这个记录判断标签页文件是否在别处改过（§2.3）。
  - 标签页或场景有未保存改动且文件变化时，读回照常进行但不记 MD5，将其标为冲突（§6.5）以阻止重构覆写。
  - 保存场景时，编辑器在 `scene_saved` 之后静默保存外部资源和脚本，再调用各插件的 `_save_external_data()`（`editor/editor_node.cpp:2521-2526, 2374-2408`，`editor/editor_data.cpp:421-425`）。服务在这两处各走查一遍，将期间变化记为编辑器写入并记录 MD5，防止读回替换子资源而撤销历史和检查器仍持旧实例。
  - 【已知限制】以下写入同样不发信号，比对时按外部写入读回并替换已加载资源的子资源：
    - 文件系统面板移动文件后改写依赖它的文件（编辑器已重载打开场景，读回会再重载一次，`editor/docks/filesystem_dock.cpp:1676-1705`）；
    - 工具脚本调用 `ResourceSaver.save`；
    - 保存没有根节点的场景时保存改过的外部资源（`editor/editor_node.cpp:3495`）。
- **UTF-16 换算与跨平台路径归一化**：LSP 按 UTF-16 码元计列，编译器按码点（§2.1），两者只在 `src/compiler/lexer.h` 的 `utf16_positions()` 和 `utf16_offset()` 中换算（按 `\n`、`\r\n` 和 `\r` 断行）。
  - 服务器只接受项目根下的 `file:` URI，识别 Windows 盘符大小写和百分号编码。`.godot/` 下（Windows 和 macOS 不分大小写）、项目外和非 `.pet` 文件不同步也不报错。
  - Windows 上项目根和客户端路径先经 `GetLongPathNameW` 把已存在部分的 8.3 短名换成长名再比较，未保存文件也认得。给客户端的其他文件 URI 同样用长名。Windows 和 macOS 上仅差大小写的路径统一换回真实文件名，防止引擎将其当作另一个文件（`editor/file_system/editor_file_system.cpp:1964-1975, 2496-2503`）。
  - 同一文件以两种 URI 打开时共用一份文本、诊断发给两边，最后一个关闭时才交还。关闭磁盘上不存在的文件时，分析同步丢掉其缓存结果。

#### LSP 诊断、查询与重构请求

LSP 服务器提供诊断、补全、参数提示、悬停、定义、类型定义、引用、重命名、快速修复、格式化、大纲和同名高亮。GDScript 服务器缺少类型定义、快速修复和格式化（`modules/gdscript/language_server/godot_lsp.h:1744-1798`）。各类查询沿用编辑器的查询实现，按会话所见文本计算（会话未打开的文件按其视图）。场景中的位置给 `.tscn` 行号供客户端以文本打开，二进制 `.scn` 无行号则给文件开头；引用不列候选，因为 LSP 位置没有候选标记。

- **诊断分帧推送**：诊断只发给会话打开的文件（与编辑器只检显示标签页一致），每次携带所依据的文档版本。关闭文件时清空诊断，位置越界按 LSP 规定夹到行尾或文末。刚打开的文件立即发送，其余在工作区与各会话文档停止变化 `idle_parse_delay` 秒后发送；编辑器处理完保存或场景编辑停下后立即重发。每帧至少发一个文件，其余在帧预算内分批发送，避免打开大量文件时单次修改卡住编辑器。
- **补全、悬停与导航查询**：
  - 补全给出编辑器的列表和替换规则（`scene/gui/code_edit.cpp:3837-3875, 3916-3927`）：字符串内从引号起替换并加同种引号，否则替换光标前含 `/` 的词；触发字符同脚本编辑器（`editor/gui/code_editor.cpp:2077`）。客户端支持片段时，以 `(` 结尾的项转为光标在括号内的片段，与 GDScript 服务器相同（`modules/gdscript/language_server/gdscript_language_protocol.cpp:559-569`）。
  - 参数提示取自补全的调用提示并标出光标所在参数。悬停显示声明（含种类、类、成员、签名或类型，函数前标 `static` 和 `async`）与 `##` 文档，签名写法同调用提示。引擎成员也这样显示，因为扩展读不到引擎类文档。
  - 跳转定义时，本语言声明跳到名字，节点路径（如 `$Head/Camera`）跳到各文本场景中该节点的 `[node]` 行，引擎声明不跳。类型定义和大纲是编译器查询（`src/compiler/navigation.h`，与 `lookup` 并列），类型定义取光标处名字或表达式的类型（含 T? 和容器内类型，同 rust-analyzer）。同名高亮只查本文件引用表，遮蔽同名声明算作另一声明。场景和资源引用给出重命名改写位置（会拒绝时给拒绝所在行）；有语法错误时格式化回复错误并附编辑器提示原因。
- **快速修复（`codeAction/resolve`）**：按编辑器灯泡列表给出，自动修复标为首选，“修复本文件中这一种”排在后面。客户端支持时列表先不带编辑，选中时再经 `codeAction/resolve` 求编辑，避免 VS Code 应用过时编辑时因不核对版本而错位。
  - 每项带上检查戳和修复标识（错误区间、消息、标题或要修复的种类），求编辑时按戳找回（§2.1），戳变则单独重检再找回。找不到时不带编辑，经 `window/showMessage` 提示项目已变。
  - 编辑带上客户端文档版本，未打开文件版本为 null。若修复改到会话未打开且有未保存内容的文件（判定同重命名），则拒绝该修复。它仍列在菜单中，标题后括注要先保存的文件和位置且不带编辑，选中后不改文件并经 `window/showMessage` 说明原因。不标为不可用是因为 VS Code 菜单不显示不可用项及其原因。
- **重命名**：`prepareRename` 做打开改名框前的检查，可改名返回区间和名字，否则回复错误。改名由编译器 `rename` 按会话所见计算，新名字非标识符或与原名相同时的回答与编辑器一致。
  - 脚本和场景改动放进同一个 `WorkspaceEdit`（客户端文档带版本，场景和资源版本为 null、按磁盘算位置），由客户端预览、写入与撤销；写入后 Godot 按外部写入步骤读回。候选带上需确认的修改注解（预览起初不勾选）；客户端不支持修改注解时不给候选，以免与确定引用一并改掉。
  - 拒绝时回复错误，每个原因一行并带文件和行（所改脚本自身无行号的原因如非标识符除外）。会话没打开的受影响文件有未保存内容时，拒绝并列出文件提示先保存（服务器按会话所见算位置，客户端却按磁盘文本应用）。未保存内容在两个视图都含 Godot 标签页和未保存场景；人的视图还含另一会话未保存文本，磁盘视图不算。客户端不同步的文件在 VS Code 有未保存改动时，扩展同样拒绝，因为 VS Code 会把 null 版本编辑套到打开文本上导致错位。
  - VS Code 默认在多文件重构后自动保存全部文件，与 Godot 重构一致（§2.3）。【已知限制】在 VS Code 中撤销重命名后，改过的文件留着未保存改动，因为 `files.refactoring.autoSave` 只在应用重构后保存、撤销后不保存。保存之前，Godot 和磁盘上仍是改名后的文件。

#### VS Code 扩展客户端

VS Code 扩展位于 `editors/vscode/`，是不经构建的 JavaScript，经 `vscode-languageclient` 连接编辑器内置服务器。语言 id 为 `petrichor`，扩展名为 `.pet`。TextMate 语法按本语言词法 token 另写，类型只按位置着色，不按大小写猜。

- **多项目根与路径别名**：每个项目对应一个客户端，文档选择器只含项目根下的 `.pet`。项目根取工作区中的每个 `project.godot` 及打开脚本之上最近的一个（含工作区外脚本），按 `fs.realpathSync.native` 解析结果去重，使 8.3 短名与长名共用同一客户端。因为 VS Code 按打开时的 URI 匹配选择器，选择器会列出见到的每种写法，见到新写法时重启客户端。文件事件按最先见到的写法监视（解析还会跟随链接，而服务器按 Godot 的写法比较）。
  - 【已知限制】嵌套在另一项目中的项目，其脚本也由外层客户端同步，而 Godot 会跳过嵌套项目（`editor/file_system/editor_file_system.cpp:3494-3499`）。
- **重连与文件监视**：扩展读 `lsp.json` 经 socket 连接，进程已不在时不连（编辑器被杀时会留下文件）；连不上时每 3 秒重试，`lsp.json` 写出时立即重试。断开后新建客户端而不用库的重启，因为服务器分不出重连者是否为原客户端（godot-tools 亦然）。扩展还换掉了库默认“3 分钟内断开 5 次后放弃”的错误处理。连接问题只在显示本项目脚本时于状态栏提示，不弹错误框。扩展监视项目中的 `.pet`、`.gd`、场景、资源和 `project.godot`，经 `didChangeWatchedFiles` 和 `didSave` 提示服务器立即比较文件，不必等下一次定时走查（§6.5）。
- **打包与发布**：`.vsix` 附在 GitHub release 上，版本在打包时给出，与插件包相同。上架扩展市场和 Open VSX 在 0.9（§5 第 12 步）；此前没有发布者，扩展 ID 为 `undefined_publisher.petrichor`。

#### 运行前构建、字节码校验与热重载

从编辑器运行时，扩展在 `_build` 中完成编译并把字节码写入 `.godot/petrichor/`，游戏进程只读取。因为 `$X` 等类型取决于场景（规范 §7），游戏自行编译既要重析全部场景拖慢启动，结果也可能与编辑器不同。命令行的 `build` 同样写出字节码供测试和 CI 使用（§6.5），导出插件则把字节码放进导出包。场景缺必须赋值导出值的错误标为 `Diagnostic::runs`，不妨碍运行前编译（规范 §7.5）。

版本号定下之前（§6.1），字节码只带格式标识（构建时对 `src/bytecode/` 的哈希），标识不同的构建拒绝读取。带着源码加载的脚本还会额外确认两点，否则要求重新构建：

- **源码哈希**：确认字节码由当前这份源码编译；
- **编译器标识**：按构建时 `src/compiler/` 与扩展 API 的哈希校验，防止升级后旧字节码按旧含义运行。补全、格式化、迁移、导航、重命名、场景文本定位和警告的文件不计入，它们不改变编译出的模块和错误。该标识不计入格式标识，因为导出游戏不带源码、导出模板也不含编译器，计入会导致编译器每次改动都要重编导出模板。

**函数体热重载**：保存脚本后，编辑器重新编译并经调试连接通知游戏重载。只改函数体时实例换用新代码。一旦声明有变化，游戏保留原代码并提示一次，此后不再应用任何重载直到重新运行（规范 §12.4）。之后的重载请求不读字节码也不再提示，因为编辑器保存时依赖脚本可能尚未写入、字节码编译不出来。

## 3. 测试

测试围绕规范、引擎和真实代码三个维度编写，不从实现细节反推：

- **规范一致性**：按规范各节规则编写用例，编译期检查放入不启动引擎的 compiler 测试，运行时行为放入引擎测试。
- **引擎兼容**：经无界面运行的 Godot 测试项目，验证脚本挂载、保存和重载，以及 GDScript 与本语言的双向调用。生命周期测试覆盖三类边界：
  - `await` 期间所属对象或信号源被释放；
  - 信号同步发出后再次挂起，以及同一个挂起点被恢复两次；
  - GDScript 调用本语言后，本语言再等待外部信号。
- **真实代码**：让[第二次纸面迁移](https://github.com/YYF233333/petrichor-corpus/blob/main/surveys/paper-migration-2.md)所用的 FPS 项目和 Ring，以及 deck_builder_tutorial 真正跑起来。
  - 三者的脚本都是迁移工具的输出再经人工收尾，只用反向转换能转回的写法（规范 §13.4）。
  - 迁移测试复制原项目并换入迁移后的脚本，未迁移部分保持 GDScript。迁移后的运行只能报告原项目也报告的错误，退出时也只能占用原项目占用的资源。
  - deck_builder_tutorial 的检查脚本从主菜单开局，经地图打完一场战斗，再领取奖励。随机数固定，每次跑同一局。
  - Ring 的 `main.gd` 属于视觉小说，要用测试不复制的 C# 运行时，所以保持 GDScript。Ring 测试不需要 .NET：`tests/engine/ring/ring_check.tscn` 代替 `Root.cs`，发出 Ring 的 `main.md` 构造的消息。C# 的 `Call()` 与 GDScript 动态调用一样，都经引擎按名字派发。

编译器测试经同一个辅助函数编译源码，自动校验 §2.1 的三项约定：

- token 流无损；
- 节点的范围依次嵌套；
- 每个解析出的名字都有引用，且原文相符。

能运行的编译结果还要通过与运行时加载相同的字节码校验。对无错误源码，辅助函数还把每行从中间截断后再编译，要求不崩溃、只报语法错误，其余行仍留在树上（未闭合括号后更深缩进除外）。每个新特性测试由此顺带验证这些约定。边输边改时的典型语法错误另设专组用例，写明位置与措辞。`tests/engine` 中的 `.pet` 文件不含真实引擎 API，只检查 token 流、节点范围和截断后的解析。

每个引擎测试写明它预期的错误，出现其他任何错误都算失败。运行器启动的导入不做检查，因为 Godot 4.7.2 编辑器在导入后立即退出时可能崩溃（Godot issue #111048）。

## 4. 性能

性能评测将本语言与 GDScript 放在四组基准上对照，分别衡量虚拟机自身和跨引擎边界的开销：

| 基准 | 测量内容 |
|---|---|
| 启动与编译 | 冷启动、重复运行、修改代码后重新运行 |
| 纯计算 | 整数和浮点循环、函数调用、成员访问、向量、数组 |
| 引擎边界 | 属性读写、调用引擎方法、Callable、信号 |
| 分配 | 创建对象、闭包、协程挂起 |

比较基于优化构建，不使用 `dev_build`。后续是否生成原生代码、优先优化哪些路径，都由这组数据决定。

纯计算组对代码布局高度敏感：在 AMD Zen 5 上，仅改动解释器之前无关函数的大小，`int_loop` 就慢了 24%。这一组数字只作记录，回归不阻塞提交。引擎边界组与分配组的时间主要花在引擎调用上，受布局影响的波动在几个百分点以内。

`benchmarks/` 中有 14 对运行时用例和一个 32 脚本项目的启动与编译基准，采样方式如下：

- **运行时用例**：预热一次后交替语言顺序采样五次，逐次核对结果一致。进程固定在单个逻辑核心上运行，避免大小核混排（如 Zen 5 加 Zen 5c）把计时拉成相差一成以上的两档。
- **启动与编译基准**：涉及多线程，不绑核。预热一轮后交替采样三轮，每轮用刚导入的新副本计量首次、重复和改单个脚本后的耗时，逐次检查结果。总耗时含编辑器准备（本语言为 `--petrichor-build`，GDScript 为等待编辑器扫描）与游戏进程。同一状态两轮间可差约 300 ms（约一成），两种语言相差几个百分点时分不出快慢。

## 5. 推进顺序

1. **引擎接入**：不含语言实现，让 `.pet` 脚本能挂到节点上，在编辑器中和导出后都能运行。已完成。
2. **探针**：在运行的引擎上实测验证规范中仅由源码推出的几处行为。已完成。
3. **最小编译链**：语言子集挂进场景运行，GDScript 能调用它，支持断点与函数体热重载。已完成。
4. **第一个里程碑**：第二次纸面迁移中的 FPS 代码真正运行。已完成。
5. **偿还技术债**：处理第一版实现留下的规范偏差、重复规则和不实的测试与文档。已完成。
6. **第二个里程碑**：第二次纸面迁移中 Ring 的 breakout 以迁移后的脚本运行。已完成。
7. **补齐第一版的语言**：第 4、6 步只覆盖了两个项目用到的写法，这一步实现规范第一版其余特性并同步写成测试。
   - 每个特性均满足 §2.1 的约定，第 8 步的工具建在其上。
   - 改动热路径的特性各跑一次基准（§4），代价记入提交说明但暂不优化。写进规范的运行时检查是长期约束，定下前须摸清代价。
   - 第 9 步只等待改动热路径的特性，其余部分（如 match 数组模式和剩余参数）放到第 9 步及第 8 步前一段之后。

   验收：[实现覆盖调查](https://github.com/YYF233333/petrichor-corpus/blob/main/surveys/implementation-coverage.md)表中的写法都得到支持，重跑调查。已完成。
8. **工具链**：实现规范 §13.2 的第一版工具，包括带场景部分的重命名（§13.3）。
   - **两段节奏**：前一段排在第 7 步其余部分之前，覆盖分析服务、诊断、格式化与除查找引用外的导航。后一段在 0.1 之后随迁移工具一起做（第 11 步），避免依赖未落地规则和 IR 分析导致返工。例如查找引用和重命名要涵盖字面量名字（规范 §10.4），lint 用的 IR 活跃性分析随第一个 lint 一起实现。大项目和多人协作中的重命名按 §6.4。
   - **先内置编辑器、后 LSP**：Godot 只给语言留了诊断、补全、跳转和自动缩进回调，其余由编辑器插件提供（`core/object/script_language_extension.h:304, 391, 441, 475`）。因为场景只能经引擎读取，分析服务和 LSP 都在 Godot 进程中。

   按依赖分为：
   - 常驻的分析服务，构建和无界面命令共用缓存（验收：Ring 构建不再重复编译基类和列举场景，只改函数体时只重检一个文件）；
   - 诊断和 lint：场景错误标在节点上，提供 lint、`@warning_ignore` 及其失效提示，无界面命令给出同样诊断；
   - 格式化：在全部测试脚本及 FPS、Ring 上保持语法树不变，第二次格式化不再改动，注释全部保留；
   - 导航：悬停类型、跳转到定义、含场景的查找引用与补全，引用表补上场景导出属性的键；
   - 带场景部分的重命名；
   - 快速修复；
   - LSP：编辑器进程中的服务器，把同一组查询映射为 LSP 请求，也可由无界面编辑器启动。

   验收：§13.2 所列的每项工具。
9. **性能**：拿 §4 四组基准与 GDScript 比较，再按数据优化解释器和引擎边界（原生代码留到 1.0 之后的第 14 步）。这一步排在第 7 步改动热路径的特性之后，因为先满足约束才谈得上快。IR 活跃性分析留到原生代码寄存器分配或 lint 用时再做。引用按语句和块释放（规范 §6.8），复用槽位和常见复制消除都不需要它。验收：明显快于 GDScript（规范 §12.2）。已完成。
10. **0.1，首次公开发布**：2026-11-15 发布，用于在 1.0 之前收集语义反馈，不等第 8 步后一段，也不等语言新增。

## 6. 以后必须能做到的事

下面六件事要到第 8 步或更晚才能全部落地，但任何一件若做不到，真实项目要么无法选用本语言，要么用到中途无路可走。本节说明现有设计如何为它们留出通路，以及在此之前不能打破的约束。

### 6.1 Mod

用本语言写的游戏需要在运行时加载 Mod 包：Mod 类可继承、调用和实现游戏的类并使用游戏场景，而作者拿不到游戏源码。

- **加载**：Mod 包由 `ProjectSettings.load_resource_pack` 载入，包内 `.remap` 同样生效（`core/config/project_settings.cpp:581-585`，`core/io/resource_loader.cpp:1491-1519`），脚本与游戏本身经同一路径到达运行时。挂载不刷新已缓存资源，包须在目标脚本和场景首次加载前挂载（`core/io/resource_loader.cpp:622, 801`）。字节码按路径指称类，不必登记全局类名（`src/bytecode/module.h` 的 `ClassRef`）。
- **链接**：脚本之间按路径和名字引用，运行时做四项检查：
  - 加载时检查基类的成员布局和签名（`src/runtime/class_image.cpp` 的 `ClassImage::load_class`）；
  - 调用时检查方法的签名（`src/runtime/vm.cpp` 的 `has_signature`）；
  - 读写时检查其他脚本的成员和静态变量的类型（`src/runtime/values.h` 的 `TypeImage::type_id`）；
  - 使用处检查场景中节点的类（`vm.cpp` 的 `fits_class`）。

  版本不符或替换了场景的 Mod 只会得到加载错误或程序错误，不会读错内存，与 C# 和 Java 的带检查动态链接一致。
- **格式**：支持 Mod 的那一版为格式定下版本号，此后可读取兼容版本编译的 Mod；此前 Mod 须与游戏同构建编译（§2.4）。普通项目升级后重新构建，用不到跨版本字节码，格式由此不随语言在 0.9 冻结，原生代码和泛型仍可调整它。
- **声明**：编译器对其他脚本只检查声明（`src/compiler/project_api.h` 的 `ProjectApi::script_source`、`src/compiler/script_classes.h` 的 `ScriptClasses::declarations`）。游戏随 Mod 工具附上去掉函数体的脚本（按节点 token 范围生成，§2.1），Mod 就能获得完整检查和补全。游戏包中的场景经 SceneState 直接可读。
- **信任**：verifier 拒绝损坏和过时的文件，但信任表中的引擎签名，伪造文件可使游戏崩溃（`module.h` 的 `EngineCall`）。GDScript 写的 Mod 本就能做任何事，加载 Mod 本身是信任决定；要防不受信任的字节码，有两条扩展路径（规范 §14.2）：
  - 加载时对照引擎核对签名；
  - 改用含编译器的运行时库，由游戏编译 Mod 源码。
- **在此之前要守住**：
  - 脚本间引用保持按路径和名字，在加载或调用时检查。跨脚本优化（BACKLOG 的性能部分）在加载或首次调用时完成，不把别的脚本的下标或布局不经检查编进字节码。
  - 泛型（规范 §3.10）定义留在自己模块中，如加载时按类型实参特化、不在使用处单态化。别的模块无需泛型源码即可实例化，寄存器仍存原生值（§1）：
    - 导出库不含编译器，特化器放在 `src/bytecode/` 中，只改写操作数和表，不选择也不插入指令；
    - 作用于值的操作由按类型操作数行事的指令完成，不在编译时按类型选指令（现有例外是 `SOME` 与写入容器前的 `BOX`，随泛型一起改）；
    - 新代码不另算字节偏移：帧偏移只由 emit 算，字段按寄存器和字段下标访问，现有字段视图、成员与静态变量布局随泛型改为可重算；
    - 字节码中新增类型信息按类型表下标引用，不写成字符串（现有字符串有 `TypeDesc::task_result`、函数类型名、`base_signature` 和 `interface_signatures`）；
    - 按类型缓存或去重时以完整类型为键，不以声明名为键。
  - 编译器只经接口读取其他脚本，构建已保证这一点（`SConstruct` 的 `compiler_library`）。

### 6.2 struct 与带载荷 enum 的导出

struct 和带载荷 enum 的成员支持 `@export`，可直接存进场景和 `.tres`（规范 §4.3）。第一版（第 7 步）完成存储、默认值和静态检查，按类型编辑和 `Node` 字段留到后续版本。

- **存储**：两者在引擎边界编码为按字段名的 Dictionary，带载荷 enum 以 `"$variant"` 记分支名（规范 §10.1）。场景保存时经 `get` 读出、实例化时经 `set` 交由脚本实例入口检查解码，无需改动引擎（`scene/resources/packed_scene.cpp:494, 861-883`，`core/object/object.cpp:239-246`）。
  - 值为 `None` 的 `T?` 字段是否写键由声明定出（`keeps_none_key()`，`src/compiler/ast.h`）。编译器把它记在字节码类型表的字段上（`FieldDesc::keeps_none_key`），运行时编码与检查器默认值由此出自同一判定。类型键不含这一标记，只改默认值的热重载不改变类型。
  - 调试器同样显示编码后的值，所以也看不到省略了键的字段。
- **编辑**：第一版复用检查器通用字典编辑器，能编辑但不按类型（`editor/inspector/editor_properties.cpp:4280-4287`）。按类型的面板随第 8 步后一段由本扩展注册的 EditorInspectorPlugin 提供，属性提示字符串写明类型（`editor/inspector/editor_inspector.h:356, 360`，`editor/plugins/editor_plugin.cpp:674`）。因为通用字典编辑器总把提示字符串读作键值类型（`editor/inspector/editor_properties_array_dict.cpp:1203-1226`），字符串写作 `0:类型名`，以 `0` 使键保持无类型。
- **默认值**：成员初始值由常量、构造和字段常量默认值组成时，编译器生成算出其编码的代码（反射函数，§2.2），作为检查器的默认值和还原值。由代码算出的初始值没有默认值，与 GDScript 相同（`modules/gdscript/gdscript_analyzer.cpp:5652-5661`）。热重载不另比较初始值：成员从字段常量默认值开始时，初始化函数也含这些默认值。
- **值转换与静态检查**：场景和 `.tres` 存下的导出值由资源检查（§6.4）按导出类型核对（规范 §4.3），值不符报在节点上，资源上的报在文件上。编译期接受的值与运行时 `set` 写入一致，反映引擎先转换容器再交入口检查的规则：
  - 成员持有容器时，引擎先把存下的 Array 和 Dictionary 转为目标类型（`scene/resources/packed_scene.cpp:450-482`，`core/variant/array.cpp:217-280`）。转换后元素按引擎类型检查（对象元素可为 null，`int` 元素可来自整数值 float），有损或改义转换（如 `1.5` 或 `bool` 转 `int`）仍报编译错误。
  - 内层容器与顶层值不经转换（`int` 导出不接受 `1.0`，同入口检查）；值为 `None` 的 `T?` 也不经转换，无初始化式或初始化式为 `None` 时算作 `None`。
  - 节点存为路径并在场景建好后解析（`scene/resources/packed_scene.cpp:376-395, 597-640`）。索引按打包数据标记解析场景内路径并校验节点类，路径超出场景时不检查（`scene/resources/packed_scene.cpp:1002, 1811-1831`）。
  - 非空对象导出存 null 时按缺值处理（规范 §7.5）：必须赋值的由缺值检查报告，其余错误不妨碍运行。
  - 【已知限制】索引读到的资源文件容器已由引擎转为成员类型；转换失败时引擎报错并留下空容器，检查看不到该错误，也看不到有损转换。
- **索引读取与层级覆盖**：场景索引只读两类节点自存的属性值（`src/compiler/project_api.h` 的 `SceneNode::properties`）。它们是挂本语言脚本的节点，以及所实例化场景中被它修改的节点（供必须赋值导出和存值检查）。
  - 资源文件和场景中的资源由引擎加载再读属性（`SceneResource::properties`）。引擎经 `set` 设下文件存值，占位实例保留与默认值不同的值，与保存时一致（`scene/resources/resource_format_text.cpp:640-716, 1955-1994`）。
  - 资源文件的外部资源不含本语言脚本或场景时不加载。资源脚本在编辑器编译失败时占位实例列不出属性，索引不读其值（`SceneResource::unread`）。节点或资源的脚本无法读取或声明时同样不检查，由脚本自身检查报告原因。
  - 实例化时，被实例化或继承的场景先设值，外层场景再设自己的值，每个值都过入口检查（`scene/resources/packed_scene.cpp:263-266, 494`）。每个值都在存它的场景上检查；继承场景整体替换基场景的值，不与它合并。
- **`Node` 字段**：引擎只把顶层属性和带类型容器中的节点引用存为路径，等节点建好再解析（`scene/resources/packed_scene.cpp:390-394, 597-630`）。嵌套在编码中的节点引用会丢失，第一版报编译错误；后续有两条路：
  - 运行时存为相对路径，在节点入树或首次读取时解析；
  - 推动上游让 PackedScene 解析嵌套在导出值中的节点引用。
- **在此之前要守住**：支持导出后，§10.1 的编码即成为存储格式。它按字段名和分支名编码，增字段、调顺序均不破坏旧数据；带载荷 enum 按该编码实现，0.1 发布后不再以丢失旧数据的方式修改它。

### 6.3 全平台的预编译库

用户无需安装 C++ 工具链就能导出到 Windows、Linux、macOS、Android、iOS 和 Web，且后续 Godot 4.x 版本继续可用。

- **分发**：`.gdextension` 按功能标签为每个平台和架构列出库，导出插件自动选用相符的一份（`core/extension/gdextension_library_loader.cpp:82-96`，`editor/export/gdextension_export_plugin.h:107-117`）。iOS 静态库由导出插件生成注册代码（`:119-137`，`editor/export/editor_export_platform_apple_embedded.cpp:1233-1325`），Android 放进 `lib/<abi>/`（`platform/android/export/export_plugin.cpp:800-822`），Web 用带扩展支持的导出模板（`platform/web/export/export_plugin.cpp:362-374`，规范 §1.3）。发布即按平台各自编库，godot-cpp 已附带这些平台的构建脚本。
- **代码与可移植性**：编译器和字节码是普通 C++17，运行时和 adapter 只用 godot-cpp，导出库不含按平台的条件编译（`SConstruct` 的 `configure_godot_cpp`）。编辑器部分与 `pet` 仅面向桌面构建，其中路径、进程和套接字按平台分支。解释器不生成机器码，能在禁止运行时生成代码的 iOS 和主机上运行（规范 §12.2）。
- **主机退路**：主机能否加载扩展取决于移植方；退路是编为引擎模块合进各平台导出模板（Godot 的 `SConstruct:1237`、`modules/SCsub:32-42`）。C++17、SCons 与和引擎同名的类型正是为保留这条路而选（§1、§2.2）。
- **引擎版本演进**：更新的引擎加载同一个构建（§1），行为变动靠[引擎事实](engine-facts.md)随升级逐条复核。API 变动在运行时按名和哈希查方法时暴露，不会静默调错（`src/bytecode/module.h` 的 `EngineCall`）。
- **旧引擎版本**：从 4.4 到当前版本，每个小版本支持其最新补丁版，方便不轻易中途升引擎的大型商业项目采用。每个小版本以对应 `api_version` 编一份 godot-cpp 与库，从该版本 `extension_api` 生成内置类型与工具函数表（§2.1），并在引擎事实中注明各条成立的版本及 GDScript 版本差异。
- **在此之前要守住**：
  - 导出库中平台相关代码只经 godot-cpp，正确性不依赖生成机器码，且导出库不含编译器（`SConstruct` 的 `target == "editor"` 分支）；
  - 用到 4.4 之后才有的引擎接口或行为时，在引擎事实中写明引入版本及旧版本做法；
  - 功能依赖上游修改时，旧版本须保留不依赖它的路径，至少给出明确报错。

### 6.4 大项目和多人协作中的重命名

在上千个脚本、数百个场景且多人并行分支修改的项目中，重命名成员、方法或节点既要响应快，也不能迫使人一次改写别人正在编辑的场景。

#### 场景文本定位与安全改写

场景按名字存导出属性值和信号连接方法，名字不存在时存值会被悄悄丢弃（`scene/resources/packed_scene.cpp:494, 666, 682`），重命名必须同步改写这些键（规范 §13.3）。改写是 token 区间上的文本替换，只动用到名字的行，只在别人改了同一行时冲突。

- **文本定位器（`src/compiler/scene_text.h`）**：只读文本、不依赖引擎，与编译器在一起并由编译器测试检验。
  - 它按引擎读法分词，认得字符串、`&"`、`@"`、`;` 注释、括号、逗号和冒号（`core/variant/variant_parser.cpp:160-505, 1750-1960`，`ed1daf0`）。引擎写名字和节点路径时只转义引号、撇号和反斜杠（`core/string/ustring.cpp:4473-4494, 5052-5063`），字符串反斜杠后的字符照原样取。
  - 它不按行匹配（多行值和字符串可能让行首出现 `[` 或 `key =`），而是按节头识别 `[node]`（name/parent）、`[sub_resource]`（id）、`[resource]`、`[gd_resource]` 及 `[connection]` 四个字段。
  - 在节内按引用表结构路径找到键、所存值字符串、NodePath 第一个子名或方法轨道键方法名。每处须恰好找到一次且解码等于旧名，否则放弃，以此捕获与引擎读法的偏差。
  - 新名字按引擎写法写入：键含非 ASCII 字符时加引号，字符串中名字无须转义（`core/string/ustring.cpp:4474-4496, 5053-5064`）。节点存 Node 类型导出时，一并改写节头 `node_paths` 列出的键，因为引擎只把列出的键读成节点路径（`scene/resources/resource_format_text.cpp:225-232, 305`）。
  - 改全局类名时一并改写 `.tres` 节头的 `script_class`（供 `preload` 定型和编辑器筛选，`scene/resources/resource_format_text.cpp:1806`）。二进制 `.res` 中的 `script_class` 不改写也不拒绝，它只用于筛选，引擎重存时更新。
- **冲突拒绝与不可改写载体**：
  - **旧键冲突**：挂本类或子类的节点或资源已存有新名字的键时拒绝（如先前删掉导出留下的键），避免旧值悄悄生效。节点键取自场景索引，资源上的这种键加载时被丢掉，改在文本文件中查（`src/adapter/pet_placeholder.cpp:113-116`）。
  - **跨场景共用冲突**：一处待改写存储（如共用动画或继承场景换根后的基场景连接）若被别场景用于另一声明，就拒绝并指出该场景。否则对方轨道或连接会悄悄失效，另一边是 `.gd` 或 `.cs` 时无检查报错。
  - **二进制与导入资源**：二进制 `.scn`、`.res`、`.anim` 和 `.repl` 不能按 token 区间改写，命中引用时拒绝并提示先另存为文本格式（漏改导出键会被静默丢弃）。导入资源（如 `.glb` 中的动画）同样拒绝，因其名字由导入重新生成。
  - **内置 PackedScene**：存在节点或资源属性中的内置 PackedScene 由场景索引按 `文件路径::id` 当作场景读，覆盖检查、查找引用和导出校验。其节点存名落在与节点名共用的 `_bundled` `names` 表中无法改写。引用落在其中时拒绝重命名，指出文件、节点和属性，提示先用属性“另存为…”存成单独文件（`editor/inspector/editor_resource_picker.cpp:365-368`）。它所用的子资源是文件独立节，照常改写。
- **不改写场景的渐进迁移退路**：设置属性和按名调用连接方法均先经脚本实例（`core/object/object.cpp:239-246, 800-816`），运行时可接受成员声明中写明的旧名（语言规则）。场景下次保存时写成新名，在有人本来就要编辑时迁移；引用表列出仍用旧名的场景（§2.1），都迁移后删去旧名。本语言自有占位实例（§2.4）同样可在这里接受旧名（`core/object/script_language.cpp:680-707`）。

#### 惰性检查与浅层反向索引

大项目的响应速度靠惰性：只检查被问到的单元，单元输入以自身点名为准。反向问题（谁用了我）全部走浅层索引，避免触发全项目类型检查。

- **脚本检查与资源检查**：
  - **脚本检查**确定脚本自身类型与诊断，输入为源码、所用脚本声明和索引回答。它只问一种反向问题：挂载它的场景及逐层实例化这些场景的场景（供 `$X` 定型，规范 §7.1），由 `ScriptClasses::scenes_with_script` 按场景列表与脚本基类路径算出。
  - **资源检查**核验场景和 `.tres` 本身，涵盖节点脚本、存值、信号连接、轨道、必须赋值导出、`@parent` 与 `@owner`。输入是该文件、逐层实例化场景及各处脚本声明，错误标在文件或节点上。编辑器打开或保存资源时检查它，无界面构建和导出检查全部资源，脚本编辑器也列出资源报在脚本上的错误。资源错误不使脚本编译失败（类型和补全照常可用），但阻止构建和导出（规范 §7.5 不阻止运行者除外）。
- **浅层索引与根场景判定**：索引汇总不经类型检查就能得到的事实，包括场景与资源结构及存值（场景索引）、各脚本基类路径，以及字面量 `preload` 和 `load`。
  - 场景是否当作根使用（`ScriptClasses::root_use`）含三类来源：主场景、`.pet` 和 `.gd` 中字面量路径 `preload`/`load` 的场景、以及场景和资源文件中节点和资源存的场景。GDScript 的 `get_dependencies` 不列 `preload`，改按 token 查找（`modules/gdscript/gdscript_resource_format.cpp:88`，`gdscript_parser.h:1647-1650`）。
  - 一次分析只读一遍所有脚本和场景即可得出全部回答。编辑器按文件缓存这些调用并在磁盘变化后按修改时间和大小判定（§2.1，`SceneIndex::literal_loads`），后续只重读改过的脚本。
- **跨文件摘要与节点路径归属**：用到其他文件函数体事实时，由那个文件检查时算出摘要放进声明，声明哈希包含决定摘要的输入以便变更时重做。
  - `_init` 在每条路径上赋值的成员记在 `FuncDecl::assigned` 上（子类沿用最近的 `_init`，同 `new()`）。为使用方查声明时一并检查 `_init` 函数体以算摘要，但不保留其中错误；编辑器加载脚本时不检查它。
  - 场景检查从脚本语法树找出字面量节点路径并逐节点走查（`for_each_node_path`）。若另有挂载场景存在该节点，缺失场景在自身检查中报错；若都没有，`$X` 无从定型，由脚本检查报而不重复。场景检查按全文比对这些脚本以响应路径改动，只用其声明的脚本不重检。
- **在此之前要守住**：检查只依赖经接口传入的输入，不读接口之外的状态，也不读其他文件的检查结果；引用表保持按文件组织（§2.1）。

### 6.5 项目服务

日常开发常有三方同时在场：Godot 开着，人在第三方编辑器中读写代码，代理直接改磁盘。各方经同一个项目服务看待项目，磁盘是它们共同的依据。

#### 服务定位与双视图模型

服务专管代码和语义，场景仍由人在 Godot 中编辑、由代理直接写 `.tscn`。不拆分 Godot 是因为被编辑场景即编辑器进程中的节点，视口、检查器和编辑器插件都直接使用它（`editor/editor_data.h:113-114`，`editor/editor_node.cpp:4610`）。Rojo、Rider 的 Unity 支持与 Bevy 的编辑器设计同样把场景留在编辑器进程中。

- **单项目单服务**：有界面编辑器开着时，服务就是它的服务器（§2.4，上游不支持同项目开两个编辑器，godot#125578）。没有它时，命令行按需启动无界面服务，有客户端时保留，闲置后退出；无界面服务给后开编辑器让位，客户端随后重连。`.godot/petrichor/lsp.json` 同时带上构建标识。
  - 【待定】Windows 上的让位：编辑器模式进程占着库的 `~` 副本，后开编辑器加载不了扩展（§2.4）。不带 `-e` 的进程直接加载原库不做副本（`core/extension/gdextension_library_loader.cpp:196`），先探明分析在其中缺什么；在那之前，打开编辑器前先停掉无界面服务。
- **双视图与多会话**：项目分人的视图与磁盘视图，服务器同时服务分属两视图的多个会话，请求仍在编辑器主线程逐个执行。
  - 人的视图即工作区（§2.1），把 Godot 未保存状态与各第三方编辑器打开的文本叠在磁盘上；磁盘视图只读文件，供代理、命令行、构建和游戏使用。同一人的 Godot 与编辑器互通未保存改动，而他打了一半的代码不影响代理检查。
  - gopls 按会话存放未保存文本、只共享磁盘结果（`gopls/internal/cache/session.go`）；这里单机只有一人，编辑器合用一个视图。同一文件在两编辑器各有未保存改动时，各自诊断按各自文本算，两份文本不同步。

#### 磁盘变化感知

服务自行记录项目中每个文件的修改时间和大小（`src/adapter/editor/project_files.h`），按编辑器文件系统相同的规则跳过隐藏项、以点开头的目录、嵌套项目和带 `.gdignore` 的目录（`editor/file_system/editor_file_system.cpp:1174-1185, 3488-3508`）。走查不按扩展名筛选，因为列出目录的开销不因筛选减少，而任何文件增删都需要编辑器扫描。

- **主线程复核与后台轮询**：回答磁盘视图请求前，主线程直接走查比较并重读变化文件。后台线程约每秒做一次同样比较以让人的视图跟上，发现不同只打标记。主线程在下一帧重新走查并读回，确保已发现的变化不漏在磁盘视图回答之外。察觉后的读回步骤见 §2.4，客户端文件事件只让比较立即触发。
- **实测开销与实现取舍**：生成的大项目加上 2500 个图片、模型和声音，连同导入文件共 7424 个文件、78 个目录。在官方 4.7.2 编辑器中走查一遍约 10 毫秒，磁盘视图请求多 10 到 15 毫秒。不采用操作系统文件监视，它只缩短延迟，而 gopls 为无界面模式引入它后在 Windows 上修了多处问题（golang/go#74292）。

#### 命令行工具 `pet` 与 LSP 转接

命令行客户端 `pet` 不依赖 Godot，源码在 `src/pet/`，由 `scons` 编辑器构建产出并随插件分发。它须与插件同属一次构建，存放在 `addons/petrichor/bin/`，从 `bin/` 向上三层即项目根（与当前目录无关）。因片段管理器 knqyf263/pet 同名，文档一律写项目内路径，由 `addons/petrichor/pet`（sh）与 `pet.cmd`（Windows）按系统选出二进制。有编辑器开着时，命令直接复用其服务，不再另起进程。

- **命令与统一输出**：提供 `check`（磁盘视图检查，不写字节码）、`build`（检查并写字节码）、`format [--check]`（格式化或仅列未格式化文件）、`migrate [--dry-run] [<路径>...]`（迁移 GDScript，§6.6）以及 `lsp`（stdio 转接）。
  - 前三个命令在经服务与无界面模式下共用输出与退出码逻辑：每条错误、警告或提示占一行（如 `player.pet:12:5: error: 消息`，路径从项目根起用 `/` 分隔，列按码点从 1 计）。经服务时每个冲突先占一行 `warning:`（不改退出码），末行打印计数（如 `petrichor check: 3 script(s), 2 scene(s), 0 resource file(s), 1 with errors`）。
  - 退出码：0 表示无错误；1 表示有错误（`format --check` 时也表示有未格式化脚本）；2 表示没能运行（如构建标识不符、找不到 Godot 或连接被拒绝）。
- **经服务执行与构建标识**：`pet` 读 `lsp.json`（进程不在或连不上则视作无服务），以磁盘视图 `initialize` 后发 `petrichor/run`（参数 `{command, args}`）。服务先比对文件再返回 `{output, exitCode}`。命令与无界面退路一样等编辑器的文件扫描结束才运行，比对引起的扫描也等。扫描期间编辑器推迟登记全局类，其间写下的脚本会按旧的全局类编译（`editor/file_system/editor_file_system.cpp:1074, 2552-2554`，`ed1daf0`）。请求留到之后的帧再处理，不阻塞扫描收尾所在的主线程。经服务格式化按重构方式写盘（先记文件、标签页再跟上，§2.3），但凡 Godot 或人的视图会话对某文件有未保存改动，就不写该文件并列为错误、退出码为 1。
  - 构建标识为构建时 HEAD 提交，由 SCons 写入 `pet` 和库（按源码哈希会导致每次改动都重编两者），库写入 `lsp.json`。标识不符时 `pet` 说明原因并以 2 退出，不擅自重启人的编辑器。
- **无服务退路**：无服务时 `pet` 运行 `godot --headless -e --path <项目> -- --petrichor-<命令>`，通过 `--petrichor-output=<文件>` 拿取首行为退出码的完整输出，与经服务逐字节一致。
  - 输出文件先写临时名再改名，即使编辑器退出时崩溃（godot#111048）结果仍完整可用。引擎横幅、进度和错误写进 `.godot/petrichor/pet.log`（每次重写）；无输出文件时 `pet` 打印日志末 20 行、写明日志路径并以 2 退出。
  - 项目缺少 `.godot/` 时先跑 `--headless --import`（忽略其退出码，godot#111048，输出同样进日志）。编辑器路径优先取 `--godot <路径>`，否则读有界面编辑器留下的 `.godot/petrichor/editor_path`（编辑器退出后保留，`lsp.json` 则删除）。无服务且没有可用记录时须传入 `--godot`，例如全新的 CI 工作区。
  - 子进程在 Windows 上放进随 `pet` 结束的作业，其他系统随终止信号停掉。【已知限制】无界面服务暂不常驻在命令之间，大项目每次命令都要重开项目，耗时 80 到 150 秒。
- **`pet lsp` 转接**：在 stdio 与服务 socket 间双向透明转发字节，不改写消息，客户端照常在 `initialize` 中选视图。无服务时启动 `godot --headless -e --path <项目> -- --petrichor-lsp` 并等 `lsp.json` 出现，进程输出写进 `.godot/petrichor/lsp.log` 避免不读 stderr 的客户端撑满管道卡死，stdin 关闭时按进程号停掉该进程。

#### 跨端冲突检测与取舍

服务不持有未保存文本：跨文件重构直接把改动脚本写盘（先保存受影响的未保存改动，撤销同样写盘），只改一个已打开脚本时仍走其标签页编辑。VS Code 默认在多文件重构后保存文件（§2.4），Godot 移动文件时也直接改写依赖文件（`editor/docks/filesystem_dock.cpp:1676-1705`）。

- **冲突判定与上报**：服务读回磁盘改动（§2.4）或察觉文件删除时，若 Godot 对该文件有未保存改动即记为冲突。
  - Godot 未保存改动分三类：未保存脚本标签页、`get_unsaved_scenes()` 中的已打开场景，以及已加载且 `is_object_edited()` 为真的外部资源（脚本和场景除外，随场景一并保存，`editor/script/script_editor_plugin.cpp:2408-2418`，`editor/editor_interface.cpp:719-722, 738-748`，`editor/editor_node.cpp:2374-2408`）。【已知限制】只看文件主资源，只改子资源时看不到，编辑器却按文件保存（`editor/editor_node.cpp:2379-2388`）。
  - 冲突一直持续到 Godot 保存、关闭或重载该文件，或磁盘内容回到编辑器上次所见。察觉时立即提示且每个冲突只提示一次：Godot 弹出提示框（`editor/gui/editor_toaster.cpp:563`），每个会话（含代理所在的磁盘视图）收到 Warning 级 `window/showMessage`，均写明文件。
  - 两视图客户端都可发 `petrichor/unsavedFiles` 查询 Godot 未保存文件列表（URI 及是否冲突）；因没有列出已加载资源的绑定，外部资源只在冲突时列出。
- **用户取舍与引擎边界**：服务不自动合并也不替人决策，取舍留给 Godot 的原生对话框。
  - 重获焦点时 Godot 按修改时间检出冲突并弹出三按钮对话框：从磁盘重载、忽略外部改动（保存 Godot 版本）或取消（两边留着，`editor/script/script_editor_plugin.cpp:803-850, 4118-4142`，`editor/editor_node.cpp:1550-1591, 9354-9382`）。读回不动未保存标签页、场景及其修改时间，对话框照常弹出。
  - 【已知限制】保存场景若顺带保存了编辑过的脚本，编辑器会重记每个脚本标签页的修改时间（`editor/editor_node.cpp:2411-2413`，`editor/script/script_editor_plugin.cpp:2504-2510`）。此后冲突标签页不再弹窗，下次保存会写掉磁盘改动；服务仍列出该冲突，重构也继续拒绝。
  - 对编辑过的外部资源，引擎重获焦点时不询问而是直接重读丢掉改动（`editor/file_system/editor_file_system.cpp:1018-1025`，`editor/editor_node.cpp:1291-1323`）。服务只是更早读回并提示磁盘替换了未保存改动，资源仍标为编辑过直到 Godot 保存它。
  - 文件被删时引擎不为场景询问（`editor/editor_node.cpp:1565-1567`），服务提示在 Godot 按 Ctrl+S 会把它写回。无未保存改动的已打开场景文件变了就直接重载并清空历史（`editor/editor_node.cpp:7143-7151`）。服务发起的保存遇冲突直接拒绝并列文件，重构须先保存项有冲突时什么都不改（§2.3）。
- **在此之前要守住**：分析可按任一视图读项目（`Analysis::Pass`），检查不读视图外状态。新命令做成服务请求，无界面参数只作无服务退路并共用代码；编辑器不再增加自有未保存文本。

### 6.6 迁移工具

迁移工具把 GDScript 文件转为本语言文件，也支持反向转回（规范 §13.4）。刚迁移完要退回时用版本控制即可。反向转换留住的是迁移后用本语言写的代码，供团队试用后退出或本项目停止维护时使用。

#### 职责分工与五段管线

类型是否正确全由编译器判定，工具写下的每个类型都会经过检查器核验。工具自己只担保两件事：不改变求值结果，且每处改写都有反向规则。推断因此可以取证不全：推错的类型是一个编译错误，不会变成悄悄的错。

- **入口与退出语义**：迁移作为项目服务请求经 `pet migrate [--reverse] [--dry-run] [--allow-dirty] [<路径>...]` 触发，`--reverse` 为反向转换，读磁盘视图（§6.5），路径从项目根算起（不给路径则迁移整个项目）。因拒绝或失败什么都没写时退出码为 1，否则为 0；留下的编译错误只计入报告。预演只在所给路径下没有要转换的文件时为 1。迁移不是编辑器撤销历史中的一步，退回靠版本控制。
- **版本控制前提**：正反两向写入前，检查本次要写的文件，即脚本、改了路径的场景和资源、`project.godot` 与 `.uid`。
  - 这些文件有未提交的改动（含已暂存）、未被 git 跟踪、项目不在 git 仓库中或找不到 git 时，拒绝运行，退出码为 1，列出文件和原因；
  - `--allow-dirty` 跳过检查。预演照样检查并以同样的行列出，但退出码仍为 0，干净的预演由此预示写入不会被拒；
  - 只查要写的文件，因为其余未提交的改动不妨碍还原。命令不交互，代理和 CI 也会调用，只给提示时文件已经写下。
- **五段正向流程**（前四段只在内存中计算，不写入的预演走同一条路径）：
  1. 定出要迁移的集合；
  2. 推断类型，写进文本；
  3. 循环应用保持含义的修复，直到不再变化；
  4. 再检查一遍，结果就是报告；
  5. 作为一次重构写入（§2.3）。
- **内存覆盖视图与预处理**：内存项目叠在磁盘视图之上（`compiler::Migrated`）：集合文件在新路径且文本在内存，场景、全局类、autoload、依赖和其他脚本中的路径一并换新。底层场景索引把集合中的 GDScript 当作本语言文件读，场景和资源由此给出导出值。检查用单独的分析，结果不进入编辑器缓存。
  - 检查前，单引号和双引号中的跨行字符串改写为本语言只接受的三引号（规范 §2.2）。GDScript 两种写法走同一段代码且原文无未转义同种引号，读出值相同（`modules/gdscript/gdscript_tokenizer.cpp:873-878, 1064-1098`，`ed1daf0`）；反向转换保留三引号。
  - 给 String 的字符赋值（规范 §5.1）不改写，留作写明改法的编译错误。GDScript 只取所赋首字符且越界时在调试构建停止函数（`core/variant/variant_setget.cpp:785-809`，`modules/gdscript/gdscript_vm.cpp:1084-1098`，`ed1daf0`），改用 `erase` 和 `insert` 越界仍照常运行导致结果不同（corpus v1 仅有一处）。

#### 迁移集合与连带边界

迁移集合由请求路径加上必须同批迁移的连带文件构成，即整棵 `extends` 继承树以及对其做类级访问的 GDScript 文件（规范 §11.2、§11.3）。基类须先迁移，GDScript 子类又须一起迁移；连带文件不经询问加入，报告列出它们和原因。集合之外的 `.gd` 只读（决定哪些成员要 `pub` 并提供类型证据），只改写指向已改名文件的路径。

- **类级访问判定**：按 token 找出指向另一 GDScript 文件的名字（全局类、autoload，或以字面量 `preload()`、`load()` 初始化的常量和变量），其后的 `.名字` 属以下情形即算类级访问：
  - 静态方法（经 autoload 的除外，那是实例调用）；
  - 写在类型处的 enum、常量或内部类（`->`、`as`、`is`、声明冒号之后及类型化容器方括号中）；
  - 写在同一行所声明常量初始值中的 enum、常量或内部类。
  - autoload 名本身写在类型处也算，因为 GDScript 只为 GDScript 写的 autoload 定型（`modules/gdscript/gdscript_analyzer.cpp:806-829`，`ed1daf0`）。经 autoload 调用方法不算：GDScript 把本语言 autoload 视作 Node，找不到的方法只给警告（`modules/gdscript/gdscript_analyzer.cpp:3750-3752, 4579-4587`）。
- **排除边界**：含 `@tool` 的文件及其继承树不在其中（规范 §13.4）；凡被留在 GDScript 的文件做类级访问的目标文件连同其继承树也不在其中。位于项目设置 `editor/script/templates_search_path` 下的脚本模板不是游戏代码（GDScript 也不解析，`modules/gdscript/gdscript.cpp:767-772`，`ed1daf0`），排除并在报告中列出。
  - `res://addons/` 下的插件是第三方代码，保持 GDScript（规范 §1）。没有路径指到某个插件中的文件时，该插件的文件连同其继承树都留下，报告按插件目录各列一行。Ring 的 `addons/dialogue_manager` 由此不再迁移，留下的错误从 1049 个降到 95 个。

#### 流入类型推断与合并规则

迁移只运行一次，类型随后写进源码，全项目推断在这里不会带来“报错随远处代码漂移”的编译器弊端。推断只看流入槽位的值，不看槽位如何被使用（写下类型后再由编译器检查）。用法很少指向唯一类：引擎 API 中 `position` 由 11 个类声明，同时有 `play` 和 `stop` 的类有 8 个（godot-cpp `8070599` 的 `gdextension/extension_api-4-7.json`），这与渐进类型推断先例一致（Rastogi、Chaudhuri、Hosmer，POPL 2012）。

- **待推断槽位**：推断覆盖以下未写类型或跨文件未知类型的槽位（覆盖方法缺省的参数和返回类型取自被覆盖者，流入值归被覆盖者槽位）：
  - 没写类型的参数（剩余参数和 lambda 参数除外）与信号参数；
  - 没写 `->` 而有 `return` 值的函数返回值；
  - 没写类型、无初始值或初始值为 `null` 的成员、静态变量和局部变量；
  - 没写类型、以 `[]` 或 `{}` 初始化的上述变量，槽位是其元素和键；
  - 没写类型也没写 `:=`、以 `int` 值初始化的上述变量，GDScript 中它是 `Variant`。初始值算一个流入，推断中它始终按 `int` 检查，只在 `float` 按下文规则并入时写下 `float`。tanks-of-freedom-ii 的子类给 `var delay = 0` 赋 `0.3`，由此写成 `var delay: float = 0`（`scenes/board/logic/scripting/outcomes/base_outcome.gd:3`）；未并入的保持 `int`，留下的赋值错误不套 `int(x)`（§2.1）；
  - 没写类型、以值定型的局部变量，某轮检查发现给它赋了类型不合的值（`Variant` 和有修复转换的除外）时，下一轮起作槽位，只试 GDScript 中它的 `Variant`。所赋的值常读它本身，合并会随之摇摆。tanks-of-freedom-ii 的 `scenes/map_editor/story/stories/types/base_edit_action.gd:63-65` 先存文本、再存 `int(...)`，由此写成 `Variant`；`scenes/ui/menu/settings/setting_text.gd:32-34` 随后在它上面调用 `to_int()`，撤回后保持原文；
  - 由场景定型且被其他文件读取的成员（如 `@onready var camera = $Camera`，§2.4；只由本文件读则仍由场景定型，规范 §7.1）；
  - 由资源定型且被其他文件读取的常量（如 `const STYLE := preload("res://style.tres")`）。
- **流入证据**：
  - 调用实参、赋给它的值、`return` 表达式、默认值与复合赋值运算结果；
  - 代码中连接的信号参数类型与 `bind()` 绑定的实参；
  - 空容器的 `append`、`push_back`、`push_front`、`insert`、`fill` 和 `set` 实参，下标写入的值和键，以及赋给它或传给 `append_array`、`merge` 的带类型容器；
  - 场景给出的所连信号签名、导出存值和节点路径类型；
  - 按名调用（接收者无类型、`Variant`、缺该方法的类或其 `T?`，如 `Object` 上的 `collider.damage(5)`）计为项目中每个接受同实参数量同名函数的流入。
- **两段固定点求解**：检查器在迁移模式（`CompileOptions::inflows`）下多轮检查全部本语言脚本与场景，槽位取本轮试用类型且不报错。每轮记下流入集合并按顺序无关规则合并，结果不随文件检查次序变化。
  - 场景检查给出所连信号参数和导出存值，所在文件检查给出场景定型成员类型。一轮中发现被他文件读取的这类成员从下一轮起才作槽位，保证单轮内各文件所见相同。
  - 修复循环随后会修好带自动修复的错误（如补 `pub`），推断中不把对应声明算作出错，其他文件照常读其类型。
  - 求解分两段，每段轮数上限与修复循环相同。先只试有流入的槽位直到稳定，再让其余槽位试 `Variant` 继续求解；即使第一段到上限第二段照常进行，确保每个槽位都有试用类型。
- **合并与写回规则**：
  - `Variant` 流入不参与（GDScript 未写类型的值就是 `Variant`，只有 `Variant` 流入算作无流入）；
  - 单一类型直接选用；有 `null` 流入写成 `T?`（流入 `T?` 算作 `T` 和 `null`）；具公共基类的几个类取最近公共基类，几个场景取其根的最近公共类，有根不明的只得 `PackedScene`；
  - GDScript 隐式给的 `null` 也算流入：无初始值的变量合并出类时算，函数有路径只写 `return` 或走到末尾时其返回值总算。值类型变量不算，GDScript 写了类型的成员本就取类型默认值（`modules/gdscript/gdscript_compiler.cpp:2366-2391`，`ed1daf0`），只有赋值前读取才看得出差别。规范 §6.2 证明有值的成员也不算：`_init` 每条路径都赋值的成员，以及场景或资源存了值的导出。只由祖先在 `_ready` 中赋值的成员照样写成 `T?`；
  - 同时有 `int` 和 `float` 时，须确认每处使用对整数输入结果不变才写 `float`；
  - 合并不出或无流入时试 `Variant`，容器试无类型 `Array` 或 `Dictionary`（还原 GDScript 原意）；空容器元素与键都合并出非 `Variant` 类型才写 `Array[T]` 或 `Dictionary[K, V]`。
  - 类型写在槽位名后、返回类型写在参数表后（`var a := []` 写成 `var a: Array[int] = []`），本文件 enum 和内部类不带类名。
  - 无 `class_name` 的类经文件里的 `preload` 常量指名，它只当类型用，不随文件加载（规范 §2.1）。文件已有或从基类继承该脚本的这种常量就沿用其名字；否则在类头之后按名排序补上 `const 名字 = preload("res://….pet")`，报告列出补上的常量。基类补上的常量子类照样继承，所以只由继承链最上方补上它的文件写出。名字取文件名的 PascalCase（`main_menu.pet` 得 `MainMenu`）。若本文件、其基类或子类的声明、全局类、引擎类或 autoload 已用此名，就依次在前面加上由近及远各级目录名的 PascalCase，直到不重名为止（`outcomes/camera.pet` 得 `OutcomesCamera`）。与所加前缀的名字同名的目录跳过（`ui/online/online.pet` 得 `UiOnline`）。仍写不出名字的类型不写，留作编译错误并在报告写明。
- **写宽了的类型**：GDScript 把父类的值赋给子类的位置时到运行时才检查，本语言在此报编译错误（规范 §3.14）。写了对象类型的参数、返回值或变量，读出的值在某处因此报错时也作槽位求解。流入合并出所写类型的子类时，在所写类型到该子类之间取能消除这些读取错误的最宽类改写；没有这样的类则原文不动，由下文的 `as` 处理。
  - deck_builder_tutorial 中 7 个导出写作 `Texture`，资源存的 PNG 载入为 `CompressedTexture2D`，读出的值赋给 `Texture2D` 属性（`custom_resources/stats.gd:7`、`scenes/enemy/enemy.gd:72`），最宽可用类为 `Texture2D`，检查器仍接受 `AtlasTexture`。`-> Resource` 而只返回 `CharacterStats` 的 `create_instance()` 同理（`custom_resources/character_stats.gd:42-50`）。
  - 改窄的导出在检查器里从此只接受子类。集合外 GDScript 的赋值看不到，与其余推断相同。
  - 检查器按读出处的引用找到所读声明并记下读出处要的类，下一轮起它才作槽位，未试过时与未写类型的槽位一样取 Error。所写类型的 `?` 不变，声明原本会改为 `T?` 时改窄后照样带上。
  - 读出处要的类比流入合并出的类还窄时没有可取的类，原文不动。deck_builder_tutorial 的 `Stats.create_instance()` 由此保持 `-> Resource`：它返回 `Stats`，而 `enemy.gd:30` 要的是 `EnemyStats`（`custom_resources/stats.gd:48`）。
  - 成员与其具名 setter 的参数一并求解：写入属性即流入参数，所以 setter 里把参数赋给成员不算流入。成员改窄时，参数的类型写成同一个。
  - 写作 `PackedScene` 的导出报错后（规范 §7.4），下一轮起同样作槽位。所存场景和代码所赋场景的根合并出最近公共类 `T`，写成 `PackedScene[T]`。没有流入或有根不明的场景流入时写 `PackedScene[Node]`，根不明的赋值随即报错。
  - 写作 `Array[PackedScene]` 的导出不报错，但同样作槽位，所存数组的各个场景和代码放入的场景是元素的流入。元素合并出 `PackedScene[T]` 才改写，否则保持原文。
  - 写作 `PackedScene` 的其他声明，读出的值进入 `PackedScene[T]` 的位置时同样作槽位，合并不出时保持原文。deck_builder_tutorial 的 `event_rooms` 由所存两个场景写成 `Array[PackedScene[EventRoom]]`，再经 `get_random()` 的返回值传给 `Room.event_scene`（`custom_resources/event_room_pool.gd:4, 7`，`custom_resources/room.gd:15`，`scenes/map/map_generator.gd:208`）。
  - 这些场景的根把必须赋值的导出留给 `instantiate()` 时，报错带上改为 `T?` 的修复：场景只设所存的属性，GDScript 写了对象类型的成员起初为 null（`scene/resources/packed_scene.cpp:365-371`，`modules/gdscript/gdscript_compiler.cpp:2369-2393`，`ed1daf0`）。deck_builder_tutorial 的 `EnemyStats.ai` 由此写成 `PackedScene[EnemyActionPicker]`，其根的 `enemy` 和 `target` 改为可空（`custom_resources/enemy_stats.gd:4`，`scenes/enemy/enemy_action_picker.gd:4-5`）。
  - GDScript 写不出嵌套容器的内层类型，所以写作 `Array[Array]` 的参数、返回值和变量不等报错，下一轮起就作槽位。内层 `Array` 的元素只取自流入，合并出类型 `T` 才写成 `Array[Array[T]]`。写下后仍有涉及它的错误时，照常保持原文。
    - 容器不转换（规范 §3.14），值经过的各个声明须一并改写。所以别的这类声明流入的 `Array[Array]` 在它改窄前不算依据，与 `Variant` 相同。遍历它的循环变量写作 `Array` 时同样作槽位，取元素的类型。
    - 读出内层元素处要的类型与 `T` 不同时，同样在元素上取能消除读取错误的最宽类，取不出时保持原文。流入的内层数组恰为 `Array[T]`，容器又不转换，所以只有 `T` 可取：读出处要的是 `T` 或它的基类时写成 `Array[Array[T]]`，要的是 `T` 的子类时保持原文。
    - deck_builder_tutorial 的地图由此写成 `Array[Array[Room]]`，连同生成函数的返回值、局部变量、`load_map()` 的参数、遍历的循环变量和存档的导出（`scenes/map/map_generator.gd:25-66`，`scenes/map/map.gd:14-62`，`custom_resources/save_game.gd:13`）。
    - 改写后读出内层数组和从引擎进入时，都校验它恰为 `Array[T]`（规范 §3.8），GDScript 只校验它是数组。存档逐个写出内层数组连同类型，读回时脚本有效即恢复类型（`core/variant/variant_parser.cpp:1354-1370, 2339-2397`，`ed1daf0`）。

#### 候选校验、失败撤回与数值核对

候选写下后须通过检查：仍在迁移模式下重检（不再试类型），第一轮没有报且修复循环也不修的错误会撤回所涉槽位。撤回的槽位留作编译错误，列出收到的类型和来处，重写重查直到不再撤回。检查器直接记下错误所涉位置和读出元素，不按报错文字判断。

- **错误所涉槽位**：
  - 错误涉及三类槽位：错误落在其写下的类型中、错误范围引用了它，或函数的裸 `return` 涉及返回值。引用覆盖方法缺省参数时，归入被覆盖者槽位。
  - 值的类型不合时，值一侧只涉及给出这个类型的槽位：
    - 名字涉及所指槽位，读成员涉及该成员自身的槽位，调用涉及被调者的返回值，下标读出涉及容器；
    - 所读的对象、调用的接收者、实参和下标都不涉及；
    - 由初始值或迭代值定型的局部或循环变量，按同一规则追溯到该值。
  - 撤回接收者只会把值变成同样不合的 `Variant`，还丢掉流入支持的类型。tanks-of-freedom-ii 把 `pivot_rotation.y` 赋给 `int` 成员时，`camera_pivot` 不受牵连（`scenes/camera.gd:101-102`）。它的 `loader.gd` 由调用定型的局部变量出错时，实参 `campaign_name` 和 `mission_no` 也不受牵连（`scenes/map/loader.gd:33-34`）。
  - 所赋值不合时还涉及目标所引用的槽位。值是 `Variant` 时不涉及目标，留作编译错误由人写转换。实参和 `return` 错误不涉及接收的槽位。
  - 关于接收者本身的错误只涉及给出接收者类型的槽位，与值不合时相同，如调用 `Variant`、缺该方法的类或 `T?` 的方法，以及在它们上读成员。取下标、`in` 查找、迭代、一元运算和条件中的值是 `Variant` 而出错时也是如此，下标和所查找的值不受牵连：tanks-of-freedom-ii 的 `map_data["tiles"][key]` 不牵连 `key`（`scenes/ui/menu/skirmish/skirmish.gd:83-89`）。Ring 的 `balls.gd` 读 `new_ball.collision_shape.shape.radius` 出错时，`new_ball` 由之定型的 `instantiate_new_ball()` 和 `collision_shape` 不受牵连，因为 `shape` 是引擎属性。运算（含比较、`and`、`or` 和复合赋值）仅一个操作数是 `Variant` 而出错时，只涉及给出该操作数类型的槽位。
  - 无类型 `Array` 或 `Dictionary` 的元素是 `Variant`（经下标、`for` 或 `get()` 读出），错误不涉及容器和下标槽位。
  - 声明在别的文件中不可用（不是 `pub` 或自身有错）的错误不涉及任何槽位。【已知限制】同一范围的其他错误目前也不涉及，如调用尚未补 `pub` 的方法所得的值不合目标。
- **`int` 并入 `float` 安全核对**：编译器看不出求值变化，由工具自行核对：
  - 保持结果的使用是一张白名单：与 `float` 做算术（含复合赋值）、比较，以及进入要求 `float` 的位置（参数、变量和返回值）；表外运算一律算改变结果。语言测试用 `3` 和 `3.0` 运行表中每种使用并比对结果，以便及时发现引擎变化。
  - `float(x)` 总算保持。
  - 参数和局部变量只在所在函数内核对（跟踪以它为整个初始值的局部变量），值流出函数或流进另一槽位即算改变结果。成员读取在所有文件中核对，集合外 GDScript 不经检查、出现 `.名字` 读同名成员即算改变结果。返回值、信号参数和空容器元素不核对，一律算改变结果。
  - 推断中这类槽位先试 `Variant`，推断结束后才按最后一轮检查核对，确保与之运算的 `float` 不是另一待核对槽位。超过 2^53 的整数转 `float` 会丢精度，GDScript 把 `int` 传给 `float` 参数时同样如此，这里照样接受。
- **依据不全标注**：靠按名调用对上的、由集合外未写类型调用方给出的，以及略去了 `Variant` 流入的类型，均在报告中标明依据不全并列出相关流入位置。

#### 修复循环与语义改写

  - **补 `_: pass`**：`match` 因不穷尽又无 `_` 报错时（规范 §5.6），在最后一个分支之后按分支缩进补上 `_: pass`。GDScript 把分支编成一串 if/else，没有分支匹配就什么都不执行（`modules/gdscript/gdscript_compiler.cpp:1938-1943, 1983, 1999-2002`，`ed1daf0`）。编辑器中它只作备选，因为用户也可能想处理余下的值；反向转换保留它。

- **不转换的 `as` 写回原值**：GDScript 的 `x as T` 转为非类的类型时由 `x` 构造。`x` 已是 `T` 时得到原值；`x` 为 `Array[E]` 而 `T` 为 `Array[T']` 时得到同一个数组，不查元素（`modules/gdscript/gdscript_byte_codegen.cpp:1041-1048`，`modules/gdscript/gdscript_vm.cpp:1627-1643`，`core/variant/variant_construct.cpp:204`，`ed1daf0`）。本语言的 `as` 只转对象（规范 §5.3），修复因此写回 `x`。

- **静态类型缺失成员**：
  - 静态类型为 `Object` 时改为按名访问（GDScript 本来就按名查找）：弃返回值调用改为 `call("名字", ...)`，属性写改为 `set("名字", v)`，项目中同名函数补 `pub`。读属性或用返回值得到 `Variant`，留作编译错误由人定型。值为 `Object?` 时先补 `.unwrap()`，与其他未判空的使用相同。报告列出每处，注明可改用接口或具体类：前者转不回 GDScript，后者要靠场景事实判断。
  - 静态类型是缺该成员的具体类时，先由场景定出更准类型（导出场景写 `PackedScene[T]`，一致父节点写 `@parent(T)`）。定不出的留作编译错误，提供按名访问和转具体类两项备选，不自动转 `Object` 按名访问。
- **值上的 `new()`**：GDScript 在值上调用 `new(...)` 时，按名调用其类最近的 `_init`（`modules/gdscript/gdscript.cpp:122-128, 192-197, 1078`，`ed1daf0`）。检查器看不出是哪个类，本语言的这种构造却只接受 `pub` 的 `_init`（规范 §4.2，`src/adapter/pet_script.cpp:262-265`）。所以推断之后，集合中接受同样多实参的 `_init` 都补上 `pub`，与按名调用同名函数相同。
  - 补多了不改变 GDScript 中的含义，补少了要到运行时才出错。tanks-of-freedom-ii 以 0 到 4 个实参这样构造触发器、结果、事件和 AI 动作（`scenes/board/logic/scripting/triggers/templates.gd:16`，`scenes/board/logic/events.gd:20`）。
  - 它的 46 个 `_init` 由此全部带 `pub`。新补的 34 个中，5 个属于只由场景创建的能力类，其余都这样构造。
  - 实参不计为这些 `_init` 参数的流入。计入时，由已知类构造定型的参数会合并成 `Variant`：tanks-of-freedom-ii 撤回的类型从 500 个增到 521 个（`scripts/services/online/connector.gd:11`）。

  - 写入后内存项目设置换上新路径，因为检查读的是它（`core/config/project_settings.cpp:359-369`）。文件系统先更新旧文件移除 uid，新文件再从改名后的 `.uid` 取得同一 uid（`editor/file_system/editor_file_system.cpp:2415-2423, 2450, 2496-2501`），其余按重构步骤读回（§2.3、§2.4）。
  - 无界面命令同样逐个更新新旧文件。每次更新都存下 uid 缓存和全局类缓存，而游戏运行原样读取它们，不再扫描（`editor/file_system/editor_file_system.cpp:2503, 2552-2554, 2160-2195`，`core/io/resource_uid.cpp:343-380`，`main/main.cpp:2287`）。缺了这一步，刚转回的项目直接运行时找不到改名的全局类。
- **报告内容与格式**：命令输出即迁移报告，汇总文件去向、各类改写数、依据不全类型与遗留错误，并标出需过目的行为保持处（如截断和按名访问）：
  - 每个迁移文件一行（如 `boss.gd → boss.pet`，连带文件注原因），跳过文件也各占一行；
  - 写下类型一行（如 `9 × Write the type`，同时收到 `int`/`float` 且有使用分辨二者的槽位另计一行），每种修复一行（如 `3 × Make it pub`）；
  - 撤回槽位、依据不全类型与遗留错误采用与 `pet check` 相同的诊断写法；
  - 末行输出计数，如 `petrichor migrate: 4 script(s), 0 added, 2 left out, 9 type(s), 1 withdrawn, 3 fix(es), 6 path(s) renamed, 0 error(s)`。
- **反向转换**：只读 `.pet` 的 token 与检查结果（引用表和检查后的类型），不依赖正向留下的记录，迁移后人工改过的文件也能转回。改写只删除或替换 token，不打印检查后的语法树，因为检查器在树上改写了约十几种写法。人工写下的 `@late` 直接去掉，GDScript 中的成员同样从 null 开始。
  - 擦除规则（规范 §1.2、§10.1）：去掉 `pub`、`async`、`@late`、`@owner(T)`、`@parent(T)`、`.unwrap()`、`.detach()` 和对象类型的 `?`。`None` 写成 `null`。`Some(v)` 写成 `v`；它是运算的操作数而 `v` 带运算符时写成 `(v)`。`PackedScene[T]` 写成 `PackedScene`。
  - 类型按 GDScript 能写的写（规范 §3.11、§10.1）：
    - 值类型的 `T?` 不写类型，以它推断的 `:=` 改为 `=`，因为 GDScript 推断不出无类型的值；
    - 导出的值类型 `T?` 写成 `Variant`，属性信息与本语言导出的相同（`src/adapter/pet_script.cpp:85`，`modules/gdscript/gdscript_parser.cpp:4850-4854`，`ed1daf0`）；
    - 函数类型写成 `Callable`；
    - 嵌套容器只写外层，如 `Array[Array[int]]` 写成 `Array[Array]`；元素含值类型 `T?` 的容器不写类型参数。
  - GDScript 读作无类型之处：
    - 以 `:=` 推断这样的值时不转换，因为 GDScript 推断不出（`modules/gdscript/gdscript_analyzer.cpp:2140-2142`）。
    - 这样的值包括值类型的 `T?`、嵌套容器的元素、`var x = v` 声明的变量、函数值 `call()` 的结果（GDScript 中它是 `Callable`），以及以它们为操作数的运算（`:3166-3180`）。
    - 在这样的对象上赋值或调用，或放进嵌套容器时，带类型容器的字面量写成 `[...] as Array[T]`，GDScript 由此给它类型（`:3808-3815`）。类没有全局名时不转换。
  - `@warning_ignore` 去掉本语言的名字，名字全去掉时删去注解，因为 GDScript 拒绝不认识的名字（`modules/gdscript/gdscript_parser.cpp:5122-5129`，`ed1daf0`）。
  - 用到 GDScript 没有的特性（规范 §13.4）、有编译错误（含场景检查报在它上面的，§6.4），或同名 `.gd` 已在时，文件不转换，报告以 `hint:` 列出每处。摘要把这样的文件计入留下的文件，不计为错误，错误只计转换造成的（见下文）。
  - GDScript 不接受的三种写法也使文件不转换：
    - 内部类只写名字读外层类的静态变量或调用其静态函数。GDScript 只经外层类名找到它们（`modules/gdscript/gdscript_analyzer.cpp:4228-4256, 4270-4275`，`ed1daf0`），只写名字的 `log` 会读成数学函数；
    - 返回值的函数靠穷尽而无 `_` 的 `match` 覆盖返回路径（规范 §5.6）。GDScript 只在有接住任意值的分支时才这样算（`modules/gdscript/gdscript_parser.cpp:2467-2475, 2543`）；
    - 静态变量的初始化式经它读的静态变量（含其中 lambda 读的）绕回自己。GDScript 解析变量时连带解析初始化式读到的成员，绕回时报错（`modules/gdscript/gdscript_analyzer.cpp:984-987, 1052-1054, 2110, 4198-4199`）；本语言运行时报为成环（规范 §4.8）。环上的每个文件都不转换。
  - Option 的方法：接收者是局部变量、参数或无 getter 的本类成员时写成条件表达式，作操作数时加括号。
    - 本语言的方法调用总是先求值实参（规范 §3.4），条件表达式只求值用到的一支。所以实参须求值看不出来：字面量、`self`、lambda、包着这类值的 `Some`、不经调用即可读的名字、常量、作值的方法或类，以及以它们为操作数的运算。`/` 和 `%` 除外，因为除数为零时出错。
    - 实参为其他写法的，如 `x.unwrap_or(spawn())`，使文件不转换。
    - `x.unwrap_or(d)` 和 `x.or(y)` 写成 `x if x != null else d`；
    - `x.unwrap_or_else(f)` 和 `x.or_else(f)` 写成 `x if x != null else f.call()`；
    - `x.map(f)` 和 `x.and_then(f)` 写成 `f.call(x) if x != null else null`；
    - `x.filter(p)` 写成 `x if x != null and p.call(x) else null`；
    - `expect(消息)` 是 `var` 声明或给名字赋值的整个值时，删去它，并在该语句后另起一行补 `assert(名字 != null, 消息)`；
    - 其余写法使整个文件不转换，报告列出位置。
  - 迁移为隐式向下转换写下的 `(x as T).unwrap()` 和 `(x as T).unwrap() if x != None else None`，值进入 GDScript 中也写着类型 `T` 的位置时写回 `x`。
    - 这样的位置是写了类型的变量和成员、函数的参数和返回值，以及对象上写了类型的属性。GDScript 在调试构建中在该处检查，放过 null，类不符时出错，与这两种写法相同（`modules/gdscript/gdscript_vm.cpp:586-603, 1533-1625, 2924-3025`，`core/variant/variant_caster.h:135-145, 159-174`）。
    - 给对象的属性赋值都经 `set_named()`，由 GDScript 的成员或引擎的 setter 检查类。成员类不符时不写入，setter 收到 null，调试构建随即出错（`modules/gdscript/gdscript_compiler.cpp:1158-1159`，`modules/gdscript/gdscript.cpp:1536-1549`，`core/object/class_db.cpp:1597-1607`，`modules/gdscript/gdscript_vm.cpp:1219-1240`）。godot-tiny-mmo 的 `arc.source = source` 由此原样转回（`source/common/gameplay/items/weapons/bow/arrow.gd:199`）。
    - 其余位置照常去掉 `.unwrap()`，写成 `(x as T)` 和 `(x as T) if x != null else null`，类不符时得 null。
  - `State(x)` 写成 `x as State`。GDScript 把 `int` 转为 enum 时不查范围（`modules/gdscript/gdscript_analyzer.cpp:3826-3828`），与去掉 `.unwrap()` 一样，出错时改为 GDScript 原来的行为。常量中的不转换，GDScript 中它不是常量表达式。
  - 元素只在本语言中存在的 `Array(x)` 写成 `Array(x, TYPE_NIL, &"", null)`，`Dictionary(x)` 同理，得到同样的无类型副本（`core/variant/array.cpp:874-879`，`core/variant/dictionary.cpp:753-758`）。
  - `var x := T.new(m = v)` 的具名成员改为语句后另起一行的 `x.m = v`，与调用后按书写顺序经 setter 赋值相同（`src/compiler/lower.cpp:1594-1600`）。`instantiate(...)` 须写明变量类型，GDScript 把它的结果定为 `Node`。其余位置的具名成员不转换。
  - match 的 `Some(p)` 写成 `p`。`p` 是绑定或 `_` 时 GDScript 也接住 `null`，所以前面须有 `None` 分支才这样转换。
    - 前面没有 `None` 分支的 `Some(var x)` 写成 `var x when x != null`，已有的守卫接在后面并加括号。GDScript 按序试各分支，模式匹配后才求值守卫，守卫不成立就试下一个分支（`modules/gdscript/gdscript_compiler.cpp:1938-1983`，`ed1daf0`），与本语言对 `None` 越过 `Some(var x)` 相同。
    - 前面没有 `None` 分支的 `Some(_)` 不转换，守卫无名字可判。
  - 对象 `T?` 上的 `None` 模式写成 `var _none when not is_instance_valid(_none)`，名字取文件中没有的，已有的守卫同样接在后面。
    - GDScript 的 `null` 模式先比较类型，已释放对象的类型不是 null（`modules/gdscript/gdscript_compiler.cpp:1435-1453`，`ed1daf0`）。`is_instance_valid()` 把它与 null 同样对待，同本语言读作 `None`（规范 §3.3）。
    - 嵌在其他模式中或与其他模式并列的这种 `None` 使文件不转换。
    - `== None` 照常写成 `== null`。GDScript 中对象与 null 的 `==` 同样把已释放对象当作 null（`core/variant/variant_op.h:484-494, 533-543`）。
  - 转回一个类时连带它的整棵继承树，与正向相同；树中有文件不转换时整棵树留下，报告写明是哪个文件。
  - 要转的文件对留下的 `.pet` 类做 GDScript 做不到的类级访问时（规范 §11.3），连带转换那棵树；那棵树转不了，这个文件的树也留下。
  - 只转回部分文件时照样转换，随后在内存中检查留下的 `.pet` 文件，转回的类按其 GDScript 看待（规范 §11.1）。
    - 转回的类按反射会给出的样子提供：对象为 `T?`，脚本的 enum 为 `int`，未写类型的为 `Variant`，enum 名为 `Dictionary` 常量（`src/adapter/editor/class_db_api.cpp:23-62`，`src/adapter/editor/scene_index.cpp:879-939`）。
    - 转换前没有、转换后才有的错误按正向遗留错误的写法列出，如改为 GDScript 协程后结果上的 `.detach()`。它们不阻止写入，也不改变退出码。
    - 调用转回函数的 GDScript 不在其中，由 GDScript 加载时报告。
  - 写出前复核：每个文件先用本语言解析器按 GDScript 重读输出，语法树须等于 `.pet` 的树去掉擦除的部分。不等时什么都不写，报告为转换器的缺陷并请用户报告。擦除式转换的静默错误出在擦除后相邻 token 的解析变了（如优先级），GDScript 编译器照样接受，只有这一步能发现。
  - 两棵树各打印成规范化的文本按行比较。`.pet` 一侧略去本次擦除记下的调用和类型。两侧都略去总被删去的部分：`pub`、`async`、类型的 `?`、`None` 的写法、`@late`、`@owner`、`@parent`、`PackedScene` 的根类型和本语言的警告名。
  - 替换成另一种写法的表达式和补上的语句，`.pet` 一侧打印其 GDScript 写法重读的树，其中的操作数仍是 `.pet` 的子树。
  - 往返的已知改写：迁移再转回的文件与原文只应差以下几处，corpus 的往返据此比对：
    - 跨行字符串写成三引号；
    - 不穷尽的 `match` 补上的 `_: pass`；
    - 从根取 autoload 改用的名字；
    - 不转换的 `as` 写回的原值，以及遍历这样的数组的循环变量写上的类型；
    - 补上的 `return None` 写回为 `return null`，包括对象类型函数中原本只写的 `return`；
    - 推断写下或改窄的类型。反向只读 `.pet`，分不出哪些类型是推断写下的；它们都经检查器核验，GDScript 照样接受；
    - 真值判断写成的比较、`is_empty()` 和 `is_instance_valid()`。GDScript 的真值即 `is_zero()` 之反，对象按存活判断，与 `!= null` 相同（`core/variant/variant.cpp:878-953`，`core/variant/variant_op.cpp:1120-1122`，`ed1daf0`）；
    - 修复写下的转换：`int(x)`、`float(x)`、packed array 的构造和写成 `6.0` 的 `6`，以及改用方法或信号本身的 `call_deferred()` 和 `emit()`。期望 enum 处的 `int` 写成的 `E(x)` 转回 `x as E`：GDScript 照收 `int`（`modules/gdscript/gdscript_analyzer.cpp:6397-6400`，`ed1daf0`），引擎 enum 开放，本语言 enum 只在 `int` 是其某个值的常量时这样写，转换都不改变它（规范 §3.7）；
    - 声明无类型容器写下的 `Array` 或 `Dictionary`，GDScript 照样接受；
    - 隐式向下转换在其余位置写下的 `(x as T)` 和 `(x as T) if x != null else null`，以及值可能为空时写下的 `x as T`；
    - 写了类型之处的显式 `x as T`，迁移补上 `.unwrap()`，转回写成 `x`。类不符时原文得 null，转回的文件在调试构建中出错，迁移后的文件本已在 `unwrap()` 处出错；
    - 给无 `class_name` 的类补上的 `preload` 常量。GDScript 照样加载它所指的脚本，留下的 `.pet` 也是。它作类型、`is` 和 `new()` 都同原来的类，类不符的赋值和传参照样出错（`modules/gdscript/gdscript_analyzer.cpp:4755-4780, 5720-5729`）。
  - 转回的已知差异：转回的文件照 GDScript 的做法运行而不报错，与本语言只差以下几处：
    - 不带 `pub` 的成员，GDScript 按名访问也找得到，且先于 `_get()`；本语言在此隐藏它（规范 §10.5）。正向迁移把按名用到的成员改为 `pub`，迁移来的文件遇不到；
    - `match` 头部求出的临时值，本语言在进入分支前释放（规范 §6.8）；GDScript 把它留在栈上，`match` 结束时也不清除，直到那一格另作他用或函数返回（`modules/gdscript/gdscript_compiler.cpp:1909-1912, 2004`，`modules/gdscript/gdscript_byte_codegen.cpp:1907-1909`）；
    - 只作类型的 `preload` 常量，GDScript 加载这个类时就加载它所指的脚本，运行其静态初始化；本语言不加载（规范 §2.1）；
    - 值模式读到持有已释放对象的 `T?`，本语言按 `None` 匹配（规范 §3.3、§5.6），GDScript 先比较类型而不匹配（`modules/gdscript/gdscript_compiler.cpp:1435-1453`）。
  - 语言测试转回后，逐条比较检查的结果（第 5 步第 11 项的验收）。
    - 本语言出错之处转回后照 GDScript 的做法，所以比较略去检查本语言自有行为的检查。它们在 `language_test.gd` 中以 `OWN` 开头。
    - 自有行为包括程序错误、其文本及其后果，以及上面转回的已知差异。
    - 按名访问使测试自己的代码出错的脚本留下不转换。
