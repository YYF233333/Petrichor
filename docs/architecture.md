# Petrichor 实现架构

本文记录实现层面的决定：组件划分、值的表示、测试和推进顺序。语言规则以[语言规范](language-spec.zh.md)为准。实现中发现规范有问题时，单独提交修改规范，不在实现中放宽规则。引擎事实对照 Godot 4.7.2-stable（提交 `ed1daf0`）核对，汇总见[引擎事实](engine-facts.md)。

## 1. 已定的选择

- **C++17、godot-cpp、SCons。** 解释器要在 iOS 和主机上运行（规范 §12.2），以后还可能改为引擎模块（§1.3）。引擎用 C++17 编译（`SConstruct:916, 921`），引擎模块只能用 SCons 构建。godot-cpp 固定在某个提交，以 `api_version=4.7` 构建。引擎提高 C++ 标准之前本项目也不提高：C++20 只带来方便，强制尾调用是编译器扩展。
- **目标引擎是 Godot 4.7。** 引擎加载最低版本不高于自身的扩展，所以声明 4.7 的构建也能在之后的引擎上加载（`core/extension/gdextension_library_loader.cpp:315-329`）。但只对照 4.7.2 核对过。在之后的引擎上运行，还要求引擎的值保持本构建依赖的布局（`src/runtime/values.h`）：
  - Variant 先存类型，数据从第 8 字节起，对象存为 ObjectID 和指针；
  - 各内置类型不超过字节码为它预留的大小，运行时在加载时检查。
- **导出的游戏只含字节码**（规范 §1.3）。`.gdextension` 按功能标签为编辑器和导出模板选择不同的库（`gdextension_library_loader.cpp:82-96`）。编辑器用的库含编译器，导出模板用的库只含运行时。
- **寄存器按静态类型存放原生值。** GDScript 即使静态类型已知，寄存器也是 Variant，运算和引擎调用都经 Variant（`modules/gdscript/gdscript_vm.cpp:536, 848-862, 2273-2313`）。本语言省掉这些开销，这是“明显快于 GDScript”（规范 §12.2）的主要来源。
- **从编辑器运行时，游戏读取编辑器写好的字节码，自己不编译**（§2.4）。

## 2. 组件

| 组件 | 依赖 | 内容 |
|---|---|---|
| compiler | 不依赖 Godot | 词法和语法分析、语义分析、场景检查、带类型的 IR、字节码生成、诊断、符号索引 |
| bytecode | 不依赖 Godot | 编译结果的格式、序列化和校验，compiler 与 runtime 共用 |
| runtime | godot-cpp | 字节码加载、虚拟机、值和类型描述、任务、程序错误、引擎边界上的检查和转换 |
| adapter | godot-cpp、runtime；编辑器用的库还依赖 compiler | 脚本语言、脚本和脚本实例三个扩展接口，资源的加载和保存，导出插件，编辑器插件，无界面命令 |

### 2.1 compiler

- 不含 Godot 的头文件，构建时也不给它 godot-cpp 的头文件路径。所以它的测试是不启动引擎的普通 C++ 程序，改为引擎模块时也能原样使用。
- 外部信息经接口取得：
  - 引擎 API：类、方法、属性、信号、enum、内置类型的运算符表；
  - 项目：场景、资源、autoload、全局类；
  - GDScript 类的静态视图（规范 §11.1）；
  - 绑定审核的数据（§10.3），放在 `src/compiler/binding_metadata.txt`。
- adapter 实现这些接口时，引擎类取自 ClassDB，场景取自引擎读出的 SceneState，GDScript 类取自 Script 的反射接口。这样其他扩展的类、更新版本引擎的 API 和二进制场景都按引擎的理解读到。
- 内置类型、工具函数和引擎的可空性元数据（规范 §10.2），ClassDB 不提供（`core/object/method_info.cpp:37-51`）。它们取自构建时从 `extension_api-4-7.json` 生成的表，可空性再与审核数据合并。这些表不随扩展变化；其他扩展的类按 §10.2 的默认规则处理。
- 流程：词法 → 语法树 → 语义分析 → 场景检查（规范 §7）→ 带类型的 IR → 字节码、调试信息和类的元数据。语义分析处理名字、类型、收窄、match、泛型、接口和可见性。
- IR 由显式的基本块和虚拟寄存器组成，不是 SSA；寄存器带类型，行号指令标出源码位置。字节码与 IR 基本一一对应。语法糖（`?`、链式赋值的写回、await、match、就绪前的 setter）在生成 IR 时展开。
- 生成 IR 照检查器的决定执行，不从寄存器的表示反推语义。
  - 转换的种类只由源类型和目标类型决定。检查器判断能否赋值，生成 IR 时据此转换，两者调用同一个函数（`conversion()`）。
  - 比较时两侧转换到的类型、Variant 的比较方式和特殊的内置方法，由检查器记在节点上。
  - 收窄由节点的类型与局部变量声明的类型不同得出。
- struct 的字段是 struct 字节上的视图寄存器，没有自己的槽位，读写不需复制。推理寄存器的处理（复用槽位、协程保留的槽位）把视图算作所视寄存器的一部分。struct 在所有字段求值后才构造到新寄存器中，以免读取的字段先被覆盖。
- 参数的默认值在函数开头计算（规范 §4.6）。调用把实参的个数写进帧中的一个槽位，开头据此跳过已传入的参数。所以 IR 只有一个入口，GDScript 则跳进函数中段（`modules/gdscript/gdscript_vm.cpp:2781-2784`）。
- 不是常量的 struct 字段默认值，由声明该 struct 的类中的一个函数计算。别的类构造时按名字调用这个函数，不把另一个脚本的代码编进自己的字节码（§6.1）。
- 引用按作用域释放（规范 §6.8），由生成 IR 时插入的 `CLEAR` 完成。它把一组寄存器放回默认值，只含能持有引用的类型。
  - 插入处是语句结束、复合语句头部判定之后和离开块时；
  - break 和 continue 清空所离开各块的局部变量；
  - 函数体的局部变量随栈帧释放，不另清空。
- 有的指令先读完操作数再写结果。赋给局部变量的值由这样的指令算出时，直接写进局部变量，不经临时寄存器。引擎的运算对数学类型先算出值再写入，数组相加则不然（`core/variant/variant_op.h:50-83, 659-673`）。
- 计数的 `for` 循环中，循环体不给循环变量赋值时，以循环变量本身计数。
- 常量表达式（规范 §4.5）在类型检查时求出。编译器算出标量和容器的结构；引擎类型的部分写进常量表，由运行时在类加载时算（§2.2）。编译期按虚拟机指令的算法计算（如 int 回绕），因为同一表达式在函数体中由虚拟机计算。
- 分析（`src/compiler/analysis.h`）保留每个脚本完整检查的结果：诊断、引用表和字节码。结果用到它读过的输入改变为止：自己的源码、其他脚本的声明，和项目对它所问问题的答案。
  - 其他脚本的声明按函数体之外的 token 求哈希，所以只改函数体不会使用到它的脚本重新检查。`_init` 的函数体除外，因为其他脚本用它的摘要（§6.4）。
  - 为 `$X` 定型时，脚本检查只读场景的结构，即节点的路径、类、脚本和实例。所以改挂载它的场景存的值或连接，不会使它重新检查。
  - 每个结果记下验证它时工作区的 revision。revision 未变时直接沿用，与 salsa 的 verified_at 相同。变了才逐项重读输入比较。检查只经接口读取输入（§6.4）。
  - 一次分析（一次构建或校验）把项目当作不变：场景只列举一次，其他脚本只解析一次，项目的每个问题只问一次。检查过的声明指向其他文件的语法树，只在一次分析内共享；分析之间只保留结果。否则一次检查会混用同一文件的两个版本。
  - 分析进行中不得写入工作区，嵌套的分析也不得另给项目。两者都直接终止。
  - 引擎的类只在扩展加载、卸载或重载时改变，这时清空所有结果（`core/extension/gdextension_manager.cpp:483-485`）。
  - 场景的检查（§6.4）也这样保留，输入是场景、节点上各脚本的全文、其他脚本的声明和项目的回答。
  - 它的错误可在这些脚本的任一行，所以按全文比较，行号随脚本更新。
  - 它对节点上和所实例化场景的根上的脚本只检查声明，再查这个场景怎样放置它们（`CompileOptions::scene`）。
  - 这些脚本的基类也这样检查，因为基类的要求（如 `@parent`）也适用于子类的节点。
  - 场景的轨道、同步属性和信号连接的两端可以是所实例化场景中的节点。所以场景有轨道、同步属性或这样的连接时，也检查那些场景中的脚本。
  - 场景也可以给所实例化场景中的节点存值。存了这样的值时，同样检查那些脚本。
  - 当作根使用的场景也检查那些脚本，因为它逐层的每个节点都要有必须赋值的导出（规范 §7.5）。
  - 资源文件是没有节点的场景，场景也检查它所含资源的脚本。资源没有就绪阶段，所以文件要给出它必须赋值的成员（规范 §6.2）。
  - 它的错误位于脚本的源码中，记下所在的文件（`Diagnostic::file`）。
- 编辑器的检查都读工作区（`src/compiler/workspace.h`），所以各功能看到每个文件的同一份文本。它把未保存的文本叠在磁盘上：
  - 打开的脚本的缓冲区；
  - 重构改过、没有打开的脚本的文本（§2.3）；
  - 有未保存修改的场景。
  - 适配层在每次分析前同步打开的脚本。代码编辑器的版本号随每次编辑增加，撤销和重做还原对应文本的版本号，所以版本号不变就不取文本（`scene/gui/text_edit.cpp:4784-4848, 9193, 9233`）。
  - 未保存的场景在编辑停下后打包写入（§2.4）。查找引用和重命名之前也重新打包。
  - 写入的内容与原来相同时，revision 不变，与 rust-analyzer 的 VFS 相同。
  - 文件的版本是它最后一次改变时的 revision。所以关闭再打开的文件不会拿到用过的版本，与 TypeScript 相同。
  - 文件打开期间，磁盘上的改动不影响它，与 rust-analyzer、gopls 和 TypeScript 相同。
- 磁盘上的变化由编辑器的事件得知，不在每次使用前重读：
  - 保存资源或场景、`filesystem_changed` 和 `settings_changed` 使 revision 加一（`editor/plugins/editor_plugin.cpp:284-289`，`core/config/project_settings.cpp:575`）。
  - 本语言的保存器写入文件后先通知，再编译依赖它的脚本。
  - 编辑器在窗口重获焦点时扫描（`editor/editor_node.cpp:1049-1058`）。所以编辑器有焦点时外部进程改的文件，要到下次扫描后才看到。
  - 场景索引在两次变化之间沿用读到的场景；变化之后按修改时间判定。修改时间只到秒，所以读取前 2 秒内改过的文件不按修改时间沿用，与 gopls 相同（gopls `internal/cache/fs_memoized.go:72-80`，`v0.24.0`）。
- 构建和导出读磁盘，不读工作区。运行前编辑器默认保存所有脚本和场景，所以两者通常一致（`editor/editor_node.cpp:2590-2603`）。无界面构建只运行一遍。
- 之后才用的结果带戳：算出它时的 revision，和它含有位置的文件。其中某个文件的版本晚于这个 revision 时，结果已经过时。
  - 戳在算出结果时取，不在使用时取。分析沿用的结果，取它当初算出时的 revision。
  - 只用于显示的结果按 revision 判定，revision 变了就重算。
- 一个文件中的每个类（含内部类，规范 §4.1）各有一个检查器，检查函数体之前所有类先完成声明。同文件的类经彼此的检查器读取声明，常量和 enum 在第一次用到时检查。裸名由近及远到外层类中查找。每个类生成自己的模块，文件的模块包含其内部类的模块。
- 语法树建在无损的 token 流上。语法 token 和 trivia（注释、续行的 `\`、非法字符）分成两列，按字节偏移合并即是原文。
  - 注释不在语法 token 中，所以解析器的前瞻不必跳过它们。格式化和 `##` 文档注释按偏移找注释；GDScript 也把注释另存为按行号的表（`modules/gdscript/gdscript_parser.cpp:4066-4106`）。
  - 行列只在报告时由行首表换算，列按码点计。
  - 每个节点记下首尾 token 的下标。名字和运算符另记自己的 token 下标，因为引用表需要每个名字的位置。
  - 诊断是字节区间；Godot 的接口只取起点的行列（`core/object/script_language_extension.h:322-330`）。快速修复和格式化以 token 为单位编辑。
  - 不采用无损的具体语法树（Roslyn 的 red-green 树），它要重写解析器和检查器。格式化器大多建在 AST 和 token 上（gofmt、Ruff）。
  - GDScript 的解析器只留与执行有关的 token，给它写的格式化器因此丢了字面量的写法和括号（[godotengine/godot#76211](https://github.com/godotengine/godot/pull/76211)）。
- 名字的解析记在引用表中。每解析一个名字记一条：位置、所指声明的标识和角色（声明或引用）。
  - 位置在 `.pet` 中是字节区间，因为字面量里的方法名和 `$"Head/Camera"` 的各段只是字符串 token 的一部分。场景中的位置是场景路径、节点路径、种类和键。
  - 场景中的位置还带着改写它所需的结构路径（§6.4）：
    - struct 字段和 enum 分支：从所存的值到这个名字，逐层的元素或键值的下标；
    - 轨道和同步属性：所在 Animation 或 SceneReplicationConfig 的路径、轨道或属性的序号、方法轨道中键的序号；
    - 信号连接：存它的场景。继承的场景也列出基场景存的连接。
  - 声明的标识由种类、作用域和名字组成，按值比较，跨文件稳定，如 `Hit.damage`。一处源码可有多条，如挂在两个场景中的脚本的 `$Head/Camera`。解析不出的名字记为只有名字的未解析标识。
  - 覆盖或实现另一声明的条目带上被覆盖者的标识，供重命名找全相关声明（clangd 亦然）。
  - 表属于一个文件的检查，重新检查时整份替换。场景中的引用（信号连接的信号和方法、节点路径、导出属性的键）写入该场景检查的表（§6.4）。
  - 分析保留每个脚本的表。一条占 680 字节，其中 480 字节是场景中位置的字段，脚本中的条目也带着。字符串大多存在自身之内，另分配的不到 5%。
  - 在官方 4.7.2 编辑器中查找引用，检查全部脚本和场景后：
    - 生成的大项目（1000 个脚本、300 个场景）有 1.9 万条，约 15 MB，是无界面编辑器进程私有内存的 2.4%；
    - 演示项目有 778 条，约 0.7 MB。
  - 每 KB 源码约 60 到 80 条，表约 60 KB。源码到约 1.7 MB 时，表才到 100 MB。那时先把场景中位置的字段移出条目。
  - 跳转和悬停按位置查表，查找引用和重命名按声明反查；补全不用这张表。重命名执行时按当前文本核对每一处，对不上就放弃；未解析的同名候选只列出供确认（规范 §13.3）。
  - 字面量节点路径另记它在各场景中从哪个节点走到哪个节点。节点改名或移动时，据此重写路径（§2.3）。
  - GDScript 的语言服务器没有这张表，按文本搜索名字再逐处解析，找不到字面量和场景中的引用（`modules/gdscript/language_server/gdscript_workspace.cpp:434-500`）。
- 有语法错误时，诊断只报语法错误（GDScript 亦然，`modules/gdscript/gdscript_editor.cpp:150-153`）。补全、悬停和跳转在恢复后的语法树上运行检查。编译也运行检查器，只是丢弃诊断、不生成 IR，使恢复的路径始终受检验。
- 补全只列出在光标处能通过检查的名字（规范 §13.2）。
  - 编辑器在光标处放一个 U+FFFF，它读作名字的一部分（`scene/gui/code_edit.cpp:2390-2400`）。检查器只检查声明和光标所在的函数体。
  - 候选取自各处的列举，多于能写的。每个候选换到光标处，由检查器自己的查找判断。所以规则只写在查找一处。
  - TypeScript 同样用检查器的可访问性判断过滤成员（`isValidPropertyAccessForCompletions`）。
  - 全局类按项目列出的名字给出，不逐个解析，因为解析要读每个脚本。
  - 列表总是完整的。退格后编辑器只在已有列表中筛选，不再询问（`editor/gui/code_editor.cpp:1008-1012`）。
  - 实参提示由检查器在检查调用时给出，所以显示的参数类型就是检查所用的。光标在嵌套的调用中时，取最内层的。
  - 注解名由解析器判断。它报告读到注解的位置，补全列出该处接受的名字。
  - 字符串按所在的参数补全，如路径、输入动作和本类的 `pub` 方法名（规范 §10.4、§10.5）。
- 恢复以行为单位：出错时丢弃本行余下的 token，缺少的部分由错误节点填补。行后的块照常解析（GDScript 亦然，`modules/gdscript/gdscript_parser.cpp:2366-2373`）。
  - 未闭合的括号会吞掉其后的行结构，而这是边输入边编辑时最常见的状态。所以词法分析把未闭合的括号视为在其后第一个合适的换行处闭合。合适指下一行缩进不深于括号所在行，且不以闭括号开头。
  - 这样 `print("a",` 后同一缩进的 `set_process(true)` 仍是下一条语句；只凭语法决定的做法（Ruff）会把它读成实参。
  - 解析器在括号内出错时，本行止于括号内的下一个换行，词法和解析各重做一遍。
- 一个原因只报一条错误，报在错处（参照 CPython 3.10 和 rustc）：
  - 未闭合的括号在开括号处报一次，它闭合前发现的问题不再报；
  - 词法分析已报错的行，解析器不再报；
  - 漏掉的逗号报在应有逗号处，多出的闭括号报为不匹配。
- 检查器把错误节点当作类型 Error，不再因它报错；格式化器不处理有语法错误的文件。
- 已保存的脚本有语法错误时，其他脚本看到恢复出的声明。没有错误（语法或检查）的声明照常可用，函数只看签名。
  - 用到有错误的声明时报在使用处，如 `Partly.bad has errors (res://partly.pet, line 4).`。
  - 缺少的块是开启它那一行的错误，报在冒号处（GDScript 亦然，`modules/gdscript/gdscript_parser.cpp:238-240、1956`）。
  - 【已知限制】报错中的行号是使用者上次检查时的；只移动声明的修改不会让使用者重新检查。
  - 实现接口有错误的类仍可使用，但不能当作该接口，如 `Half implements Combat.Damageable with errors (res://half.pet, line 1).`。子类要求基类的声明全都没有错误。
  - 找不到的名字所在的类或其本语言基类的文件有语法错误时，报错附上第一处，如 `A has no method "hit()"; res://a.pet has syntax errors (line 4).`。
- 警告经 `@warning_ignore` 过滤后显示在脚本编辑器的警告列表中。第 8 步加入的 lint 是检查器中的检查，与编译器的警告共用诊断和 `@warning_ignore`（规范 §13.2）。
- 快速修复（第 8 步）是 token 区间上的文本替换。每个修复属于一个种类，能否自动应用按种类定，不在报错处判断。
  - 检查器在报错处生成修复，修复随诊断进入 `CompileResult`（`Diagnostic::fixes`）。
  - 每处编辑带上它替换的原文，应用前先核对。
  - 自动的种类同时满足以下各条。这是 Clang 和 Swift 对错误上的 fix-it 的要求（[设计说明](design-notes.md)）：
    - 只有一种明显的改法；
    - 只改报错的表达式或语句，或只在一个声明前补上 `pub`；
    - 保持 GDScript 中的含义；
    - 检查器报出错误后，按已经应用了修复继续检查。
  - 自动的种类有：
    - 真值改写、`float` 实参和 `is_instance_valid`；
    - 两层 Option 当作 GDScript 的 null，如与 null 比较和传给 `Variant`；
    - `.detach()`，以及字面量名字改用方法或信号本身；
    - 补上 `pub`。声明会因此露出不带 `pub` 的类型时，不提供这个修复。
  - 其余种类只作备选，如 `.unwrap()`、改为 `T?`、补上 `async`、`await` 和 null 模式。
  - 自动的修复排在第一，且无需输入。
  - 一键修复（`compiler::fix_all()`）每次只应用本脚本中的一种自动修复。同种修复的区间重叠时，跳过后一个，留给下一次。跨种类的批量修复属于迁移工具（第 11 步）。
  - 改写给操作数加括号，名字、成员、调用、下标、字面量和已在括号中的除外。
  - 改写后能否通过检查，由检查器在原树上暂时改写并重新检查得出，如加上 `.unwrap()` 后成员能否找到。通不过就不提供这个修复。这次检查的报错、引用和警告随即撤回。补全时不做这种检查。
  - 修复可以编辑其他脚本，如给另一文件中的声明补上 `pub`。这处编辑带上那个脚本的 res:// 路径，原文从关键字取到名字。
- 格式化器（`src/compiler/formatter.h`）只改 token 之间的空白和空行（规范 §13.2）。输出再词法分析一遍，token 或注释与原文不同就放弃（Black 亦然），所以语法树不变由构造保证。token 和注释分开比较，看不出交错的次序，所以去掉空白后与原文不同也放弃。验收：编译器测试格式化全部测试源码和 `tests/engine`、`benchmarks/project` 的脚本，再格式化一次不应再改动。FPS 和 Ring 用格式化后的脚本构建和运行。

### 2.2 runtime

- 值：int、float 各 8 字节；引擎的内置值类型就地存放，按引擎的规则复制和析构；String、Array、Dictionary 用引擎的类型。Option 有带判别字段的布局。struct 依次存放各字段，字段就是 struct 槽位内的槽位，verifier 从类型表得出它们。struct 的 `==` 是一条按类型表逐字段比较的指令。
- 带载荷的 enum 按 struct 存放：先是分支的序号，再依次是每个分支的字段。
  - 其他分支的字段保持默认值，所以复制和析构与 struct 相同。
  - 构造先读入该分支的常量，各字段都是默认值，再写入实参。
  - 相等、排序、哈希和编码只看序号和该分支的字段。
  - 不重叠存放的代价是槽位更大，可以以后再改为按最大分支共用。
- `Result[T, E]` 是名为 `Result` 的带载荷 enum，分支为 `Ok(value: T)` 和 `Err(error: E)`。
  - 类型键含字段的类型，所以不同的 T、E 是不同的类型。
  - 它的方法和后缀 `?` 编译为按序号的跳转。`unwrap` 和 `expect` 另有一条指令，失败时报出错误值。
- `T.try_from(v)` 是一条指令，与 struct 字段共用解码函数，所以两者的规则由构造保持一致。
  - 解码失败时，`Err` 中的 `ConversionError` 记下入口检查的报错。
  - `ConversionError` 由编译器声明，没有脚本，字节码中名为 `::ConversionError`。
- 引擎 API 的 `try_` 版本在每个调用处展开：先调用原方法，再调用读取错误的 getter（规范 §10.3）。
  - 作为值时，检查器把它改写成调用它的 lambda，如 `func(path, flags): return FileAccess.try_open(path, flags)`。
  - 降级和运行时因此没有新路径。
- struct 的方法是声明它的类的静态函数，名为 `Hit.total`。
  - 实例方法的第一个参数是 struct 本身，即 `self`。lambda 像捕获局部变量一样捕获它的副本。
  - 名字中的点使它们不与类的函数同名。它们不是 pub，引擎找不到。
  - 本类和子类用 `CALL` 调用，其他类经 `CALL_METHOD` 按名调用，所以运行时没有新指令。
- 必须赋值的成员（规范 §6.2）在槽位之后跟 8 字节的标记，赋值后不为零。
  - 本语言的写入之后有一条置位指令，引擎经 `set` 写入时由运行时置位。读取之前检查标记。
  - 标记对所有类型一致：struct 和带载荷 enum 没有可以表示"未赋值"的值。
  - 节点就绪时由运行时按 owner 决定当场检查，还是在 owner 发出 `ready` 时检查。所以不用跨文件分析谁赋了值。
- 元素是本语言独有类型的容器（规范 §3.8）及其嵌套的容器存为引擎容器，元素装在不可变的盒子里。
  - 盒子是用本库的 token 创建的自定义 Callable，数据是元素的类型和值，不能调用（`core/extension/gdextension_interface.cpp:1617-1631`）。
  - 引擎经盒子的 equal 回调比较 Callable，`has`、`find`、`erase`、容器的 `==` 和 Dictionary 查找都经 `hash_compare` 走到这里（`core/variant/callable.cpp:265-288`，`core/variant/variant.cpp:3351-3355`）。所以这些操作和只移动元素的操作，由构造保证按本语言的语义进行。
  - Callable 的哈希在创建时算一次（`gdextension_interface.cpp:221-227`），所以只有键的盒子在创建时哈希内容。键的内容只读（规范 §3.8）；引擎类型的值用引擎的哈希，它把所有 NaN 和正负零各视为相等（`core/templates/hashfuncs.cpp:39-64`）。
  - 运算表不比较 Callable 的大小（`core/variant/variant_op.cpp:731-791`）。所以 `sort`、`bsearch`、`min`、`max` 和容器的 `<` 由运行时用本语言的 `<` 完成。`hash`、`has_all` 和深复制也由运行时经盒子完成。
  - `resize` 后编译器生成的代码把新元素设为默认值，因为只有编译器知道 struct 字段的默认值。
  - 插入的键是逐层只读的副本，交出的键就地设为只读。虚拟机在修改容器前检查 `is_read_only()`，因为引擎在这里只报错或写进临时值（`core/variant/array.cpp:104-108, 518`）。
  - `Array(hits)`、`Dictionary(d)` 按规范 §10.1 编码。代价是每个元素一个盒子；不逃逸的容器以后可由逃逸分析换成私有表示。
  - 引擎检查不了 Callable 的签名和 Task 的结果类型，所以函数值和 `Task[T]` 也装盒。各函数类型共用一种盒子，调用时再检查签名（规范 §3.11）。
  - struct 经容器包含自己时（规范 §3.6），类型表中容器的元素可以排在容器之后。字段和 `T?` 的 `T` 仍排在前面，所以大小可以算出。
  - 这样的值可以经共享的容器包含自己。比较、哈希、打印、编码、解码和深复制进入盒子超过 100 层时停下。
  - 深复制遇到正在复制的容器时也停下，因为该值包含自己。
  - 本线程上运行着本语言的函数时，停下的遍历留下标记，其后的遍历立即结束。其他程序错误结束调用链时也清掉标记。
  - 可能遍历的指令在其辅助函数中取走标记，在该语句报程序错误（规范 §3.6）。检查放在分派循环里会使不遍历的基准也慢 5–10%。
  - 引擎运算符的指令在循环内直接调用引擎，所以不能遍历盒子。容器的 `==` 因此也用 struct 的比较指令。
  - 本线程上没有本语言的函数时，遍历由引擎发起。停下时报引擎的错误，给出引擎在同一深度给出的结果（`core/variant/array.cpp:149-153`，`ed1daf0`）。调试器显示变量时同样停下，不算程序错误。
- 不是 RefCounted 的对象存为 ObjectID 和指针，访问时检查存活（规范 §3.3）；RefCounted 持强引用。实例的成员由实例和其上运行的调用共同持有。方法运行中实例被删除时（`free()`、`set_script`），成员只标记为已释放；之后访问成员或 self 是程序错误。
- debug 构建记下释放位置（规范 §3.3），即释放时本线程上本语言正在执行的语句。
  - 来源有三种：
    - 本语言实例的 `PREDELETE`；
    - 本语言调用的 `free()`；
    - 本语言调用 `queue_free()` 之处。
  - 位置存入本线程的一个 4096 项的环，记录时不分配内存，也不等待。
  - 各线程的环登记在一张表中。线程结束后环仍保留，由下一个新线程接着使用。
  - 报对象已释放的程序错误时，在每个环中按 ObjectID 从新到旧查找。查找逐个锁住环，记录遇到锁时跳过这一次。
  - 更早的释放不再有位置，与 AddressSanitizer 的隔离区相同。
- debug 构建还记下创建位置，退出时列出泄漏（规范 §6.7）。
  - 本语言的实例在其存储中记下创建时本语言正在执行的语句。
  - 退出时列出本语言的全部存活实例。引擎或其他语言创建的实例没有位置，按类列出。
  - 本语言的 `new()` 创建的引擎对象记入本线程的表。表长翻倍时删去已释放的对象。
  - 位置指向类镜像的路径和函数名。镜像第一次记录时复制它们，保留到退出。
  - 列表在扩展的 CORE 级反初始化时打印。此前场景树和各服务器已释放所持对象（`main/main.cpp:5259, 5295-5391`，`ed1daf0`）。
- 每种类型有类型描述，提供复制、移动、析构和与 Variant 的转换（§10.1）。编译器为每个栈帧生成槽位类型表，供析构、协程搬移栈帧和调试器使用。
- 常量表在类加载时经引擎的接口求值一次，标量写回表中，容器逐层只读、每次使用读到同一个。
  - 每个 `preload` 都是常量表的条目，函数体中的也是，所以资源随类加载。这与 GDScript 在编译脚本时加载相同，使用处不再加载。
  - 因此 preload 不能成环，否则类要等正在加载它的文件（规范 §7.6）。GDScript 经引擎内部的接口取得正在加载的资源，GDExtension 没有这个接口。
  - 编辑器加载脚本时只检查声明，这样的类不加载资源。GDScript 按名字读取含 `preload` 的常量时才求值。
- 函数体中的 int、float 和 bool 常量是栈帧的预设值，建帧时与清零一并写入，读取不需指令。引擎值类型的常量表达式（如 `Vector2(1, 2)`）读常量表；容器的字面量每次求值都新建。内置类型的常量在加载时转成原生布局，读取时原样复制。
- 编译好的函数不可修改，带版本。只改函数体的热重载替换函数表，运行中和挂起的栈帧继续用旧版本（§12.4）。
- 静态变量（规范 §4.8）存在类的镜像创建的存储中，只改函数体的热重载把它交给新镜像。
  - 适配层在脚本加载时初始化它们，编辑器中除外。另一个类的静态初始化先用到的类，在那时初始化。
  - 使用未初始化的静态变量和初始化之间的环，都由初始化状态和本线程上进行中的初始化发现。
  - 有静态变量的脚本整个运行中保持加载，除非带 `@static_unload`。
- 协程挂起时，栈帧放下槽位中指向 self 的引用，恢复时放回（规范 §9.4）。self 在此期间释放时，协程已被取消（§9.7）。所以临时值和局部变量中的 self 都不使它保持存活。
- 协程的栈帧在堆上，按归属成树，取消沿树传递（§9.3）。释放通知来自运行时自己的实例绑定，它与 godot-cpp 的绑定并存（`core/object/object.cpp:2167-2201`）；是否报错在每帧回调中判定（§9.7）。
- `Task` 值是运行时自己的句柄，按引用计数，槽位存放它的指针（`ValueType::Task`）。
  - 引擎看到的 `CoroutineTask` 在任务第一次进入引擎时才建出，如传给 GDScript、存入 Variant 或容器。
  - 它存活期间，同一个任务总是同一个对象。任务运行期间持有它，所以连到其信号的代码会收到信号（§9.8）。
  - 原因：每次调用协程都建一个扩展类的对象，曾占 coroutines 用例约 22% 的时间。
  - 本语言等待任务不经引擎的信号，任务结束时直接通知等待方，再发出 `completed`。
  - 未结束的任务按所属对象成表，释放对象只遍历它自己的任务。每帧回调只看所等对象已被释放的任务。
- `Task.of` 和 `Task.delay` 的任务不运行函数，只等一个信号（§9.5）。
  - 等待、取消和释放监听与其他协程共用，所以规则一致。
  - 信号源被释放时，同样推迟到每帧回调判定，再取消该任务。
  - `Task.delay` 就是 `SceneTree.create_timer` 的 `timeout`，暂停和时间缩放按引擎的默认值。
- `t.settled()`、`Task.any` 和 `Task.all` 的任务也不运行函数，只等所等任务结束（§9.2、§9.5）。
  - 它拥有为它启动的任务，自己结束时取消它；对已有的任务只停止等待。
  - 所等任务因所属对象释放而取消时，同样推迟到每帧回调判定。
  - `Settled` 与 `Result` 一样是没有脚本的带载荷 enum，`CancelReason` 是没有脚本的 enum。
- 等待 `GDScriptFunctionState` 时，运行时持有第一个状态直到 `completed` 发出，并监听接收者或 Callable 目标的释放和 `script_changed`（§9.8）。
  - 协程再次挂起后，内层状态只以 ObjectID 记住第一个状态，后者又已离开待处理列表（`modules/gdscript/gdscript_vm.cpp:2634-2639`，`modules/gdscript/gdscript_function.cpp:329-330`）。
  - 实例析构时引擎不发出 `completed`（`modules/gdscript/gdscript.cpp:2069-2079`，`gdscript_function.cpp:343-362`），状态也不暴露所属实例（`gdscript_function.cpp:288-307, 337, 364-370`，`modules/gdscript/register_types.cpp:140`，`object.cpp:995`）。
- 程序错误沿本语言的调用栈展开，释放局部变量，回到引擎的调用入口。入口返回该类型的默认值（§8.1）。
- 对本语言类的方法的调用不经过引擎（§8.1）。虚拟机找到实例或类的当前镜像，按名字找到方法并核对签名，再按槽位的原生布局传参。一次运行中的脚本总是一起编译（§12.4）。签名不同只出自不是一起构建的字节码，这时调用是程序错误。
- 函数类型的 `f.call(x)` 中，`f` 是本语言的 lambda 或方法值时同样直接调用。其他 Callable、`async` 函数和签名不同的方法值经引擎调用。
  - lambda 的捕获值依次存在 lambda 对象内，放得下时不另行分配。
  - 直接调用不复制 lambda 的镜像和上下文，因为调用方的寄存器在调用期间持有它。
- 无类型 `Callable` 的 `call()` 遇到本语言的 lambda 或方法值时，也按槽位直接调用。它按引擎入口处理，被调用者出错后调用方得到默认值继续（规范 §8.1）。
- 其他实例的成员同样不经过引擎读写：
  - 虚拟机按名字在其当前镜像中找到成员，核对类型，直接读写槽位；
  - 有访问器的成员经 `CALL_METHOD` 调用该对象的访问器；
  - 所以不是 `pub` 的成员可以按规范 §4.2 访问，装箱的容器也不必经反射暴露（§10.5）。
- 有 MethodBind 的引擎方法经它的 ptrcall 调用，`$Path` 也是。这与 GDScript 调用已知类的方法相同，不经过脚本实例（`modules/gdscript/gdscript_vm.cpp:2273-2313`）。
  - 参数和结果按槽位的原生布局传指针，对象传它的指针。
  - 编辑器按引擎的算法，从 ClassDB 的方法信息算出 hash，写进字节码（`core/object/method_info.cpp:87-116`）。
  - 类加载时按 hash 取得 MethodBind。算法与引擎不一致时，加载即失败。
  - 调用可省略的参数，默认值按引擎 `var_to_str` 的文本记下，加载时转成原生值。
  - `free()` 没有 MethodBind，可变参数的方法不支持 ptrcall。它们和其他语言的类的方法仍按名字、以 Variant 调用。
- 引擎属性的读写是对它的 getter 和 setter 的调用，同样经 ptrcall（规范 §10.5）。
  - 带下标的属性先传下标。ClassDB 不向脚本提供下标（`core/object/class_db.h:478`），构建时从 godot-cpp 的 `extension_api` 取得。
  - 其他扩展的这类属性、其他语言的类的属性和接口的属性，仍按名字读写。
- 内置类型的方法同样以 ptrcall 调用。
  - 有的方法签名固定，结果不是 Variant，也不处理元素和键。这样的调用只做只读检查，参数直接取槽位。
  - 其余方法经通用的调用，由它检查元素、键和结果（规范 §3.8）。
  - 可变参数的方法，如 `emit()` 和 `bind()`，经 Variant 按名字调用，与 GDScript 相同（`modules/gdscript/gdscript_byte_codegen.cpp:1191-1192`）。
  - 它们的 ptrcall 每次在堆上复制参数（`core/variant/variant_call.cpp:561-578`）。
- Array 元素的读、写和 `for` 的每次迭代都只调用引擎一次。
  - 读取越界时，引擎给出空指针而不报错（`core/extension/gdextension_interface.cpp:1289-1295`）。
  - 标量的类型化 Array 中，元素都是该类型的 Variant，不持有资源。引擎的写入检查保证这一点（`core/variant/variant.h:268-272`）。
  - 所以写入只替换元素的数据，不经 `Array::set` 的复制和检查（`core/variant/array.cpp:517-523`）。
  - Packed 数组的元素经引擎的指针 getter 和 setter，按元素槽位的布局读写（`core/variant/variant_setget.cpp:348-354, 421-428`）。
- `for` 的每次迭代是一条 ITERATE 和一条 JUMP，与 GDScript 相同（`modules/gdscript/gdscript_vm.cpp:3471-3492, 3661-3681`）。计数的 `for` 用 ITERATE_INT。
- 遍历对象的 `for` 由检查器写成对 `_iter_*` 的三个普通调用，本语言的类因此直接调用（§8.1）。
  - 调用的对象、Array 和状态放在没有名字的局部变量中，调试器不显示它们。
  - 每次调用 `_iter_init` 或 `_iter_next` 前新建单元素 Array，调用后由 ITER_STATE 核对长度并取回状态（规范 §5.7）。
- 从引擎进入的调用做入口检查（§10.1）。
- 虚拟机可以在任意线程上运行，不使用没有锁保护的全局可变状态（§12.3）。
- 运行时直接用 godot-cpp 的类型，它们对应引擎内部的同名类型。改为引擎模块时，运行时换用引擎的头文件，adapter 重写，编译器和字节码原样使用（§2.1、§2.3）。
- 第一版只用 switch 分派，各平台只有一条代码路径要测试。本语言的优势在按类型存放的寄存器，不在分派（GDScript 在 GCC、Clang 上用 computed goto，`modules/gdscript/gdscript_vm.cpp:254-450`）。每条指令的处理只写一次，以后可从同一份定义生成 computed goto 或尾调用分派。是否加入由 §4 的基准决定。switch 分派始终保留，因为并非所有工具链都保证尾调用（如 MSVC 的 debug 构建）。
- 原生代码由一个多后端的代码生成模块按函数生成，运行时生成和事先生成共用它。生成时机暂不决定（§7）。CPython 的 JIT 因维护、评估和调试支持说不清而将被移除（[PEP 836](https://peps.python.org/pep-0836/)）。所以本语言的原生代码从一开始就要支持调试器、程序错误的位置和性能剖析。动手之前先定好基准和目标。

### 2.3 adapter

- 实现 ScriptLanguageExtension、ScriptExtension 和 ScriptInstanceExtension，把实例的属性读写、方法调用和通知转给 runtime。
- Script 类绑定 `new`，并把 `pub` 的 `_init` 报告为返回该类的静态方法，供 GDScript 检查 `Player.new(...)`（`modules/gdscript/gdscript.cpp:1078`，`modules/gdscript/gdscript_analyzer.cpp:5958-5961`）。不带 `pub` 的 `_init` 不报告，GDScript 视其为无参构造（`:6005-6031`，规范 §10.1）。
- `Class.new` 作为值是名为 `new` 的静态函数值（规范 §3.11）。它与 Script 的 `new` 共用构造，但不查 `_init` 的可见性。可见性由检查器在取值处检查（§4.2）。
- async 方法在反射中报告为无类型的 Variant（`PROPERTY_USAGE_NIL_IS_VARIANT`，§9.8）。反射没有协程标记（`core/object/method_info.h:37-44`），而报告为 T 有两个问题：
  - GDScript 会给出多余 await 的警告（`gdscript_analyzer.cpp:3102-3107`）；
  - 取消时的 `completed(null)` 不经检查写进 T 类型的临时变量，Transform3D 等值类型因此崩溃（`modules/gdscript/gdscript_vm.cpp:2667-2668`，`modules/gdscript/gdscript_byte_codegen.cpp:998-1001`）。
- `.pet` 源码和字节码文件的加载与保存。
- 内部类的脚本（规范 §4.1）没有资源路径，由所在文件的脚本持有并一并取得镜像。运行时以文件路径后接 `::` 和各级名字指称它。
- 导出插件用字节码替换 `.pet`，经 `add_file(..., true)` 生成重映射，与 GDScript 换成 `.gdc` 时一样（`modules/gdscript/register_types.cpp:99-116`）。
  - 它还检查导出的每个场景，有错误时报告导出失败。
- 编辑器插件提供：
  - 分析服务（§13.1）和场景编辑器中的错误标记；
  - 运行前的编译；
  - 右键菜单中的格式化（§13.2）。它作为一步撤销只改动空白，断点和书签因此留在原来的行上。改动超出撤销栈的容量时，它替换全文，这些标记随之丢失。改动脚本编辑器中文本的功能都经同一个函数应用编辑；
  - 脚本编辑器中的语法高亮。它按词法分析的 token 着色，颜色取 GDScript 高亮器所读的编辑器设置。引擎的标准高亮器不对扩展开放（`editor/register_editor_types.cpp:175`）。
- 带场景部分的重命名（§13.3）读取工作区（§2.1），所以预览准确，取消不留下改动：
  - 有未保存修改的场景经 `PackedScene.pack()` 得到 SceneState，与磁盘上的场景经同一接口读取（`editor/editor_node.cpp:2505`）；
  - 文本定位器读这样的场景时，引擎按文本格式把它写到 `.godot/` 下的临时文件。文件按绝对路径写，编辑器不当它是项目的文件，也不给它 uid（`core/io/resource_saver.cpp:146-147`，`editor/file_system/editor_file_system.cpp:3672-3676`）；
- 改动涉及场景或资源文件，或者有候选时，先在引用面板中按文件预览，与 JetBrains 的 IDE 相同。每处带复选框：确定的引用勾选且不能取消，候选起初不勾选。
- 已打开、还没有文件的场景中有节点用到声明成员的脚本或其子类时，拒绝给成员改名，提示先保存这个场景。它不在工作区中，其中按名字存的值改不到。
- 应用的顺序：
  - 保存有未保存修改、显示所改场景中节点的已打开场景，即所改的场景和实例化或继承它们的场景。编辑器只保存当前场景，所以先切换到它（`editor/editor_interface.cpp:699-704, 775-777`）；
  - 保存后按位置切回原来的标签页，所以没有路径的场景也能切回。标签页就是按顺序排列的已打开场景（`editor/scene/editor_scene_tabs.cpp:263-292`，`editor/editor_node.cpp:8847`）；
  - 每切换一次标签页，余下的步骤就延后执行。显示场景时，场景面板延后的调用持有面板中的项，同一帧再切换或重载会释放它们，编辑器随即崩溃（`editor/editor_node.cpp:4651-4675`，`editor/scene/scene_tree_editor.cpp:995-1004, 1131-1140`）；
  - 按保存后的状态重新计算。结果与预览不同时，刷新预览，不应用；
  - 核对每个文件的现有文本。有一处对不上，就什么都不改；
  - 场景和资源文件按字节写入，保留换行。有一个写不成时，已写的写回原来的字节，什么都不改；
  - 编辑器默认安全保存，写不成要到关闭文件时才发生，所以写后读回比对（`drivers/windows/file_access_windows.cpp:197-216, 245-277`）；
  - 然后改脚本的文本，见下一条；
  - 都写完后，已加载的所改脚本先换上工作区中的新文本，在一次分析中重载，文件不写，见下一条；
  - 然后通知编辑器的文件系统。已加载的资源重新读取，与编辑器发现文件变化时相同（`editor/editor_node.cpp:1291-1323`）；
  - 顺序不能反。按旧的脚本读回时，按新名字存的值被丢弃。Ctrl+S 先存资源，后存重构留下的文本，于是把值写掉（`editor/editor_node.cpp:2518-2526`）；
  - 已加载的场景也重新读取。显示一个场景的标签页时，编辑器若发现其中实例化或继承的文件变了，就从已加载的场景重建它（`editor/editor_data.cpp:722-771`，`scene/resources/packed_scene.cpp:848`）；
  - 重新读取就地改动已加载场景的状态。显示它的已打开场景正按这个状态比较自己的改动，所以都重载（`core/io/resource.cpp:234`，`scene/resources/packed_scene.cpp:2477, 2610`）。有未保存改动的不重载，重载会丢掉这些改动；
  - 最后查找新名字的引用。它与所改之处不符时，给出警告。
- 重构对脚本的改动留在文本中，等用户保存，与编辑器自己的未保存标签页相同。重命名和改动其他脚本的快速修复都是这样：
  - 打开的脚本经同一个函数在标签页中改动。这是标签页的一步撤销，原有的历史保留；
  - 改动使标签页的文本回到文件的内容时，如撤销之后，标签页标为已保存；
  - 没打开的脚本，改后的文本存在工作区中，没有标签页。与文件相同的文本不存；
  - 已加载的这样的脚本随即换上这段文本，与标签页的脚本取通过检查的文本相同；
  - 这段文本记下它所依据的文本：文件的，或客户端打开着时客户端的。保存、标签页换上和推给客户端之前，先比较它；
  - 依据的文本变了时，如文件在别处改过、客户端恢复了未保存的改动，丢弃这段文本，并提示文件名。否则写入或推送会抹掉那些改动；
  - 这样的脚本打开时，标签页换上这段文本，标为未保存，没有可撤销的内容；
  - 插件在 `editor_script_changed` 中换上文本。打开时它先于标签页的第一次检查发出（`editor/script/script_editor_plugin.cpp:399-410, 2305`）；
  - 插件经 `_get_unsaved_status` 报告这些脚本，经 `_save_external_data` 保存。脚本编辑器也这样报告和保存它的标签页（`editor/script/script_editor_plugin.cpp:4332-4378`）；
  - 于是保存场景时和运行前都保存它们。当前场景没有根节点时按保存，也保存它们（`editor/editor_node.cpp:2415-2420, 3488-3495, 2526, 2603`）；
  - 退出时编辑器列出它们，问是否保存（`editor/editor_node.cpp:3730-3733, 3793-3806`）；
  - 【已知限制】脚本编辑器的"全部保存"只保存标签页，不保存它们（`editor/script/script_editor_plugin.cpp:2449-2502`）；
  - 问到某个场景时，插件不报告它们。它们不属于场景，报告的话编辑器会把场景的标签页也标为未保存（`editor/editor_node.cpp:2657-2677`）；
  - 保存时按字节写入，保留字节顺序标记和换行。文件已不在的，丢弃它的文本；
  - 已加载的脚本先都换上新文本，再在一次分析中重载。每个脚本于是按其他脚本的新文本只编译一次；
  - 退出时选择不保存，这些文本随之丢弃，与脚本编辑器的标签页相同。已写入的场景这时按新名字存值，与脚本不符；
  - 编辑器离开场景树时，不论用户怎样选择，都再让每个插件保存一次（`editor/editor_node.cpp:969-991`）。脚本编辑器这时不保存标签页，插件也不保存这些文本（`editor/script/script_editor_plugin.cpp:4375-4378`）；
  - 插件是编辑器的子节点，先离开场景树，由此得知编辑器在退出（`editor/editor_node.cpp:4365-4370`，`scene/main/node.cpp:421-427`）；
  - 所以退出时编辑器只问是否保存资源或场景、不问插件时，这些文本与脚本编辑器的标签页一起丢弃。各脚本之间在磁盘上保持一致：改名在脚本中的部分全都留在旧名（`editor/editor_node.cpp:3778-3790, 3845`）；
  - 【已知限制】已写入的场景和资源文件仍按新名字存值，与脚本不符，见上。加载时这些值被悄悄丢弃（§6.4）；
  - 构建、导出和运行中的游戏读磁盘（§2.1），与编辑器自己的未保存标签页相同。
- 所有改动都在一个打开的脚本中时，它们是该脚本的一步撤销，如局部变量和只在本文件用到的私有成员。否则重构是全局历史中的一步：
  - 重命名撤销时按当时的文本把名字改回。它按声明的 id 找到声明，所以改名之后的编辑保留。旧名已被占用时拒绝撤销；
  - 前一步改过的候选，按它们改后的位置找到。位置变了时拒绝撤销；
  - 声明已是目标名字时，视为已经完成。经菜单撤销被拒时，全局历史已经退了一步，之后的重做由此与文本重新一致；
  - 撤销和重做也只改文本，不写脚本文件；
  - 重载清空受影响场景的历史，与引擎给文件改名相同（`editor/editor_node.cpp:7151`）。编辑器重建显示所改场景的场景时，也清空它的历史（`editor/editor_node.cpp:4747-4753`）；
  - 它在编辑器的撤销或重做返回后才运行。重载场景会清空该场景的历史，编辑器随即检查各历史，而撤销进行中全局历史只改了一半（`core/object/undo_redo.cpp:432-434`，`editor/editor_undo_redo_manager.cpp:321-325, 402-407`）；
  - 这一步不把全局历史标为未保存，未保存的是它改过的文件。否则退出时编辑器只问是否保存资源，不再问插件（`editor/editor_node.cpp:3778-3790, 3845`）。
- 在脚本中按撤销键，撤销改过它的重构。条件是脚本已无可撤销的内容，或它的最后一步就是这次重构的改动。按重做键时，条件是脚本已无可重做的内容：
  - 插件在 `_input` 中先于代码编辑器收到 `ui_undo` 和 `ui_redo`（`scene/main/viewport.cpp:3537`，`scene/gui/text_edit.cpp:2737-2746`）；
  - 插件先按当时的文本试算一遍。会被拒绝时，吞掉按键并提示，各历史都不动；
  - 它经主菜单的撤销项撤销，编辑器的各历史因此保持一致。主菜单收起成一个按钮时不接管；
  - 编辑器按时间在全局和当前场景的历史中选一步撤销（`editor/editor_undo_redo_manager.cpp:136, 340-367, 509-538`）。重命名之后别的历史有过步骤时，选哪一步不确定，所以不接管；
  - 【已知限制】经脚本编辑器的"编辑"菜单撤销时，插件不接管。这只撤掉这个脚本中的改动，场景中按新名存的值与它不符（`editor/script/script_editor_base.cpp:385-387`）。
- 在场景编辑器中给节点改名或移动节点时，脚本中的字面量路径随之改写（规范 §13.3）。改动并入编辑器刚提交的动作：
  - 插件按对象 id 记下当前场景所拥有节点的路径。切换场景、撤销、重做和处理完一次改名之后，它重记一遍；
  - 提交动作期间改名或重新入树的节点及其子孙，路径有变的才算移动。所以撤销、重做和 `@tool` 代码在动作之外的改名都不算（`scene/main/node.cpp:366, 1472`，`editor/editor_undo_redo_manager.cpp:252-260, 298`）；
  - 把节点设为场景根时，其余节点都随之移动，所以也算。场景的根换了，但新根原是场景中的节点（`editor/docks/scene_tree_dock.cpp:1111-1135`）；
  - 删除和剪切只移走节点，不移动别的节点，所以不改写。粘贴的是复制出的新节点，也不算移动（`editor/docks/scene_tree_dock.cpp:709-769, 2887-2983`）；
  - 在提交后发出的 `history_changed` 中，以场景根为上下文，创建同名、`MERGE_ALL` 的动作；
  - 不能在动作执行中追加操作：移动节点时动作内不发出信号，提交时又先退出动作再执行；
  - 合并要求离编辑器创建动作不到 800 毫秒，所以插件先提交，改写推迟到之后计算（`core/object/undo_redo.cpp:97`）；
  - 多选改名和批量改名的动作带 `backward_undo_ops`，合并不成。这时改写是同一场景历史中紧随其后的一步（`editor/scene/scene_tree_editor.cpp:1678`，`editor/scene/rename_dialog.cpp:601`）；
  - 这个动作的执行和撤销调用插件的同一方法，分别带上新旧路径的对应和它的反向。它在编辑器的撤销或重做返回后，按当时的文本重算，与重命名相同；
  - 改名前的场景由当前的场景按反向的对应还原；
  - 这一步可能连同移动加入或去掉父节点，如 Reparent to New Node 及其撤销。还原的场景缺这样的父节点时，补上一个 Node，路径才走得通（`editor/docks/scene_tree_dock.cpp:3223-3274`）；
  - 继承它的场景按基场景存盘的结构读取，可能是改名前的样子，也可能是改名后的。对它也按两个方向改写路径，不论原是哪样，都得到前后两样；
  - 根换了时，每个继承的场景都有根，分不出它是哪一样，所以不改写它上面的脚本；
  - 【已知限制】所以基场景改名后、保存之前，继承场景上改写过的路径在检查中报找不到节点。连续改名而不保存时，第二次起不再改写这些脚本；
  - 改名前的检查覆盖所有脚本，与重命名相同。没有读到这些场景的脚本沿用已有的结果；
  - 路径从起点的新位置重算到目标的新位置，与编辑器改写 NodePath 属性相同（`editor/docks/scene_tree_dock.cpp:2077-2120`）；
  - 含 `%Name` 的路径保留到最后一个 `%Name` 为止的部分，从那个节点重算。那个节点改名时，`%Name` 换成新名；
  - 删除节点不改写脚本，到它的路径报编译错误；
  - 改写后在移动后的场景中再检查一遍。在某个放置脚本的场景中，路径会指向别的节点或不再指向节点时，它不改写，只列在输出面板中；
  - 非字面量的 `get_node()` 中，字符串以整段写出改名或移动的节点名时，也只列出；
  - 改动留在脚本的文本中，与重构相同。输出面板每处一行，写明文件、行、旧路径和新路径；
  - 【已知限制】在脚本标签页中按撤销键，只撤销该脚本中的改写，场景的历史不动。之后在场景中撤销这一步时，按当时的文本重算，两边仍会一致。
- 无界面命令：
  - `--petrichor-build` 运行同一套分析，并检查每个场景。警告和提示只打印（§13.1）；
  - `--petrichor-format` 格式化项目的脚本（§13.2），加 `--check` 时只列出未格式化的。有这样的脚本或语法错误时以非零退出。

### 2.4 编辑、运行、导出和热重载

- 分析服务在编辑器进程中持有整个项目的编译结果，诊断显示在脚本编辑器和场景编辑器中。
- 编辑器中本语言脚本的实例是自己的占位实例（`src/adapter/pet_placeholder.h`）。它像引擎的占位实例一样保存导出的属性，脚本有错时保留场景设的值（`core/object/script_language.cpp:680-923`）。它还回答 `_get_configuration_warnings`，场景面板由此把错误标在节点上；引擎的占位实例不回答任何调用（`scene/main/node.cpp:3522-3532`，`editor/scene/scene_tree_editor.cpp:493-519`，`core/object/script_language.cpp:793-804`）。
- 脚本有错时，默认值和信号取它上次编译成功时的声明，与 GDScript 相同（`modules/gdscript/gdscript.cpp:546-548, 575-578`）。否则保存场景时，未存的导出写成 null，连到它的信号的连接被丢掉。
- 场景用错脚本的诊断记下场景和节点，信号连接的错误记在连接的目标上。动画轨道和同步属性的错误记在它们所指的节点上。节点的位置是它所属场景中的路径，实例化的场景根记为 `.`。
- 节点上的错误取自它的脚本的检查，和它所在各场景的检查。
  - 这些场景沿 owner 链向上找：实例化的场景的根拥有它的节点，外层场景的根又拥有这个根（`scene/resources/packed_scene.cpp:567-573`）。
  - 在每个场景中，节点的位置是从该场景的根到它的路径。
- 脚本编辑器列出挂载脚本的场景报在脚本中的错误，但仍判脚本有效，照常应用它的源码（`editor/script/script_text_editor.cpp:841-886`）。
- 节点上的错误和脚本编辑器列出的场景的错误都读工作区（§2.1）。所以行号按未保存的文本算，节点上的错误也取脚本的缓冲区。
- 只有看得见的结果主动重算：节点上的错误，和当前显示的本语言标签页。其余在使用时按需重算。
  - 场景的编辑、撤销和重做停下后，打包未保存的场景，再重算这两者（`editor/editor_node.cpp:8406-8409`）。
  - 一次重算要重新检查该场景放置的脚本，远长于一帧。所以编辑停下 `text_editor/completion/idle_parse_delay` 秒后才重算，与脚本编辑器检查脚本前所等的相同（`editor/gui/code_editor.cpp:1014, 1166, 1696-1699`）。
  - 标签页检查过脚本后，节点重新取错误。
  - 磁盘上的变化（§2.1）之后也重算这两者。分析只重新检查输入变了的脚本。
  - 每个 revision 只重算一次。
  - 隐藏的标签页不检查。每个标签页记下上次检查时的 revision。
  - 切换标签页时，编辑器自己重新检查新显示的那个（`editor/script/script_editor_plugin.cpp:410`，`editor/gui/code_editor.cpp:1701-1702`）。
  - 回到脚本画面时，引擎不检查标签页（`editor/script/script_editor_plugin.cpp:4318-4325`）。所以脚本编辑器重新显示时，当前标签页上次检查后工作区改过，就重新检查。
- 编辑器加载脚本时只编译声明，足以提供反射信息，但不能运行。
  - 这时不能加载用到这个脚本的场景，引擎会当作循环加载拒绝（`core/io/resource_loader.cpp:1049-1056`）。
  - 所以完整编译在加载之外进行：编辑时的检查、保存、运行前的构建和导出。
  - 只编译声明时不读场景，由场景定型的成员（如 `@onready var camera = $Head/Camera`）这时是 Variant。
  - 脚本编辑器检查通过后，把标签页的文本交给脚本，再要它的导出（`editor/script/script_text_editor.cpp:874-878`）。这段文本没编译过时，也只编译声明，占位实例于是在保存前就有新的导出，与 GDScript 相同。这不写文件，运行中的游戏不重载。
  - 支持 tool 脚本时，它们在加载后补一次完整编译。
- 跳转到定义和悬停经 `_lookup_code`，按光标处的引用表条目（§2.1）：
  - 本语言的声明跳到所在的行，按工作区中的文本算；局部变量和参数悬停显示类型；
  - 引擎的声明打开它的文档页，GDScript 类的成员跳到声明它的行；
  - 各种声明悬停时显示自己的文档。
- 查找引用由编译器的 `find_references`（`src/compiler/navigation.h`）完成，LSP 可以直接沿用。
  - 它在一次分析中编译每个本语言脚本，检查每个场景和资源文件，按声明反查引用表（§2.1）。未变的结果照常沿用。
  - 它读取工作区，与重命名相同（§2.3）。所以它列出的就是重命名预览的改动。
  - 引用面板记下查找时的 revision。点击的那一处所在的文件之后改过时，先重新查找，再跳转。
  - 重新查找从声明开始，按 id 找到它，与撤销重命名相同。跳转到同一文件中次序相同的那一处。
  - 重新查找推迟到选中之后。Tree 在遍历条目的过程中发出 `item_selected`，这时重填面板会释放它正在遍历的条目（`scene/gui/tree.cpp:3006-3074`）。
  - 找不到声明时，清空面板，提示项目已变。局部变量的 id 含声明的偏移，所以声明之前改过就找不到。
  - 一个声明与经覆盖或实现相连的本语言声明一起查找，因为重命名要一起改它们。连接不经过引擎的声明，它们不能改名。
  - 候选是可能指向它、却解析不到它的名字。检查器把目标为 `Object` 或 `Variant` 的字面量名字记为未解析的引用，候选取其中同名的。`.gd` 和 `.cs` 文件按文本取整词相同的名字。
  - 所查的本语言声明能被引擎按名找到时，才列出候选（规范 §10.5）。局部变量和不带 `pub` 的成员没有候选。
- 重命名由编译器的 `rename`（`src/compiler/rename.h`）算出，编辑器只负责预览、应用和撤销。
  - 它改查找引用列出的每一处，给出字节区间、现有文本和新文本。应用时先核对现有文本。
  - 按名字匹配字段的模式中，`var x` 是 `x = var x` 的简写（规范 §5.6）。这个名字既指字段，也声明局部变量。只改其中一个时，写成完整的形式，如 `amount = var damage`。
  - 新名字须是一个标识符 token，所以关键字不行。
  - 冲突交给检查器判断，不另写一套冲突规则。改后的源码在一遍单独的分析中重新检查，读取项目时换上这些源码。
  - 改后多出错误，或某处名字改指另一个声明，就拒绝。后者如同名的局部变量遮蔽了成员。
  - 【已知限制】新名字原有的按名用法改后可能开始指向这个声明，如 GDScript 中的 `o.has_method("take_damage")`。接收者为 `Object` 或 `Variant` 的字面量名字、`.gd` 和 `.cs` 文件以及场景中的这类用法都不检查。成熟的重命名都只按旧名找动态用法，Roslyn 还有意不报改前解析不到、改后解析到的引用（`src/Workspaces/Core/Portable/Rename/ConflictEngine/ConflictResolver.Session.cs:546-550`，roslyn `644d001`）。
  - 改前的结果取自查找引用那一遍。
  - 改后与改前是同一个缓存结果的脚本不再比较，因为它读过的都没变。
  - 改局部变量时只检查所在的脚本。
  - 这一遍的结果照常留存。应用后它们就是新的结果；取消时，下一遍按读取的记录重新检查。
  - 覆盖引擎或其他语言的方法的声明不能改名，因为调用方按原名调用。
  - 场景和资源文件中的名字由文本定位器找到（§6.4）。
- 代码编辑器的上下文菜单插件，其快捷键只在菜单打开时起作用（`editor/inspector/editor_context_menu_plugin.cpp:155-176`，`editor/script/script_editor_plugin.cpp:3111`，`ed1daf0`）。所以查找引用的快捷键由编辑器插件的 `_shortcut_input` 接收。
- 重命名的快捷键 F2 也由它接收，但只在焦点位于当前代码编辑器时。场景面板和文件系统面板也用 F2 改名，它们只在自己有焦点时接收（`editor/docks/scene_tree_dock.cpp:181-184`，`editor/docks/filesystem_dock.cpp:2780, 3885`）。
- 打开改名框之前，编辑器先做不依赖新名字的检查，即编译器的 `renamed_name`。`rename` 也先做这些检查。
  - 光标处没有名字、名字指节点或引擎的声明、声明覆盖引擎或其他语言的方法时，提示原因，不打开改名框。
  - 否则改名框中填入这个名字。
- 快速修复（规范 §13.2）取自脚本编辑器刚做的检查，即分析缓存的结果。
  - 本语言脚本的标签页有一列自己的边栏，在折叠边栏右侧，紧挨文本。光标所在行有带修复的错误时，其中画一个灯泡。
  - 工作区在检查后改动时，灯泡隐去，其他标签页的改动也算。打开列表时先重新检查。
  - 点灯泡、按 Alt+Enter 或选右键菜单的 Quick Fix 打开列表。Ctrl+. 已是转到下一个断点（`editor/script/script_text_editor.cpp:2672`）。
  - 列表列出光标所在行各错误的修复：先是包含光标的错误，其余按位置。相同的修复只列一次。
  - 分隔线后，这些修复中的每个自动种类各有一项，修复本脚本中这一种的全部，如 `Fix all 'Write the truth test' in file`。
  - 本脚本自己的检查中，这一种只改本脚本的修复有两个以上时，才列出这一项。
  - 场景的检查报在脚本中的错误，只提供只改本脚本的修复。
  - 列表带戳（§2.1），其中有修复所改的各个文件。
  - 戳未变时，单个修复在列出它的检查中按错误和标题找回。
  - 戳变了，就单独检查一遍，不用缓存。其他脚本的声明不变时，分析沿用结果，其中别的文件的偏移却可能已经移动。
  - 找不到修复就不应用，提示项目已变，并刷新灯泡。
  - 修复一种的全部，由同一次检查经 `compiler::fix_all()` 得出编辑。
  - 只改本脚本的修复，以及修复一种的全部，是本脚本的一步撤销。
  - 保存时不做修复。
- 改动其他脚本的修复，如补上 `pub`，保持当前标签页。
  - 应用前按工作区中目标脚本的文本核对原文，不符就拒绝。
  - 改动留在文本中，与重命名相同（§2.3）。
  - 它是全局历史中的一步。撤销和重做按当时的文本应用核对过的编辑。编辑已经在文本中时，视为已经完成。
  - 应用后当前标签页立即重新检查。插件发出代码编辑器的 `validate_script` 信号，标签页的检查连在它上面（`editor/gui/code_editor.cpp:1696-1699`，`editor/script/script_editor_base.cpp:653`）。
- 本语言的类经 `_get_documentation` 提供文档，取自声明的检查，命名同 GDScript，类型按本语言的写法（`modules/gdscript/editor/gdscript_docgen.cpp:40-46, 339-347, 594-598`）。
  - 文档也列出没有 pub 的成员，因为悬停与帮助页共用文档，而类里悬停的多是自己的成员。
  - `##` 注释（规范 §2.2）按 GDScript 的读法成为说明（`modules/gdscript/gdscript_parser.cpp:3938-4243`）；局部变量的注释在悬停时显示。
- LSP 服务器在编辑器进程中，与编辑器共用分析和工作区（§2.1）。
  - 成熟的服务器由客户端启动，经 stdio 通信。本语言的检查要用运行中的 ClassDB 和场景，所以不这样做。
  - 扩展不另启无界面编辑器。Windows 上同一项目的第二个编辑器进程加载不了扩展（`core/extension/gdextension_library_loader.cpp:196`，`platform/windows/os_windows.cpp:488-504`）。
  - 无界面编辑器只在 `--petrichor-lsp` 下开服务器。所以构建、测试和 godot-tools 启动的无界面编辑器都不开。
- 连接：
  - 编辑器插件只监听 127.0.0.1，端口由系统分配。端口和进程号写进 `.godot/petrichor/lsp.json`。
  - 扩展按项目根读这个文件，同时打开的几个项目各连自己的编辑器。GDScript 用固定端口，第二个编辑器绑不上（`modules/gdscript/language_server/gdscript_language_server.cpp:95-99`）。
  - 不用 6005 和 6008。godot-tools 连这两个端口，会把它当作 GDScript 的服务器。
  - 主线程每帧轮询，分析也在主线程，与编辑器的检查相同。
  - 编辑器失焦时每帧睡 100 毫秒，请求因此最多多等这么久（`editor/editor_node.cpp:1064-1073`）。GDScript 的服务器亦然。
  - 服务器在 `src/adapter/editor/lsp_server.cpp`，由编辑器插件在 `process_frame` 中轮询。有界面的编辑器总是开服务器。
  - 分析进行中不轮询，轮询也不重入。进度框会在调用中途跑一帧（`editor/gui/progress_dialog.cpp:148-154`）。
  - 一次只服务一个客户端。另一个连接等候一秒后，它的请求得到一个说明原因的错误，随后断开。
  - 等候是因为前一个客户端可能正在断开。它最后发来的内容读完，才看得出它已断开。
  - 客户端断开后，还没被告知拒绝的连接按先后补上。所以客户端断开后立即重连，照常连上。
  - 连接后 10 秒内没有发来 `initialize` 的，断开。客户端连上就发 `initialize`；这样不发的连接不会一直占着位置。
  - 消息头按行读取，只认名为 `Content-Length` 的行。
  - 消息头没有可用的 `Content-Length` 时，其后先是这条消息的正文，所以从下一个 `Content-Length` 起读下一条。
  - 消息体不是 UTF-8 的 JSON 时，回复 ParseError。通知的字段不合要求时，整条忽略。回复永远不回答，没有 id 的也是。
  - 正文中的 `\u0000` 换成 U+FFFD，两者在 UTF-16 中一样长。引擎的 String 每遇一个 NUL 打印一条错误（`core/string/ustring.cpp:202-206`）。
  - 不读取的客户端，待发的内容超过 128 MB 时断开。
  - 单条消息限 16 MB。超过的跳过它的正文，经 `window/showMessage` 告知。
- 文本：
  - 同步是增量的，编辑应用到全文。
  - 客户端打开一个文件后，工作区取它的文本，不再取 Godot 标签页的。这是 LSP 对 `didOpen` 的要求。Godot 的标签页仍检查自己的文本。
  - 客户端关闭文件后，工作区回到 Godot 的标签页或磁盘。客户端断开时，它打开的文件都这样交还。
  - 客户端的改动与编辑器自己的改动一样算数。工作区停止变化 `idle_parse_delay` 秒后，编辑器重新检查显示的标签页和节点上的错误，每个 revision 一次。客户端断开交还文件时立即检查。
  - 所以工作区中脚本的文本依次取客户端的、标签页的和重构留下的，都没有时读磁盘（`src/adapter/editor/scene_index.cpp`）。
  - 客户端打开重构留下文本的脚本时（§2.3），服务器经 `workspace/applyEdit` 把这段文本推给它。它在客户端也是未保存的改动，改名的两半保持一致。
  - 客户端已打开的脚本有了这样的文本时，也这样推送。推送带上文本所依据的文档版本，客户端此后改过就拒绝。
  - 客户端应用后，编辑器不再保留这段文本。客户端拒绝时，服务器经 `window/showMessage` 告知，文本仍留在编辑器中。
  - 客户端保存后，服务器通知工作区和编辑器的文件系统，再走编辑器保存脚本后的热重载。
  - 热重载即写入字节码，再经调试会话发出 `reload_scripts`。重构留下的文本保存时也这样。
  - 字节码按磁盘上的文件编译，与构建相同，不读客户端或标签页中未保存的依赖。游戏读的是磁盘，字节码应能由磁盘上的源码重现。
  - 条件与编辑器相同：脚本没有错误，且调试菜单中开着 Synchronize Script Changes（`editor/script/script_editor_plugin.cpp:776-801`，`editor/debugger/debugger_editor_plugin.cpp:238`）。
  - 客户端保存其他文件后，如场景和资源文件，服务器通知工作区，再让编辑器的文件系统扫描变化。`didChangeWatchedFiles` 也这样。
  - 这与编辑器重获焦点时的扫描相同：已加载的文件变了，就重新读取（`editor/editor_node.cpp:1049-1058, 1291-1323`，`editor/file_system/editor_file_system.cpp:1597-1607, 1018-1025`）。
  - 不只更新这一个文件。那样文件系统记下新的修改时间，之后的扫描就不再重新读取它。
  - 这时不动 Godot 的标签页。编辑器重获焦点时自己检查：没改过的重载，改过的询问（`editor/script/script_editor_plugin.cpp:803-850`）。
  - GDScript 的服务器在保存时直接换掉标签页的文本，其中未保存的改动丢失（`modules/gdscript/language_server/gdscript_text_document.cpp:95-124`，`editor/script/script_editor_plugin.cpp:2535-2588`）。
- LSP 按 UTF-16 码元计列，编译器按码点（§2.1）。服务器只接受项目根之下的文件。
  - 字节偏移与 LSP 位置只在 `utf16_positions()` 和 `utf16_offset()` 中换算（`src/compiler/lexer.h`）。行按 `\n`、`\r\n` 和 `\r` 断开，与 LSP 相同。
  - 只接受 `file:` URI。盘符的大小写和百分号编码按 Windows 上客户端的写法都认得。
  - 在 Windows 和 macOS 上，路径中与文件名只差大小写的名字，换成文件的名字。引擎会把另一种大小写当作另一个文件，并照样记下（`editor/file_system/editor_file_system.cpp:1964-1975, 2496-2503`）。
  - `.godot/` 之下的文件、项目外的文件和非 `.pet` 文件都不同步，也不回复错误。在 Windows 和 macOS 上，`.godot` 不分大小写。
  - 同一文件以两种 URI 打开时，两者共用一份文本，各自的改动都应用上去。诊断发给每一个，最后一个关闭时文件才交还。
  - 关闭磁盘上没有的文件时，分析也丢掉为它保留的结果。
- 诊断只发给客户端打开的文件，与编辑器只检查显示的标签页相同。
  - 刚打开的文件立即发送。其余在工作区停止变化 `idle_parse_delay` 秒后发送，与脚本编辑器检查前所等的相同。
  - 编辑器处理完一次变化时，如保存或场景的编辑停下，立即重发，不再等待。
  - 每帧至少发一个文件，其余在帧的预算内发送，剩下的下一帧接着发。所以打开的文件很多时，一次修改也不让编辑器停顿。
  - 每次发送带上所依据的文档版本。关闭文件时清空它的诊断。
  - 位置越界时夹到行尾或文末，与 LSP 的规定相同。
- 服务器提供诊断、补全、参数提示、悬停、定义、类型定义、引用、重命名、快速修复、格式化、大纲和同名高亮。
  - GDScript 的服务器没有类型定义、快速修复和格式化（`modules/gdscript/language_server/godot_lsp.h:1744-1798`）。
  - 场景中的位置给 `.tscn` 中的行，客户端以文本打开。二进制的 `.scn` 没有行，给文件开头。
  - 引用不列候选，因为 LSP 的位置没有候选的标记。
- 查询沿用编辑器的查询，请求时按工作区的文本计算。客户端没打开的文件也是这样。
  - 补全给出编辑器的列表，替换的文本也与编辑器相同（`scene/gui/code_edit.cpp:3837-3875, 3916-3927`）：
    - 在字符串中，从引号起替换，插入的文本加上同样的引号；
    - 否则替换光标前的词，`/` 算在词内。
  - 客户端支持片段时，以 `(` 结尾的插入成为片段，光标在括号内。GDScript 的服务器也这样（`modules/gdscript/language_server/gdscript_language_protocol.cpp:559-569`）。
  - 触发补全的字符与脚本编辑器的相同（`editor/gui/code_editor.cpp:2077`）。
  - 参数提示取补全的调用提示，标出光标所在的参数。
  - 悬停显示声明和 `##` 文档。声明有种类、类和成员，函数和信号带上签名，变量和常量带上类型。
  - 签名与调用提示的写法相同，函数前写出 `static` 和 `async`。引擎的成员也是这样，因为扩展读不到引擎的类文档。
  - 跳转到定义时，本语言的声明跳到名字，引擎的声明不跳。
  - 节点路径如 `$Head/Camera` 跳到各文本场景中该节点的 `[node]` 行。
  - 类型定义和大纲是编译器的查询，在 `src/compiler/navigation.h` 中，与 `lookup` 并列。
  - 类型定义取光标处名字或表达式的类型，来自检查过的语法树。T? 和容器中的类型也算，与 rust-analyzer 相同。
  - 同名高亮只查本文件的引用表。遮蔽的同名声明是另一个声明。
  - 场景和资源文件中的引用给出重命名改写的位置。重命名会拒绝时，给拒绝所在的行。
  - 有语法错误时，格式化回复错误，带上编辑器提示的原因。
- 快速修复按编辑器灯泡的列表给出。自动的修复标为首选，"修复本文件中这一种"排在后面。
  - 客户端支持时，列表不带编辑，选中一项时再经 `codeAction/resolve` 求出编辑。VS Code 应用编辑时不核对文档版本，过时的编辑会落到新文本中错开的位置。
  - 每项带上检查的戳和修复的标识：错误的区间、消息和标题，或者要修复的那一种。
  - 求编辑时与编辑器相同，按戳找回修复（§2.1）。戳变了就单独检查一遍，再按错误和标题找回。
  - 找不到时，这一项不带编辑，服务器经 `window/showMessage` 提示项目已变。
  - 编辑带上客户端的文档版本。客户端没打开的文件，版本为 null。
  - 修复改到客户端没打开的文件，而它在 Godot 中有未保存的内容时，拒绝这个修复。理由与重命名相同。
  - 拒绝的修复照常列出，标题后括注要先在 Godot 中保存的文件，不带编辑。选中它不改任何文件，服务器经 `window/showMessage` 说明原因。
  - 不标为不可用，因为 VS Code 的快速修复菜单不显示不可用的项，也不显示原因。
- 重命名：
  - `prepareRename` 做编辑器打开改名框之前的检查。可以改名时给出名字的区间和名字，否则回复错误，带上原因。
  - 改名由编译器的 `rename` 按工作区的文本算出，与编辑器相同。新名字不是标识符或与原名相同时，回答也与编辑器相同。
  - 脚本和场景的改动都作为文本编辑，放进同一个 `WorkspaceEdit`。客户端预览、写入和撤销，改名的两半一起撤回。
  - 编辑带上客户端的文档版本，与快速修复相同。场景和资源文件的版本为 null，位置按磁盘上的文本算。
  - 候选带上需要确认的修改注解，预览中起初不勾选。
  - 客户端不支持修改注解时，不给候选。否则候选与确定的引用无从区分，会一起改掉。
  - 拒绝时回复错误，每个原因一行，带上文件和行，与编辑器的引用面板相同。所改脚本自身的、没有行的原因不带位置，如新名字不是标识符。
  - 受影响的文件在 Godot 中有未保存的内容时，拒绝并提示先保存。服务器按工作区算位置，客户端却按磁盘上的文本应用。
  - 未保存的内容包括标签页、重构留下的文本和未保存的场景。错误中列出这些文件。
  - 服务器记下改名确定要改的文件和它们改前的字节。客户端写完这些文件后，编辑器按自己写完文件后的步骤读回（§2.3）：
    - 已加载的脚本先都换上新文本，在一次分析中重载。没有未保存改动的标签页也换上新文本，与编辑器重获焦点时相同（`editor/script/script_editor_plugin.cpp:2535-2588`）；
    - 然后重新读取已加载的资源和场景，重载显示它们的已打开场景。有未保存改动的场景不重载，重载会丢掉它们的改动。
  - 顺序不能反。资源和场景按已加载的脚本读回。脚本还是旧的时，按新名字存的值被丢弃，Godot 之后的保存就把它们写掉。
  - 等待期间，分析照常读磁盘。编辑器文件系统的扫描推迟到读回之后，因为扫描也会按旧的脚本重新读取资源和场景。
  - 客户端只写了一部分时，如关了自动保存、逐个保存，最后一次写入两秒后读回已写的文件。之后再写的文件按各自的保存处理。
  - VS Code 默认在多文件重构后保存全部文件，编辑器中的重构则留在文本中（§2.3）。两者各按各的编辑器。
  - 【已知限制】在 VS Code 中撤销重命名后，改过的文件留着未保存的改动。VS Code 应用重构后保存（`files.refactoring.autoSave`），撤销后却不保存。保存之前，Godot 和磁盘上仍是改名后的文件。
- VS Code 扩展在 `editors/vscode/` 中，是不经构建的 JavaScript，经 `vscode-languageclient` 连接：
  - 语言 id 为 `petrichor`，扩展名为 `.pet`。TextMate 语法按本语言的词法 token 另写。类型只按位置着色，不按大小写猜。
  - 每个项目一个客户端，文档选择器只含项目根之下的 `.pet`。
  - 项目根取工作区中的每个 `project.godot`，以及打开的脚本之上最近的一个。后者包括工作区外的脚本。
  - 【已知限制】嵌套在另一个项目中的项目，其脚本也由外层的客户端同步。Godot 跳过嵌套的项目（`editor/file_system/editor_file_system.cpp:3494-3499`）。
  - 它读 `lsp.json`，经 socket 连接。其中的进程已不在时不连，因为编辑器被杀掉时文件留下。
  - 连不上时每 3 秒重试，`lsp.json` 写出时立即重试。
  - 服务器拒绝时提示一次，之后每 10 秒重试。
  - 服务器在对 `initialize` 的回复中拒绝，随即断开。库先处理断开，丢掉这条回复，所以扩展自己读连接上的第一条消息。
  - 断开后新建客户端，不用库的重启。服务器分不出重连的客户端是否是原来的那个，godot-tools 也这样做。
  - 库默认在 3 分钟内断开 5 次后放弃，所以换掉它的错误处理。
  - 连接的问题只在状态栏中显示，库不为它弹出错误。状态栏只在本项目的脚本显示时出现。
  - 它监视项目中的 `.pet`、`.gd`、场景、资源和 `project.godot`，变化经 `didChangeWatchedFiles` 告知服务器。
  - 重命名后保存的场景和资源文件也由此得知。`.gd` 也监视，因为在 VS Code 中保存的 GDScript 会改变本语言看到的类。
  - `.vsix` 附在 GitHub 的 release 上，版本在打包时给出，与插件包相同。
  - 上架扩展市场和 Open VSX 在 0.9（§5 第 12 步）。此前没有发布者，扩展的 ID 为 `undefined_publisher.petrichor`。
- 从编辑器运行时，运行前编译（`_build`），字节码写入 `.godot/petrichor/`，游戏只读取。因为 `$X` 等的类型取决于场景（规范 §7）。游戏自己编译要重新分析全部场景，启动更慢，结果也可能与编辑器不同。
- 无界面命令同样写出字节码，供测试和 CI 使用；导出插件把字节码放进导出包。
- 场景缺必须赋值导出的值的错误标为 `Diagnostic::runs`，不妨碍运行前的编译（规范 §7.5）。
- 版本号定下之前（§6.1），字节码只带格式标识，即构建时对 `src/bytecode/` 的哈希；标识不同的构建不读它。带着源码加载的脚本还按源码的哈希确认字节码由它编译，否则要求重新构建。
- 热重载：保存脚本后编辑器重新编译，经调试连接通知游戏重新加载。只改函数体时实例换用新代码。声明有变化时，游戏保留原代码，此后不再应用任何重载，直到重新运行（规范 §12.4）。

## 3. 测试

测试来自规范、引擎和真实代码三个方面，不从实现反推：

- **规范一致性**：按规范各节的规则编写测试。编译期的检查放在不启动引擎的 compiler 测试中，运行时的行为放在引擎测试中。
- **引擎兼容**：无界面运行的 Godot 测试项目，检查脚本的挂载、保存和重载，以及 GDScript 与本语言的双向调用。生命周期方面检查：
  - await 期间所属对象被释放，或信号源被释放；
  - 信号同步发出后再次挂起，同一个挂起点被恢复两次；
  - GDScript 调用本语言后，本语言再等待外部信号。
- **真实代码**：[第二次纸面迁移](https://github.com/YYF233333/petrichor-corpus/blob/main/surveys/paper-migration-2.md)中的 FPS 和 Ring 代码真正运行起来。
  - 迁移测试复制原项目，换入迁移后的脚本，尚未迁移的仍是 GDScript。迁移后的运行只能报告原项目也报告的错误，退出时也只能占用原项目占用的资源。
  - Ring 的测试不需要 .NET：`tests/engine/ring/ring_check.tscn` 代替 `Root.cs`，发出 Ring 的 `main.md` 构造的消息。C# 的 `Call()` 与 GDScript 的动态调用一样，都经引擎按名字调用。

编译器测试经同一个辅助函数编译源码，它检查 §2.1 的约定：

- token 流无损；
- 节点的范围依次嵌套；
- 每个解析出的名字都有引用，且原文相符。

能运行的编译结果还要通过字节码的校验，与运行时加载时相同。对没有错误的源码，它还把每一行从中间截断后再编译。要求不崩溃、只报语法错误，其他行的语句仍在语法树上；未闭合括号之后缩进更深的行除外。这样每个新特性的测试同时检验这些约定。语法错误的报错另有一组用例，取边输入边编辑时的典型错误，写明位置和措辞。`tests/engine` 中的 `.pet` 文件没有真实的引擎 API，只检查 token 流、节点的范围和截断后的解析。

每个引擎测试写明它预期的错误，出现其他任何错误都算失败。运行器启动的导入不做检查：Godot 4.7.2 的编辑器在导入后立即退出时可能崩溃（Godot issue #111048）。

## 4. 性能

与 GDScript 比较四组基准，分别测量虚拟机本身和跨引擎边界的开销：

| 基准 | 测量内容 |
|---|---|
| 启动与编译 | 冷启动、重复运行、修改代码后重新运行 |
| 纯计算 | 整数和浮点循环、函数调用、成员访问、向量、数组 |
| 引擎边界 | 属性读写、调用引擎方法、Callable、信号 |
| 分配 | 创建对象、闭包、协程挂起 |

比较使用优化过的构建，不用 `dev_build`。是否生成原生代码、优化哪些路径，由这些数据决定。

纯计算组对代码布局很敏感。只改动解释器之前无关函数的大小，int_loop 就慢了 24%（AMD Zen 5）。所以这一组的数字只作记录，回归不阻塞提交。引擎边界组和分配组的时间主要花在引擎调用上，受布局的影响在几个百分点以内。

`benchmarks/` 中有 14 对运行时用例，以及一个 32 脚本项目的启动与编译基准。

- 运行时用例预热一次，再交替语言顺序采样五次，逐次检查结果一致。
- 运行时用例固定在一个逻辑核心上运行。CPU 混有两种核心时（如 Zen 5 加 Zen 5c），不固定的计时会分成相差一成以上的两档。启动基准用到多线程，所以不固定。
- 启动基准预热一轮，再交替采样三轮，每轮用刚导入的新副本。它计量首次、重复和修改一个脚本后的运行，每次检查结果。
- 启动时间是编辑器准备加游戏进程。编辑器准备在本语言是 `--petrichor-build`，在 GDScript 是等待编辑器扫描。
- 同一状态的启动时间在两轮之间可差 300 ms 左右，约一成。所以两种语言相差几个百分点时，分不出快慢。

## 5. 推进顺序

1. **引擎接入**：不含语言，`.pet` 脚本能挂到节点上，在编辑器中和导出后都能运行。已完成。
2. **探针**：在运行的引擎上验证规范中只由源码推出的几处。已完成。
3. **最小编译链**：语言的一个子集挂进场景运行，GDScript 能调用它，断点能停，函数体能热重载。已完成。
4. **第一个里程碑**：第二次纸面迁移中的 FPS 代码真正运行。已完成。
5. **偿还技术债**：处理第一版实现留下的与规范不符的行为、重复的规则和不实的测试与文档。已完成。
6. **第二个里程碑**：第二次纸面迁移中 Ring 的 breakout 以迁移后的脚本运行。已完成。
7. **补齐第一版的语言**：第 4、6 步只覆盖了两个项目用到的写法。这一步实现规范第一版其余的特性，对应的规则同时写成测试。
   - 每个特性都满足 §2.1 的约定，第 8 步的工具建在其上。
   - 改动热路径的特性各跑一次基准（§4），把代价记进提交说明，但不为它优化。写进规范的运行时检查是以后的约束，定下之前要知道它的代价。
   - 第 9 步只等这一步中改动热路径的特性。其余特性放到第 9 步之后，如 match 的数组模式和剩余参数。

## 6. 以后必须能做到的事

下面四件事要到第 8 步或更晚才能做完。做不到时，真实项目要么无法选用本语言，要么用到中途无法继续。本节说明现有设计允许以后做到它们，以及在那之前不能打破的约束。

### 6.1 Mod

用本语言写的游戏在运行时加载 Mod 的包。Mod 的类继承、调用和实现游戏的类，使用游戏的场景，而 Mod 的作者拿不到游戏的源码。

- 加载：Mod 的包由 `ProjectSettings.load_resource_pack` 载入，包中的 `.remap` 同样生效（`core/config/project_settings.cpp:581-585`，`core/io/resource_loader.cpp:1491-1519`）。所以 Mod 的脚本与游戏的脚本经同一条路径到达运行时。挂载不刷新已缓存的资源，所以包须在目标脚本和场景首次加载前挂载（`core/io/resource_loader.cpp:622, 801`）。字节码按路径指称类，不必登记全局类名（`src/bytecode/module.h` 的 `ClassRef`）。
- 链接：脚本之间按路径和名字引用。运行时做四项检查：
  - 加载时检查基类的成员布局和签名（`src/runtime/class_image.cpp` 的 `ClassImage::load_class`）；
  - 调用时检查方法的签名（`src/runtime/vm.cpp` 的 `has_signature`）；
  - 读写时检查其他脚本的成员和静态变量的类型（`src/runtime/values.h` 的 `TypeImage::type_id`）；
  - 使用处检查场景中节点的类（`vm.cpp` 的 `fits_class`）。

  所以版本不符或替换了场景的 Mod 得到加载错误或程序错误，不会读错内存。C# 和 Java 的 Mod 也建在这种带检查的动态链接上。
- 格式：支持 Mod 的那一版为格式定下版本号，此后可读取兼容版本编译的 Mod。在那之前，Mod 须用与游戏相同的构建编译（§2.4）。
  - 普通项目升级后重新构建，用不到跨版本的字节码。需要它的只有 Mod。
  - 所以格式不随语言在 0.9 冻结，原生代码和泛型还可以改它。
- 声明：编译器对其他脚本只检查声明（`src/compiler/project_api.h` 的 `ProjectApi::script_source`、`src/compiler/script_classes.h` 的 `ScriptClasses::declarations`）。所以游戏随 Mod 工具附上去掉函数体的脚本，Mod 就有完整的检查和补全。这些脚本可以按节点的 token 范围生成（§2.1）；游戏包中的场景经 SceneState 直接可读。
- 信任：verifier 拒绝损坏和过时的文件，但信任表中的引擎签名，伪造的文件可以使游戏崩溃（`module.h` 的 `EngineCall`）。GDScript 写的 Mod 本就能做任何事，加载 Mod 本身是信任的决定。要防不受信任的字节码，有两条增加的路（规范 §14.2）：
  - 加载时对照引擎核对签名；
  - 改用含编译器的运行时库，由游戏编译 Mod 的源码。
- 在此之前要守住：
  - 脚本之间的引用保持按路径和名字，在加载或调用时检查。跨脚本的优化（BACKLOG 的性能部分）在加载或首次调用时完成。它不把别的脚本的下标或布局不经检查地编进字节码。
  - 泛型（规范 §3.10）的定义留在自己的模块中，例如加载时按类型实参特化，不在使用处按源码单态化。这样别的模块无需泛型的源码就能实例化它，寄存器仍存原生值（§1）。
  - 编译器只经接口读取其他脚本，构建已保证这一点（`SConstruct` 的 `compiler_library`）。

### 6.2 struct 与带载荷 enum 的导出

struct 和带载荷 enum 的成员可以 `@export`，存进场景和 `.tres`（规范 §4.3）。第一版（第 7 步）做到这些，按类型编辑和 `Node` 字段在之后。

- 存储：两者在引擎边界上编码为按字段名的 Dictionary，带载荷的 enum 以 `"$variant"` 记分支名（规范 §10.1）。场景保存时经 `get` 读出它们，实例化时经 `set` 先交给脚本实例的入口检查解码，引擎无需改动（`scene/resources/packed_scene.cpp:494, 861-883`，`core/object/object.cpp:239-246`）。
- 编辑：第一版用检查器的通用字典编辑器，它能编辑，只是不按类型（`editor/inspector/editor_properties.cpp:4280-4287`）。按类型的面板随第 8 步的后一段，由本扩展注册的 EditorInspectorPlugin 提供，属性的提示字符串写明类型（`editor/inspector/editor_inspector.h:356, 360`，`editor/plugins/editor_plugin.cpp:674`）。
  - 通用字典编辑器总把提示字符串读作键和值的类型（`editor/inspector/editor_properties_array_dict.cpp:1203-1226`）。
  - 所以提示字符串写作 `0:类型名`，`0` 使键保持无类型。
- 默认值：编译器知道成员的初始值时，把它的编码写进字节码，作为检查器的默认值和还原值。
  - 初始值由常量、构造和字段的常量默认值组成时，编译器知道它。
  - 由代码算出的初始值没有默认值，与 GDScript 相同（`modules/gdscript/gdscript_analyzer.cpp:5652-5661`）。
- 检查：场景和 `.tres` 中存的值由资源检查（§6.4）按类型检查。缺字段、分支名不存在和类型不符都报在节点上，资源上的报在文件上。
  - 场景索引读出场景自己存的属性值（`src/compiler/project_api.h` 的 `SceneNode::properties`）。只读两种节点：
    - 挂本语言脚本的节点；
    - 所实例化场景中被它修改的节点，供必须赋值的导出和存值的检查。
  - 资源文件和场景中的资源由引擎加载，再读出属性（`SceneResource::properties`）。
  - 引擎经 `set` 设下文件存的每个值，占位实例保留与默认值不同的值，与保存时相同（`scene/resources/resource_format_text.cpp:640-716, 1955-1994`）。
  - 资源文件的外部资源中没有本语言脚本或场景时，不加载它。
  - 资源的脚本在编辑器中编译失败时，占位实例列不出文件存的属性。索引因此不读它的值（`SceneResource::unread`）。
  - 节点或资源的脚本无法读取或声明时，也不检查给它的值。脚本自己的检查报告原因。
  - 实例化时，被实例化或继承的场景先设它的值，外层场景再设自己的，每个值都经过解码（`scene/resources/packed_scene.cpp:263-266, 494`）。
  - 所以每个值在存它的场景上检查。继承场景整个替换基场景的值，不与它合并。
- `Node` 字段：引擎只把顶层属性和带类型容器中的节点引用存为路径。它等场景的节点都建好后再解析（`scene/resources/packed_scene.cpp:390-394, 597-630`）。嵌套在编码中的节点引用会丢失，所以第一版报编译错误。以后有两条路：
  - 运行时把它们存为相对路径，在节点入树或首次读取时解析；
  - 上游让 PackedScene 也解析嵌套在导出值中的节点引用。
- 在此之前要守住：可以导出之后，§10.1 的编码就是存储格式。它按字段名和分支名编码，加字段、调顺序都不影响旧数据。带载荷的 enum 按这个编码实现，0.1 发布后不再以丢失旧数据的方式修改它。

### 6.3 全平台的预编译库

用户不装 C++ 工具链就能导出到 Windows、Linux、macOS、Android、iOS 和 Web；之后的 Godot 4.x 版本继续可用。

- 分发：`.gdextension` 按功能标签为每个平台和架构列出库，导出插件取相符的那个（`core/extension/gdextension_library_loader.cpp:82-96`，`editor/export/gdextension_export_plugin.h:107-117`）。
  - iOS 的静态库由导出插件生成注册代码（`:119-137`，`editor/export/editor_export_platform_apple_embedded.cpp:1233-1325`）；
  - Android 把库放进 `lib/<abi>/`（`platform/android/export/export_plugin.cpp:800-822`）；
  - Web 要用带扩展支持的导出模板（`platform/web/export/export_plugin.cpp:362-374`，规范 §1.3）。

  所以发布就是为每个平台构建一份库，godot-cpp 带有这些平台的构建脚本。
- 代码：编译器和字节码是普通 C++17，运行时和 adapter 只用 godot-cpp，`src/` 没有按平台的条件编译（`SConstruct` 的 `configure_godot_cpp`）。解释器不生成机器码，所以能在禁止运行时生成代码的 iOS 和主机上运行（规范 §12.2）。
- 主机：扩展能否加载取决于移植方；退路是构建为引擎模块，编进每个平台的导出模板（Godot 的 `SConstruct:1237`、`modules/SCsub:32-42`）。C++17、SCons 和与引擎同名的类型都是为保留这条路选的（§1、§2.2）。
- 引擎版本：之后的版本加载同一个构建（§1）。引擎行为的变化，靠[引擎事实](engine-facts.md)在换提交时逐条复核。API 的变化在运行时按名字和哈希查找方法时暴露，不会悄悄调错方法（`src/bytecode/module.h` 的 `EngineCall`）。
- 旧引擎版本：从 4.4 到当前版本，每个小版本支持其最新的补丁版。大型商业项目很少中途升级引擎，这样它们也能用上本语言。
  - 每个小版本构建一份库，godot-cpp 以该版本的 `api_version` 构建。
  - 内置类型和工具函数的表由该版本的 `extension_api` 生成（§2.1）。
  - 引擎事实写明每条在哪些版本成立，GDScript 在各版本间的行为差异也记在那里。
- 在此之前要守住：
  - 平台相关的代码只经 godot-cpp。正确性不依赖生成机器码。导出用的库不含编译器（`SConstruct` 的 `target == "editor"` 分支）。
  - 用到 4.4 之后才有的引擎接口或行为时，在引擎事实中写明它出现的版本和旧版本上的做法。
  - 功能依赖上游的修改时，旧版本上要有不依赖它的路，至少给出明确的报错。

### 6.4 大项目和多人协作中的重命名

在上千个脚本、数百个场景、多人在分支上并行修改的项目中，重命名成员、方法或节点要响应快。它也不应迫使人一次改写别人正在编辑的场景。

- 为什么改写场景：场景按名字存导出属性的值和信号连接的方法，名字不存在时值被悄悄丢弃（`scene/resources/packed_scene.cpp:494, 666, 682`）。所以重命名要改写这些键（规范 §13.3）。改写是 token 区间上的文本替换，只动用到名字的行，只在别人改了同一行时冲突。
- 区间由文本定位器（`src/compiler/scene_text.h`）找出。它只读文本，不依赖引擎，所以与编译器在一起，由编译器测试检验。
  - 它按引擎读取的方式分词，认得字符串、`&"` 和 `@"`、`;` 注释、括号、逗号和冒号（`core/variant/variant_parser.cpp:160-505, 1750-1960`，`ed1daf0`）。
  - 引擎写名字和节点路径时只转义引号、撇号和反斜杠（`core/string/ustring.cpp:4473-4494, 5052-5063`）。所以字符串中反斜杠后的字符照原样取，不解其他转义。
  - 它不按行匹配，因为多行的值和字符串可以让行首出现 `[` 或 `key =`。
  - 节由节头认出：`[node]` 的 name 和 parent，`[sub_resource]` 的 id，`[resource]`，`[gd_resource]`，以及 `[connection]` 的四个字段。
  - 在节中，它按引用表的结构路径找到名字：键、所存值中的字符串、NodePath 的第一个子名或方法轨道键的方法名。
  - 每处须恰好找到一次，解码后须等于旧名，否则放弃。这是与引擎读法之间偏差的检查，定位器读错的地方都成为拒绝。
  - 新名字按引擎在该处的写法写入。键含非 ASCII 字符时加引号，字符串中的名字无须转义（`core/string/ustring.cpp:4474-4496, 5053-5064`）。
  - 节点存 Node 类型的导出时，节头的 `node_paths` 也列出这个键。引擎只把列出的键读成节点路径，所以一并改写（`scene/resources/resource_format_text.cpp:225-232, 305`）。
- 改全局类名时，脚本是该类的 `.tres` 节头中的 `script_class` 一并改写。`preload` 按它定型，编辑器也按它筛选资源（`scene/resources/resource_format_text.cpp:1806`）。
  - 二进制 `.res` 中的 `script_class` 不改写，也不因它拒绝。它只用于筛选，引擎重新保存时更新。
- 挂本类或子类的节点或资源已存着新名字的键时拒绝，例如先前删掉的导出留下的键。否则那个旧值会在改名后悄悄生效。
  - 节点的键取自场景索引。
  - 资源上的这种键在加载时被丢掉，索引看不到，所以在文本格式的文件中查（`src/adapter/pet_placeholder.cpp:113-116`）。
- 一处要改写的存储也可能被别的场景用于别的声明。例如共用的动画文件，或继承场景换了根上的脚本时基场景存的连接。
  - 某个场景用到它，而该场景的检查不把它指向所改的声明时，拒绝并指出那个场景。
  - 不拒绝的话，那个场景的轨道或连接会悄悄失效。另一边是 `.gd` 或 `.cs` 时，没有检查报告它。
- 二进制的 `.scn`、`.res`、`.anim` 和 `.repl` 不能按 token 区间改写。引用落在其中时拒绝重命名，提示先另存为文本格式。只报告不够，因为漏改的导出键会被悄悄丢弃。
  - 导入的资源（如 `.glb` 中的动画）同样拒绝，它的名字由导入重新生成。
- 文件可以把场景作为内置的 PackedScene 存在节点或资源的属性中。场景索引把它当作一个场景读，路径是文件的路径、`::` 和它的 id：
  - 所以检查、查找引用和导出的检查都覆盖它存的值；
  - 它的节点存的名字落在 `_bundled` 的 `names` 表中，与节点名共用，所以不改写；
  - 引用落在其中时拒绝重命名，指出文件、存它的节点和属性，提示先用属性的"另存为…"把它存成单独的文件（`editor/inspector/editor_resource_picker.cpp:365-368`）；
  - 它所用的子资源是文件自己的节，照常改写。
- 不改写场景的做法：设置属性和按名字调用连接的方法，都先经脚本实例（`core/object/object.cpp:239-246, 800-816`）。所以运行时可以接受成员声明里写明的旧名。
  - 场景下次保存时写成新名字，于是在有人本来就要编辑时迁移。引用表列出仍用旧名的场景（§2.1），都迁移后删去旧名。
  - 占位实例已是本语言自己的（§2.4）。它像引擎的一样拒绝属性列表之外的名字，接受旧名也在这里处理（`core/object/script_language.cpp:680-707`）。
  - 写明旧名是语言规则。
- 响应靠惰性：只检查被问到的单元，单元的输入以它自己点名的为主。检查分两种单元：
  - 脚本检查确定脚本自身的类型和诊断。输入是它的源码、所用脚本的声明，以及下述索引的回答。
  - 资源检查查场景和 `.tres` 本身，如节点上的脚本、存的值、信号连接、轨道、必须赋值的导出、`@parent` 和 `@owner`。
  - 资源检查的输入是该文件、它逐层实例化的场景，以及其中各处脚本的声明。错误标在该文件上，场景的错误标在节点上。
  - 编辑器在打开或保存资源时检查它；无界面构建和导出检查全部资源。脚本编辑器也列出用到该脚本的资源报在脚本上的错误。
  - 资源上的错误不使脚本编译失败，所以脚本的类型和补全照常可用。构建和导出仍因它失败，除非它不阻止运行（规范 §7.5）。
- 反向的问题（谁用了我）只查浅层索引。索引汇总每个文件不经类型检查就能得到的事实：
  - 场景和资源文件的结构和它们存的值，含其中的资源（场景索引）；
  - 每个脚本的基类路径；
  - 字面量路径的 `preload` 和 `load`。
- 脚本检查只问一种反向问题：挂载它的场景，及逐层实例化这些场景的场景，供 `$X` 定型（规范 §7.1）。它来自语言设计，挪不走。
- 编译器从项目列出的场景和各脚本的基类路径算出挂载它的场景（`ScriptClasses::scenes_with_script`）。
- 资源检查问的反向问题，如场景是否被当作根使用、是否无人引用，也只查这些索引。
  - 当作根使用的场景（`ScriptClasses::root_use`）：
    - 主场景；
    - `.pet` 和 `.gd` 中字面量路径 `preload` 和 `load` 的场景；
    - 场景和资源文件中的节点和资源存的场景。
  - GDScript 的 `get_dependencies` 不列出 `preload`，所以按 token 找这些调用（`modules/gdscript/gdscript_resource_format.cpp:88`，`gdscript_parser.h:1647-1650`）。
  - 一次分析只读一遍所有脚本和场景，得出全部回答。
  - 编辑器按文件保留每个脚本的这些调用，与场景一样在磁盘变化后按修改时间判定（§2.1，`SceneIndex::literal_loads`）。所以之后的分析只重读改过的脚本。
- 用到其他文件函数体中的事实时，由那个文件检查时算出摘要，放进它的声明。
  - 如 `_init` 在每条路径上赋值的成员。
  - 声明的哈希包含决定摘要的输入，所以摘要可能变化时，依赖它的检查重做。
- `_init` 的摘要记在它的声明上（`FuncDecl::assigned`）。子类沿用最近的 `_init`，与 `new()` 相同。
  - 为用到它的文件检查声明时，也检查 `_init` 的函数体，以算出摘要，不保留其中的错误。编辑器加载脚本时不检查它。
- 场景检查从脚本的语法树中找出字面量节点路径，从挂该脚本的节点逐个走（`for_each_node_path`）。
  - 另有挂载它的场景有该节点时，缺它的场景在自己的检查中报错。
  - 都没有时 `$X` 无从定型，所以由脚本检查报，场景检查不重复。
  - 场景检查按全文比较这些脚本，所以改路径时它重新检查；只用到其声明的脚本不重新检查。
- 在此之前要守住：
  - 检查只依赖经接口传入的输入，不读接口之外的状态，也不读其他文件的检查结果；
  - 引用表按文件（§2.1）。
