# Petrichor Language Specification (Draft)

**v0.2 draft · 2026-10-25** · 中文: [language-spec-draft.zh.md](language-spec-draft.zh.md)

This document rewrites the language specification from the [design decisions](decisions.en.md); once the discussion is complete it will replace v0.1 (git tag `spec-v0.1`). Where this document disagrees with the design decisions, the decisions prevail and this document is corrected. Questions the design decisions leave open are marked [Open] here.

## 1. Overview

### 1.1 Problem and goals

- Large Godot projects written in a dynamic language are hard to manage. GDScript is bound by historical compatibility and cannot leave dynamic typing behind; and even when every script is statically typed, node paths, signals connected in the editor, animation tracks and resource property names stay dynamic, because the static information in scenes never reaches the scripts. Switching to C# makes language support second-class, and the cross-language bridge and the toolchain both have pitfalls.
- This language is fully statically typed; dynamic values appear only where the engine or third parties impose them (§3.13). Static checking extends to scenes: node paths, signals connected in scenes, animation tracks, exported properties and scene resources are typed, and renames change the scenes too (§7, §13).
- The target users are developers who read and modify code, on projects of medium size and up, where part of the code may be generated by AI. Small projects are better served by GDScript.
- New projects are the main use. Third-party plugins stay in GDScript and need not be migrated (§11).
- Performance should be clearly better than GDScript's; C# is not the target (§12.2).

### 1.2 Relationship to GDScript

- The surface syntax follows GDScript: indentation, `func`, `var`, `extends`, `signal`, `@export`, `$X` and so on. New constructs extend it in the same style (§2).
- **Syntax hard rule**: a construct spelled as in GDScript either behaves as in GDScript or is a compile error with a suggested fix; it never behaves differently in silence. Every rule in this document that differs from GDScript satisfies this; where a rule says "as in GDScript", it means the agreement this rule requires.
- This language does not promise to compile GDScript source directly. Migration is guided by compile errors and quick fixes (§13.4).

### 1.3 Delivery

- It is delivered as a GDExtension implementing Godot's script language extension interface (`core/object/script_language_extension.h:393, 493, 533, 596, 754`). Code that accesses the engine is kept in a thin adapter layer, so that an engine-module build remains possible later.
- A GDExtension can be installed in the official editor and uses the official export templates. The cost is that Web exports need "Extensions Support" enabled and cross-origin isolation headers configured.

### 1.4 Conventions

- Rules that define legal programs and required behavior are normative. Rationale, examples, §15 and Appendix B are not.
- Status markers:
  - **[Open]**: not yet decided; corresponds to an item in §10 of the [design decisions](decisions.en.md);
  - **[Known limitation]**: not supported in the first version; rules that restrict which programs are legal remain normative;
  - **[Later]**: can be added compatibly later and is not part of the first version.
- A **compile error** is an error the analysis service reports before running, making the program illegal. **Warnings** and **hints** do not affect legality. A **program error** is the runtime error defined in §8.1.
- Engine behavior cited here was checked against Godot master (4.8-beta, commit `469659e`), with sources listed in Appendix A. This is the verification baseline, not a statement of supported versions.
- The `.pet` extension used in examples is provisional [Open].

## 2. Lexical structure and surface syntax

### 2.1 Files and classes

- A source file is a class, as in GDScript. A file may declare a global class name with `class_name Name`; files without `class_name` are referred to through `preload`. Global names come only from `class_name` (§4.1).
- The class header may contain, in order: class-level annotations, `class_name`, `extends`, `implements`. `extends` and `implements` may be on the same line as `class_name` or on lines of their own:

  ```gdscript
  class_name Player extends CharacterBody3D implements Combat.Damageable
  ```

- A file may declare inner classes (`class Name:`), structs, enums and interfaces, all of which belong to the file's class (§2.4).

### 2.2 Lexical structure

- Indentation, comments, identifiers, literals and operators are as in GDScript, with these changes:
  - New keywords: `pub`, `struct`, `interface`, `implements`, `async`, `None`.
  - A new postfix operator `?` (§8.2). In GDScript `?` is a syntax error (`modules/gdscript/gdscript_parser.cpp:3834-3835`).
  - Prefix `!` remains logical not (`gdscript_parser.cpp:2965-2967`).
  - The handling of the `null` literal is [Open].
- Literals: integers, floats, strings (including triple quotes and the `r` prefix), `&"…"` (StringName), `^"…"` (NodePath), arrays `[…]`, dictionaries `{k: v}` and `{k = v}`, `true`, `false` and `None`, as in GDScript; `None` is the empty value of Option (§3.4). The types of literals are in §3.2 and §10.7.

### 2.3 Annotations

- GDScript's annotations are kept with their meaning: the `@export` family, `@onready`, `@tool`, `@icon`, `@warning_ignore`, `@rpc`, `@static_unload`.
- New class-level annotations: `@parent(T)` and `@owner(T)` (§7.3).
- Whether `@abstract` is supported is [Open].
- Annotations precede the declaration and may share its line; `pub` comes after annotations and before `static` (§2.4).

### 2.4 Declaration spellings

- **Structs**: `struct Name:` followed by fields declared with `var`, which may have default values. Construction takes arguments by name only, and fields with defaults may be omitted:

  ```gdscript
  struct Hit:
      var damage: int
      var point: Vector3
      var crit: bool = false

  var h = Hit(damage = 3, point = p)
  ```

- **Enums**: GDScript's brace form, where variants may carry named payload fields. Enums without payloads are as in GDScript. A variant with a payload is constructed with arguments by name:

  ```gdscript
  enum Command { IDLE, MOVE(target: Vector3), ATTACK(target: Node3D, power: int) }

  var c = Command.MOVE(target = Vector3.ZERO)
  ```

- **Interfaces**: an indented block that can declare `var`, `signal` and `func`. A method without a body has no colon, as with GDScript's `@abstract func` (`gdscript_parser.cpp:1790-1791`); a method with a body is a default method:

  ```gdscript
  interface Damageable:
      var hp: int
      signal died
      func take_damage(amount: int)
      func is_dead() -> bool:
          return hp <= 0
  ```

- **Implementing interfaces**: the class header writes `implements A, B` (§2.1).
- **pub**: a keyword written after annotations and before `static`, for example `@export pub var max_hp: int`, `pub static func make() -> Player`, `pub signal died`.
- **Placement and naming**: structs, enums, interfaces and inner classes belong to the class of the file that declares them. In that file they are written by name; in other files as `ClassName.Name`, for example `Combat.Hit` or `Player.Command.MOVE(target = p)`. Types shared by several classes go into a class that exists to hold them. [Later] Aliases or `import`.
- The spelling of **generic** declarations and type arguments is [Open]; the spelling of **function types** is [Open].

### 2.5 Statements

- `var`, `const`, `if`/`elif`/`else`, `while`, `for`, `match`, `break`, `continue`, `pass` and `return` are as in GDScript; their rules are in §5.
- `assert(condition, message)` is a program error when it fails; whether it is removed in release builds is [Open].
- There is no form that uses an if/else block as a value; the only conditional expression is `a if c else b` (§5.5).

## 3. Types

### 3.1 Overview

| Category | Types |
|---|---|
| Numbers and booleans | `int` (64-bit), `float` (64-bit), `bool` |
| Strings | `String`, `StringName`, `NodePath` |
| Core value types | `Vector2`, `Vector2i`, `Vector3`, `Vector3i`, `Vector4`, `Vector4i`, `Color`, `Rect2`, `Rect2i`, `Transform2D`, `Transform3D`, `Basis`, `Quaternion`, `Plane`, `AABB`, `Projection`, `RID`, and the `Packed*Array` types |
| Containers | `Array[T]`, `Dictionary[K, V]` (§3.8) |
| Objects | engine classes, classes of this language, global classes of GDScript and C#; non-null `T` and nullable `T?` (§3.3) |
| Value types of this language | structs (§3.6), enums (§3.7) |
| Interfaces | §3.9 |
| Standard types | `T?` (Option, §3.4), `Result[T, E]` (§3.5), `Task[T]` and `Settled[T]` (§9), `weak[T]` (§3.12), `ConversionError` (§5.3) |
| Functions | function types (§3.11), `Callable`, `Signal` |
| Dynamic | `Variant` (§3.13) |

### 3.2 Numbers

- The first version has only `int` and `float`, both 64-bit, matching Variant (`core/variant/variant.h:257-258`). There are no narrow types for users; fixed-width arithmetic uses wrapping methods and bit operations on `int`.
- Integer literals have type `int`, floating-point literals type `float`.
- An `int` converts implicitly to `float` in assignments, arguments and returns. Converting a `float` to an `int` requires `int(x)` and is otherwise a compile error; implicit truncation would make `hp = 2.5` silently differ from GDScript.
- The result types of operators follow §5.1.
- Numeric boundaries with the engine follow §10.6.

### 3.3 Objects and nullability

- A value of object type `T` always refers to an object; a value of `T?` is an object or None.
- After an object is freed:
  - reading a reference of type `T?` that refers to it yields None, so a `!= None` check, and the narrowing it brings (§5.4), is also a liveness check;
  - a reference of type `T` may still hold the freed object; reading, comparing and passing it do not count as access, and accessing its members is a program error. In debug builds, if the object is an instance of this language or was freed by code of this language, the diagnostic says where it was freed;
  - after `queue_free()` and until the object is actually deleted at the end of the frame, it still counts as alive. `is_instance_valid` behaves as in GDScript.
- Every read of an object reference of type `T?` performs a liveness query.

### 3.4 Option

- `T?` is Option: a value of T, or None. A value of T is wrapped into `T?` implicitly.
- Option is a value, and operations on it are methods with the same names as in Rust: `unwrap` and `expect(message)` (both a program error on failure), `unwrap_or`, `unwrap_or_else`, `map`, `and_then`, `or`, `or_else`, `filter`, `ok_or`, `ok_or_else`. There are no `!`, `??` or `?.` operators.
- The only special syntax is postfix `?`: on None the current function returns None (§8.2).
- Null tests use `!= None` and narrowing (§5.4); there is no truthiness.
- Nested Options (`T??`) are [Open].

### 3.5 Result

- `Result[T, E]` expresses an operation that may fail in an expected way. It is constructed with `Ok(v)` and `Err(e)`; success values are not wrapped implicitly.
- Operations are methods with the same names as in Rust: `unwrap`, `expect`, `unwrap_or`, `unwrap_or_else`, `map`, `map_err`, `and_then`, `or_else`, `ok`, `err`.
- Postfix `?` makes the current function return `Err(e)` on `Err(e)` (§8.2).
- Discarding a Result is a compile error; to deliberately ignore one, write `.ok()`.

### 3.6 Structs

- Structs have value semantics: assignment, argument passing and return copy them. They exist only inside this language.
- Construction takes arguments by name only, and fields with defaults may be omitted (§2.4). [Later] Positional arguments.
- When crossing the engine boundary (signal arguments, Variant, cross-language messages), a struct is encoded automatically as a Dictionary keyed by field name; decoding checks the presence and type of every field and descends into containers and nested structs, as in `Dictionary[String, ConsumableState]`. Fields are decoded by the same rules as `T.try_from` (§5.3).
- [Known limitation] In the first version structs cannot be `@export`ed or stored in `.tres`; data edited in the editor uses Resource.
- Whether structs can have methods, which copy `s.x = 1` changes, and `==`, comparison and hashing as Dictionary keys are [Open].

### 3.7 Enums

- Enums without payloads are as in GDScript.
- Payload fields of a variant must be named, as in `MOVE(target: Vector3)`. Naming keeps the encoding independent of field order.
- A match over an enum must be exhaustive (§5.6). When a variant is added, the compiler lists every place that does not handle it.
- What the engine sees is in §10.1: an enum without payloads is an int and is shown as a drop-down when exported; an enum with payloads is encoded as a Dictionary keyed by field name, with a reserved key recording the variant name.
- Whether enums with payloads can be `@export`ed, and their `==` and hashing, are [Open], to be decided with the corresponding struct item.

### 3.8 Containers

- There is one `Array[T]` and one `Dictionary[K, V]`, with the same API. `Array` and `Dictionary` without type arguments have Variant elements, as in GDScript.
- When elements are representable by the engine, the container is the engine's typed container, shared with the engine. When elements are of a type only this language has (structs, enums with payloads and so on), it uses its own representation; passing it to the engine requires an explicit conversion, which makes a copy. Rationale: implicit copying would create pitfalls of the "you modified a copy" kind.
- Access:
  - `pop_front()` and `pop_back()` return `T?`: the engine returns null on an empty array without reporting an error (`core/variant/array.cpp:798-817`);
  - `front()` and `back()` return T and are a program error on an empty array, where the engine reports an error too (`array.cpp:364-372`);
  - an out-of-range index is a program error.
- The standard library provides `map`, `filter`, `sort` and similar methods taking typed lambdas on the native containers (§3.11).

### 3.9 Interfaces

- Interfaces are nominal: a class must declare with `implements` which interfaces it implements.
- Interfaces may declare methods, properties and signals, and may have default methods, which read and write state through interface properties.
- A property requirement can be satisfied by an inherited engine property, for example `var global_position: Vector2` by Node2D's property of that name; the type must be the same and the read and write access must match.
- Members that implement an interface must be `pub` (§4.2).
- Only classes of this language can implement interfaces; foreign objects need an explicit wrapper.
- [Known limitation] The first version has no stateful mixins.
- Whether interfaces can extend interfaces, and whether they can be generic, is [Open].

### 3.10 Generics

- Functions, structs, enums, and RefCounted classes created only by code of this language may be generic. Node and Resource scripts and autoloads cannot, because the engine provides no type arguments when it instantiates them.
- Constraints are expressed with interfaces. Type arguments are kept at runtime.
- The spelling is [Open].

### 3.11 Function types and Callable

- A function type records the parameter types, the return type, and whether the function is async. The spelling is [Open].
- Method values (such as `change_weapon` or `_on_hit`) and lambdas have function types; handed to the engine, they become Callables that refer to the method directly rather than by name (§10.5).
- The type of `f.bind(a, b)` is f's function type without its last two parameters, because the engine appends bound arguments after the call's arguments (`core/variant/callable_bind.cpp:141-150`).
- A `Callable` of unknown signature needs an explicit conversion to a function type and is checked on every call, for its arguments and return value.
- Lambdas capture by value, as in GDScript. In a RefCounted class, capturing self is a strong reference (`modules/gdscript/gdscript_lambda_callable.cpp:285-291`) and is not silently made weak; weak capture uses `weak` (§3.12).
- The types of lambdas are inferred by the local rules (§4.6).

### 3.12 Weak references

- `weak[T]` is a typed weak reference: `weak(x)` creates one, and `.get()` returns `T?`.
- To capture self weakly in a closure, write `var me = weak(self)` outside the closure and use `me.get()` inside it.

### 3.13 Variant

- Dynamic values have only three sources: engine interfaces declared as Variant; parameters, return values and members left untyped in GDScript plugins (§11.1); and messages from other languages.
- A dynamic value entering static code needs an explicit conversion (§5.3), which reports an error on failure; there are no implicit checks.
- Types are fixed at the source wherever possible: constraints the engine has but does not export are added in this language's binding metadata (§10.3).
- Which operations Variant allows (assignment, passing as an argument, `==`, `is`, `as`, conversions, dynamic access by name) is [Open].

## 4. Declarations

### 4.1 Classes and inheritance

- Class names use the engine's flat global class table. The compiler checks for duplicates, including clashes with class names of GDScript plugins and C#. [Known limitation] The first version has no namespaces.
- A class may extend an engine class or a class of this language.
- [Known limitation] It cannot extend a GDScript class. When a plugin requires extending its GDScript classes (such as Beehave's ActionLeaf), users hand-write a thin GDScript subclass that calls code in this language (§11.2).
- A GDScript script cannot extend a class of this language: when GDScript resolves `extends GlobalClassName`, it parses the base class's file as GDScript (`modules/gdscript/gdscript_analyzer.cpp:471-487`). The analysis service reports an error explaining this on such a GDScript file (§11.2).
- The signature rules for overriding methods are in §4.6, the visibility rules in §4.2.

### 4.2 Visibility

- Members without `pub` are visible in the file that declares them, including inner classes in that file, and subclasses may read, write, call and override them; other classes cannot see them.
- Members marked `pub` are visible to all code.
- Overriding keeps visibility: an override of a `pub` member must be `pub`, and an override of a member without `pub` cannot add it.
- Members that implement an interface must be `pub`.
- A type that is not `pub` appearing in the signature of a `pub` member is a compile error.
- A must-assign member (§6.2) without `pub` that no scene or ancestor assigns is an error at the class definition.
- Which members the engine, GDScript and C# can access by name is in §10.5.
- [Later] A stricter `private`.

### 4.3 Member variables

- `var` declares a member. With an initializer, the type may be inferred from it by the same rules as for locals: `var speed = 5.0` is float, and `@onready var label = $Label` is inferred from the scene as Label (§7.1). Inferred types appear on hover, in completion and in the property information the engine sees.
- These members must be annotated: those without an initializer, and those whose initializer does not determine a type, such as empty containers and None.
- In GDScript `var hp = 10` is an untyped member; in this language it is inferred as int, and assigning another type afterwards is a compile error, which the syntax hard rule allows.
- Members without an initializer:
  - numbers, bool, String, StringName, NodePath, core value types, containers and enums without payloads start at their default value, as in GDScript;
  - a struct starts at its default when every field has a default, and must otherwise be assigned like an object reference;
  - an enum with payloads must be assigned;
  - the rules for must-assign members are in §6.2.
- `@export` follows GDScript, and in addition: structs cannot be exported (§3.6); exported scenes are written `PackedScene[T]` (§7.4); exports of non-null object type must be assigned (§7.5).
- `@onready` is in §6.3.

### 4.4 Property accessors

- Setters and getters are written as in GDScript: inline `set(value):` and `get:`, or named `set = f` and `get = g`.
- Inside a property's own accessors, the property name refers to its storage field; elsewhere in the class, reads and writes go through the accessors, as in GDScript.
- Initializers write the field directly, bypassing the setter (§6.1).
- Setters and getters cannot be coroutines.
- The rules for setters that run before ready are in §6.5.

### 4.5 Constants

- `const` is as in GDScript.

### 4.6 Functions

- Function signature types are written by hand, not inferred. Parameters must be annotated.
- An override of an engine virtual or of a base-class method may omit its parameter and return types; the omitted types are taken from the overridden declaration and shown on hover. Types that are written must match it exactly, while parameter names may differ. For example, delta in `func _process(delta):` is a float (`scene/main/node.h:433-434`). This is not inference: the types are set by the overridden declaration, not by the body.
- For a function that is not an override, an omitted return type means void; returning a value from it is a compile error, and the quick fix adds the return type.
- Parameters may have default values, as in GDScript. Whether rest parameters `...args` are supported is [Open].
- Calls pass arguments by position, as in GDScript. Arguments by name are used only to construct structs and variants with payloads (§2.4), and to pass must-assign members to `instantiate(...)` and `new(...)` (§6.2).
- Local variables inside functions may infer their type from an initializer. A lambda is code inside a function and is inferred by the local rules: its parameter types come from the expected function type when there is one and must be written otherwise, and its return type is inferred from its body, as in `weapon.map(func(w): return w.name)`.
- Coroutines are declared in the signature as `async func` (§9.1).

### 4.7 Signals

- Signal parameters must be annotated, for example `pub signal died(cause: String)`.
- `emit` and `connect` are both checked statically: the arguments at the emit, and the parameter count and types of the connected function.
- Connections stored in scenes are checked by the scene model (§7.7).
- Signals of engine classes are typed from ClassDB; unaudited object parameters are nullable (§10.2).
- The result of awaiting a signal is in §9.6.

### 4.8 Static members

- `static var`, `static func` and `_static_init()` are written and timed as in GDScript: when a class is loaded, base classes first, its static members are initialized in declaration order and `_static_init` is called last (`modules/gdscript/gdscript_compiler.cpp:2646-2649`). Static initializers bypass setters too (`gdscript_compiler.cpp:2620-2643`).
- When a class's static initialization reads a static member of another class, that class is initialized first.
- A cycle between static initializations is a program error whose diagnostic lists the dependency chain; cycles that can be determined statically are compile errors. Default or unfinished values are never read. Related GDScript issues: #104161, #82141, #104588.
- Static initialization cannot await.
- Changing static members is a structural change; hot reload asks for a restart (§12.4).

## 5. Expressions and statements

### 5.1 Operators

- The result types of operators follow the engine's operator table, as GDScript's static checks do (`core/variant/variant_op.cpp:256-368`). For example, `Vector2 * float` is a Vector2, `Vector2i * float` is a Vector2, and `int / int` is integer division. Combinations missing from the table, such as `Vector2 + Vector2i`, are compile errors.
- Mixed `int` and `float` arithmetic promotes to `float`.
- Integer division by zero is a program error.
- The typing of utility functions bound with Variant (lerp, clamp, min, max, abs, wrap and others) is in §10.3.

### 5.2 Comparison

- The rules for `==` and `!=` are [Open]: how int and float, objects and containers compare, and which combinations are compile errors.
- `==` between String and StringName compares contents (§10.7).

### 5.3 Conversions

- `x as T` is only for object types, and its result is `T?`: None when the type does not match, as in GDScript (`modules/gdscript/gdscript_vm.cpp:1665-1666`). When the static type of x already is T, the result is T and the redundant `as` is pointed out.
- `as` to a built-in type is a compile error. GDScript converts through the constructor there (`gdscript_vm.cpp:1630-1637`), so the quick fix offers two rewrites:
  - `T(x)`, which keeps that conversion, as in `int("5")` or `int(2.7)`;
  - `T.try_from(x)`, the strict conversion.
- `T.try_from(v)` returns `Result[T, ConversionError]`. It follows the rules for decoding a struct field: the value's type must match T; for `int`, a float that is exactly an integer within the int64 range is accepted (§10.8). `?` propagates the failure, and `.unwrap()` or `.expect(…)` turns it into a program error.
- A downcast that must succeed is written `(x as T).unwrap()`.
- For code that tests group membership and then downcasts, the quick fix suggests narrowing with `is` instead. Interfaces that filter by a literal class name are typed by that class (§10.3).

### 5.4 Narrowing

- Kotlin's rule is used: locals and parameters narrow after `!= None`, `is` and early returns, and likewise in both branches of the conditional expression `a if c else b` and in the right operand of `and` and `or`.
- Members do not narrow and must first be read into a local. Evidence: in the [second paper migration](surveys/paper-migration-2.en.md), the locals added for this were 4.4 per 1,000 lines. [Later] Conditional binding (such as `if var t = _tween:`), or narrowing fields without a getter when no call, await or assignment occurs between the check and the use.
- There is no truthiness: conditions must be bool. GDScript's `if x:` is a compile error, and the quick fix rewrites it according to x's type, as `x != None`, `x != 0`, `x != ""` and so on.
- Non-null does not mean the object is still alive; access still checks (§3.3).

### 5.5 Conditional expressions

- The only one is GDScript's `a if c else b`, where c must be bool.

### 5.6 match

- Every GDScript pattern is kept with its meaning (`modules/gdscript/gdscript_parser.cpp:2499-2723`): literals and constant expressions compare by equality; `var x` binds; `_` is a wildcard; array and dictionary patterns, with `..` inside them; several comma-separated patterns, which cannot bind; and `when` guards.
- New patterns:
  - Enum variants: `Type.VARIANT(field = pattern, ...)`. `var field` is short for `field = var field`. Fields not listed must be covered by `..`, as in dictionary patterns. Patterns nest.
  - Structs: the same form, for example `Hit(damage = var d, ..)`.
  - Result: `Ok(var v)` and `Err(var e)`, written positionally, as they are constructed.
  - Option: `None` and `var x`; the value bound by the latter is narrowed to T.

  ```gdscript
  match cmd:
      Command.IDLE:
          stop()
      Command.MOVE(var target):
          walk_to(target)
      Command.ATTACK(target = var enemy, power = 0):
          taunt(enemy)
      Command.ATTACK(var target, ..) when target.is_boss:
          flee()
      Command.ATTACK(..):
          hit()
  ```

- A match over an enum (with or without payloads), a Result or an Option must be exhaustive or have `_`; branches with `when` do not count toward coverage. A match over other types need not be exhaustive, as in GDScript.
- [Known limitation] The first version has no type patterns (use `if x is T`), no match expressions, and no binding in comma-separated patterns.

### 5.7 Loops

- `for` is as in GDScript: `for i in n` iterates from 0 to n-1 with i an int; `range(...)`, containers, Strings and the keys of a Dictionary can be iterated.
- The loop variable may be annotated, as in `for i: int in ...`, with the element type or one of its base types; there is no implicit downcast.
- Iterating over a float or a vector is a compile error, and the quick fix uses `range(...)`. GDScript allows it and treats the vector as a range (`gdscript_vm.cpp:3093-3230`); under static typing this is almost always a mistake.
- `while`, `break` and `continue` are as in GDScript.

## 6. Initialization and lifecycle

### 6.1 Member initialization

- Member initializers write the field directly, bypassing the setter, for instance and static members alike, as in GDScript (`modules/gdscript/gdscript_compiler.cpp:2435-2451, 2620-2643`). The initializer gives the first value and the setter handles changes; during initialization there are no observers, and members declared later are not initialized yet.
- Derived state is computed in `_ready` or `_static_init`. When a member has both an initializer and a setter, the compiler notes that initialization bypasses the setter.
- Members without an initializer start at a default value or must be assigned (§4.3).

### 6.2 Must-assign members

- `_init` of Node and Resource scripts cannot take parameters, because the engine always constructs them with zero arguments ([pitfall catalog](surveys/pitfalls.en.md) G-02). Constructor parameters are expressed as must-assign members: non-null members without a default.
- A must-assign member must be assigned before its scene has finished becoming ready, by one of:
  - the scene: exported members are provided by the scene (§7.5);
  - the creator: `instantiate(...)` and `new(...)` accept member values by name and assign them before returning, as in `BulletScene.instantiate(speed = 300.0, target = enemy)`. For `PackedScene[T]`, the compiler checks at the call site that every must-assign member the scene does not provide is passed, and leaving one out is a compile error;
  - an ancestor: an ancestor node in the same scene assigns it in its own `_ready`, provided the scene model can see the assignment, that is, it is written `$Child.target = v` or goes through an `@onready` reference.
- When checks happen:
  - members provided by the scene or the creator are checked when the node becomes ready, before `@onready` initialization;
  - members assigned by an ancestor are checked once the whole scene is ready. Ready propagates synchronously when a node enters the tree (`scene/main/node.cpp:3425-3429`), and per-frame callbacks come from the main loop, so ordinary logic cannot read the missing value;
  - a child reading a member assigned by an ancestor in its own `_ready` is a compile error;
  - reading a member that has not been assigned yet before ready is a program error whose diagnostic names the member;
  - if the configuration is invisible to the scene model (for example assignments in a loop over `get_children()`), the member must be written `T?`.
- Scenes whose path is known only at runtime have only the check at ready.
- Resources have no ready phase: assignments in `.tres` files are checked statically, and resources created with `new()` in code are checked on read.
- RefCounted classes created only by code of this language use `_init` with parameters as usual.
- An autoload outlives scenes, so its members that refer to scene nodes can only be `T?`. Where non-null is wanted, make the manager a node in the scene and refer to the other nodes through must-assign exports. [Known limitation] The first version has no "non-null member assigned after ready" (like Kotlin's `lateinit`). Evidence: across 20 repositories, registering a node on an autoload member in `_ready` occurs only 6 times, 5 of them in Ring ([second paper migration](surveys/paper-migration-2.en.md)).

### 6.3 `@onready`

- GDScript's timing is kept: `@onready` initializers run before `_ready`, base class first, each in declaration order (`modules/gdscript/gdscript.cpp:1956-1972`).
- The following are compile errors: combining `@onready` with `@export`; await in an initializer; reading an `@onready` member directly in `_init` or `_enter_tree`.
- Reading an `@onready` member that is not initialized yet through a call is a program error whose diagnostic names the member. Evidence: [pitfall catalog](surveys/pitfalls.en.md) G-04.

### 6.4 Ready order

- Children become ready before their parent, following the engine's order; no lifecycle hooks are added.
- When a child reads a member of its parent that is not initialized yet in `_ready`, a program error explains the cause. The quick fix offers two rewrites: have the parent configure the child in its own `_ready` (§6.2), or declare the child's `_ready` async and `await get_parent().ready`.
- Such a read is legal when a child is added at runtime under a parent that is already ready, so it is not rejected wholesale at compile time.
- Re-entering the tree does not run `_ready` again, as in the engine. Evidence: [pitfall catalog](surveys/pitfalls.en.md) G-03, G-05.

### 6.5 Setters before ready

- When a scene is instantiated, the engine sets a node's saved properties before adding the node to its parent (`scene/resources/packed_scene.cpp:567, 616`), when the node's children and `@onready` members are not yet available.
- A setter runs immediately as usual. At the first statement that needs the node to be ready, if the node is not ready yet, the setter suspends there and continues from that point once the node is ready:
  - statements that need readiness are determined by static analysis: accessing `@onready` members, `$X` or children, or calling methods of the class that access them, including overrides in subclasses;
  - accesses inside an `if is_node_ready():` branch do not count;
  - the position of the suspension point is visible on hover in the editor.
- When a property is written several times before ready, only the last suspended call continues and the earlier ones are all cancelled. Suspended calls continue after `@onready` initialization and before `_ready`, in the order they were written. If the node is freed before it is ready, the suspended calls are dropped. Once the node is ready, setters no longer suspend.
- Transformation and storage happen before the suspension point, so a read before ready sees the transformed value.
- This is what GDScript code writes by hand as `if not is_node_ready(): await ready`, done by the compiler. Evidence: in the [property accessor survey](surveys/property-accessors.en.md), all 6 setters with `await ready` read the field's current value after resuming.
- A property whose value lives only in nodes (no field, with a getter that reads children) is a program error when read before ready, and the diagnostic names the node that is not ready yet. If it must be readable before ready, keep the value in a field.
- A property that was never written does not run its setter at ready, as in GDScript. A hint is given when an exported property's setter synchronizes nodes but its default value never goes through the setter.

### 6.6 Destruction

- No new syntax: `NOTIFICATION_PREDELETE` is still handled in `_notification(what)`, and cleanup related to the scene tree goes in `_exit_tree`, written and timed as in GDScript; the order of destruction follows the engine.
- The runtime guarantees that a RefCounted object can read and write its own fields and call its own methods during PREDELETE, without taking a new reference to self.
- In the branch handling PREDELETE, passing self out, storing it in a member or container, and using await are compile errors. During that time, `weak` references to self return None. Evidence: [pitfall catalog](surveys/pitfalls.en.md) G-09.

### 6.7 Reference cycles and leaks

- There is no tracing GC. RefCounted uses the engine's reference counting, and cycles are not freed.
- The compiler warns about evident cycles, with a quick fix that rewrites them to use `weak`:
  - a closure capturing self stored in a member of self, a signal connection of self itself, or a container held by self;
  - two RefCounted classes pointing at each other through fields of strong reference types.
- Nodes are not reference counted. Warnings are given when:
  - a node obtained from `new()` or `instantiate()` is, on some path, neither added to the scene tree nor returned, stored or freed;
  - a node after `remove_child` is neither stored nor freed.
- Debug builds list leaked nodes and objects, with where they were created, on exit.
- Cycles formed indirectly through engine containers or other objects cannot be found by static analysis. Evidence: [pitfall catalog](surveys/pitfalls.en.md) G-10.

## 7. Scene model

### 7.1 Typing nodes

- The compiler collects every scene structure a script can see, including inherited scenes and edits on instances, and types `$X`, `%X` and `get_node` with a literal path from them.
- If different scene structures give different types, that is an error requiring an annotation. Evidence: in the game repositories of the [scene structure survey](surveys/scene-structures.en.md), none of 2,023 literal paths resolves to different types in different structures.
- A path that cannot be found is a compile error, marked on the scene that lacks the node, except in the three cases of §7.2.

### 7.2 Structure declared by scripts

- Three cases are declared by the script, with a spelling that is [Open]:
  - child nodes required by a base class and provided by inheriting scenes;
  - child nodes added at runtime;
  - optional child nodes, of type `T?`.

### 7.3 Upward access

- Autoload access via `/root/X` uses typed autoload global names instead.
- Parent and owner requirements are written as the class-level annotations `@parent(T)` and `@owner(T)`, placed where `@tool` goes. `get_parent()`, `..` and `owner` then have type T; without a declaration they are Node, and an explicit conversion is needed for a more specific type (§5.3).

  ```gdscript
  extends Node
  class_name HealthComponent
  @owner(Combat.Combatant)

  func _ready():
      current_health = owner.init_health
  ```

- The static check happens where scenes place the script. The owner is the root of the scene that contains the node. A script on a scene's root has no owner, so declaring `@owner` there is a compile error.
- At runtime:
  - the parent requirement is checked when the node is attached to a parent (`NOTIFICATION_PARENTED`, `scene/main/node.h:466`);
  - `owner` is checked on every read to be non-null and to satisfy the requirement, and a failure is a program error whose diagnostic names the requirement and the actual owner. Owner is not checked when nodes move: when a node is taken out of its owner's subtree, the engine sets owner to null (`scene/main/node.cpp:391-396, 1799-1801`), and that is a legitimate operation; owner is also set to null when the owner is freed (`node.cpp:299-302`).
- Code that needs to test whether there is an owner uses `get_owner()`, whose type is `Node?`.

### 7.4 Scene resources

- `preload` and `load` with a literal path are typed by the resource's actual contents; a scene yields `PackedScene[T]`, where T is the type of the scene's root node, or the class of its script when it has one.
- Exported scenes are written `PackedScene[T]`, and the editor checks the scene that is filled in. `instantiate()` yields T.
- `load` with a path known only at runtime yields a Resource, as the engine's signature says, with nullability per the audit in §10.2; for a scene loaded this way, `instantiate()` yields a Node. Converting to a more specific type needs an explicit conversion (§5.3).

### 7.5 Required exports

- Exports of non-null object type must be assigned. Ones that may genuinely be missing are written `T?`.
- The check follows how each scene is used:
  - when a scene is instanced or inherited by other scenes, an assignment at any level of the instance and inheritance chain counts; each instance is checked separately, and a missing value is marked on the scene containing that instance. For example, `crosshair` in player.tscn points to a node that exists only in main.tscn, which assigns it on the instance, so player.tscn itself is not an error;
  - when a scene is used as a root, that is, as the main scene, loaded with `load` or `preload` from a literal path, or exported as `PackedScene[T]`, the scene itself is checked;
  - a scene created in code with `instantiate(...)` is checked against the values passed at the call site (§6.2);
  - a scene referenced from nowhere gets only a warning, because a `load` whose path is known only at runtime cannot be seen.
- Checks happen at three points:
  - while editing, clearing is allowed. The field in the Inspector and the node in the scene tree are marked with an error at once, but no operation is blocked, and the mark disappears when a value is assigned again;
  - when running, the game may run; a node still missing a value raises a program error when it becomes ready, checked before `@onready` initialization, and the diagnostic names the member, as when player.tscn is run on its own in the editor;
  - when exporting a release build, export is refused where a value is certain to be missing, and warnings do not block it.
- When the remote inspector writes null to a non-null member, the entry check rejects the write and the value is unchanged.
- Rationale: clearing and then replacing is a normal step while editing, so non-null constrains the finished scene. Replacing does not even require clearing first, since node references are stored as paths in `.tscn` and resolved during instantiation (`scene/resources/packed_scene.cpp:449-468`).

### 7.6 Shared resources

- The semantics of resource sharing are unchanged; the scene model finds the problems. The compiler knows which resources are shared: resources from `load`, `preload` and exported properties come from the cache, and embedded sub-resources in a scene that are not set to "local to scene" are shared by all instances of that scene.
- Writing a property of a resource known to be shared, or calling a method that modifies it, gives a warning listing where it is shared, with two quick fixes: make it local to the scene, or `duplicate()` it before modifying. Deliberate modification of a shared resource is silenced with `@warning_ignore`. Resources replaced at runtime cannot be tracked and are not warned about.
- `duplicate()` returns the static type of its receiver; the depth of copying is stated with `duplicate_deep(mode)`.
- Reference cycles between `preload`, exported PackedScenes and resources are reported before running, with a suggestion to turn one edge into a runtime `load`. Evidence: [pitfall catalog](surveys/pitfalls.en.md) G-19, G-20, G-34.

### 7.7 Connections and paths in scenes

- For signal connections stored in scenes, the scene model checks that the method exists and that its parameters match the signal.
- Property paths in animation tracks, method names in method tracks, and property paths such as `"position:x"` are resolved as static references (§10.4).
- These references take part in rename and find references (§13.3).

## 8. Errors

### 8.1 Program errors

- A program error aborts the entire call chain of this language back to the entry point through which the engine called in. On the way out, held references are released and the error and call stack are logged; when running in the editor, the debugger breaks. The game keeps running.
- Debug and release builds behave the same.
- If the engine's entry point must return a value, the engine receives the default value of its type.
- Every situation this document calls a "program error" is handled by this rule, including: accessing a freed object (§3.3), a failed `unwrap` or `expect`, an out-of-range index, integer division by zero, reading a member that has not been assigned yet before ready, a failed entry check at the engine boundary (§10.1), and awaiting a cancelled task (§9.2).
- Rationale: after an error GDScript builds a default value for the return type and the caller continues (`modules/gdscript/gdscript_vm.cpp:3975-3979`); under static typing this would hand code fake values.

### 8.2 Expected failures

- Expected failures are expressed with Option (§3.4) or Result (§3.5), following Rust's model: Option is a value, and Result is for control flow.
- The only special syntax is postfix `?`, a short-circuit return:
  - applied to `Result[T, E]`: on `Err(e)` the current function returns `Err(e)`; otherwise it yields T. The current function must return `Result[_, E]` with the same E; a different E is first converted with `map_err`.
  - applied to `T?`: on None the current function returns None; otherwise it yields T. The current function must return `_?`.
  - Using `?` in a function that returns void, or propagating between Option and Result, is a compile error; the two are converted with `ok()` and `ok_or()`.
  - Its precedence makes `await f()?` parse as `(await f())?`.

  ```gdscript
  func load_profile(path: String) -> Result[Profile, Error]:
      var text = read_text(path)?
      return Ok(parse_profile(text)?)
  ```

- Rationale: a short-circuit return changes control flow and needs syntax; everything else transforms values, for which methods suffice, and Rust's documentation applies directly. If optional chaining `?.` were also provided, whether `x?.y` returns from the function or yields None would depend on the type of x.

### 8.3 Assertions

- `assert(condition, message)` is a program error when it fails. Whether it is removed in release builds, as in GDScript, is [Open].

### 8.4 Diagnostics

- Compile errors, warnings and hints are reported by the analysis service and marked in the source, the Inspector and the scene tree (§13).
- The diagnostic of a program error gives the location, the members or objects involved, and the call stack. For some program errors this document states what the diagnostic must contain, such as the name of a must-assign member, where a freed object was freed, or the owner requirement and the actual owner.

## 9. Coroutines

### 9.1 async and Task

- Coroutines are declared in the signature as `async func`. A function whose body contains await without the declaration is a compile error. Engine virtual functions may be declared async.
- Calling an async function yields a `Task[T]`. The task starts immediately and runs until its first suspension; `await f()` and `await t` yield T.
- Discarding the result of an async call is a compile error; to deliberately not wait, write `f().detach()`. In GDScript, using the result of a coroutine call as a value is already a compile error, so giving `var t = f()` a new meaning does not violate the syntax hard rule.
- Setters, getters, `@onready` initializers and static initialization cannot await.

### 9.2 How tasks end

- A task ends in one of three ways:
  - **finished**, with its return value;
  - **cancelled**, by `t.cancel()`, by its owning object being freed, or by the awaited object being freed;
  - **failed**, by a program error inside the task.
- Awaiting a cancelled task is a program error. A failure propagates up the await chain to the root task, which is a detached task or a task called by the engine, and cannot be intercepted.
- `await t.settled()` waits for the task to end in any way without an error and returns `Settled[T]`: `Finished(value: T)` or `Cancelled(reason: CancelReason)`, where `CancelReason` is `Requested`, `OwnerFreed` or `AwaitedFreed`. This is not expressed with Result, because being cancelled is not an error.

### 9.3 Cancellation and ownership

- For a suspended task, `cancel()` immediately disconnects the signal or task it is waiting for, and the task ends as cancelled.
- For a running task (which only happens when its own synchronous code indirectly cancels it), it ends as cancelled at its next await or return, and the return value is discarded.
- For a task that has ended, `cancel()` has no effect. After `cancel()` is called, the outcome is always cancelled.
- Cancellation propagates along ownership: a child task the task starts and awaits directly with `await f(...)` belongs to it and is cancelled with it; awaiting a task value obtained elsewhere with `await` means cancellation only stops the waiting, and that task keeps running. The two forms can be told apart at compile time. For example, if the cutscene `cutscene` is cancelled while stopped at `await walk_to(door)`, `walk_to` is cancelled with it and the character stops.

### 9.4 Release

- A coroutine frame, its locals and suspension point, is released as soon as the task ends; held references are handled as at scope exit, and code after the await does not run. [Known limitation] The first version has no finally or defer.
- A Task object is a RefCounted handle that only holds the result. It is freed when no variable, no waiter and no signal wait of the runtime refers to it any more.
- A suspended coroutine does not keep self alive, as in GDScript.

### 9.5 Combination and reentrancy

- `Task.of(signal)` wraps a signal as a task; `Task.delay(seconds)` waits for a time; `Task.any(list)` returns the index of the first task to finish and cancels the others by the ownership rule; `Task.all(list)` waits for all of them.
- Reentrancy has no automatic policy; when needed, the old call is cancelled through its handle. [Later] Annotations such as `@restart`. Evidence: [pitfall catalog](surveys/pitfalls.en.md) G-12, G-13; proposals #8838, #6243.

### 9.6 Awaiting signals

- A signal can be awaited directly.
- A signal without parameters yields no value; a signal with one parameter yields a value of that parameter's type; awaiting a signal with several parameters is allowed only as a statement. Evidence: in the [await signal results survey](surveys/await-signal-results.en.md), only 1 of 1,356 awaits uses the result of a signal with several parameters. GDScript yields an Array of the arguments there (`modules/gdscript/gdscript_function.cpp:237-255`), so GDScript code that uses such a result is a compile error.

### 9.7 Freed objects and suspended coroutines

- When the object a coroutine belongs to is freed, the coroutine is cancelled silently and the references its suspended frame holds are released, as in GDScript.
- When an awaited object (a coroutine on another object, or the signal source of another object) is freed before it completes, the waiter raises a program error at the await and aborts to the engine boundary, with a diagnostic naming the freed object and where it was freed; awaiting with `settled()` yields `Cancelled(AwaitedFreed)`. GDScript leaves the waiter suspended forever in this case (`modules/gdscript/gdscript_function.cpp:335-349`).
- The freeing of any object can be observed through the instance-binding free callback that GDExtension exposes. Evidence: [pitfall catalog](surveys/pitfalls.en.md) G-11.

### 9.8 Cross-language await

- Calls to GDScript methods may be awaited. If the runtime receives a `GDScriptFunctionState`, it waits for its `completed` signal (`modules/gdscript/gdscript_function.cpp:327`) and then checks the result against the declared return type; receiving one without await is a program error. Whether a method is a coroutine is not in its reflection information (`core/object/method_info.h:37-44`), so this cannot be decided at compile time.
- When GDScript awaits a coroutine of this language, the coroutine returns its Task's `completed` signal at its first suspension; GDScript's await accepts any Signal value (`modules/gdscript/gdscript_vm.cpp:2585-2599`). The Task emits `completed(value)` when it finishes, and `completed(null)` when it is cancelled or fails, so a GDScript waiter is never left suspended forever; a separate `cancelled` signal serves code that needs to tell the cases apart.
- Both directions must be tested in an environment that can build the engine.

## 10. Engine boundary

### 10.1 Types as the engine and GDScript see them

| This language | What the engine and GDScript see |
|---|---|
| `int`, `float`, `String`, classes such as Node | the type of the same name |
| objects `T` and `T?` | that class in both cases; non-null is guaranteed by entry checks |
| nullable values such as `int?` | an untyped Variant |
| `Array[T]` and `Dictionary[K, V]` with engine-representable elements | the engine's typed containers |
| enums without payloads | int; shown as a drop-down when exported |
| structs | Dictionaries keyed by field name |
| enums with payloads | Dictionaries keyed by field name, with a reserved key recording the variant name |

- GDScript types global classes of other languages through the Script reflection interface (`modules/gdscript/gdscript_analyzer.cpp:804-819, 4329-4370, 6054-6063`), so GDScript's calls into classes of this language are statically checked too.
- **Entry checks**: wherever a value enters this language from the engine, GDScript or C# (arguments, `set` writes to members, signal arguments, results of await, decoding), it is checked against the declared type, and a failure is a program error. Writes by the remote inspector go through entry checks too (§7.5).

### 10.2 Nullability of objects returned by the engine

- Unaudited interfaces are all nullable.
- The audit proceeds in descending order of call frequency in the corpus and has three outcomes:
  - non-null, typed T;
  - null only on misuse, such as `get_tree()`: treated as non-null, and a null is a program error;
  - possibly null in normal use, such as `get_collider()` and `get_first_node_in_group()`: typed `T?`.
- Rationale: the engine annotates only about 50 interface declarations with `RequiredResult`, 29 of them in Tween.

### 10.3 Binding metadata

- Constraints the engine actually has but does not export are added in this language's binding metadata; metadata the engine already exports is used directly.
- Utility functions bound with Variant (lerp, clamp, min, max, abs, wrap and others) are typed by their arguments: when the arguments have the same type, the result has that type. Mixing int and float is a compile error, and the quick fix turns the integer argument into a float, as in `min(ratio, 1.0)`. Rationale: the engine's min, max and clamp return one of their arguments unchanged (`core/variant/variant_utility.cpp:643-760`), so in GDScript `min(1.5, 1)` is an int, and promoting to float would make the result silently differ; lerp itself requires both arguments to have the same type (`variant_utility.cpp:466-470`).
- Interfaces that filter by a literal class name are typed by that class, for example `find_children("*", "MeshInstance3D")` returns `Array[MeshInstance3D]`.
- Interfaces that "return null on failure and report the error separately" (such as `FileAccess.open`) are wrapped by standard library functions that return Result.

### 10.4 Member names as strings

- For `connect`, `emit_signal`, `call`, `call_deferred`, `set_deferred`, `has_method`, `Callable(obj, "m")`, `tween_property` and property paths such as `"position:x"`, a literal is resolved as a static reference when the target type is known: the name's existence and the value's type are checked, and it takes part in rename and find references.
- Which parameters are names is marked in the binding metadata.
- A non-literal name is explicit dynamic access.

### 10.5 Members exposed through reflection

- Through reflection (`get_property_list`, `has_method`, and `call`, `get` and `set` by name), the engine, GDScript and C# see only:
  - `pub` members;
  - members the engine must find by name: exported properties, signals, overrides of engine virtuals, methods connected in scenes, and members that code in this language hands to the engine by a literal name, such as `call_deferred("reset")`, `tween_property(self, "current_speed")` and property paths in animation tracks of scenes. The compiler collects the latter.
- All other members are invisible to access by name: referring to them from GDScript is a GDScript compile error, and C#'s `Call` and dynamic access with a non-literal name report a missing member at runtime.
- A Callable formed from a method value (for example `tween_callback(change_weapon)` or `sig.connect(_on_x)`) refers to the method directly, not by name, and is not affected.
- The debugger sees all members.
- Rationale: members without `pub` are referred to only by their file, subclasses and the literal names the compiler collects, so the tools can find every reference when renaming them.

### 10.6 Numeric boundaries

- Writing to an engine 32-bit float location narrows implicitly, for example real_t vector components, which are float in standard builds (`core/math/math_defs.h:143-146`).
- Passing a value to an engine int32 parameter is range-checked, and an out-of-range value is a program error; the engine itself truncates there (`core/variant/variant.h:348-349`).

### 10.7 String and StringName

- Both directions convert implicitly where needed, as in GDScript; `==` compares contents.
- Where StringName or NodePath is expected, a string literal is constructed as that type at compile time, with no runtime conversion. Constructing a StringName from a String needs a lookup under the global table's mutex (`core/string/string_name.cpp:280-302`).
- The `&"x"` and `^"x"` prefixes remain. Runtime conversions on hot paths get a performance hint.

### 10.8 JSON

- The engine parses every number in JSON as a float (`core/io/json.cpp:390-396`). Decoding to `int` accepts a float that is exactly an integer within the int64 range and otherwise reports an error, without truncating.
- The standard library provides encoding and decoding between structs and enums and JSON, `var_to_str` and ConfigFile.

## 11. Coexisting with GDScript and C#

### 11.1 The static view of GDScript classes

- This language sees GDScript classes and autoloads through reflection:
  - object-typed members, parameters and return values are taken as `T?`;
  - value types are as declared;
  - untyped ones are dynamic values (§3.13).
- Autoload names are global identifiers whose type is the class of their script.

### 11.2 Inheritance

- Cross-language inheritance is not supported in either direction:
  - A class of this language cannot extend a GDScript class. When a plugin requires extending its classes, users hand-write a thin GDScript subclass that calls code in this language; GDScript sees this language's types through reflection, so those calls are still statically checked. Evidence: [pitfall catalog](surveys/pitfalls.en.md) C-17.
  - A GDScript script cannot extend a class of this language (§4.1), and GDScript then reports only "Could not resolve super class" (`modules/gdscript/gdscript_analyzer.cpp:479, 485`). The analysis service reports an error explaining this on such a GDScript file.
- Migrating a class therefore requires migrating its GDScript subclasses with it. Before migrating, the analysis service lists the affected subclasses and offers to migrate them together (§13.4).

### 11.3 Cross-language calls and messages

- GDScript and C# can access by name only the members listed in §10.5.
- Messages to and from C# are expressed as structs, encoded as Dictionaries keyed by field name (§3.6), and decoded and checked at the entry.
- Cross-language await is in §9.8.

## 12. Runtime

### 12.1 Adapter layer

- Code that accesses the engine is kept in a thin adapter layer. Creating and freeing instances, reading and writing properties, and calling methods all go through GDExtension's script instance interface.

### 12.2 Performance

- Clearly faster than GDScript; C# is not the target.
- The interpreter must reach the performance goal on its own: iOS and most consoles do not allow generating machine code at runtime, and a copy-and-patch style JIT is only an extra on desktop.

### 12.3 Threads

- The virtual machine must run safely on whatever thread the engine chooses, for example background resource-loading threads and the physics thread.
- Data races on shared objects are the user's responsibility.
- [Known limitation] The first version adds no threading API and uses the engine's Thread, WorkerThreadPool and Mutex. Evidence: across the 20 surveyed repositories, `Thread.new` occurs 11 times and `WorkerThreadPool` twice.

### 12.4 Hot reload

- When only function bodies change, they are replaced while running: the next call uses the new code, and suspended coroutines finish on the old version.
- When members, signatures or class structure change, state is not migrated and a restart is requested; tool scripts in the editor rebuild their instances.

### 12.5 Debugging support

- It plugs into the engine's debugging UI: breakpoints, stepping, locals and call stacks.
- Debug builds record where instances of this language are freed, for the diagnostics on freed objects (§3.3), and list leaked nodes and objects on exit (§6.7).

## 13. Toolchain

### 13.1 Analysis service

- The analysis service runs in the editor process. External IDEs connect through LSP; the command line and CI run the same analysis headless.
- Rationale: refactorings across scenes must modify scenes the editor has open, which only the editor can do safely. GDScript's LSP is an editor plugin too (`modules/gdscript/language_server/gdscript_language_server.h:35`, `modules/gdscript/register_types.cpp:170`).

### 13.2 Tools in the first version

- Live diagnostics, with the same analysis in the editor, LSP and command line;
- completion, types on hover, go to definition, and find references, including references in scenes;
- rename including the scene half (§13.3);
- scene checks: `$X`, signal connections, `PackedScene[T]`, parent and owner requirements and required exports, with errors marked in the scene editor;
- quick fixes: inserting inferred types, completing match branches, adding explicit conversions for dynamic values, and the rewrites mentioned throughout this document;
- the debugger (§12.5);
- a built-in test runner: discovery, running and reporting, also headless. Rationale: gdUnit4 and GUT require test classes to extend their GDScript base classes, and cross-language inheritance is not supported.

### 13.3 Refactoring

- Refactorings include their scene half. Mechanical, meaning-preserving edits are applied with the refactoring, previewed and undoable: renamed export property keys, method names in signal connections, animation track paths, and lossless value conversions.
- Edits that need judgment are only reported, with options, and never applied automatically, for example changing a node's type or an existing resource no longer matching a new type.
- Rationale: today, renaming an exported member silently loses the values saved in scenes: loading does not check whether `node->set` succeeded (`scene/resources/packed_scene.cpp:567`), and saving writes only properties in the node's current property list (`packed_scene.cpp:941-950`).
- When a node is renamed or moved in the scene editor, the `$X`, `%X` and literal `get_node` paths that refer to it in scripts of this language are updated automatically, in the same undo step as the editor's own updates of NodePath properties and animation tracks in the scene (`editor/docks/scene_tree_dock.cpp:2173-2260, 2280-2400`), without a preview, and the changed places are listed in the output panel afterwards. Non-literal paths, and scripts attached in other scenes where the same path still refers to another node, are only reported, not changed, with a quick fix to update the path.

### 13.4 Migration

- Migration is guided by compile errors and quick fixes. Mechanical edits, such as adding `pub`, adding parameter types, rewriting truthiness tests and adding `.detach()`, can be done by quick fixes. Evidence: in the [second paper migration](surveys/paper-migration-2.en.md), 197 of 230 edits were mechanical.
- Before a class is migrated, its GDScript subclasses are listed, with the option to migrate them together (§11.2).

### 13.5 Later

- [Later] Formatting; refactorings such as extract method, change signature and pull members up to a base class; deeper profiler integration; documentation generation; generating GDScript forwarding shells for GDScript plugin classes that require inheritance.

## 14. First-version scope and open questions

### 14.1 Known limitations

- Cross-language inheritance is not supported in either direction (§11.2).
- There are no namespaces, aliases or `import` (§2.4, §4.1).
- Structs cannot be `@export`ed or stored in `.tres` (§3.6).
- There are no stateful mixins (§3.9).
- match has no type patterns, no match expressions, and no binding in comma-separated patterns (§5.6).
- Coroutines have no finally or defer (§9.4).
- There is no "non-null member assigned after ready" (§6.2).
- No threading API is added (§12.3).

### 14.2 Compatible later additions

- Positional arguments for struct construction (§3.6);
- a stricter `private` visibility (§4.2);
- conditional binding, or narrowing fields when no call occurs between the check and the use (§5.4);
- reentrancy annotations such as `@restart` (§9.5);
- aliases or `import` (§2.4);
- the tools listed in §13.5.

## 15. Conformance checklist (non-normative)

This checklist gives test instances of the rules above and adds no language requirements.

| Area | What to check |
|---|---|
| Syntax hard rule | For every rule in this document that differs from GDScript, the corresponding GDScript spelling gets a compile error with a fix rather than a different runtime behavior |
| Numbers | `var hp: int = 10; hp = 2.5` is a compile error, and `hp = int(2.5)` gives 2; an int argument to a float parameter needs no conversion; `7 / 2` is 3; `Vector2i(1, 2) * 0.5` is a Vector2; `Vector2() + Vector2i()` is a compile error; integer division by zero is a program error; a value outside the int32 range passed to an engine int32 parameter is a program error |
| Nullability and freeing | A freed object read through `T?` is None; accessing its members through `T` is a program error whose diagnostic says where it was freed; after `queue_free()` and before the end of the frame it still counts as alive |
| Option and Result | `?` returns from the current function on None or `Err`; `?` in a function returning void is a compile error; propagating an Option into a function returning Result is a compile error; `await f()?` equals `(await f())?`; discarding a Result is a compile error; a failed `unwrap` is a program error |
| Conversions | `node as Sprite2D` is `Sprite2D?`; `x as int` is a compile error offering `int(x)` and `int.try_from(x)`; `int.try_from(2.0)` is `Ok(2)`, while `int.try_from(2.5)` and `int.try_from("2")` are `Err` |
| Narrowing | Locals narrow after `!= None`, `is` and early returns; branches of conditional expressions and the right operand of `and` narrow; members do not narrow; `if x:` is a compile error with a fix depending on the type |
| Visibility | Members without `pub` are invisible in other classes, and readable, writable and overridable in subclasses; changing visibility in an override is a compile error; a type without `pub` in the signature of a `pub` function is a compile error; GDScript referring to a member without `pub` is a GDScript compile error; `call_deferred("reset")` makes `reset` callable by name from the engine |
| Signatures | delta in `func _process(delta):` is a float; writing a mismatching type in an override is a compile error; returning a value from a non-override function with an omitted return type is a compile error; lambda parameters with an expected type need no annotation |
| Members | `var speed = 5.0` is float; empty-container members require an annotation; an int member without an initializer is 0; a struct member takes its default when every field has one and must otherwise be assigned |
| Must-assign | `BulletScene.instantiate(speed = 300.0)` without `target` is a compile error; an ancestor assigning `$Child.target = v` in `_ready` is not an error; the child reading that member in its own `_ready` is a compile error; reading an unassigned member before ready is a program error |
| Export checks | `crosshair` in player.tscn assigned by the instance in main.tscn is not an error; an instance without the value is marked on the scene containing it; a scene referenced from nowhere gets only a warning and does not block export; a missing value at runtime is a program error at ready naming the member |
| Initialization | Member initializers do not call setters; `@onready` with `@export` is a compile error; reading an `@onready` member in `_init` is a compile error; a static initialization cycle is reported with its dependency chain |
| Setters before ready | A value saved in a scene makes the setter suspend where it accesses an `@onready` member and continue after ready; of several writes before ready only the last continues; a transforming setter's value read before ready is the transformed one; suspended calls are dropped when the node is freed before ready |
| Scene typing | `$Head/Camera` is typed Camera3D from the scene; two scenes giving different types is an error; a path that cannot be found is marked on the scene lacking the node; `@owner(T)` on a scene root is a compile error; after a node leaves its owner's subtree, not reading owner is fine and reading it is a program error |
| Resources | Modifying a shared resource gives a warning with two quick fixes; `duplicate()` keeps the static type; a `preload` cycle is reported before running |
| match | A non-exhaustive match over an enum is a compile error; branches with `when` do not count toward coverage; unlisted fields without `..` are a compile error; in the `var x` branch of an Option, x is T; a match over int need not be exhaustive |
| Loops | i in `for i in 5` is an int; `for x in 2.5` and iterating over a vector are compile errors; annotating the loop variable with a subclass is a compile error |
| Containers | `pop_front()` on an empty array is None; `front()` on an empty array is a program error; an out-of-range index is a program error; an array of structs passed to the engine needs an explicit conversion and yields a copy |
| Coroutines | await without async is a compile error; discarding a Task is a compile error; after `cancel()` the outcome is always cancelled; a child task started with `await f(...)` is cancelled with its parent, while `await t` only stops waiting; when an awaited object is freed the waiter gets a program error, and `settled()` yields `Cancelled(AwaitedFreed)`; when the owning object is freed the coroutine is cancelled silently |
| Signals | Mismatching emit arguments and connect parameters are compile errors; a connection in a scene that does not match its signal is marked in the scene; the await result of a one-parameter signal has that parameter's type; using the await result of a multi-parameter signal is a compile error |
| Cross-language | A GDScript file extending a class of this language gets an explanatory error from the analysis service; awaiting a GDScript coroutine yields a result checked against the declared type; GDScript awaiting a coroutine of this language gets null on cancellation instead of hanging |
| Utility functions | `min(1.5, 1)` is a compile error offering `min(1.5, 1.0)`; `lerp(a, b, t)` has a's type; `find_children("*", "MeshInstance3D")` is `Array[MeshInstance3D]` |
| Strings | A literal where StringName is expected is constructed at compile time; `&"a" == "a"` is true; a literal member name that does not exist is a compile error and takes part in rename |
| Refactoring | Renaming an exported member changes the keys in scenes too; renaming a node in the scene editor changes `$X` in scripts in the same undo step; non-literal paths are only reported |
| Leaks | A node removed and neither stored nor freed gets a warning; a closure capturing self stored in a member of self gets a warning with a `weak` quick fix; debug builds list leaked objects and where they were created on exit |

## Appendix B: Alternatives considered but not adopted (non-normative)

| Alternative | Why not adopted | Current rule |
|---|---|---|
| Delivery as an engine module (v0.1) | The pitfall catalog has no item only a module could fix; a GDExtension works with the official editor and export templates | §1.3 |
| Narrow integer types such as i32 and u8 (v0.1) | The largest migration cost; scripts rarely care about the performance of numeric types | §3.2 |
| Inferring function signatures (v0.1) | Signatures are contracts and should not change with the body | §4.6 |
| Cross-language inheritance at the language level | Depends on GDScript's internal implementation | §11.2 |
| Optional chaining `?.`, defaulting `??`, postfix `!` | Combined with Result's short-circuit return, the meaning of `x?.y` would depend on the type of x; methods suffice for Option | §3.4, §8.2 |
| A Swift-style `try` covering a whole expression | Which subexpressions are unwrapped would depend on types; Rust's postfix `?` is more direct | §8.2 |
| Chaining Results with `?.` as well | When the two types nest, one operator cannot say which layer it handles | §8.2 |
| An `apply:` block for setters | Makes users think about when and how often logic runs; automatic suspension can be done by the compiler | §6.5 |
| Recording only a setter's raw input before ready | A transforming setter (such as one adding 【】 around a character name) would be read untransformed before ready | §6.5 |
| `@late` (like `lateinit`) | The code that needs it is uncommon; a parent configuring a child is covered by the ancestor-assignment rule | §6.2 |
| Subclasses seeing only `pub` members | In the migration, 29 of 102 `pub` markers existed only for subclasses | §4.2 |
| A `@public` annotation for the public marker | It is written often, at least 22 times per 1,000 lines | §2.4 |
| Top-level types of a file becoming global names | Breaks "a file is a class" and needs a second global name table | §2.4 |
| Intersection types for interfaces, such as `@owner(Node2D & Combatant)` | A new concept; engine properties may satisfy interface property requirements instead | §3.9 |
| A tracing GC, or closures capturing self weakly by default | Would silently differ from GDScript | §6.7 |
| Checking owner when nodes move | Taking a node out of its owner's subtree is a legitimate operation | §7.3 |
| Unreferenced scenes with missing values also blocking export | A `load` whose path is known only at runtime cannot be seen, so it cannot be concluded that the scene is unused | §7.5 |
| Strict checking for `as` to built-in types | Would silently differ from GDScript's constructor conversion | §5.3 |
| Promoting utility functions with mixed int and float to float | GDScript returns the argument unchanged, so the result would silently differ | §10.3 |
| `pop_front()` on an empty array being a program error | The engine returns null there without an error, so it would silently differ | §3.8 |
| Awaiting a multi-parameter signal yielding an Array, or destructuring | Real code almost never uses such results; destructuring can be added later | §9.6 |
| Using an if/else block as a value | Duplicates the conditional expression | §5.5 |
