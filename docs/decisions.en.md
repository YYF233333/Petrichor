# Petrichor design decisions

**2026-10-23** · 中文: [decisions.zh.md](decisions.zh.md)

As of 2026-10-23 the project is being redesigned from the problem up. This document records the decisions made so far; each states the rule first, then the rationale and evidence. The v0.1 specification is frozen as the git tag `spec-v0.1`; where it conflicts with this document, this document prevails. A new specification will be written from it. All engine source locations refer to Godot commit `469659e`.

## 1. Problem and positioning

- **Problem**: large projects written in a dynamic language are hard to manage. GDScript is bound by backward compatibility and cannot leave dynamic typing behind; more fundamentally, the toolchain is the problem: static information from scenes never reaches the scripts, so even when every script is statically typed, node paths, signals connected in the editor, animation tracks and resource property names remain dynamic. Switching to C# makes language support second-class; the bridge has hidden pitfalls, some engine capabilities are restricted, and the toolchain's integration with Godot has pitfalls of its own.
- **Goal**: fully static typing, with dynamic values only where the engine or a third party imposes them; the same experience extends into scenes.
- **Target users**: developers who read and modify code, on medium-sized or larger projects; part of the code may be AI-generated. Small projects are better served by GDScript and are not a target.
- **Usage**: mainly new projects; third-party plugins stay in GDScript and are not required to migrate. When a plugin requires extending its GDScript classes (such as Beehave's ActionLeaf), in the first version users hand-write a thin GDScript subclass that calls code in this language; GDScript sees this language's types through reflection, so those calls are still statically checked (`modules/gdscript/gdscript_analyzer.cpp:804-819`). Cross-language inheritance at the language level would depend on GDScript's internal implementation and is not provided. Evidence: [pitfall catalog](surveys/pitfalls.en.md) C-17. The other direction is impossible too: when GDScript resolves `extends GlobalClassName`, it parses the base class's file as GDScript (`modules/gdscript/gdscript_analyzer.cpp:471-487`), so a GDScript script cannot extend a class of this language, and GDScript reports only "Could not resolve super class" (`:479, 485`). Migrating a class therefore requires migrating its GDScript subclasses with it. The analysis service reports, on any GDScript file that extends a class of this language, an error that explains why; before a class is migrated, it lists the affected subclasses and offers to migrate them together. Evidence: in the [second paper migration](surveys/paper-migration-2.en.md), Ring's Brick and Enemy brought 5 subclasses along for this reason.
- **Performance**: clearly faster than GDScript is enough; C# is not the target. Most scripts never hit the interpreter's performance limits.

## 2. Delivery and toolchain

- **Delivered as a GDExtension.** Code that touches the engine is kept in one thin adaptation layer, so that a module build remains possible later. Rationale: the [pitfall catalog](surveys/pitfalls.en.md) contains no entry that only a module could fix, and what a GDExtension cannot fix, a module cannot fix either; a GDExtension installs into the official editor and uses the official export templates. The hooks a script language needs are exposed to extensions (`core/object/script_language_extension.h:393, 493, 533, 596, 754`). Cost: web export needs "Extensions Support" enabled and cross-origin isolation headers configured.
- **The analysis service runs in the editor process.** External IDEs connect over LSP; the command line and CI run the same analysis headless. Rationale: refactorings that span scenes must modify scenes the editor has open, and only the editor can do that safely. GDScript's LSP is likewise an editor plugin (`modules/gdscript/language_server/gdscript_language_server.h:35`, `modules/gdscript/register_types.cpp:170`).
- **Refactorings include their scene half.** Mechanical, meaning-preserving edits are applied with the refactoring, previewed and undoable: renamed export property keys, method names in signal connections, animation track paths, and lossless value conversions. Edits that need judgment are only reported, with options, and never applied automatically, for example changing a node's type or an existing resource no longer matching a new type. Rationale: today, renaming an exported member silently loses the values saved in scenes. Loading does not check whether `node->set` succeeded (`scene/resources/packed_scene.cpp:567`), and saving writes only properties in the node's current property list (`packed_scene.cpp:941-950`).
- **First-version tools**:
  - live diagnostics, with the editor, LSP and command line using the same analysis;
  - completion, type on hover, go to definition, find references (including scenes);
  - rename including the scene part;
  - scene checks (`$X`, signal connections, `PackedScene[T]`, parent requirements), with errors shown in the scene editor;
  - quick fixes: insert the inferred type, add missing match arms, add an explicit conversion for a dynamic value;
  - a debugger wired into the engine's debugger UI: breakpoints, stepping, locals, call stack;
  - a bundled test runner: discovery, running, reporting, headless. Rationale: gdUnit4 and GUT require test classes to extend their GDScript base classes, and Godot does not support cross-language inheritance.
- **Later**: formatting; refactorings such as extract method, change signature and pull members up to a base class; deeper profiler integration; documentation generation; generating forwarding GDScript shells for GDScript plugin classes that must be extended.
- **Hot reload has two levels.** When only function bodies change, they are replaced while running; the next call uses the new code, and suspended coroutines finish on the old version. When members, signatures or class structure change, no state is migrated and a restart is requested; tool scripts in the editor get their instances rebuilt.

## 3. Scenes and nodes

- **Node types are inferred from scenes.** The compiler collects every scene structure a script can see, including inherited scenes and edits on instances, and types `$X`, `%X` and literal `get_node` paths from them. If structures disagree on a type, that is an error requiring an annotation. Evidence: in the game repositories of the [scene-structure survey](surveys/scene-structures.en.md), none of 2,023 literal paths resolves to different types in different structures.
- **Three cases are declared in the script**: children a base class requires and inherited scenes provide; children added at runtime; optional children, typed as Option. Any other path that cannot be found is an error, reported on the scene that lacks the node.
- **Upward access.** Autoload access via `/root/X` uses typed autoload global names instead. The types of `get_parent()`, `owner` and `..` come from the parent or owner requirement the script declares: checked statically where scenes instance the script, and at runtime when the node is attached to a parent (`NOTIFICATION_PARENTED`, `scene/main/node.h:466`). Without a declaration the type is Node and needs an explicit conversion.
- **Scene resources.** `preload` and `load` with a literal path are typed by the resource's actual content. An exported scene is written `PackedScene[T]`, and the editor checks the scene assigned to it; `instantiate()` yields T. `load` with a path known only at runtime yields Node and needs an explicit conversion.
- **Non-null exported references must be assigned.** The check follows how each scene is used. When a scene is instanced or inherited by other scenes, an assignment at any level of the instance and inheritance chain counts; each instance is checked separately, and a missing value is marked on the scene containing that instance. When a scene is used as a root (the main scene, a scene loaded with `load` or `preload` from a literal path, a scene exported as `PackedScene[T]`), the scene itself is checked. A scene created in code with `instantiate(...)` is checked against the values passed at the call site (see the next item). A scene referenced from nowhere gets only a warning, because a `load` whose path is known only at run time cannot be seen. For example, `crosshair` in player.tscn points to a node that exists only in main.tscn, which assigns it on the instance, so player.tscn itself is not an error. Checks happen at three points. While editing, clearing is allowed: the field in the Inspector and the node in the scene tree are marked with an error at once, but no operation is blocked, and the mark disappears when a value is assigned again. When running, the game may run; a node still missing a value raises a program error when it becomes ready, checked before `@onready` initialization, and the diagnostic names the member, as when player.tscn is run on its own in the editor. When exporting a release build, export is refused where a value is certain to be missing, and warnings do not block it. Nodes created in code must be assigned before they become ready. Reading a member that has not been assigned yet before ready is a program error. Resources have no ready phase: assignments in `.tres` files are checked statically, and resources created with `new()` in code are checked on read. When the remote inspector writes null to a non-null member, the entry check rejects the write and the value is unchanged. Members that may genuinely be missing are written `T?`. Rationale: clearing and then replacing is a normal step while editing, so non-null constrains the finished scene; replacing does not even require clearing first, since node references are stored as paths in `.tscn` and resolved during instantiation (`scene/resources/packed_scene.cpp:449-468`).
- **Constructor parameters are expressed as members that must be assigned.** `_init` of Node and Resource scripts cannot take parameters, because the engine always constructs them with zero arguments ([pitfall catalog](surveys/pitfalls.en.md) G-02). Non-null members without a default must be assigned before ready: exported ones may be provided by the scene, the rest by the creator; the checks of the previous item apply to them as well. `instantiate(...)` and `new(...)` accept member values by name and assign them before returning. For `PackedScene[T]`, the compiler checks at the call site that every must-assign member the scene does not provide is passed; for example, leaving out `target` in `BulletScene.instantiate(speed = 300.0, target = enemy)` is a compile error. A must-assign member that is private and assigned by no scene is an error at the class definition. Scenes whose path is known only at runtime have only the check at ready. RefCounted classes created only by code of this language use `_init` with parameters as usual.
- **`@onready` keeps GDScript's timing**: initializers run before `_ready`, base class first, each in declaration order. The following are compile errors: combining `@onready` with `@export`; await in an initializer; reading an `@onready` member directly in `_init` or `_enter_tree`. Reading an `@onready` member that is not initialized yet through a call is a program error, and the diagnostic names the member. Evidence: [pitfall catalog](surveys/pitfalls.en.md) G-04.
- **Children become ready before their parent, as in the engine; no lifecycle hook is added.** When a child reads a member of its parent that is not initialized yet in `_ready`, a program error explains why; quick fixes offer two rewrites: configure the child from the parent's own `_ready`, or declare the child's `_ready` async and `await get_parent().ready`. Such a read is valid when the child is added at runtime under a parent that is already ready, so it is not rejected at compile time. A node that re-enters the tree does not run `_ready` again, as in the engine. Evidence: [pitfall catalog](surveys/pitfalls.en.md) G-03, G-05.
- **Initializers write fields directly, without the setter**, for both instance and static members, matching GDScript's current behavior (`modules/gdscript/gdscript_compiler.cpp:2435-2451, 2620-2643`). An initializer gives the first value, while a setter handles changes; at initialization there are no observers, and members declared later are not initialized yet. Derived state is computed in `_ready` or `_static_init`; when a member has both an initializer and a setter, the compiler notes that initialization does not go through the setter.
- **Static members** keep GDScript's spelling and timing: `static var`, `static func`, `_static_init()`; when a class loads, static members are initialized base class first, in declaration order, and then `_static_init` is called (`gdscript_compiler.cpp:2646-2649`). When a class reads another class's static member during its static initialization, that class is initialized first; a cycle among static initializations is a program error whose diagnostic lists the dependency chain, reported at compile time when statically visible, so default or half-initialized values are never read (for GDScript's related problems see #104161, #82141, #104588). Static initialization cannot await. Changing static members is a structural change, and hot reload requests a restart. Rationale: the corpus has about 214 `static var` and 4 `_static_init`, so contact is rare.

- **Resource sharing keeps its semantics; the scene model finds the problems.** The compiler knows which resources are shared: resources from `load`, `preload` and exported properties come from the cache, and embedded subresources not set to local-to-scene are shared by every instance of their scene. Writing a property of a resource known to be shared, or calling a method that modifies it, produces a warning that lists where it is shared, with two quick fixes: make it local to scene in the scene, or `duplicate()` it before modifying. Deliberate changes to a shared resource are silenced with `@warning_ignore`; resources replaced only at runtime cannot be tracked and produce no warning. `duplicate()` returns the receiver's static type; copy depth is stated with `duplicate_deep(mode)`. Reference cycles among `preload`, exported PackedScenes and resources are reported before running, with a suggestion to turn one edge into a runtime `load`. Evidence: [pitfall catalog](surveys/pitfalls.en.md) G-19, G-20, G-34. Example: in godot-open-rpg, the CircleShape2D embedded in `interaction_popup.tscn` is not local to scene, the setter at `interaction_popup.gd:30` changes its radius, and in `main.tscn:484-486` only one instance sets radius to 64; by the engine's sharing rules, the dozen or so instances share one shape whose radius is whatever the last setter wrote (inferred, not verified by running).

## 4. Type system

- **Function signature types are written by hand, not inferred**; local variables inside functions may be inferred.
- **Member variables may infer their type from an initializer**, by the same rules as locals: for example, `var speed = 5.0` is float, and `@onready var label = $Label` is inferred from the scene as Label. Members without an initializer, and members whose type cannot be inferred (empty containers, None), must be annotated. Inferred types appear on hover, in completion and in the property information the engine sees. In GDScript `var hp = 10` is an untyped member; here it is inferred as int, and assigning another type is a compile error, which the syntax hard rule allows.
- **Numbers.** The first version has only `int` (64-bit) and `float` (64-bit), matching Variant (`core/variant/variant.h:257-258`); there are no narrow types for users, and fixed-width arithmetic uses wrapping and bit-operation methods on `int`. Writing to an engine f32 location narrows implicitly, for example real_t vector components, which are float in standard builds (`core/math/math_defs.h:143-146`). Passing a value to an engine int32 parameter is range-checked, and out-of-range values are a program error; the engine itself truncates there (`core/variant/variant.h:348-349`). Mixed `int`/`float` arithmetic promotes to `float`. Assigning a `float` to an `int` requires an explicit `int(x)` and is otherwise a compile error; implicit truncation would make `hp = 2.5` silently differ from GDScript.
- **Result types of operators** follow the engine's operator table, as GDScript's static checks do (`core/variant/variant_op.cpp:256-368`). For example `Vector2 * float` is a Vector2, `Vector2i * float` is a Vector2, `int / int` is integer division, and combinations missing from the table (such as `Vector2 + Vector2i`) are compile errors. Integer division by zero is a program error.
- **Narrowing** follows Kotlin's rule: locals and parameters narrow after `!= None`, `is` and early returns, and likewise in the branches of the conditional expression `a if c else b` and in the right operand of `and` and `or`; members do not narrow and must first be read into a local. There is no truthiness; conditions must be bool. Non-null does not mean the object is still alive; access still checks.
- **Freed objects.** A reference of type `T?` that refers to a freed object reads as None, so a `!= None` check, and the narrowing it gives, is also a liveness check. A non-null reference of type `T` may hold a freed object; accessing its members is a program error, while reading, comparing and passing it are not accesses. In debug builds, if the object is an instance of this language or was freed by code of this language, the diagnostic says where it was freed. `is_instance_valid` behaves as in GDScript; after `queue_free()` an object counts as alive until it is deleted at the end of the frame. Rationale: `is_instance_valid` appears about twice per thousand lines in the corpus and eight times per thousand in phantom-camera; since 4.4 the engine also treats freed objects as false in conditions (PR #93885). The cost is a liveness lookup on every read of a `T?` object reference. Evidence: [pitfall catalog](surveys/pitfalls.en.md) G-07, G-08.
- **Reference cycles and leaks.** There is no tracing GC; RefCounted uses the engine's reference counting, and cycles are never freed. Closures capture self as in GDScript, which in a RefCounted class is a strong reference (`modules/gdscript/gdscript_lambda_callable.cpp:285-291`); by the syntax hard rule this is not silently changed to a weak reference. A typed weak reference `weak[T]` is provided: `weak(x)` creates one and `.get()` returns `T?`; to capture self weakly, write `var me = weak(self)` outside the closure and use `me.get()` inside, so no new capture syntax is needed. The compiler warns about obvious cycles, with a quick fix that rewrites to `weak`: a closure that captures self being stored in a member of self, in a connection to self's own signal, or in a container self holds; two RefCounted classes pointing at each other through fields of strong reference types. Nodes are not reference-counted: a node from `new()` or `instantiate()` that on some path is neither added to the scene tree nor returned, stored or freed gets a warning, and so does a node that is neither stored nor freed after `remove_child`. Debug builds list leaked nodes and objects with their creation sites at exit. Cycles formed indirectly through engine containers or other objects are beyond static analysis. Evidence: [pitfall catalog](surveys/pitfalls.en.md) G-10.
- **No new destructor syntax.** `_notification(what)` keeps handling `NOTIFICATION_PREDELETE`, and tree-related cleanup stays in `_exit_tree`, with the same spelling and timing as GDScript; destruction order is the engine's. The runtime guarantees that a RefCounted can read and write its own fields and call its own methods during PREDELETE, without re-referencing self. In the branch handling PREDELETE, passing self out, storing it in a member or container, and using await are compile errors; a `weak` pointing at self returns None during that time. Rationale: `NOTIFICATION_PREDELETE` occurs only 68 times in the corpus, mostly inside gdUnit4. Evidence: [pitfall catalog](surveys/pitfalls.en.md) G-09.
- **Interfaces.** Nominal: a class must declare which interfaces it implements. Interfaces may declare methods, properties and signals, and may have default methods, which read and write state through interface properties. Only classes of this language can implement interfaces; foreign objects need an explicit wrapper. The first version has no stateful mixins. Evidence: in the [cross-branch duplication survey](surveys/cross-branch-duplication.en.md), duplication caused by different native base classes is about 4–10 lines per kLOC in most game repositories; by manual judgement, 185 of its 353 lines in games could be removed with composition or static functions, and 72 of the 102 lines suited to stateful mixins come from a single project, Ring. Duplication that inheritance could have removed but did not is larger, 4.9 times as much (between unrelated scripts on the same native base) and 8.2 times as much (along one inheritance chain), but it comes mostly from a single repository, tanks-of-freedom-ii.
- **Generics.** Functions, structs, enums, and RefCounted classes created only by code in this language may be generic; Node and Resource scripts and autoloads may not, because the engine instantiates them without type arguments. Constraints are expressed with interfaces. Type arguments are kept at runtime.
- **Encapsulation and names.** Members without `pub` are visible in the file that declares them, including inner classes in that file, and subclasses may read, write, call and override them; other classes cannot see them. Members meant for other code are marked `pub` (spelling in §9). Overriding keeps visibility: an override of a `pub` member must be `pub`, and an override of a member without `pub` cannot add it. If a stricter level is needed later, a `private` keyword can be added without affecting existing code. Members that implement an interface must be `pub`. A type that is not `pub` appearing in the signature of a `pub` member is a compile error. Members the engine accesses by name (exported properties, signals, overrides of engine virtuals, methods connected in scenes) are not restricted for the engine. Evidence: in the [member visibility survey](surveys/member-visibility.en.md), about 25% of the members whose names could be resolved are accessed from other files. In the [second paper migration](surveys/paper-migration-2.en.md), if subclasses could see only `pub` members, 29 of the 102 `pub` markers would exist only for subclasses; the 7.2% estimated by the earlier survey is low because it counted common names such as `type` and `update_stat` as ambiguous. Class names use the engine's flat global table, and the compiler checks for duplicates, including clashes with GDScript plugin class names; the first version has no namespaces.

## 5. Dynamic boundary and engine bindings

- **Dynamic values have only three sources**: engine interfaces declared as Variant, parameters and return values left untyped in GDScript plugins, and messages from other languages.
- **Type at the source wherever possible.** Constraints the engine actually has but does not export are added in our own binding metadata; metadata the engine already exports is used directly. Any other dynamic value entering static code needs an explicit conversion, which reports an error on failure; there are no implicit checks.
- **Nullability of engine object returns.** Unaudited interfaces are nullable. Auditing proceeds in descending order of call frequency in the corpus and has three outcomes: non-null, typed T; null only on misuse, for example `get_tree()`, treated as non-null with a program error if null; legitimately nullable, for example `get_collider()`, typed T?. Rationale: only about 50 engine interface declarations use the `RequiredResult` annotation, 29 of them in Tween.
- **Member names as strings.** For `connect`, `emit_signal`, `call`, `call_deferred`, `set_deferred`, `has_method`, `Callable(obj, "m")`, `tween_property` and property paths such as `"position:x"`, a literal is resolved as a static reference when the target type is known: the name's existence and the value's type are checked, and it takes part in rename and find references. Which parameters are names is marked in our binding metadata. A non-literal name is explicit dynamic access.
- **Types as the engine and GDScript see them**:

  | This language | Seen by the engine and GDScript |
  |---|---|
  | `int`, `float`, `String`, classes such as Node | the type of the same name |
  | object `T` and `T?` | both the class; non-null is enforced by entry checks |
  | nullable values such as `int?` | untyped Variant |
  | `Array[T]`, `Dictionary[K, V]` with engine-representable elements | the engine's typed containers |
  | payload-less enum | int; shown as a drop-down when exported |
  | struct | Dictionary keyed by field name |
  | enum with payloads | Dictionary keyed by field name, with one reserved key holding the variant name |

  Evidence: GDScript types global classes of other languages through the Script reflection interface (`modules/gdscript/gdscript_analyzer.cpp:804-819, 4329-4370, 6054-6063`).

- **String and StringName.** Both directions convert implicitly where needed, as in GDScript; `==` compares contents. When the expected type is StringName or NodePath, a string literal is built as that type at compile time and not converted at runtime; building a StringName from a String looks it up in a global table under a mutex (`core/string/string_name.cpp:280-302`). The `&"x"` and `^"x"` prefixes remain. Runtime conversions on hot paths get a performance hint.

## 6. Data

- **Enums with payloads and exhaustive match.** Payload fields must be named, for example `Move(target: Vector3)`. Rationale: when a variant is added, the compiler lists every place that does not handle it; named fields keep the encoding independent of field order.
- **Structs** have value semantics and exist only inside this language. When crossing the engine boundary (signal arguments, Variant, messages) they are encoded automatically as Dictionaries keyed by field name and checked when decoded. In the first version they cannot be `@export`ed or stored in `.tres`; data edited in the editor uses Resource.
- **Containers.** There is one `Array[T]` and one `Dictionary[K, V]`, with the same API. When elements are engine-representable, it is the engine's container, shared with the engine; when elements are of a type only this language has, it uses its own representation, and passing it to the engine requires an explicit conversion, which makes a copy. Rationale: implicit copying would create pitfalls of the "you modified a copy" kind.
- **JSON.** The engine parses every JSON number as a float (`core/io/json.cpp:390-396`). Decoding into `int` accepts floats that are exactly integral and within int64 range, and otherwise reports an error instead of truncating.
- **The standard library** does not reimplement what the engine provides; it adds three things: typed wrappers produced by the binding audit, for example turning interfaces that return null on failure and report the error separately (such as `FileAccess.open`) into ones that return Result; support for this language's types, namely encoding and decoding structs and enums to and from JSON, `var_to_str` and ConfigFile, combinators on Option and Result, and map, filter and sort with typed lambdas on native containers; and the test runner. There is no package manager.

## 7. Errors, coroutines and signals

- **A program error** aborts the entire call chain of this language back to the entry point through which the engine called in; on the way out held references are released, the error and call stack are logged, and when running in the editor the debugger breaks; the game keeps running. Debug and release builds behave the same. If that entry point must return a value, the engine receives a default value. Expected failures are expressed with Result or Option. Rationale: after an error GDScript builds a default value for the return type and the caller continues (`modules/gdscript/gdscript_vm.cpp:3975-3979`); under static typing this would hand code fake values.
- **Option and Result** follow Rust's model: Option is a value, Result is for control flow. The only special syntax is postfix `?`, a short-circuit return. Applied to `Result[T, E]`, on `Err(e)` the current function returns `Err(e)`, otherwise it yields T; the current function must return `Result[_, E]` with the same E, and a different E is first converted with `map_err`. Applied to `T?`, on None the current function returns None; the current function must return `_?`. Using `?` in a function that returns void, or propagating between Option and Result, is a compile error. `await f()?` parses as `(await f())?`. Everything else is a method, with the same names as in Rust, for example `unwrap`, `expect` (a program error on failure), `unwrap_or`, `unwrap_or_else`, `map`, `and_then`, `or`, `or_else`, `filter`, `map_err`, `ok`, `ok_or`, `ok_or_else`; there are no `!`, `??` or `?.` operators. Results are constructed with `Ok(v)` and `Err(e)`, and success values are not wrapped implicitly; Option wraps implicitly and its empty value is None. Discarding a Result is a compile error; to deliberately ignore one, write `.ok()`. Rationale: a short-circuit return changes control flow and needs syntax; everything else transforms values, for which methods suffice, and Rust's documentation applies directly. If optional chaining `?.` were also provided, whether `x?.y` returns from the function or yields None would depend on the type of x.
- **Coroutines are declared in the signature**, for example `async func`; a function whose body contains await without the declaration is a compile error. Calling an async function yields a `Task[T]`; the task starts immediately and runs until its first suspension; `await f()` and `await t` yield T. Discarding the call's result is a compile error; to deliberately not wait, write `f().detach()`. In GDScript, using the result of a coroutine call as a value is already a compile error, so giving `var t = f()` a new meaning does not violate the syntax hard rule. Engine virtual functions may be declared async.
- **A task ends in one of three states**: finished, yielding its return value; cancelled, caused by `t.cancel()`, by its owning object being freed, or by the object it awaits being freed; failed, when a program error occurs inside it. Awaiting a cancelled task is a program error; a failure propagates up the await chain to the root task (a detached task or a task called by the engine) and cannot be intercepted. `await t.settled()` waits for the task to end in any way without an error and returns `Settled[T]`: `Finished(value: T)` or `Cancelled(reason: CancelReason)`, where `CancelReason` is `Requested`, `OwnerFreed` or `AwaitedFreed`. Result is not used, because being cancelled is not an error.
- **Cancellation.** For a suspended task, `cancel()` immediately disconnects the signal or task it is waiting on, and the task ends as cancelled. For a running task (which only happens when its own synchronous code indirectly cancels it), it runs to the next await or to its return and then ends as cancelled, discarding the return value. For a task that has already ended it has no effect. After `cancel()` the result is always cancelled. Cancellation follows ownership: a child task that a task started itself with `await f(...)` and is waiting on directly belongs to it and is cancelled with it; when awaiting a task value obtained elsewhere, cancellation only stops the wait and that task keeps running. The two forms are distinguishable at compile time. For example, when a `cutscene` suspended at `await walk_to(door)` is cancelled, `walk_to` is cancelled too and the character stops.
- **Release.** The coroutine frame (locals and the suspension point) is released as soon as the task ends; held references are released as on scope exit, and no code after the await runs. The first version has no finally or defer. The Task object is a RefCounted handle that only holds the result; it is freed when no variable, awaiter, or runtime wait on a signal refers to it any longer.
- **Combinators and re-entrancy.** `Task.of(signal)` wraps a signal as a task; `Task.delay(seconds)` waits; `Task.any(list)` returns the index of the first task to finish and cancels the others under the ownership rule above; `Task.all(list)` waits for all of them. Re-entrancy has no automatic policy; where needed, cancel the earlier call through its handle. Annotations such as `@restart` can be added compatibly later. Evidence: [pitfall catalog](surveys/pitfalls.en.md) G-12, G-13; proposals #8838 and #6243.
- **Setters and getters cannot be coroutines.**
- **Setters suspend automatically before ready.** A setter runs immediately as usual; on reaching the first statement that needs the node to be ready, if the node is not ready yet, it suspends there and continues from that point once the node is ready. Statements that need readiness are determined by static analysis: accesses to `@onready` members, `$X` or child nodes, or calls to methods of the class that access them (including overrides in subclasses). Accesses inside an `if is_node_ready():` branch do not count. If the property is written several times before ready, only the last suspended call continues and the earlier ones are cancelled; suspended calls continue after `@onready` initialization and before `_ready`, in write order; if the node is freed before it becomes ready, its suspended calls are dropped. After ready, setters never suspend. The editor shows the suspension point on hover. Rationale: this is the hand-written GDScript idiom `if not is_node_ready(): await ready`, done by the compiler, so users need no new concept. Transformation and storage finish before the suspension point, so reads before ready see the transformed value; deferring the whole setter and recording the raw input would make reads before ready see the untransformed input (for example, Ring's `Runtime/AVGRuntime/UI/UI.cs:16-35` wraps character names in 【】). In a sample of 6 corpus setters that use `await ready`, every one reads the field's current value after resuming ([property-accessor survey](surveys/property-accessors.en.md)).
- **A property whose value lives only in nodes** (no field; the getter reads a child node) is a program error to read before ready, and the diagnostic names the node that is not ready yet. If it must be readable before ready, store it in a field.
- **A property that was never written does not run its setter at ready**, as in GDScript. When an exported property's setter synchronizes nodes but its default value never passes through the setter, a hint is shown.
- **Cross-language await is supported in both directions.** A call to a GDScript method may be awaited: if a `GDScriptFunctionState` comes back at runtime, its `completed` signal is awaited and the result is checked against the declared return type; receiving one without await is a program error. Whether a function is a coroutine is not part of method reflection data (`core/object/method_info.h:37-44`), so it cannot be decided at compile time. When GDScript awaits a coroutine of this language, the coroutine's first suspension returns the `completed` signal of its Task. A Task emits `completed(value)` when it finishes, and `completed(null)` when it is cancelled or fails, so that GDScript awaiters are never left suspended; a separate `cancelled` signal serves code that needs to tell the cases apart. Both directions must be tested in an environment that can build the engine.
- **Freed objects and suspended coroutines.** When the object a coroutine belongs to is freed, the coroutine is cancelled silently and the references held by the suspended frame are released, as in GDScript. When the thing being awaited (a coroutine on another object, or the source of another object's signal) is freed before it completes, the awaiter gets a program error at the await and aborts to the engine boundary, with a diagnostic naming the freed object and where it was freed (awaiting with `settled()` yields `Cancelled(AwaitedFreed)` instead); GDScript leaves the awaiter suspended forever in this case (`modules/gdscript/gdscript_function.cpp:335-349`). A suspended coroutine does not keep self alive, as in GDScript. The freeing of any object can be observed through the instance-binding free callback that GDExtension exposes. Evidence: [pitfall catalog](surveys/pitfalls.en.md) G-11.
- **Signals and function values.** Signal parameters must be typed; emit and connect are checked statically; connections stored in scenes are checked by the scene model; engine class signals are typed from ClassDB, with unaudited object parameters nullable. Function types record parameters, return value and whether they are async. Lambdas capture by value, as in GDScript. A Callable of unknown signature needs an explicit conversion to a function type and is checked on every call.

## 8. Runtime

- **The interpreter must meet the performance goal on its own.** iOS and most console platforms do not allow generating machine code at runtime; a copy-and-patch style JIT is only an extra benefit on desktop.
- **Threads.** The virtual machine must run safely on whatever thread the engine chooses, for example background resource-loading threads and the physics thread. Data races on shared objects are the user's responsibility. The first version adds no threading API and uses the engine's Thread, WorkerThreadPool and Mutex. Evidence: across the 20 surveyed repositories, `Thread.new` occurs 11 times and `WorkerThreadPool` twice.

## 9. Syntax

- The surface follows GDScript: indentation, `func`, `var`, `extends`, `signal`, `@export`, `$X`. New constructs extend it in the same style, including structs, enums with payloads, match, interfaces, generics `[T]` and `T?`.
- **Hard rule**: a construct spelled as in GDScript either behaves as in GDScript or is a compile error with a suggested fix; it never behaves differently in silence.
- **Declaration spellings**:
  - Structs: `struct Hit:` followed by fields declared with `var`, which may have default values. Construction takes arguments by name only, for example `Hit(damage = 3, point = p)`, and fields with defaults may be omitted; allowing positional arguments later does not break existing code.
  - Enums with payloads extend GDScript's brace form, for example `enum Command { IDLE, MOVE(target: Vector3), ATTACK(target: Node3D, power: int) }`, constructed as `Command.MOVE(target = p)`. Enums without payloads keep their meaning.
  - An interface is an indented block that can declare `var`, `signal` and `func`. A method without a body has no colon, as with GDScript's `@abstract func` (`modules/gdscript/gdscript_parser.cpp:1790-1791`); a method with a body is a default method. All members of an interface are public.
  - The class header declares implemented interfaces with `implements A, B`, either on the same line as `extends`, for example `class_name Player extends CharacterBody3D implements Damageable`, or on a line of its own. They are not folded into `extends`, so the base class and the interfaces are told apart at a glance.
  - `pub` is a keyword, written after annotations and before `static`, for example `@export pub var max_hp: int`, `pub static func`, `pub signal died`. It is a keyword rather than an annotation because it is written often: at least 22 times per 1,000 lines in the [member visibility survey](surveys/member-visibility.en.md).
  - Placement and naming follow GDScript: a file is a class, and the structs, enums and interfaces declared in a file belong to that class. In the same file they are written by name; in other files as `ClassName.Name`, for example `Combat.Hit` or `Player.Command.MOVE(target = p)`; files without `class_name` are reached through `preload`. Global names come only from `class_name`. Types shared by several classes go into a class that exists to hold them. Aliases or `import` can be added later without changing the meaning of existing code.
- **Expressions.** The only conditional expression is GDScript's `a if c else b`, and its condition must be bool; there is no form that uses an if/else block as a value. For the meaning of postfix `?`, see §7; in GDScript `?` is currently a syntax error (`modules/gdscript/gdscript_parser.cpp:3834-3835`).
- **match** keeps every GDScript pattern with its meaning: literals and constant expressions compare by equality, `var x` binds, `_` is a wildcard, array and dictionary patterns with `..` inside them, several comma-separated patterns (which cannot bind), and `when` guards (`modules/gdscript/gdscript_parser.cpp:2499-2723`). New patterns:
  - An enum variant is written `Type.VARIANT(field = pattern, ...)`, where `var field` is short for `field = var field`, for example `Command.MOVE(var target)` or `Command.ATTACK(target = var enemy, power = 0)`. Fields not listed must be covered by `..`, as in dictionary patterns. Patterns nest. Structs use the same form, for example `Hit(damage = var d, ..)`.
  - `Ok(var v)` and `Err(var e)` are written positionally, as they are constructed. Option uses two branches, `None` and `var x`, and the value bound by the latter is narrowed to T.
  - A match over an enum (with or without payloads), a Result or an Option must be exhaustive or have `_`, and branches with `when` do not count toward coverage; a match over other types need not be exhaustive, as in GDScript.
  - The first version has no type patterns (use `if x is T`), no match expressions, and no binding in comma-separated patterns; adding them later does not change the meaning of existing code.
- **for** is written as in GDScript: `for i in n` iterates from 0 to n-1 with i an int; `range(...)`, containers, Strings and the keys of a Dictionary can be iterated; the loop variable may be annotated, as in `for i: int in ...`. Iterating over a float or a vector is a compile error suggesting `range(...)`; GDScript allows it and treats the vector as a range (`modules/gdscript/gdscript_vm.cpp:3093-3230`), which under static typing is almost always a mistake.

## 10. Not yet decided

- The cost of members not narrowing: to be measured in the paper migration. Two directions could relax it compatibly: conditional binding, for example `if var t = _tween:`; and narrowing fields without a getter when no call, await or assignment occurs between the check and the use.
