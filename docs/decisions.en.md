# Petrichor design decisions

**2026-10-23** · 中文: [decisions.zh.md](decisions.zh.md)

As of 2026-10-23 the project is being redesigned from the problem up. This document records the decisions made so far; each states the rule first, then the rationale and evidence. The v0.1 specification is frozen as the git tag `spec-v0.1`; where it conflicts with this document, this document prevails. A new specification will be written from it. All engine source locations refer to Godot commit `469659e`.

## 1. Problem and positioning

- **Problem**: large projects written in a dynamic language are hard to manage. GDScript is bound by backward compatibility and cannot leave dynamic typing behind; more fundamentally, the toolchain is the problem: static information from scenes never reaches the scripts, so even when every script is statically typed, node paths, signals connected in the editor, animation tracks and resource property names remain dynamic. Switching to C# makes language support second-class; the bridge has hidden pitfalls, some engine capabilities are restricted, and the toolchain's integration with Godot has pitfalls of its own.
- **Goal**: fully static typing, with dynamic values only where the engine or a third party imposes them; the same experience extends into scenes.
- **Target users**: developers who read and modify code, on medium-sized or larger projects; part of the code may be AI-generated. Small projects are better served by GDScript and are not a target.
- **Usage**: mainly new projects; third-party plugins stay in GDScript and are not required to migrate. When a plugin requires extending its GDScript classes (such as Beehave's ActionLeaf), in the first version users hand-write a thin GDScript subclass that calls code in this language; GDScript sees this language's types through reflection, so those calls are still statically checked (`modules/gdscript/gdscript_analyzer.cpp:804-819`). Cross-language inheritance at the language level would depend on GDScript's internal implementation and is not provided. Evidence: [pitfall catalog](surveys/pitfalls.en.md) C-17. The other direction is impossible too: when GDScript resolves `extends GlobalClassName`, it parses the base class's file as GDScript (`modules/gdscript/gdscript_analyzer.cpp:471-487`), so a GDScript script cannot extend a class of this language, and GDScript reports only "Could not resolve super class" (`:479, 485`). Migrating a class therefore requires migrating its GDScript subclasses with it. The analysis service reports, on any GDScript file that extends a class of this language, an error that explains why; before a class is migrated, it lists the affected subclasses and offers to migrate them together. Evidence: in the [second paper migration](surveys/paper-migration-2.en.md), Ring's Brick and Enemy brought 5 subclasses along for this reason.
- **Performance**: clearly faster than GDScript is enough; C# is not the target. Most scripts never hit the interpreter's performance limits.

## 2. Delivery and toolchain

- **Delivered as a GDExtension.** Code that touches the engine is kept in one thin adaptation layer, so that a module build remains possible later. Rationale: the [pitfall catalog](surveys/pitfalls.en.md) contains no entry that only a module could fix, and what a GDExtension cannot fix, a module cannot fix either; a GDExtension installs into the official editor and uses the official export templates. The hooks a script language needs are exposed to extensions (`core/object/script_language_extension.h:393, 493, 533, 596, 754`). Cost: web export needs "Extensions Support" enabled and cross-origin isolation headers configured.
- **The analysis service runs in the editor process.** External IDEs connect over LSP; the command line and CI run the same analysis headless. Rationale: refactorings that span scenes must modify scenes the editor has open, and only the editor can do that safely. GDScript's LSP is likewise an editor plugin (`modules/gdscript/language_server/gdscript_language_server.h:35`, `modules/gdscript/register_types.cpp:170`).
- **Refactorings include their scene half.** Mechanical, meaning-preserving edits are applied with the refactoring, previewed and undoable: renamed export property keys, method names in signal connections, animation track paths, and lossless value conversions. Edits that need judgment are only reported, with options, and never applied automatically, for example changing a node's type or an existing resource no longer matching a new type. Rationale: today, renaming an exported member silently loses the values saved in scenes. Loading does not check whether `node->set` succeeded (`scene/resources/packed_scene.cpp:567`), and saving writes only properties in the node's current property list (`packed_scene.cpp:941-950`). The other direction works the same way: when a node is renamed or moved in the scene editor, the `$X`, `%X` and literal `get_node` paths that refer to it in scripts of this language are updated automatically, in the same undo step as the editor's own updates of NodePath properties and animation tracks in the scene (`editor/docks/scene_tree_dock.cpp:2173-2260, 2280-2400`), without a preview, and the changed places are listed in the output panel afterwards. Non-literal paths, and scripts attached in other scenes where the same path still refers to another node, are only reported, not changed, with a quick fix to update the path.
- **First-version tools**:
  - live diagnostics, with the editor, LSP and command line using the same analysis;
  - completion, type on hover, go to definition, find references (including scenes);
  - rename including the scene part;
  - scene checks (`$X`, signal connections, `PackedScene[T]`, parent requirements), with errors shown in the scene editor;
  - quick fixes: insert the inferred type, add missing match arms, add an explicit conversion for a dynamic value;
  - a debugger wired into the engine's debugger UI: breakpoints, stepping, locals, call stack;
  - a bundled test runner: discovery, running, reporting, headless. Rationale: gdUnit4 and GUT require test classes to extend their GDScript base classes, and Godot does not support cross-language inheritance.
- **Later**: formatting; refactorings such as extract method, change signature and pull members up to a base class; deeper profiler integration; documentation generation; generating forwarding GDScript shells for GDScript plugin classes that must be extended.
- **The source file extension** is provisionally `.pet`, and will be fixed together with the final name before the first public release, because changing it afterwards would change every path in scenes that points to a script. The extension must be short and lowercase, must not clash with Godot or `.gd`, nor with another language in GitHub Linguist or common editors. A script language reports its extension through `get_extension` and `_get_recognized_extensions` (`core/object/script_language_extension.h:287, 697`).
- **Hot reload has two levels.** When only function bodies change, they are replaced while running; the next call uses the new code, and suspended coroutines finish on the old version. When members, signatures or class structure change, no state is migrated and a restart is requested; tool scripts in the editor get their instances rebuilt.

## 3. Scenes and nodes

- **Node types are inferred from scenes.** The compiler collects every scene structure a script can see, including inherited scenes and edits on instances, and types `$X`, `%X` and literal `get_node` paths from them. If structures disagree on a type, that is an error requiring an annotation. Evidence: in the game repositories of the [scene-structure survey](surveys/scene-structures.en.md), none of 2,023 literal paths resolves to different types in different structures.
- **Structures that differ between scenes use existing spellings**, with no new declaration. A path that cannot be found is an error, reported on the scene that lacks the node; which scenes need the node follows how scenes are used, with the same rules as required exports (below): a scene used only as the base of inheritance may lack it, a scene used as a root or instanced must have it, and a scene referenced from nowhere gets only a warning. So children a base class requires and inheriting scenes provide need no declaration, and the type of `$X` comes from the scenes that have the node; for example, tanks-of-freedom-ii's `base_ground.tscn` lacks the `$"mesh"` used by `tile.gd`, and since it is preloaded as a placeholder tile, which is a use as a root, the error is marked on it. Optional children are declared by `get_node_or_null(...)` with a literal path, typed `T?`; scenes lacking the node are not errors, and when `$X` is missing in a used scene, the quick fix changes the access to `get_node_or_null`. Children added at runtime are not typed by path: `$X` found in no scene is a compile error, and the quick fix suggests storing the node in a typed member at `add_child`, such as `var tetromino: Tetromino?`; a lookup by name that is really needed uses `get_node_or_null("X")`, which yields a `Node?` to convert with `as`. A literal path that exists in no scene gets a warning, which catches paths not updated after a rename, such as tps-demo's `door.gd:6`; for a node really added at runtime, `@warning_ignore` turns it off. Evidence: in the [scene structure survey](surveys/scene-structures.en.md), 8 paths in game code missing in some structures use `get_node_or_null`, and 7 are nodes that template or placeholder scenes lack.
- **Upward access.** Autoload access via `/root/X` uses typed autoload global names instead. Parent and owner requirements are written as the class-level annotations `@parent(T)` and `@owner(T)`, placed where `@tool` goes; `get_parent()`, `..` and `owner` then have type T, and without a declaration they are Node, with an explicit conversion needed for a more specific type. They are checked statically where scenes place the script; the owner is the root of the scene that contains the node, and a script on a scene's root has no owner, so declaring `@owner` there is a compile error. At runtime, the parent requirement is checked when the node is attached to a parent (`NOTIFICATION_PARENTED`, `scene/main/node.h:466`); `owner` is checked on every read to be non-null and to satisfy the requirement, and a failure is a program error whose diagnostic names the requirement and the actual owner. Owner is not checked when nodes move: when a node is taken out of its owner's subtree, the engine sets owner to null (`scene/main/node.cpp:391-396, 1799-1801`), and that is a legitimate operation; for example Ring's DeathComponent reads its owner and then moves itself to the foreground layer. Code that needs to test whether there is an owner uses `get_owner()`, whose type is `Node?`.
- **Scene resources.** `preload` and `load` with a literal path are typed by the resource's actual content. An exported scene is written `PackedScene[T]`, and the editor checks the scene assigned to it; `instantiate()` yields T. `load` with a path known only at runtime yields Node and needs an explicit conversion.
- **Non-null exported references must be assigned.** The check follows how each scene is used. When a scene is instanced or inherited by other scenes, an assignment at any level of the instance and inheritance chain counts; each instance is checked separately, and a missing value is marked on the scene containing that instance. When a scene is used as a root (the main scene, a scene loaded with `load` or `preload` from a literal path, a scene exported as `PackedScene[T]`), the scene itself is checked. A scene created in code with `instantiate(...)` is checked against the values passed at the call site (see the next item). A scene referenced from nowhere gets only a warning, because a `load` whose path is known only at run time cannot be seen. For example, `crosshair` in player.tscn points to a node that exists only in main.tscn, which assigns it on the instance, so player.tscn itself is not an error. Checks happen at three points. While editing, clearing is allowed: the field in the Inspector and the node in the scene tree are marked with an error at once, but no operation is blocked, and the mark disappears when a value is assigned again. When running, the game may run; a node still missing a value raises a program error when it becomes ready, checked before `@onready` initialization, and the diagnostic names the member, as when player.tscn is run on its own in the editor. When exporting a release build, export is refused where a value is certain to be missing, and warnings do not block it. Nodes created in code must be assigned before they become ready. Reading a member that has not been assigned yet before ready is a program error. Resources have no ready phase: assignments in `.tres` files are checked statically, and resources created with `new()` in code are checked on read. When the remote inspector writes null to a non-null member, the entry check rejects the write and the value is unchanged. Members that may genuinely be missing are written `T?`. Rationale: clearing and then replacing is a normal step while editing, so non-null constrains the finished scene; replacing does not even require clearing first, since node references are stored as paths in `.tscn` and resolved during instantiation (`scene/resources/packed_scene.cpp:449-468`).
- **Constructor parameters are expressed as members that must be assigned.** `_init` of Node and Resource scripts cannot take parameters, because the engine always constructs them with zero arguments ([pitfall catalog](surveys/pitfalls.en.md) G-02). Non-null members without a default must be assigned before their scene has finished becoming ready: exported ones may be provided by the scene; the rest by the creator before ready, or by an ancestor node in the same scene in its own `_ready`, provided the scene model can see the assignment (`$Child.target = v`, or through an `@onready` reference). Members assigned by an ancestor are checked once the whole scene is ready. Ready propagates synchronously when a node enters the tree (`scene/main/node.cpp:3425-3429`), and per-frame callbacks come from the main loop, so ordinary logic cannot read the missing value. A child reading such a member in its own `_ready` is a compile error. If the configuration is invisible to the scene model (for example assignments in a loop over `get_children()`), the member must be written `T?`. The checks of the previous item apply to these members as well. `instantiate(...)` and `new(...)` accept member values by name and assign them before returning. For `PackedScene[T]`, the compiler checks at the call site that every must-assign member the scene does not provide is passed; for example, leaving out `target` in `BulletScene.instantiate(speed = 300.0, target = enemy)` is a compile error. A must-assign member without `pub` that no scene or ancestor assigns is an error at the class definition. Scenes whose path is known only at runtime have only the check at ready. RefCounted classes created only by code of this language use `_init` with parameters as usual. An autoload outlives scenes, so its members that refer to scene nodes can only be `T?`; where non-null is wanted, make the manager a node in the scene and refer to the other nodes through must-assign exports. The first version has no "non-null member assigned after ready" (like Kotlin's `lateinit`); it can be added later if needed. Evidence: across the 20 surveyed repositories, registering a node on an autoload member in `_ready` (`Autoload.x = self`) occurs only 6 times, 5 of them in Ring ([second paper migration](surveys/paper-migration-2.en.md)).
- **`@onready` keeps GDScript's timing**: initializers run before `_ready`, base class first, each in declaration order. The following are compile errors: combining `@onready` with `@export`; await in an initializer; reading an `@onready` member directly in `_init` or `_enter_tree`. Reading an `@onready` member that is not initialized yet through a call is a program error, and the diagnostic names the member. Evidence: [pitfall catalog](surveys/pitfalls.en.md) G-04.
- **Children become ready before their parent, as in the engine; no lifecycle hook is added.** When a child reads a member of its parent that is not initialized yet in `_ready`, a program error explains why; quick fixes offer two rewrites: configure the child from the parent's own `_ready`, or declare the child's `_ready` async and `await get_parent().ready`. Such a read is valid when the child is added at runtime under a parent that is already ready, so it is not rejected at compile time. A node that re-enters the tree does not run `_ready` again, as in the engine. Evidence: [pitfall catalog](surveys/pitfalls.en.md) G-03, G-05.
- **Initializers write fields directly, without the setter**, for both instance and static members, matching GDScript's current behavior (`modules/gdscript/gdscript_compiler.cpp:2435-2451, 2620-2643`). An initializer gives the first value, while a setter handles changes; at initialization there are no observers, and members declared later are not initialized yet. Derived state is computed in `_ready` or `_static_init`; when a member has both an initializer and a setter, the compiler notes that initialization does not go through the setter.
- **Static members** keep GDScript's spelling and timing: `static var`, `static func`, `_static_init()`; when a class loads, static members are initialized base class first, in declaration order, and then `_static_init` is called (`gdscript_compiler.cpp:2646-2649`). When a class reads another class's static member during its static initialization, that class is initialized first; a cycle among static initializations is a program error whose diagnostic lists the dependency chain, reported at compile time when statically visible, so default or half-initialized values are never read (for GDScript's related problems see #104161, #82141, #104588). Static initialization cannot await. Changing static members is a structural change, and hot reload requests a restart. Rationale: the corpus has about 214 `static var` and 4 `_static_init`, so contact is rare.

- **Resource sharing keeps its semantics; the scene model finds the problems.** The compiler knows which resources are shared: resources from `load`, `preload` and exported properties come from the cache, and embedded subresources not set to local-to-scene are shared by every instance of their scene. Writing a property of a resource known to be shared, or calling a method that modifies it, produces a warning that lists where it is shared, with two quick fixes: make it local to scene in the scene, or `duplicate()` it before modifying. Deliberate changes to a shared resource are silenced with `@warning_ignore`; resources replaced only at runtime cannot be tracked and produce no warning. `duplicate()` returns the receiver's static type; copy depth is stated with `duplicate_deep(mode)`. Reference cycles among `preload`, exported PackedScenes and resources are reported before running, with a suggestion to turn one edge into a runtime `load`. Evidence: [pitfall catalog](surveys/pitfalls.en.md) G-19, G-20, G-34. Example: in godot-open-rpg, the CircleShape2D embedded in `interaction_popup.tscn` is not local to scene, the setter at `interaction_popup.gd:30` changes its radius, and in `main.tscn:484-486` only one instance sets radius to 64; by the engine's sharing rules, the dozen or so instances share one shape whose radius is whatever the last setter wrote (inferred, not verified by running).

## 4. Type system

- **Function signature types are written by hand, not inferred**; local variables inside functions may be inferred. An override of an engine virtual or of a base-class method may omit its parameter and return types, which are then taken from the overridden declaration and shown on hover; types that are written follow GDScript's override check: the return type may be covariant, parameter types may be contravariant, and extra parameters with defaults may be added (`modules/gdscript/gdscript_analyzer.cpp:1892-1933`); parameter names may differ. For example, delta in `func _process(delta):` is a float. This is not inference: the types are set by the overridden declaration, not by the body. For a function that is not an override, an omitted return type means void; returning a value from it is a compile error, and the quick fix adds the return type. A lambda is code inside a function and is inferred by the local rules: its parameter types come from the expected function type when there is one and must be written otherwise, and its return type is inferred from its body, as in `weapon.map(func(w): return w.name)`; a lambda containing await must be written `async func` (§7). Evidence: the [second paper migration](surveys/paper-migration-2.en.md) has 6 parameter annotations on engine virtual overrides.
- **Member variables may infer their type from an initializer**, by the same rules as locals: for example, `var speed = 5.0` is float, and `@onready var label = $Label` is inferred from the scene as Label. Members without an initializer, and members whose type cannot be inferred (empty containers, None), must be annotated. Of the members without an initializer, numbers, bool, String, core value types, containers and enums without payloads start at their default value, as in GDScript; a struct starts at its default when every field has a default and must otherwise be assigned like an object reference; an enum with payloads must be assigned. Inferred types appear on hover, in completion and in the property information the engine sees. In GDScript `var hp = 10` is an untyped member; here it is inferred as int, and assigning another type is a compile error, which the syntax hard rule allows.
- **Numbers.** The first version has only `int` (64-bit) and `float` (64-bit), matching Variant (`core/variant/variant.h:257-258`); there are no narrow types for users, and fixed-width arithmetic uses wrapping and bit-operation methods on `int`. Writing to an engine f32 location narrows implicitly, for example real_t vector components, which are float in standard builds (`core/math/math_defs.h:143-146`). Passing a value to an engine int32 parameter is range-checked, and out-of-range values are a program error; the engine itself truncates there (`core/variant/variant.h:348-349`). Mixed `int`/`float` arithmetic promotes to `float`, and an int converts implicitly to float in assignments, arguments and returns. Assigning a `float` to an `int` requires an explicit `int(x)` and is otherwise a compile error; implicit truncation would make `hp = 2.5` silently differ from GDScript.
- **Result types of operators** follow the engine's operator table, as GDScript's static checks do (`core/variant/variant_op.cpp:256-368`). For example `Vector2 * float` is a Vector2, `Vector2i * float` is a Vector2, `int / int` is integer division, and combinations missing from the table (such as `Vector2 + Vector2i`) are compile errors. Integer division by zero is a program error.
- **`==`** is typed by the engine's operator table too, and a combination missing from the table is a compile error, for example `hp == "3"`. int and float compare numerically, so `1 == 1.0` is true (`core/variant/variant_op.cpp:490-491`); String and StringName compare contents. Objects compare by identity (`variant_op.cpp:514`); when both types are classes and neither is a subclass of the other, it is a compile error, since the result is always false, while comparisons involving interfaces are allowed. Option: None equals None, two Somes are equal when their contents are, and an operand that is not an Option is wrapped first, as in `hp == 3` with hp an `int?`; comparing a value that is neither an Option nor a Variant with None is a compile error, and the quick fix changes the type to `T?`, or uses `is_instance_valid(x)` for a liveness check. Containers compare element by element as in the engine; the engine requires compared elements to have the same type (`core/variant/array.cpp:153-156`, `core/variant/variant.cpp:3213-3216`), so `[1] == [1.0]` is false while `1 == 1.0` is true; comparing containers with different element types, such as `Array[int] == Array[float]`, is a compile error, since they are equal only when both are empty. When one operand is a Variant, the comparison is evaluated at runtime by the engine's operator table, and a combination missing from the table is a program error, as in GDScript (`variant_op.cpp:1051-1056`, `modules/gdscript/gdscript_vm.cpp:756-761, 794-802`). `!=` is the negation of `==` in every case. For `==` on structs and enums with payloads, see §6.
- **Narrowing** follows Kotlin's rule: locals and parameters narrow after `!= None`, `is` and early returns, and likewise in the branches of the conditional expression `a if c else b` and in the right operand of `and` and `or`; members do not narrow and must first be read into a local. There is no truthiness; conditions must be bool. Non-null does not mean the object is still alive; access still checks. Evidence: in the [second paper migration](surveys/paper-migration-2.en.md), only 4 locals were added because members do not narrow, 4.4 per 1,000 lines. Relaxing this later, with conditional binding (such as `if var t = _tween:`) or by narrowing fields without a getter when no call, await or assignment occurs between the check and the use, would not break existing code.
- **Freed objects.** A reference of type `T?` that refers to a freed object reads as None, so a `!= None` check, and the narrowing it gives, is also a liveness check. A non-null reference of type `T` may hold a freed object; accessing its members is a program error, while reading, comparing and passing it are not accesses. In debug builds, if the object is an instance of this language or was freed by code of this language, the diagnostic says where it was freed. `is_instance_valid` behaves as in GDScript; after `queue_free()` an object counts as alive until it is deleted at the end of the frame. Rationale: `is_instance_valid` appears about twice per thousand lines in the corpus and eight times per thousand in phantom-camera; since 4.4 the engine also treats freed objects as false in conditions (PR #93885). The cost is a liveness lookup on every read of a `T?` object reference. Evidence: [pitfall catalog](surveys/pitfalls.en.md) G-07, G-08.
- **Reference cycles and leaks.** There is no tracing GC; RefCounted uses the engine's reference counting, and cycles are never freed. Closures capture self as in GDScript, which in a RefCounted class is a strong reference (`modules/gdscript/gdscript_lambda_callable.cpp:285-291`); by the syntax hard rule this is not silently changed to a weak reference. A typed weak reference `weak[T]` is provided: `weak(x)` creates one and `.get()` returns `T?`; to capture self weakly, write `var me = weak(self)` outside the closure and use `me.get()` inside, so no new capture syntax is needed. The compiler warns about obvious cycles, with a quick fix that rewrites to `weak`: a closure that captures self being stored in a member of self, in a connection to self's own signal, or in a container self holds; two RefCounted classes pointing at each other through fields of strong reference types. Nodes are not reference-counted: a node from `new()` or `instantiate()` that on some path is neither added to the scene tree nor returned, stored or freed gets a warning, and so does a node that is neither stored nor freed after `remove_child`. Debug builds list leaked nodes and objects with their creation sites at exit. Cycles formed indirectly through engine containers or other objects are beyond static analysis. Evidence: [pitfall catalog](surveys/pitfalls.en.md) G-10.
- **No new destructor syntax.** `_notification(what)` keeps handling `NOTIFICATION_PREDELETE`, and tree-related cleanup stays in `_exit_tree`, with the same spelling and timing as GDScript; destruction order is the engine's. The runtime guarantees that a RefCounted can read and write its own fields and call its own methods during PREDELETE, without re-referencing self. In the branch handling PREDELETE, passing self out, storing it in a member or container, and using await are compile errors; a `weak` pointing at self returns None during that time. Rationale: `NOTIFICATION_PREDELETE` occurs only 68 times in the corpus, mostly inside gdUnit4. Evidence: [pitfall catalog](surveys/pitfalls.en.md) G-09.
- **Interfaces.** Nominal: a class must declare which interfaces it implements. Interfaces may declare methods, properties and signals, and may have default methods, which read and write state through interface properties. A property requirement can be satisfied by an inherited engine property, for example `var global_position: Vector2` by Node2D's property of that name; the type must be the same and the read and write access must match. Only classes of this language can implement interfaces; foreign objects need an explicit wrapper. The first version has no stateful mixins. An interface can extend several interfaces, written `interface Combatant extends Damageable, Healable:`; a class implementing the child interface also implements each parent, and a value of the child interface can be used where a parent is expected. A child interface may redeclare a parent's method with a covariant return type; when two parents have members of the same name with incompatible signatures, it is a compile error on the child interface; when two parents both provide a default implementation for a method of the same name, the child interface or the implementing class must override it; a cycle of extension is a compile error. Evidence: of the 16 classes in gdUnit4 that have only abstract methods, 14 extend GdUnitAssert, which also has only abstract methods, and redeclare its methods with more specific return types; for example, `is_null() -> GdUnitAssert` at `GdUnitAssert.gd:7` is written `is_null() -> GdUnitIntAssert` at `GdUnitIntAssert.gd:7`. In the first version interfaces cannot be generic: generic interfaces need decisions on variance (whether `Source[Enemy]` is a `Source[Node]`) and on self-referential constraints such as `Comparable[T]`; no need has been seen, and sorting and comparison use lambdas; they can be added later compatibly, written `interface Source[T]:`. Evidence: in the [cross-branch duplication survey](surveys/cross-branch-duplication.en.md), duplication caused by different native base classes is about 4–10 lines per kLOC in most game repositories; by manual judgement, 185 of its 353 lines in games could be removed with composition or static functions, and 72 of the 102 lines suited to stateful mixins come from a single project, Ring. Duplication that inheritance could have removed but did not is larger, 4.9 times as much (between unrelated scripts on the same native base) and 8.2 times as much (along one inheritance chain), but it comes mostly from a single repository, tanks-of-freedom-ii.
- **Generics.** Functions, structs, enums, and RefCounted classes created only by code in this language may be generic; Node and Resource scripts and autoloads may not, because the engine instantiates them without type arguments. Constraints are expressed with interfaces. Type arguments are kept at runtime. Generic methods are not exposed through reflection, because the engine and GDScript cannot supply type arguments when calling by name; to use one as a Callable, its type arguments must be fixed, for example `sig.connect(handle[int])`. The spelling is in §9.
- **Encapsulation and names.** Members without `pub` are visible in the file that declares them, including inner classes in that file, and subclasses may read, write, call and override them; other classes cannot see them. Members meant for other code are marked `pub` (spelling in §9). Overriding keeps visibility: an override of a `pub` member must be `pub`, and an override of a member without `pub` cannot add it. If a stricter level is needed later, a `private` keyword can be added without affecting existing code. Members that implement an interface must be `pub`. A type that is not `pub` appearing in the signature of a `pub` member is a compile error. Members the engine accesses by name (exported properties, signals, overrides of engine virtuals, methods connected in scenes) are not restricted for the engine. Evidence: in the [member visibility survey](surveys/member-visibility.en.md), about 25% of the members whose names could be resolved are accessed from other files. In the [second paper migration](surveys/paper-migration-2.en.md), if subclasses could see only `pub` members, 29 of the 102 `pub` markers would exist only for subclasses; the 7.2% estimated by the earlier survey is low because it counted common names such as `type` and `update_stat` as ambiguous. Class names use the engine's flat global table, and the compiler checks for duplicates, including clashes with GDScript plugin class names; the first version has no namespaces.

## 5. Dynamic boundary and engine bindings

- **Dynamic values have only three sources**: engine interfaces declared as Variant, parameters and return values left untyped in GDScript plugins, and messages from other languages. Of the members, parameters and return values of GDScript classes seen through reflection, object types are taken as `T?`, value types as declared, and untyped ones are dynamic values.
- **Utility functions bound with Variant** (lerp, clamp, min, max, abs, wrap and others) are typed by their arguments in the binding metadata: when the arguments have the same type, the result has that type. Mixing int and float is a compile error, and the quick fix turns the integer argument into a float, as in `min(ratio, 1.0)`; the engine's min, max and clamp return one of their arguments unchanged (`core/variant/variant_utility.cpp:643-760`), so in GDScript `min(1.5, 1)` is an int, and promoting to float would make the result silently differ. lerp itself requires both arguments to have the same type (`variant_utility.cpp:466-470`).
- **Type at the source wherever possible.** Constraints the engine actually has but does not export are added in our own binding metadata; metadata the engine already exports is used directly. Any other dynamic value entering static code needs an explicit conversion, which reports an error on failure; there are no implicit checks.
- **Operations on Variant.** Static values enter a Variant implicitly, by assignment, as arguments and as return values; structs and enums with payloads are encoded as in the table below. A Variant enters static code only explicitly: `v as T` (for objects only, yielding `T?`), `T(v)`, `T.try_from(v)`, and `if v is T:`, in whose branch locals and parameters narrow to T. `==` and `!=` use the engine's Variant comparison (§4). Every other operation is a compile error with a fix, including operators, member access `v.x`, method calls `v.f()`, subscripts `v[i]` and `for x in v`; the fix inserts a conversion or `if v is T:`. Dynamic access by name, where really needed, converts to Object first and then uses the engine's `get`, `set` and `call`. GDScript executes these positions dynamically, so making them compile errors is within the syntax hard rule. A Variant includes NIL: `v == None` tests for NIL, `v is int` is false for NIL, and `v as Node` yields None for NIL; `Variant?` differs from Variant (§7). For example, the result of `JSON.parse_string(text)` is first checked with `if data is Dictionary:`, then read with `int.try_from(data.get("hp")).unwrap_or(100)`.
- **Conversions.** `x as T` is only for object types, and its result is `T?`: None when the type does not match, as in GDScript (`modules/gdscript/gdscript_vm.cpp:1665-1666`); when the static type of x already is T, the result is T and the redundant `as` is pointed out. `as` to a built-in type is a compile error: GDScript converts through the constructor there (`gdscript_vm.cpp:1630-1637`), so the quick fix offers `T(x)`, which keeps that conversion, as in `int("5")`, or `T.try_from(x)`. `T.try_from(v)` is the strict explicit conversion: it returns `Result[T, ConversionError]` under the same rules as decoding a struct field, accepting a float that is exactly an integer when converting to int; `?` propagates the failure, and `.unwrap()` or `.expect(…)` turns it into a program error. A downcast that must succeed is written `(x as T).unwrap()`. Interfaces that filter by a literal class name are typed by that class, for example `find_children("*", "MeshInstance3D")` returns `Array[MeshInstance3D]`; for code that tests group membership and then downcasts, the quick fix suggests `is` instead. Evidence: the [second paper migration](surveys/paper-migration-2.en.md) has 16 occurrences of `(x as T).unwrap()`.
- **Nullability of engine object returns.** Unaudited interfaces are nullable. Auditing proceeds in descending order of call frequency in the corpus and has three outcomes: non-null, typed T; null only on misuse, for example `get_tree()`, treated as non-null with a program error if null; legitimately nullable, for example `get_collider()`, typed T?. Rationale: only about 50 engine interface declarations use the `RequiredResult` annotation, 29 of them in Tween.
- **Member names as strings.** For `connect`, `emit_signal`, `call`, `call_deferred`, `set_deferred`, `has_method`, `Callable(obj, "m")`, `tween_property` and property paths such as `"position:x"`, a literal is resolved as a static reference when the target type is known: the name's existence and the value's type are checked, and it takes part in rename and find references. Which parameters are names is marked in our binding metadata. A non-literal name is explicit dynamic access.
- **Members exposed through reflection.** Through reflection (`get_property_list`, `has_method`, and `call`, `get` and `set` by name), the engine, GDScript and C# see only `pub` members and the members the engine must find by name. The latter are the exported properties, signals, overrides of engine virtuals and methods connected in scenes listed in §4, plus the members that code in this language hands to the engine by a literal name, such as `call_deferred("reset")`, `tween_property(self, "current_speed")` and property paths in animation tracks of scenes, which the compiler collects. All other members are invisible to access by name: referring to them from GDScript is a GDScript compile error, and C#'s `Call` and dynamic access with a non-literal name report a missing member at runtime. A Callable formed from a method value (such as `tween_callback(change_weapon)` or `sig.connect(_on_x)`) refers to the method directly, not by name, and is not affected. The debugger sees all members. Rationale: members without `pub` are referred to only by their file, subclasses and the literal names the compiler collects, so the tools can find every reference when renaming them.
- **Types as the engine and GDScript see them**:

  | This language | Seen by the engine and GDScript |
  |---|---|
  | `int`, `float`, `String`, classes such as Node | the type of the same name |
  | object `T` and `T?` | both the class; non-null is enforced by entry checks |
  | nullable values such as `int?` | untyped Variant |
  | `Array[T]`, `Dictionary[K, V]` with engine-representable elements | the engine's typed containers |
  | payload-less enum | int; shown as a drop-down when exported |
  | struct | Dictionary keyed by field name |
  | enum with payloads | Dictionary keyed by field name, with one reserved key holding the variant name |

  Evidence: GDScript types global classes of other languages through the Script reflection interface (`modules/gdscript/gdscript_analyzer.cpp:804-819, 4329-4370, 6054-6063`).

- **String and StringName.** Both directions convert implicitly where needed, as in GDScript; `==` compares contents. When the expected type is StringName or NodePath, a string literal is built as that type at compile time and not converted at runtime; building a StringName from a String looks it up in a global table under a mutex (`core/string/string_name.cpp:280-302`). The `&"x"` and `^"x"` prefixes remain. Runtime conversions on hot paths get a performance hint.

## 6. Data

- **Enums with payloads and exhaustive match.** Payload fields must be named, for example `Move(target: Vector3)`. Rationale: when a variant is added, the compiler lists every place that does not handle it; named fields keep the encoding independent of field order. `==` compares the variant first and then the fields one by one, and hashing agrees with `==`. Payload fields can be taken out only through match, not as `c.target`, so payloads cannot be modified in place; a new value is constructed instead. In the first version enums with payloads cannot have methods, because the brace form has no place for function bodies, so related functions go in the enclosing class; nor can they be `@export`ed, for the same reason as structs.
- **Structs** have value semantics and exist only inside this language. When crossing the engine boundary (signal arguments, Variant, messages) they are encoded automatically as Dictionaries keyed by field name and checked when decoded; decoding descends into containers and nested structs, as in `Dictionary[String, ConsumableState]`. In the first version they cannot be `@export`ed or stored in `.tres`; data edited in the editor uses Resource. A struct can declare `func` and `static func`, and its fields and methods are visible wherever the struct is. Inside methods self is read-only: assigning to a field of self is a compile error, and a method that needs a change returns a modified copy; methods that modify self can be added later compatibly. Rationale: a method that modifies self needs a call site that can be written back, and called on a temporary, on a property read through a getter, or on a loop variable, it would either be an error or silently modify a copy; the first version need not settle rules for that. `s.x = 1` modifies the copy where s lives (a variable, a member or a container element); a chained assignment reads, modifies and writes back along the chain, as GDScript does for `node.position.x = 1` (`modules/gdscript/gdscript_compiler.cpp:1176-1194`); for example, `player.last_hit.damage = 3` writes back through player's setter, and `hits[0].damage = 3` modifies the element in the array; assigning to a field of a temporary is a compile error, for example `get_hit().damage = 3`. Loop variables and lambda captures are copies, as with Vector2 in GDScript; modifying a field of a struct-typed loop variable that is not read afterwards gives a "modifies a copy" warning. Copies are shallow: object and container fields copy the reference, as these values do when assigned anywhere else; when an independent container is needed, call `duplicate()` on that field. `==` compares field by field, each field by the `==` of its own type (§4); hashing agrees with `==`, and structs can be Dictionary keys; a key is a copy, so later changes to the original do not affect it.
- **Containers.** There is one `Array[T]` and one `Dictionary[K, V]`, with the same API. When elements are engine-representable, it is the engine's container, shared with the engine; when elements are of a type only this language has, it uses its own representation, and passing it to the engine requires an explicit conversion, which makes a copy. Rationale: implicit copying would create pitfalls of the "you modified a copy" kind. `pop_front()` and `pop_back()` return `T?`, because the engine returns null on an empty array without reporting an error (`core/variant/array.cpp:798-817`); `front()` and `back()` return T and are a program error on an empty array, where the engine reports an error too (`array.cpp:364-372`); an out-of-range index is a program error. When T is itself nullable, `pop_front()` and `pop_back()` return `T??`, and the binding layer checks for an empty array first. `Dictionary[K, V].get(k)` returns `V?`, None when the key is missing, matching the engine returning the default for a missing key (`core/variant/dictionary.cpp:177-188`); `get(k, default)` returns V.
- **JSON.** The engine parses every JSON number as a float (`core/io/json.cpp:390-396`). Decoding into `int` accepts floats that are exactly integral and within int64 range, and otherwise reports an error instead of truncating.
- **The standard library** does not reimplement what the engine provides; it adds three things: typed wrappers produced by the binding audit, for example turning interfaces that return null on failure and report the error separately (such as `FileAccess.open`) into ones that return Result; support for this language's types, namely encoding and decoding structs and enums to and from JSON, `var_to_str` and ConfigFile, combinators on Option and Result, and map, filter and sort with typed lambdas on native containers; and the test runner. There is no package manager.

## 7. Errors, coroutines and signals

- **A program error** aborts the entire call chain of this language back to the entry point through which the engine called in; on the way out held references are released, the error and call stack are logged, and when running in the editor the debugger breaks; the game keeps running. Debug and release builds behave the same. If that entry point must return a value, the engine receives a default value. Expected failures are expressed with Result or Option. Rationale: after an error GDScript builds a default value for the return type and the caller continues (`modules/gdscript/gdscript_vm.cpp:3975-3979`); under static typing this would hand code fake values.
- **`assert` is removed in release builds, as in GDScript**, and neither its condition nor its message is evaluated (`modules/gdscript/gdscript_compiler.cpp:2182-2208`); in debug builds a failure is a program error (for GDScript see `modules/gdscript/gdscript_vm.cpp:3869-3895`). This is the only exception to "debug and release builds behave the same". The condition and message cannot contain await or postfix `?`, which is a compile error, because they would vanish with the assertion in release builds; the condition must be bool, so `assert(save_data, "...")` is a compile error whose quick fix changes it to `save_data != None`. Checks also needed in release builds use `expect` or an explicit `if`; an always-on assertion can be added later compatibly. Rationale: the syntax hard rule; in the [corpus counts](surveys/corpus-counts.en.md), the conditions of the 595 asserts are almost all queries, such as `peers.has(peer_id)`, and none has await in its arguments.
- **Option and Result** follow Rust's model: Option is a value, Result is for control flow. The only special syntax is postfix `?`, a short-circuit return. Applied to `Result[T, E]`, on `Err(e)` the current function returns `Err(e)`, otherwise it yields T; the current function must return `Result[_, E]` with the same E, and a different E is first converted with `map_err`. Applied to `T?`, on None the current function returns None; the current function must return `_?`. Using `?` in a function that returns void, or propagating between Option and Result, is a compile error. `await f()?` parses as `(await f())?`. Everything else is a method, with the same names as in Rust, for example `unwrap`, `expect` (a program error on failure), `unwrap_or`, `unwrap_or_else`, `map`, `and_then`, `or`, `or_else`, `filter`, `map_err`, `ok`, `ok_or`, `ok_or_else`; there are no `!`, `??` or `?.` operators. Results are constructed with `Ok(v)` and `Err(e)`, and success values are not wrapped implicitly; Option wraps implicitly and its empty value is None. Discarding a Result is a compile error; to deliberately ignore one, write `.ok()`. Rationale: a short-circuit return changes control flow and needs syntax; everything else transforms values, for which methods suffice, and Rust's documentation applies directly. If optional chaining `?.` were also provided, whether `x?.y` returns from the function or yields None would depend on the type of x.
- **Nested Options keep two levels**, as in Rust: `T??` is a valid type, mostly produced by generics and containers. Implicit wrapping adds levels according to the target type: a `T?` value assigned to a `T??` gives a Some containing that value, and the literal None is always the outermost None. `?`, `unwrap`, match and narrowing each remove one level, and `.flatten()` merges `T??` into `T?`. `Variant?` works the same way: None means no value, and NIL is a value. None is encoded as NIL when handed to the engine, so `X?` can be handed to the engine implicitly only when no value of X encodes as NIL; when X is an Option or Variant it is a compile error, and the quick fix offers `.flatten()` or `.unwrap_or(null)`, since otherwise Some(None) would silently turn into None after a round trip through the engine. Rationale: with one merged level, generic code would behave differently depending on T; for example, `first[T]` with T = `Enemy?` could not tell an empty array from a first element that is None, and a generic cache would take a stored None for a missing entry; a missing JSON key could not be told from null either. There is no `?.` here, so nesting appears almost only in generics and when reading from containers.
- **Coroutines are declared in the signature**, for example `async func`; a function whose body contains await without the declaration is a compile error. Calling an async function yields a `Task[T]`; the task starts immediately and runs until its first suspension; `await f()` and `await t` yield T. Discarding the call's result is a compile error; to deliberately not wait, write `f().detach()`. In GDScript, using the result of a coroutine call as a value is already a compile error, so giving `var t = f()` a new meaning does not violate the syntax hard rule. Engine virtual functions may be declared async. The same holds for lambdas: a lambda containing await is written `async func(...)`; GDScript marks such lambdas with nothing (`modules/gdscript/gdscript_parser.cpp:3223-3225, 3726-3727`), and the quick fix adds `async`. Rationale: there is a single rule for whether a function is async, and a suspension point always has async in sight; in the [corpus counts](surveys/corpus-counts.en.md), only 35 of 979 lambdas contain await, 33 of them in gdUnit4's tests.
- **A task ends in one of three states**: finished, yielding its return value; cancelled, caused by `t.cancel()`, by its owning object being freed, or by the object it awaits being freed; failed, when a program error occurs inside it. Awaiting a cancelled task is a program error; a failure propagates up the await chain to the root task (a detached task or a task called by the engine) and cannot be intercepted. `await t.settled()` waits for the task to end in any way without an error and returns `Settled[T]`: `Finished(value: T)` or `Cancelled(reason: CancelReason)`, where `CancelReason` is `Requested`, `OwnerFreed` or `AwaitedFreed`. Result is not used, because being cancelled is not an error.
- **Cancellation.** For a suspended task, `cancel()` immediately disconnects the signal or task it is waiting on, and the task ends as cancelled. For a running task (which only happens when its own synchronous code indirectly cancels it), it runs to the next await or to its return and then ends as cancelled, discarding the return value. For a task that has already ended it has no effect. After `cancel()` the result is always cancelled. Cancellation follows ownership: a child task that a task started itself with `await f(...)` and is waiting on directly belongs to it and is cancelled with it; when awaiting a task value obtained elsewhere, cancellation only stops the wait and that task keeps running. The two forms are distinguishable at compile time. For example, when a `cutscene` suspended at `await walk_to(door)` is cancelled, `walk_to` is cancelled too and the character stops.
- **Release.** The coroutine frame (locals and the suspension point) is released as soon as the task ends; held references are released as on scope exit, and no code after the await runs. The first version has no finally or defer. The Task object is a RefCounted handle that only holds the result; it is freed when no variable, awaiter, or runtime wait on a signal refers to it any longer.
- **Combinators and re-entrancy.** `Task.of(signal)` wraps a signal as a task; `Task.delay(seconds)` waits; `Task.any(list)` returns the index of the first task to finish and cancels the others under the ownership rule above; `Task.all(list)` waits for all of them. Re-entrancy has no automatic policy; where needed, cancel the earlier call through its handle. Annotations such as `@restart` can be added compatibly later. Evidence: [pitfall catalog](surveys/pitfalls.en.md) G-12, G-13; proposals #8838 and #6243.
- **Setters and getters cannot be coroutines.**
- **Setters suspend automatically before ready.** A setter runs immediately as usual; on reaching the first statement that needs the node to be ready, if the node is not ready yet, it suspends there and continues from that point once the node is ready. Statements that need readiness are determined by static analysis: accesses to `@onready` members, `$X` or child nodes, or calls to methods of the class that access them (including overrides in subclasses). Accesses inside an `if is_node_ready():` branch do not count. If the property is written several times before ready, only the last suspended call continues and the earlier ones are cancelled; suspended calls continue after `@onready` initialization and before `_ready`, in write order; if the node is freed before it becomes ready, its suspended calls are dropped. After ready, setters never suspend. The editor shows the suspension point on hover. Rationale: this is the hand-written GDScript idiom `if not is_node_ready(): await ready`, done by the compiler, so users need no new concept. Transformation and storage finish before the suspension point, so reads before ready see the transformed value; deferring the whole setter and recording the raw input would make reads before ready see the untransformed input (for example, Ring's `Runtime/AVGRuntime/UI/UI.cs:16-35` wraps character names in 【】). In a sample of 6 corpus setters that use `await ready`, every one reads the field's current value after resuming ([property-accessor survey](surveys/property-accessors.en.md)).
- **A property whose value lives only in nodes** (no field; the getter reads a child node) is a program error to read before ready, and the diagnostic names the node that is not ready yet. If it must be readable before ready, store it in a field.
- **A property that was never written does not run its setter at ready**, as in GDScript. When an exported property's setter synchronizes nodes but its default value never passes through the setter, a hint is shown.
- **Cross-language await is supported in both directions.** A call to a GDScript method may be awaited: if a `GDScriptFunctionState` comes back at runtime, its `completed` signal is awaited and the result is checked against the declared return type; receiving one without await is a program error. Whether a function is a coroutine is not part of method reflection data (`core/object/method_info.h:37-44`), so it cannot be decided at compile time. When GDScript awaits a coroutine of this language, the coroutine's first suspension returns the `completed` signal of its Task. A Task emits `completed(value)` when it finishes, and `completed(null)` when it is cancelled or fails, so that GDScript awaiters are never left suspended; a separate `cancelled` signal serves code that needs to tell the cases apart. Both directions must be tested in an environment that can build the engine.
- **Freed objects and suspended coroutines.** When the object a coroutine belongs to is freed, the coroutine is cancelled silently and the references held by the suspended frame are released, as in GDScript. When the thing being awaited (a coroutine on another object, or the source of another object's signal) is freed before it completes, the awaiter gets a program error at the await and aborts to the engine boundary, with a diagnostic naming the freed object and where it was freed (awaiting with `settled()` yields `Cancelled(AwaitedFreed)` instead); GDScript leaves the awaiter suspended forever in this case (`modules/gdscript/gdscript_function.cpp:335-349`). A suspended coroutine does not keep self alive, as in GDScript. The freeing of any object can be observed through the instance-binding free callback that GDExtension exposes. Evidence: [pitfall catalog](surveys/pitfalls.en.md) G-11.
- **Signals and function values.** Signal parameters must be typed; emit and connect are checked statically; connections stored in scenes are checked by the scene model; engine class signals are typed from ClassDB, with unaudited object parameters nullable. Function types record parameters, return value and whether they are async; the spelling is in §9. Whether a function value can be used in a position depends only on types, and lambdas and method values are treated alike: parameters are contravariant and return values covariant; there is no implicit conversion between async and ordinary function types, and passing an ordinary function where an async one is expected can be allowed later compatibly. Positions the engine calls accept async functions, including signal connections in code and in scenes and the Callable parameters of engine APIs (such as `tween_callback`); the task runs as a root task, as with async engine virtuals. Evidence: coroutine methods are used as values 91 times in the corpus, 60 of them as `connect(name)`. The type of `f.bind(a, b)` is f's function type without its last two parameters, because the engine appends bound arguments after the call's arguments (`core/variant/callable_bind.cpp:141-150`). Lambdas capture by value, as in GDScript. Awaiting a signal yields no value for a signal without parameters and a value of the parameter's type for a signal with one; awaiting a signal with several parameters is allowed only as a statement. Evidence: in the [await signal results survey](surveys/await-signal-results.en.md), only 1 of 1,356 awaits uses the result of a signal with several parameters. A Callable of unknown signature needs an explicit conversion to a function type and is checked on every call.

## 8. Runtime

- **The interpreter must meet the performance goal on its own.** iOS and most console platforms do not allow generating machine code at runtime; a copy-and-patch style JIT is only an extra benefit on desktop.
- **Threads.** The virtual machine must run safely on whatever thread the engine chooses, for example background resource-loading threads and the physics thread. Data races on shared objects are the user's responsibility. The first version adds no threading API and uses the engine's Thread, WorkerThreadPool and Mutex. Evidence: across the 20 surveyed repositories, `Thread.new` occurs 11 times and `WorkerThreadPool` twice.

## 9. Syntax

- The surface follows GDScript: indentation, `func`, `var`, `extends`, `signal`, `@export`, `$X`. New constructs extend it in the same style, including structs, enums with payloads, match, interfaces, generics `[T]` and `T?`.
- **Hard rule**: a construct spelled as in GDScript either behaves as in GDScript or is a compile error with a suggested fix; it never behaves differently in silence.
- **Declaration spellings**:
  - Structs: `struct Hit:` followed by fields declared with `var`, which may have default values. Construction takes arguments by name only, for example `Hit(damage = 3, point = p)`, and fields with defaults may be omitted; allowing positional arguments later does not break existing code.
  - Enums with payloads extend GDScript's brace form, for example `enum Command { IDLE, MOVE(target: Vector3), ATTACK(target: Node3D, power: int) }`, constructed as `Command.MOVE(target = p)`. Enums without payloads keep their meaning.
  - An interface is an indented block that can declare `var`, `signal` and `func`. A method without a body has no colon, as with GDScript's `@abstract func` (`modules/gdscript/gdscript_parser.cpp:1790-1791`); a method with a body is a default method. All members of an interface are public. An interface extends interfaces with `extends A, B` (§4).
  - The class header declares implemented interfaces with `implements A, B`, either on the same line as `extends`, for example `class_name Player extends CharacterBody3D implements Damageable`, or on a line of its own. They are not folded into `extends`, so the base class and the interfaces are told apart at a glance.
  - `pub` is a keyword, written after annotations and before `static`, for example `@export pub var max_hp: int`, `pub static func`, `pub signal died`. It is a keyword rather than an annotation because it is written often: at least 22 times per 1,000 lines in the [member visibility survey](surveys/member-visibility.en.md).
  - Placement and naming follow GDScript: a file is a class, and the structs, enums and interfaces declared in a file belong to that class. In the same file they are written by name; in other files as `ClassName.Name`, for example `Combat.Hit` or `Player.Command.MOVE(target = p)`; files without `class_name` are reached through `preload`. Global names come only from `class_name`. Types shared by several classes go into a class that exists to hold them. Aliases or `import` can be added later without changing the meaning of existing code.
  - Type parameters of generics are written in square brackets after the name, consistent with `Array[int]` and as in Python 3.12 (PEP 695), for example `func first[T](items: Array[T]) -> T?`, `struct Pair[A, B]:`, `enum Tree[T] { LEAF, NODE(value: T, children: Array[Tree[T]]) }`; a file's class declares them on `class_name`, for example `class_name Cache[K, V] extends RefCounted`. A constraint is written `T: Interface`, for example `func strongest[T: Damageable](units: Array[T]) -> T?`; in the first version each type parameter has at most one constraint, and several constraints or classes as constraints can be added later with the same spelling. At call sites type arguments are usually inferred from the arguments, and are written out when they cannot be, for example `first[int]([])` or `Pair[int, String](first = 1, second = "a")`. `name[...]` looks like a subscript and is told apart by name resolution: when the name is a generic function or a generic type, the brackets hold type arguments; otherwise they are a subscript. In GDScript `[` in each of these positions is a syntax error (`modules/gdscript/gdscript_parser.cpp:964, 1005-1010, 1616, 1822`).
  - Function types keep the shape of a function declaration without the function and parameter names, for example `func(int, Node3D)` (no return value, as when a declaration omits its return type; `-> void` may also be written), `func(Enemy) -> float`, `async func(String) -> Level` (calling it yields `Task[Level]`). A nullable function type needs parentheses, for example `(func(Enemy) -> bool)?`; otherwise the `?` belongs to the return type. Parameter names in function types can be allowed later compatibly. Calls are written `f.call(x)` as in GDScript and checked statically against the function type; writing `f(x)` gives GDScript's existing error with a fix (`modules/gdscript/gdscript_analyzer.cpp:3785-3789`), and direct calls can be allowed later compatibly. A GDScript type can only start with an identifier or `void` (`gdscript_parser.cpp:3849-3861`), so `func(...)` as a type is a syntax error.
- **`@abstract`** follows GDScript's rules: an abstract method has no colon and no body; a class with abstract methods must be marked `@abstract`; a concrete subclass must implement every abstract method; an abstract class cannot be constructed; calling an abstract method through `super` and marking a static method `@abstract` are compile errors (`modules/gdscript/gdscript_analyzer.cpp:1543-1562, 3674-3687`, `gdscript_parser.cpp:4505-4507`). In addition, a node in a scene that uses an abstract class is a compile error, reported on that scene; the engine itself does not instantiate abstract scripts (`modules/gdscript/gdscript.cpp:265-270`), and the language reports abstractness to the engine through `_is_abstract` and the global class list (`core/object/script_language_extension.h:143-147, 756-769`). A common base class with state is written with `@abstract`; a capability shared by classes with different engine bases is an interface. Evidence: in the [corpus counts](surveys/corpus-counts.en.md), 25 of 28 abstract classes are in gdUnit4, and 17 of the abstract classes declared by a file have only abstract methods, so they can be rewritten as interfaces; in game code, godot-open-rpg's BattlerAction, for example, extends Resource and has exported fields and an abstract coroutine `execute`.
- **Rest parameters**: `...args: Array` is as in GDScript; it must be the last parameter and cannot have a default value (`gdscript_parser.cpp:1723-1730`). `...args: Array[T]` is also allowed, and each argument is checked at the call site; GDScript reports typed rest parameters as a compile error (`gdscript_analyzer.cpp:1802-1809`), so this does not break the syntax hard rule. The rule that parameters must be annotated applies: a bare `...args` is a compile error, and the quick fix adds `: Array`. The method information the engine sees carries `METHOD_FLAG_VARARG`, from which GDScript accepts any number of extra arguments (`gdscript_analyzer.cpp:6101-6104`); the element type is enforced by the entry check. There is no spread at call sites, and GDScript has none either (`gdscript_parser.cpp:4336`); an existing array is passed with `callv`. A spread form can be added later without changing the meaning of existing code; without it mistakes are easy, for example Pixelorama's `_debug_msg` passes its whole args as one argument to `_prefix_print`, which then calls `prints(args)` and prints an array instead of space-separated values (`src/Classes/ObjParse.gd:59-66`). Evidence: 76 of the 78 rest parameters in the corpus are in gdUnit4's assertion interfaces, all with Variant elements.
- **`null`** is an alias of None, with GDScript's meaning everywhere: `x = null` gives a `T?` the empty value, `x != null` is the same as `x != None` and narrows, and passed as a Variant the engine receives NIL. Assigning it to a non-null `T` is a compile error, and the quick fix changes the type to `T?`. A hint suggests writing None in new code, without enforcing it. Rationale: `null` occurs 22.2 times per 1,000 lines in the [corpus counts](surveys/corpus-counts.en.md), and making it a compile error would only add mechanical migration work.
- **Expressions.** The only conditional expression is GDScript's `a if c else b`, and its condition must be bool; there is no form that uses an if/else block as a value. For the meaning of postfix `?`, see §7; in GDScript `?` is currently a syntax error (`modules/gdscript/gdscript_parser.cpp:3834-3835`).
- **match** keeps every GDScript pattern with its meaning: literals and constant expressions compare by equality, `var x` binds, `_` is a wildcard, array and dictionary patterns with `..` inside them, several comma-separated patterns (which cannot bind), and `when` guards (`modules/gdscript/gdscript_parser.cpp:2499-2723`). New patterns:
  - An enum variant is written `Type.VARIANT(field = pattern, ...)`, where `var field` is short for `field = var field`, for example `Command.MOVE(var target)` or `Command.ATTACK(target = var enemy, power = 0)`. Fields not listed must be covered by `..`, as in dictionary patterns. Patterns nest. Structs use the same form, for example `Hit(damage = var d, ..)`.
  - `Ok(var v)` and `Err(var e)` are written positionally, as they are constructed. Option uses two branches, `None` and `var x`, and the value bound by the latter is narrowed to T.
  - A match over an enum (with or without payloads), a Result or an Option must be exhaustive or have `_`, and branches with `when` do not count toward coverage; a match over other types need not be exhaustive, as in GDScript.
  - The first version has no type patterns (use `if x is T`), no match expressions, and no binding in comma-separated patterns; adding them later does not change the meaning of existing code.
- **for** is written as in GDScript: `for i in n` iterates from 0 to n-1 with i an int; `range(...)`, containers, Strings and the keys of a Dictionary can be iterated; the loop variable may be annotated, as in `for i: int in ...`, with the element type or one of its base types, and there is no implicit downcast. Iterating over a float or a vector is a compile error suggesting `range(...)`; GDScript allows it and treats the vector as a range (`modules/gdscript/gdscript_vm.cpp:3093-3230`), which under static typing is almost always a mistake.
