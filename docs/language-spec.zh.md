# Godot 新脚本语言规范

**v0.1 · 2026-10-21 · 公开征求意见稿** · English: [language-spec.en.md](language-spec.en.md)

本文规定一门面向 Godot 的静态类型脚本语言的语义，它的目标是替代 GDScript。目前只有规范，还没有实现。语言名称尚未确定，下文称“本语言”。中英两版内容同步。

## 1. 概述

### 1.1 定位

- 面向 Godot 的全新脚本语言：保持脚本开发的低摩擦体验，同时提供强静态类型与类型推断。
- 复用 Godot core 的基础类型和基础设施。对本语言来说，它们是外部类型，其生命周期、复制方式和 ABI 契约由引擎规定。
- 复用 Godot 的语义，不等于兼容 GDScript 源码。
- 以 **Godot 树外模块**的形式交付。初期用 typed IR 解释执行，以后可以加入 JIT。不以 GDExtension 兼容层或修改 core 为前提。终端用户写脚本不需要额外安装工具链。
- 不做热重载，也不做运行中的状态迁移；改完代码停止再重新运行是正常流程。

### 1.2 设计原则

1. **性能你别操心，但是语义你得说清楚。** 用户少写类型和内存管理方面的标注；但赋值、共享、转换、失效和报错都必须有明确含义。推断不出类型时报错，不退回动态类型。
2. **先定语义，再选算法。** 规则只描述“哪些程序合法、每处是什么类型”，不绑定某种具体的推断算法。
3. **引擎能观察到的表示就是语义。** 值在 Variant 中长什么样、怎么比较相等、怎么存档，GDScript、编辑器和资源文件都看得到，所以必须由规范规定。
4. **先严后松。** 限制以后可以兼容地放宽，反过来却会破坏已有代码。拿不准时先收紧。
5. **不为假想的需求做优化。** 需求还不明确的能力，列为已知限制或后续计划。

### 1.3 文档约定

- 正文是规范性内容。以下标记表示非规范性状态：
  - **【待定】**：方向已定，拼法或细节未定。
  - **【已知限制】**：第一版明确不支持。
  - **【后续】**：已在计划中，不阻塞第一版。
- 代码示例中的语法是暂定的，具体拼法【待定】。
- “程序错误”指 §10 定义的运行时错误类别。
- 文中引用的引擎行为，均对照 Godot master（4.8-beta，提交 `469659e`）核对过，出处见附录 A。

## 2. 类型系统概览

1. 强静态类型，默认靠推断。推断不出类型时报错，不会悄悄退回 `any`。
2. `any` 可以存放任意语言类型的值。需要具体类型的操作，必须先做类型检查、收窄或转换（§2.1）。
3. 方法调用和运算会形成能力约束；trait 用来给这些约束命名并复用（§4）。
4. 提供带载荷的命名 enum 和穷尽的模式匹配；Option 和 Result 也用同一套机制表达（§6）。
5. 条件表达式必须是 bool，没有普遍的“真值性”转换。
6. 单继承加覆盖，没有多继承。覆盖必须满足父方法的契约，不能缩窄父方法接受的参数。引擎回调的签名由引擎契约给出。
7. 用户不能自定义重载；保留默认参数、泛型和覆盖。引擎已有的多种调用形式由绑定层负责适配。
8. 表层语法沿用 Python／GDScript 风格的缩进和冒号。

### 2.1 any 类型

一个 `any` 值包含一个动态类型，以及该类型的一个值。基础类型和用户定义的类型，包括 enum 和 Option，都可以存入 `any`。数值进入时进行规范化：i8…i64、u8…u32 转为 i64，f32、f64 转为 f64，保留数值而不保留源位宽。u64 的所有值都用带类型盒子保留完整无符号数值及动态类型（§12.1）。`any` 本身非空：空缺由 `Option[any].None` 表示，不存在空的 `any`。

`any` 不是继承基类。把 Object 引用转换为 `any`，不改变 Object 的继承体系、所有权和存活规则（§5）。对 `any` 中的值执行需要具体类型的操作前，必须检查、收窄或转换。将一个 `any` 值赋给另一个 `any`，复制的是其中的值，不会再增加一层动态容器。

`any` 的表示见 §12.1。它兼容 Godot Variant ABI，但合法值不包含裸 NIL。把 `Option[T]` 值存入 `any` 时，保留其类型以及 `None` 或 `Some` 分支；它与外层 `any` 的空缺不同。

## 3. 类型推断

推断由规则 R1–R7 定义。按这些规则，实现只需要做函数内的局部推断，再加上返回类型和成员的跨声明联合求解（§11）；不需要 let 多态、value restriction，也不需要匿名结构约束。

### R1 类型不由调用方决定

一个声明的类型，只由它自己的声明和函数体决定；如果存在互递归，就连同它所在的强连通分量一起决定。调用处不参与决定。

理由：如果从调用方反推，每多一处调用，函数的类型就可能变；而且 `call()`、编辑器里连接的信号、AnimationPlayer 的方法轨道这类调用方，静态分析根本看不见。

例外：lambda 的参数类型可以从创建处的期望类型得到。这只涉及局部，不违反 R1。

### R2 引擎能调用的都是单态，泛型必须显式声明

类方法、信号和成员属性都是引擎的入口：`call()`、`has_method`、信号连接、`call_deferred`、Tween、RPC 都按名字调用它们，参数是 Variant。所以这些入口必须有具体的签名。泛型必须在声明上写出类型参数，例如 `func max[T: Ord](a: T, b: T) -> T`。泛型函数不对引擎暴露。

理由有两点：

- 如果允许隐式泛化，同一个调用的静态路径和 `call()` 动态路径会算出不同结果：静态路径按 i32 实例化，而动态路径只有 64 位的 Variant int。
- 如果“是不是泛型”由推断决定，那么改动函数体可能让方法从 `has_method` 中消失，编辑器里已经连好的信号会在运行时找不到方法。

### R3 参数类型

参数类型按以下顺序确定：

1. 覆盖引擎虚函数的方法，参数类型取自引擎契约。
2. 否则，看参数**直接流向的、类型已知的位置**：作为实参传给类型已知的参数；赋值给类型已知的变量或成员；作为二元运算的一侧，且另一侧类型已知（此时取同一类型）；作为有返回类型标注的返回值。如果这些位置的类型全都相同，就取这个类型。
3. 否则要求标注。

有两种情况不能作为推断依据：

- **方法调用**：从 `x.hit()` 推不出 x 的类型。同名方法可能属于任何一个类，而新增一个类不应该改变已有代码的含义。
- **流向 any 或 Option[any] 的位置**：`print(x)` 不会把 x 的类型确定为 `any`，否则就等于悄悄退回了动态类型。

```
func take_damage(amount):     # hp 是 i32，hp -= amount → amount: i32
    hp -= amount
func _on_body_entered(body):  # 只调用了 body.hit() → 要求标注
    body.hit()
```

### R4 局部变量

局部变量的类型在整个函数体范围内求解，求解完就固定下来。

- 如果初始化式给出了具体类型，类型就此确定，之后的赋值不会让它变宽（隐式转换按 §7.3 处理）。
- 初始化式中**开放的部分**，即柔性字面量（§7.2）和空容器的元素类型，按以下规则确定：
  1. **先看流入。** 如果有类型已知的值流入这个变量（赋值、复合赋值的右侧、往空容器里写入元素），类型取初始化式和所有流入值的无损公共类型。数值类型按 §7.5 的公共类型规则计算，没有公共类型时要求标注；非数值类型必须完全相同，不自动求共同父类。只由这个变量自身和柔性字面量组成的流入，不提供类型信息。
  2. **再看流向。** 如果没有这样的流入，就看变量流向哪些类型已知的位置（位置的种类同 R3）。这些位置的类型全部一致时，取这个类型；不一致或者根本没有时，柔性字面量取默认类型（整数 i32、浮点 f64），空容器的元素类型要求标注。
  3. 两个开放的局部变量之间互相赋值时，二者合为一组，共用同一个类型，按整组的流入和流向来确定。
  4. 结果与这些约束在代码中出现的先后顺序无关。

```
var ratio = 0
ratio = position / length    # 流入的是 f64 → ratio: f64，字面量 0 也跟着取 f64

var t = 0.0
t += delta                   # 流入的是 f64 → t: f64
sprite.modulate.a = t        # 流向 f32：属于精度损失，默认不警告

var groups = 1
dispatch(list, x, y, groups) # 没有流入；流向一致都是 u32 → groups: u32
```

这几条规则的依据，是对真实 Godot 项目做的一次调查，详见[调查记录](surveys/literal-local-constraints.zh.md)。调查记录中的警告默认设置为调查当时的设置；现行默认设置见 §7.3。

**按源码顺序解析成员：** 在类型尚未确定的值上调用方法或访问成员时，只看源码中这个位置之前出现的约束，按上面的规则必须能确定类型，否则报错要求标注。如果此时是柔性字面量，而之前还没有任何约束，就当场取默认类型；之后再出现的约束只当作隐式转换处理。这是 R4 中唯一与先后顺序有关的情形。

```
var a = 1
a.abs()             # 之前没有约束 → a: i32
a = big_i64         # i64→i32，截断；可选整数转换损失警告

var items = []
items[0].hp -= 1    # 此时元素类型未知 → 报错，即使后面有 append(enemy)
items.append(enemy)
```

### R5 返回类型

返回类型从函数里所有的 return 推断。如果各分支的类型不同：

- 同一个 enum 的不同分支，合并为该 enum；
- 不同的数值类型，按 §7.5 合并为公共类型；
- 不同的类，不自动求共同父类，第一版直接报错要求标注。自动求出来的往往是 Node 或 Object，而且会随类层次的变化而变；
- 整数、字符串这类不同类型的返回分支，不会自动合成一个匿名的和类型。

### R6 成员和信号

成员变量的类型来自类型标注或初始化式。初始化为空容器的成员必须标注类型，不能从其他方法或其他文件里的用法反推，因为 Inspector、`get_property_list` 和其他文件的推断都需要先知道成员的类型。信号参数也必须标注，因为 emit 的地方就是调用方（见 R1）。

### R7 推断出的签名就是接口

修改函数体，可能改变推断出的签名，从而让其他文件中的调用报错。这是推断式体验固有的代价。此时诊断信息必须同时给出：调用方期望的类型、被调方推断出的类型，以及决定这个类型的那一行源码。

### 3.8 隐式转换只在检查边界发生

隐式的数值拓宽，以及子类到父类的转换，只在检查边界发生：期望类型已知的赋值、实参和返回值，或者二元运算两侧都已经是具体类型的时候。如果遇到尚未确定的类型，就推迟到它确定以后再判断。

## 4. 泛型与 trait

- trait 显式地为能力约束命名。一个类型是否满足 trait 按结构判断：只要具备签名匹配的方法就算满足，不需要再声明一遍。
- 泛型函数是唯一的多态来源（R2）。在泛型函数内部，对类型参数的方法调用和运算，必须由 trait 约束或内建的运算约束覆盖；泛型代码中运算两侧必须同型（`T + T -> T`）。
- 第一版的 trait 只包含方法签名，只能用作泛型函数的约束；不支持默认方法、关联类型、泛型 trait 和 trait 对象。
- trait 不能用来引入字段注入、mixin 或多继承，也不改变 Node 的类型树。
- **泛型代码的语义必须与具体类型一致**，不能退化成 Variant 运算。例如 `add[T](a: T, b: T)` 以 i32 实例化时，必须按 32 位的运算和溢出规则执行；而 Variant int 是 64 位，结果会不一样。String 的写时复制、Ref 的引用计数等外部类型，复制和析构的方式也各不相同。
- 实现说明（非规范）：第一版计划为每个类型参数传入一个运行时类型描述符，内含大小、复制、析构函数以及 trait 方法表，泛型代码只保留一份。这里的“静态派发”是指：约束在编译期解析到唯一的实现，运行时通过描述符间接调用，不按名字查找，也不产生 dyn 对象。IR 级单态化和 JIT 特化留作以后的优化【待定】。

## 5. 对象模型与生命周期

### 5.1 对象的种类

所有类的实例都是 Godot Object，上面挂着 ScriptInstance。没有写 extends 的类默认继承 RefCounted，这一点与 GDScript 一致；本语言的引用计数就是引擎的引用计数。按静态类型，值分为以下几种：

| 种类 | 静态类型 | 语义 |
|---|---|---|
| 拥有引用 | RefCounted 及其子类（包括 Resource，以及没写 extends 的类） | 强引用会延长对象的寿命；可以使用 `weak` |
| 句柄 | 不是 RefCounted 子类的类（如 Node），但不包括 Object 本身 | 引用不延长寿命，本质上是 ObjectID 加一次存活检查；`weak` 对它没有意义，不允许使用 |
| 由实际对象决定 | Object | 实际对象是 RefCounted 时持有强引用，否则就是句柄；可以使用 `weak` |
| 值 | 数值、bool、Vector2 等 core 值类型、String、enum | 赋值即复制（写时复制等优化由引擎契约实现） |

**所有权不会因为静态类型改变而丢失。** RefCounted 对象上转为 Object 后，仍然持有强引用；再下转回来也一样。这与 Variant 持有对象的方式一致。RefCounted 的父类只有 Object，所以 Object 是唯一需要看实际对象来决定语义的静态类型。泛型代码以 Object 实例化时也是如此，由类型描述符负责处理。

### 5.2 引用环与 Node 的生命周期

- 不引入追踪式 GC，也不要求 move 或借用标注。
- 引用环不会被自动回收。可以用弱的反向引用，或者在明确的生命周期操作里手动断开。不要依赖析构函数去断开那些本身就阻止析构发生的引用环。
- Node 的生命周期由引擎管理，本语言的引用不会延长它的寿命。

### 5.3 外部容器与写回

- Array 和 Dictionary 是共享引用。
- Packed*Array 在脚本变量之间按引用共享，但引擎内置的属性和方法返回的是副本。所以在 GDScript 里，`line.points.append(p)` 会悄无声息地不起作用。
- **写回规则：** 修改从属性上取得的值类型（包括调用会修改自身的方法）时，按“取出、修改、写回”执行。例如 `node.position.x += 1` 和 `line.points.append(p)` 都会把结果写回属性。一个方法是否修改自身，根据 builtin method 的 const 信息判断。

### 5.4 复制与闭包

- 复制必须显式写出：复制引用、浅复制对象、深复制对象是三种不同的操作。外部类型沿用它们自己提供的能力。
- 闭包按值捕获当前的值；如果捕获的是引用类型，仍然和外部共享同一个对象。闭包不能重新绑定外部的局部变量。闭包造成的强引用环同样需要手动处理。
- 【待定】弱引用临时升级为强引用的语法；显式复制的语法，以及它与 core 中 `duplicate` 类操作的对应关系；特殊的析构顺序与线程限制。

## 6. enum、Option 与可空性

### 6.1 enum

- enum 具有值语义。引擎边界上的表示见 §12.4；存入 `any` 时使用 §12.1 的带类型装箱规则。这些编码不改变其值语义。
- **enum 的值不能原地修改**，只能构造新值。载荷中的引用类型在复制 enum 时不做深拷贝。
- **【已知限制】第一版不支持递归 enum。** enum 的值布局中不能出现循环，经过 Option 等值类型形成的循环也算，例如 `enum Tree: Node(i32, Tree?, Tree?)`。出现循环时报编译错误，诊断会列出循环路径，并建议改用 class，或者经由 Array、Dictionary 递归。经由这些引用类型的递归是允许的，例如 `enum Json: …, Arr(Array[Json]), Obj(Dictionary[String, Json])`。由于 Godot 没有轻量的 box 类型，这些绕行办法都要经过 Array 或 RefCounted 对象；需求不大，第一版不为此做优化。

### 6.2 `T?` 就是 `Option[T]`

`Option[T]` 有两个分支：`None` 表示空缺，`Some(T)` 包含一个 T 类型的值。`T?` 是 `Option[T]` 的简写。语言内部没有 `null` 值。

嵌套必须保留。对于 `first[T](a: Array[T]) -> T?`，当 `T = Enemy?` 时，数组为空（`None`）和首个元素为空缺（`Some(None)`）是不同的值；两者也都不同于 `Some(Some(enemy))`。

Option 具有值语义。除下述表示保证外，其内部布局未作规定；引擎编码见 §12.4。*niche* 是载荷类型的值不会使用、因而可以用来表示 Option 分支的表示。裸 NIL 不是合法的 `any` 表示，因此 `Option[any]` 可以用 NIL 表示 `None`，用 v 的非 NIL 表示来表示 `Some(v)`。`any` 自身不能用 NIL 表示空缺。

把 `Option[T].None` 存入 `any`，得到的是动态类型为 `Option[T]` 的有值状态，其编码是非 NIL 的带类型盒子（§12.1），不是 `Option[any].None`。

### 6.3 收窄

- 检查值是否为 `None` 后，类型收窄只对**局部变量**生效。由于闭包按值捕获（§5.4），从检查到使用之间，不会有其他代码改动局部变量，所以这种收窄是可靠的。
- 成员、属性和数组元素不做收窄，因为检查和使用之间的任何调用（方法调用、同步触发的信号、setter、await）都可能改动它们。
- 提供“检查并绑定到局部变量”的语法，例如 `if var t = target:`，拼法【待定】。

### 6.4 可空语法糖

- **后缀 `!`**：从 `Some` 中取出值；对 `None` 使用时报程序错误并给出位置。它只保证有值，不保证对象还活着。
- **`?.`**：可空链。接收者为 None 时，整条链短路，结果是可空类型。`?.` 是一个完整的记号；后缀 `?` 留给 Result 的错误传播（§10）。本语言没有 `?:` 三元运算符，所以不会产生歧义。
- `?.` 遇到已经释放的对象时，不会把它当作 None，而是照常报失效访问错误。

### 6.5 非空不等于存活

- 一个 Node 引用即使非空，对象也可能已经被释放，因此必须照常做失效访问检查。例如，同一个非空的局部 Node 变量跨过一次 await 之后，“非空”仍然成立，但“存活”就不一定了。
- 引擎契约不确定时，先标记为可空，有了证据再补全本地的绑定描述。
- 外部的可变容器，不能因为扫描过一次就永久获得静态保证（容器的类型保证见 §12.2）。
- 【待定】`$X` 是否自带非空断言（在 GDScript 中，`$X` 找不到节点时本来就会报错）；哪些外部事实可以稳定地收窄、哪些调用会让它们失效，需要统一规则。

## 7. 数值

### 7.1 类型

| 项目 | 规定 |
|---|---|
| 有符号整数 | i8、i16、i32、i64 |
| 无符号整数 | u8、u16、u32、u64 |
| 浮点数 | f32、f64 |
| 浮点后缀 | `f` 表示 f32，`d` 表示 f64 |
| 整数后缀 | 【待定】 |
| i128、usize 等 | 暂不提供 |

### 7.2 柔性字面量

- 整数字面量取另一个操作数的类型，或者期望类型；值放不下时报编译错误；完全没有约束时取 i32。
- 浮点字面量取期望类型；没有约束时取 f64。
- 整数字面量也可以取浮点类型，例如 `var v: f32 = 10`、`Vector2(1, 2)`。

例如在 `func f(x: u8): return x + 100` 中，100 取 u8，结果也是 u8；当 x ≥ 156 时会溢出，这是程序错误（§7.4）。在 `Time.get_ticks_msec() - 1000` 中，1000 取 u64。

### 7.3 数值转换

无损数值转换在检查边界（§3.8）自动进行。是否无损按源类型的完整取值范围判断，例如 i32→i64、u32→i64、i32→f64、f32→f64 都是无损转换。有损隐式转换也允许，但须满足下述常量规则。

#### 整数转换

将非常量整数 x 转换为 N 位整数类型时，令 r 为满足 `0 ≤ r < 2^N` 且 `r ≡ x (mod 2^N)` 的唯一整数。目标为无符号类型时，结果为 r。目标为有符号类型时，若 `r < 2^(N−1)`，结果为 r；否则结果为 `r − 2^N`。

因此，窄化丢弃高位，同宽的符号转换保留位模式。加宽时，有符号源做符号扩展，无符号源做零扩展，与目标是否有符号无关。即使损失值域，这些转换也有确定的结果，是合法的运行时操作，不受算术溢出检测设置影响。

| 源值与类型 | 目标 | 结果 |
|---|---|---|
| 300，i32 | u8 | 44 |
| −1，i8 | u8 | 255 |
| 255，u8 | i8 | −1 |
| −1，i8 | u16 | 65535 |
| 255，u8 | i16 | 255 |

表中描述的是非常量值的转换。整数常量超出目标范围时，隐式和显式转换都报编译错误；此错误不可关闭。范围内的常量保持原值，通过转换。

```
const limit: i32 = 300
var small: u8 = limit         # 编译错误
var small_cast = u8(limit)    # 编译错误；转换语法暂定

func narrow(x: i32) -> u8:
    return x                 # 有定义的转换；运行时 300 转为 44
```

常量传播确定操作数为单一常量值时，同样适用常量规则。`var` 声明本身不阻断传播。范围分析如果只表明运行时的值可能损失值域，并不能使该值成为常量，也不能据此报告这个错误。

编译器必须诊断越界的整数字面量，以及常量表达式中的越界整数转换。第一版可以尚不能完成其他常量传播，后续版本可以增强，包括跨声明或跨函数传播。未被诊断的常量错误仍然是错误，后续诊断可以拒绝它。漏诊既不产生未定义行为，也不允许优化器假设该转换不可达；如果执行到该转换，结果仍遵循上述整数转换规则。

#### any 中的数值

将 `any` 中的数值转换为请求的数值类型时，对其规范化后的值（§2.1）应用本节及 §7.5 的数值转换规则，不要求目标类型匹配原始源位宽。装箱的 u64 须先恢复为无符号 u64 数值，再转换为目标类型，不能先把载荷解释为负的 i64。

例如，值为 1 的 i32 和 i64 存入 `any` 后，都是同一个规范化 i64 值。下例的 x 是运行时输入；当其值为 18446744073709551615 时，same 保持该值，signed 按整数转换规则为 −1：

```
func convert_number(x: u64):
    var value: any = x
    var same: u64 = u64(value)
    var signed: i64 = i64(value)
```

显式转换的拼法暂定。此例描述运行时转换，不是越界常量转换。常量传播确定操作数的值时，存入 `any` 不能豁免常量规则。非数值不会仅因请求数值目标类型就变成数值。

#### 转换警告

| 警告类别 | 范围 | 默认 |
|---|---|---|
| 精度损失 | f64→f32；可能丢失精度的整数→浮点（如 i32→f32、i64→f64） | 关 |
| 整数转换损失 | 可能损失值域的整数窄化和符号变化 | 关 |
| 浮点转整数的值域损失 | 浮点→整数 | 开 |

各类警告可独立设为 off、warn 或 error，不影响不可关闭的常量错误。常量能被目标类型精确表示时，不报损失警告。显式转换表示接受相应损失，但不能豁免整数常量的范围规则。

引擎混用 f32 和 f64：`_process(delta)` 的参数是 double，Vector2 分量是 real_t（标准构建中为 float，见附录 A）。默认设置下，`position += velocity * delta` 不产生警告。浮点转换仍遵循 §7.5。

### 7.4 溢出

- **整数溢出是程序错误**，与数组越界、除零属于同一类。
- 运行时的溢出检测默认关闭。关闭时，溢出的结果是确定的：按位宽回绕（二进制补码），**不是未定义行为**。优化不能假设溢出不会发生，解释器和 JIT 的结果必须一致；帧同步联机、回放等功能都依赖这种确定性。
- 结果虽然确定，溢出在语义上仍然是错误：同一个程序在开启检测时会报错；如果编译期能证明会溢出，就报编译错误。
- 确实需要回绕时，使用**显式回绕运算**，例如 `wrapping_add` 或 `&+`，拼法【待定】。显式回绕运算永远不报错，也不受检测开关影响。哈希、随机数生成，以及 `mask -= 1` 这类求全 1 掩码的写法，都应该用它。
- **编译期能证明的溢出一律报错：** 只要能证明某个表达式每次求值都必然溢出，就报编译错误。
  - 所有实现都必须报告的最低范围：常量表达式求值时溢出，以及字面量超出目标类型的范围。
  - 超出最低范围的情形，随版本逐步增加识别能力，只增不减，每新增一类都加入一致性测试。因此升级编译器后，原本能编译的代码可能报错，这是在指出原本就错误的程序。
  - 证明只在函数内部进行。跨函数推出的溢出不作为编译错误，最多给警告；这样可以保持增量编译和诊断位置的稳定。
  - 不允许误报。只有每次求值都必然溢出才报错；“可能溢出”属于潜在风险警告，其触发条件【待定】，第一版可以一条都不报。
  - 同一版本中，编辑器诊断和导出构建必须使用同一个分析器。

### 7.5 混合运算、除法与边界情况

**混合运算：** 取能无损容纳双方的公共类型，例如 i32+i64→i64、i32+u32→i64、f32+f64→f64。不存在这样的类型时（例如 i64+u64），要求显式转换。整数与浮点混合运算时的选择优先级【待定】。

| 情况 | 规定 |
|---|---|
| 整数 `/` | 向零截断；不提供 `//` |
| 除零（`/` 和 `%`） | 总是程序错误，不受溢出检测开关影响 |
| `%` 的符号 | 与被除数相同 |
| MIN / -1 | 属于溢出：检测开启时报错，关闭时结果为 MIN；MIN % -1 恒为 0 |
| 移位位数超出位宽 | 属于程序错误：检测开启时报错，关闭时对位宽取模 |
| 浮点→整数（显式或隐式） | 超出范围时饱和到目标类型的上下限，NaN 转为 0 |

C++ 中越界的浮点→整数 `static_cast` 是未定义行为，本语言不沿用。浮点舍入和浮点溢出的诊断范围【待定】。

### 7.6 引擎边界

- 不沿用 GDScript 默认的标量位宽。区分三种类型：语言中的语义类型、引擎 API 的语义类型，以及 Variant／ptrcall 实际使用的 ABI 槽位。
- 引擎 API 的语义类型取自 `MethodBind::get_argument_meta()`（返回 `GodotTypeInfo::Metadata`，其中包括 INT_IS_UINT64 等）。extension_api_dump 输出的 `meta` 字段用的就是它，所以不需要手工逐个标注。
- 对静态已知的 u64 引擎 API 槽位，u64 与 Variant int 之间的 ABI 编码按位重新解释（§12.3），不属于 §7.3 的源码常量转换。u64 存入 `any` 时改用带类型盒子（§12.1）。一个现成的例子：RefCounted 对象的 ObjectID 第 63 位为 1，当作 u64 时 ≥ 2⁶³，经过 Variant 后变成负数。
- 运行时的越界检查独立于溢出检测，默认开启。【已知限制】第一版不提供关闭越界检查的方法，也不提供 unsafe 模式。

## 8. 变量、常量与初始化

### 8.1 var 与 const

- 只用 var 和 const 两个关键字，不另设 let 或 mut。
- const 只接受常量表达式。没有“运行时初始化后冻结”这种常量，也没有 `@onready const` 或单独的冻结阶段。
- 成员、构造、场景注入和 `@onready` 都沿用 Godot 的生命周期，不引入面向用户的初始化状态类型。
- 非空成员必须从有效来源初始化；`None` 不是 T 类型的值。确实可能缺失的值使用 `T?`。
- 延迟初始化的成员可以有一个内部的“未初始化”状态：能静态判定的非法读取报编译错误，其余情况在运行时检查，并给出可诊断的错误。

### 8.2 初始化顺序与规则

本语言沿用 GDScript 的初始化顺序：

- 构造时，先从基类到派生类执行所有普通成员的初始化器，再调用 `_init`。
- `@onready` 成员的初始化器在调用 `_ready` 时执行，早于用户写的 `_ready` 函数体，同样按从基类到派生类的顺序。

在此基础上规定：

1. **构造期的成员初始化器不能引用 self**：不能调用实例方法，也不能读取其他非 const 成员。这一条可以静态检查，它消除了“基类初始化器通过虚调用，读到派生类还没初始化的成员”这一整类问题。**`@onready` 初始化器例外**：它在节点就绪时才执行，可以引用 self，例如最常见的 `@onready var child = $Child`。
2. **Node 和 Resource 子类的 `_init` 必须能以零个参数调用。** 场景实例化、资源加载和 `duplicate()` 都会以零个参数调用 `_init`。违反时静态报错，或者在实例化时报错。
3. **每个非空的 `@onready` 成员都有一个“已初始化”标志。** 检查的是“这个成员的初始化器是否已经执行完”，而不是“是否已经进入 `_ready`”。读取一个还没完成初始化的成员是程序错误，诊断信息要写明成员名和调用栈。这种情况无法完全靠静态分析排除，例如：
   - 子节点的 `_ready` 先于父节点执行。如果子节点同步发出一个信号，而父节点的处理函数读取了自己的 `@onready` 成员，这个成员此时还没有初始化。
   - 某个 `@onready` 初始化器调用的方法，读取了声明在它后面、还没初始化的另一个 `@onready` 成员。如果是初始化器直接读取后面声明的成员，可以静态报错。

### 8.3 待定

- 非空 `@export` 引用在什么时候检查：场景实例化完成时，还是第一次读取时。
- static var 的初始化顺序。
- 针对选定的目标版本，固定成员初始化、`_init`、场景属性赋值、进入场景树、`@onready`、`_ready` 的完整顺序，特别是涉及继承和场景注入的情况。

## 9. await、信号与 Callable

- await 只做最小的接入，对接 Godot 的信号、计时器、帧事件和主循环，不另外实现执行器（executor）。挂起时的帧，以及局部变量的保存和恢复，由本语言负责。
- 生命周期、恢复顺序和可重入性尽量与 GDScript 保持一致；不自行发明自动延迟（deferred）或取消机制。信号可能同步地恢复执行，不能假设一定要到下一帧才继续。
- 恢复执行时会检查所属的实例：如果实例已经不存在，就报错并放弃这次恢复。这与 GDScript 的行为一致；GDScript 在 release 构建中则是静默返回。“节点退出场景树就自动取消 await”这种说法未经核实，不能当作规则。
- 签名已知的函数、闭包和回调使用静态函数类型，参数和返回值都做静态检查。
- 引擎中签名未知的 Callable 保留擦除类型的形式。第一版通过绑定层使用 callv 调用；参数按绑定契约使用 `any` 或 `Option[any]`。未知的结果类型为 `Option[any]`，除非可靠契约排除了 NIL（§12.6）；执行具体操作前须收窄。
- 【待定】节点的 owner 被销毁、节点退出场景树、信号源被销毁、挂起帧被释放，以及跨语言的异步值等情况，都需要对照目标版本测试，必须避免重复恢复、内存泄漏和失效访问。
- 【后续】保留完整签名的可变参数泛型（参数包）。但不会因此引入一整套开放记录（row polymorphism）。

## 10. 错误与诊断

- 预期之内、可以处理的失败，用 Result 作为返回值，并通过传播语法向上传递。后缀 `?` 预留作传播记号，具体语义【待定】。
- **程序错误**包括：数组越界、失效访问、读取未初始化的值、除零、非空断言失败、开启检测时的整数溢出，以及外部值检查失败（§12.5–§12.6）。程序错误会产生运行时诊断和调用栈；脚本在哪里终止执行，由引擎调试器决定，不预设整个游戏必须退出。
- **报错信息是重点，第一版允许外观简陋。** 先保证报出的文件、位置和约束之间的因果关系都是对的。
- 跨文件的错误不能只报一句“入口脚本加载失败”；类型冲突要给出两侧的类型和必要的来源位置（R7）。
- 编译失败时，不发布只编译了一半的签名或可执行产物。漂亮的排版、修复建议、完整的推断过程追踪，可以以后再做。

## 11. 编译模型

- 递归、互递归和跨文件推断，按强连通分量（SCC）联合求解。跨文件导出的签名可以推断，不强制每个公共函数都写标注。
- **SCC 以声明为单位**（函数、成员），而不是以文件为单位。Godot 项目里文件之间互相引用非常普遍，比如 Player、Enemy 和各种 autoload；以文件为单位，大半个项目都会落进同一个 SCC。
- **依赖在推断过程中按需发现。** 依赖图没法在推断之前算出来，因为方法调用的目标取决于接收者的类型。例如在 `func f(): return make_b().g()` 中，要先推出 `make_b` 返回 B，才能发现对 `B.g` 的依赖。具体做法：
  - 推断某个声明时，按需请求其他声明的签名；
  - 如果请求的声明“正在推断中”，说明遇到了回边，按 Tarjan 算法的栈把相关声明合并成一个 SCC；
  - 等到 SCC 的根推断完成后，才对外发布这些签名。
- 重入问题靠“推断中”状态和栈来处理。SCC 完成之前，其中的签名只在栈内可见；推断失败时整个 SCC 一起丢弃，不会留下只做了一半的缓存。
- 不支持多态递归。
- 模块有自己的协调器，所以引擎逐个加载、校验资源的方式，并不限制本语言必须逐个文件独立推断。不依赖引擎提供联合编译接口，也不为此修改 core。
- **初始化循环和类型循环分开处理：** const 都是常量表达式，它们之间出现循环直接拒绝；构造期的成员初始化器不能引用 self（§8.2），所以剩下的只有跨对象的构造递归，例如 A 的成员初始化为 `B.new()`，B 的成员又初始化为 `A.new()`。这会在运行时栈溢出，与类型推断无关。
- 增量编译要维护依赖、反向依赖和缓存，首先保证失效判断正确，保守地多重编一些可以接受，第一版也可以每次整个项目重新编译。接口不变时，复用调用方已有的编译结果。增量编译不是热重载；普通的运行时调用永远不会触发推断。

## 12. 引擎互操作：Variant 映射

### 12.1 值、表示与 ABI

Godot Variant 是引擎的带标记值容器，属于互操作概念，不是语言中第二种动态类型。语言代码使用 `any` 和 `Option[any]`（§2.1），绑定层自动将它们适配到引擎的 Variant 槽位。

`any` 的内部表示兼容 Godot Variant ABI，包括值布局及 Variant 调用边界的处理。数值使用下表规定的规范化表示；其他 core 能表示的值沿用原生表示。没有原生表示的值，包括存入 `any` 的语言 enum 和 Option 值，使用携带具体类型信息及载荷的只读 Array。类型信息包含恢复该值所需的类型参数。带类型盒子的精确标记格式【待定】。

| 数值源类型 | any 中的动态数值类型 | 表示 |
|---|---|---|
| i8…i64、u8…u32 | i64 | 原生 Variant INT，保留数值 |
| f32、f64 | f64 | 原生 Variant FLOAT，保留数值 |
| u64 | u64 | 带类型 Array 盒子，保留完整无符号数值，不随数值大小改变 |

从 `any` 取数时，按请求的目标类型及 §7.3／§7.5 转换，不检查原始源位宽。装箱 u64 先恢复无符号数值，再做数值转换。u64 盒子不会被无声转换成普通有符号 Variant INT。目标为静态已知的 u64 引擎 API 类型时，绑定可以使用 §12.3 独立规定的位传输契约；无类型约束的 Variant 槽位收到动态盒子。

即使载荷表示 `Option[T].None`，带类型盒子自身也不是 NIL。下文用 `box(T, e)` 示意携带类型 T 和载荷编码 e 的非 NIL 只读 Array；它不是源码语法，也不规定精确标记格式。例如，`box(Option[i32], NIL)` 编码的是含有 `Option[i32].None` 的有值 `any`。相比之下，`Option[any].None` 用 NIL 表示，`Some(v)` 用 v 的非 NIL 表示。裸 NIL 绝不是合法的 `any`。

静态已知的 T 在引擎边界上的编码（§12.3–§12.4），不必等于把该值存入 `any` 时的编码。特别是，静态类型能够补足信息时，enum 编码可以使用 NIL 或省略类型参数；动态装箱则必须保留类型信息，且不能产生裸 NIL。共享 ABI 不意味着合法值集合相同。

GDScript、编辑器、Dictionary 的键和资源文件都能观察外部编码。以下规则按类型规定编码，不为每个值重新选择。以后改变已确立的外部编码属于破坏性变更。

### 12.2 容器

- **本语言的容器就是引擎的容器**：`Array[T]`、`Dictionary[K, V]` 就是引擎的 Array、Dictionary，在两边共享，不做复制。引擎能表达的元素类型，使用引擎的 typed 容器。
- 类型保证分两部分：本语言自己写入时做静态检查；**每次读取时都做运行时检查**。如果读到的值不符合 T，就是程序错误，诊断信息类似“第 3 个元素是 null，但元素类型是 Enemy（可能被外部代码写入）”。如果实现能证明数据只被本语言写过，可以省掉检查；这是优化，不改变语义。
- 理由：引擎那边可以写入任何值。引擎的 typed Array 允许 Object 元素为 null；`Array[i32]` 在引擎那边只能表示成 `Array[int]`。如果改用本语言自己的容器、跨边界时复制一份，引擎对它的修改本语言就看不到了，这违反了“Array 是共享引用”的约定。
- 没有默认值的元素类型（例如非空 Object）只提供 `resize(n, fill)`，不提供 `resize(n)`。原因是引擎的 `Array::resize` 不会初始化新增的 Object 元素，它们都是 null。

### 12.3 类型映射表

本表规定声明目标类型对应的外部表示。u64 一行是静态已知 u64 目标的位传输；u64 存入 `any` 时改用 §12.1。读回检查按目标类型校验外部表示，与已合法进入语言的 `any` 的数值转换（§7.3）不同。

| 语言类型 | 在 Variant 中的表示 | 读回时的检查 |
|---|---|---|
| i8…i64、u8…u32 | int | 值在范围内 |
| u64 | int，按位重新解释 | 不检查（≥2⁶³ 的值显示为负数，与引擎处理 ObjectID 的方式一致） |
| f32、f64 | float | f32 需要舍入，属于精度损失 |
| core 值类型（Vector2、String 等） | 同名类型 | 类型匹配 |
| 非空的 Object 类 T | Object | 非空，且类匹配 |
| enum（包括 Option） | 见 §12.4 | 完整解码，见 §12.5 |
| `any` | 普通数值为规范化 i64／f64；u64 装箱；其余为原生非 NIL 值或带类型盒子（§12.1） | 拒绝 NIL；验证带类型盒子及载荷；取数遵循 §7.3 |
| `Option[any]` | None 为 NIL；Some 为 any 的非 NIL 表示 | NIL 得 None；否则按 any 检查 |
| 函数类型 | Callable | 本语言创建的 Callable 校验签名；其他来源的在每次调用时检查 |
| `Array[T]`、`Dictionary[K, V]` | Array、Dictionary | 读取时逐个元素检查 |

### 12.4 enum 的映射

本节规定静态已知的 enum 类型面向引擎的编码。把 enum 值存入 `any` 时，改用 §12.1 的规则。

**表示集合：** 一个类型的外部编码使用的 Variant 类型标记的集合。整数和 core 值类型各使用一种标记；非空 Object 类使用 {OBJECT}；`any` 使用除 NIL 外的全部标记；`Option[any]` 还包含 NIL。enum 的集合是在外层上下文中选定编码后，各分支集合的并集；全部装箱的 enum 使用 {ARRAY}。这些集合描述选定的编码，不决定应给哪个外层装箱。

**映射规则：** 从外层 enum 向内确定编码，选择依据是类型和载荷位置，不是具体值。

1. **无载荷的分支**：只有一个时，先为它保留 NIL；有多个时，各自表示为 INT 序号。因此，具有多个分支且全部无载荷的 enum 和 GDScript 的 enum 一样，使用 int 序号。
2. **单字段分支**：先使用字段自身的编码。如果外层 enum 已为唯一无载荷分支保留 NIL，而字段的独立编码包含 NIL，就将内层字段值编码为非 NIL 的 `box(T, e)`，其中 T 为字段类型、e 为其编码（§12.1）。该载荷位置中的所有值都使用这一选择。外层无载荷分支保留 NIL，除非下述剩余冲突规则要求全部装箱。
3. **多字段分支**：装箱为只读 Array `[&"Enum.Variant", 字段1, 字段2, …]`。开头的 StringName 记录 enum 名和分支名，但不包含类型参数：`Option[i32]` 和 `Option[String]` 都使用 `&"Option.Some"`，类型参数由读回时的静态类型补足。各字段递归使用各自的编码；`any` 字段遵循 §12.1。
4. **剩余冲突**：选定载荷编码后，重新检查各分支的表示集合，包括内层盒子新引入的每个 ARRAY。如果仍有分支重叠，外层 enum 的所有分支都装箱，包括无载荷分支（`[&"Enum.Variant"]`）和单字段分支（`[&"Enum.Variant", 字段]`）；显式分支标记保证唯一解码；这些带分支标记的盒子内部，各字段按第 3 条递归使用自身类型的独立编码。多个无载荷分支使用不同 INT 序号，不算冲突。不再用其他布局优化规避这条全部装箱规则。
5. Object 载荷只按 Variant 类型（OBJECT）区分，不按具体类区分，因为子类之间会重叠。

```
enum Cmd: Stop, Move(Vector3), Wait(f64), Hit(Node, i32)
# Stop→NIL  Move→Vector3  Wait→float  Hit→[&"Cmd.Hit", node, 5]

enum Hp: Dead, Alive(i32)              # Dead→NIL  Alive→int
enum Shape: Circle(f64), Square(f64)   # 两个分支都是 float，冲突 → 全部装箱
enum Key: A, B, Code(i32)              # 序号和 Code 都是 int，冲突 → 全部装箱
```

```
enum E: Empty, Has(Option[i32])
# Empty        → NIL
# Has(None)    → box(Option[i32], NIL)
# Has(Some(5)) → box(Option[i32], 5)
```

如果其他分支使用 ARRAY，内层装箱可能引入剩余冲突。例如，`enum F: Empty, Has(Option[i32]), Items(Array[i32])` 在第 2 步后，Has 和 Items 都表示为 ARRAY，因此按第 4 步给 F 的所有分支装箱，包括 Empty。

**Option 是这些规则的实例。** 唯一无载荷分支 None 保留 NIL。对于 `Some(x)`，T 的独立编码不含 NIL 时直接使用；否则给内层 T 值使用 `box(T, e)`。这些载荷选择与外层 NIL 不冲突，因此 None 保留 NIL niche，不需要 Option 专用的冲突规则。

Option 的值是 `None` 和 `Some`，不含语言内部的 null 值。其独立编码使用 NIL，不妨碍外层 Option 为自身的 `None` 保留 NIL。`any` 和语言 Object 类型均非空，因此 `Option[any]`、`Option[Enemy]` 不需要仅为空缺给载荷装箱。原始引擎 null 由绑定和读取检查处理（§12.5–§12.6）。

| 类型 | 表示集合 | `None` | `Some(…)` |
|---|---|---|---|
| `i32?` | {NIL, INT} | NIL | `Some(5)` → `5` |
| `Enemy?` | {NIL, OBJECT} | NIL | 对象本身 |
| `i32??` | {NIL, ARRAY} | NIL | `Some(None)` → `box(Option[i32], NIL)`；`Some(Some(5))` → `box(Option[i32], 5)` |
| `Cmd?`（上例的 Cmd） | {NIL, ARRAY} | NIL | `Some(Cmd.Stop)` → `box(Cmd, NIL)`；`Some(Cmd.Move(v))` → `box(Cmd, v)` |
| `any?` | 全部标记 | NIL | `Some(v)` → v 的非 NIL 表示；当 v 含有 `Option[i32].None` 时，包括 `box(Option[i32], NIL)` |
| `any??` | {NIL, ARRAY} | NIL | `Some(None)` → `box(Option[any], NIL)`；`Some(Some(v))` → `box(Option[any], v 的表示)` |

示例中的 NIL 是引擎编码，不是语言值。例如，`i32???` 的 `Some(Some(None))` 编码为 `box(Option[Option[i32]], box(Option[i32], NIL))`；嵌套盒子保留各层 Option。Option 存入 `any` 时，同样以非 NIL 的带类型盒子保留完整类型（§12.1），不会变成外层的 `Option[any].None`。外层 Option 的 niche 与值存入 `any` 时的动态装箱各有用途，不同层的 `None` 不得折叠。

**盒子与身份：**

盒子是只读 Array。Object 在 `==` 比较和作为 Dictionary 键时按身份比较；Array 按内容比较、计算哈希，并可直接序列化（附录 A）。enum 值不可变，因此共享盒子仍保持值语义。不做位打包：Variant 只有一个类型标记，复制时仅保留具体类型的值，不保留数据区的空余字节（附录 A）。

直接内联到引擎 Variant 的 enum 会丢失类型身份。例如，`Cmd.Move(v)` 变成 Vector3；解码能检查形状，但无法恢复来源；在无类型约束的 Dictionary 中，它与 v 是同一个键。`any` 中的带类型盒子保留 enum 的具体类型。两者是不同的编码（§12.1）。

按序号编码的无载荷 enum 调整分支顺序后，存档含义会改变；按名字编码的盒子在分支改名后会改变。

**深度：** 编码如果会超过引擎递归上限（`MAX_RECURSION`，目前为 100，见附录 A），就是程序错误；解码遵守同一上限。这保证本语言的编码器不构造超限编码，不保证外部代码以后不能加深共享的 Array 或 Dictionary。后续读取和对象访问仍须进行正常检查（§12.2、§12.5）；构造时的保证不验证外部将来写入的内容。

### 12.5 读回与解码

每当外部可变位置的内容作为受信任类型的值进入语言时，都要检查。对一个位置检查成功，不代表该地址永久有效；再次读取属性或容器元素时，须检查其当前值。

读取为 `any` 时，NIL 是程序错误；读取为 `Option[any]` 时，NIL 得到 `None`，合法的非 NIL 值得到 `Some(v)`。带类型盒子须有合法的类型信息，且载荷符合该类型。其他目标类型按以下规则检查：

- 内联 enum：Variant 标记须按 §12.4 选定的编码确定唯一分支。为无载荷分支保留 NIL 时，NIL 标识该分支。单字段分支按选定的载荷编码解码：需要带类型盒子时，先验证并拆开盒子，再按字段类型解码载荷；不需要盒子时直接解码。字段的范围、有值状态和类要求仍须满足。Option 同样遵循此规则，不另设解码规则。
- 带分支标记的 enum 盒子：Array 开头的 StringName 须指明目标 enum 的一个分支；长度须为该分支字段数加一；每个字段须符合其类型。嵌套 enum 递归解码。
- 其他类型：遵循 §12.3 的检查。

解码 enum 时，字段被复制为语言值，不保留外部编码盒子；之后修改该盒子的分支标记或值字段，不改变已经解码的 enum。引用类型的载荷仍然共享。特别是，复制 Variant 只隔离值槽，不复制它所引用的 Array 或 Dictionary 的内容。因此，检查后的 `any` 副本并不保证共享容器元素有效，每次读取仍遵循 §12.2。若带类型盒子仍可被外部修改，读取或解码时须重新检查类型信息和载荷；仅复制其 Variant 槽位并不能使该盒子成为受信任的值。非空 Object 值仍须遵守 §6.5 的存活检查。

本语言生成只读盒子，在保持值语义的前提下可以复用。收到外部盒子不代表它的共享内容以后不会变化。

### 12.6 绑定契约与入口转换

引擎 API 的 Variant 只有在可靠绑定契约排除 NIL 时，才映射为 `any`；否则映射为 `Option[any]`。参数、返回值和属性均遵循此规则。绑定层自动完成编码和检查；普通调用不要求在源码中转换为原始 Variant 类型。

本语言的类实例是 Godot Object，因此 GDScript 和引擎代码能绕过静态类型，例如 `node.call("take_damage", "hello")`、`node.set("hp", 1 << 40)`、场景属性值、AnimationPlayer、Tween，或在 Inspector 中清空导出的引用。

每个传入的 Variant 都按声明的目标类型解码并检查（§12.3、§12.5），包括 callp 参数、`set`、信号回调、场景反序列化和 Callable 调用。类型不符、外部整数越界、非空位置缺值，均为运行时错误。这是外部表示的检查，不是 §7.3 中语言值的整数到整数转换，不会悄悄截断。外部 Variant INT 的值为 300，直接读为 u8 时报错；合法语言 `any` 中的运行时规范化 i64 值为 300，转换为 u8 时得到 44。不能把直接的外部读取隐式绕经 `any` 数值转换，以跳过目标类型的范围或类型检查。

外部代码把 NIL 写入暴露为 `Option[any]` 的位置后，下次读取为 `None`；若该位置暴露为 `any`，下次读取检查失败。外部代码修改别名容器时同样如此。

### 12.7 待定

- 哪些类型有默认值（例如 enum 是否以某个分支作为默认值），这决定了 `resize(n)` 是否可用。
- `@export` 的 i32 等窄整数类型，是否自动附加范围提示（Inspector 编辑的是 64 位 int）。
- 调试器如何按静态类型解码并显示内联的 enum 和装箱的值。

## 13. 模块与引擎设施

沿用 Godot 已有的习惯：脚本文件、资源路径和类注册方式都不变，不新增包管理器，也不引入复杂的可见性体系。导出属性、信号、资源、场景和编辑器尽量复用已有机制；但“复用”不等于已经验证过兼容。`@tool` 等在编辑器中执行脚本的能力，第一版不专门去扩展，能自然接上就接上，否则延后。

## 14. 第一版范围

第一版包含 `any`、`Option[any]`、带类型动态盒子和外部读取检查（§2.1、§12）。常量传播不完备不放宽常量错误规则（§7.3）。

**【已知限制】**

- 没有 dyn trait。需要对不同类型的对象做鸭子类型式的处理时（例如遍历 `get_overlapping_bodies()` 并调用 `take_damage`），只能用 `is` 收窄，或者用擦除类型的 `call()`。
- 不支持递归 enum（§6.1）。
- 泛型函数不对引擎暴露（R2）。
- 不提供关闭越界检查的方法，也没有 unsafe 模式（§7.6）。
- 不支持热重载，也不做运行中的状态迁移。

**【待定】**

- 目标 Godot 版本。建议跟随 master；初始化顺序、await、typed Array 等行为的测试要按选定的版本固定下来。
- 实现语言、IR、JIT 后端、分发方式，以及与编辑器集成的深度。
- 各种语法的具体拼法：enum、trait、泛型、Result 的传播、绑定语法、显式转换、显式回绕运算、整数后缀。
- 没有标注类型的 const 是否像字面量一样柔性（类似 Go 的 untyped constant）；引擎的枚举和位标志常量映射为什么类型。
- 整数与浮点混合运算的优先级；浮点舍入和浮点溢出的诊断范围；潜在溢出警告的触发条件。
- 泛型的实现路线：传类型描述符，还是在 IR 层单态化（§4）。
- §5.4、§6.5、§8.3、§9 和 §12.7 中列出的细节。

**【后续】**

- **struct（值类型记录）**：社区已经有相关提议。它在 Variant 中的映射与只有一个分支的 enum 相同：单字段 struct 表示为该字段本身，多字段的装箱为 `[&"Name", …]`。struct 的字段可以修改，存放在容器中的 struct 被修改时，按“取出、修改、写回”执行。风险：如果以后 core 提供了原生的 struct Variant 类型，迁移过去会改变存档格式，需要做带版本号的迁移。
- **装箱开销的 lint**：提示 enum 或 struct 装箱造成的内存分配，主要出现在 `Array[enum]` 这类容器里。
- **递归 enum**：如果出现需求，首选 Swift 那样的手动 `indirect` 标注。这样分配在声明处一眼可见，以后还能兼容地放宽成自动间接。自动间接只是省下少数类型上的一个关键字，代价却是 enum 中出现看不见的堆分配。
- dyn trait、trait 的默认方法、关联类型；保留完整签名的参数包；允许引擎看不到的函数做隐式泛化（相对 R2 是兼容的放宽）。
- JIT 与泛型特化；`@tool`；向上游 Godot 贡献契约元数据。

## 15. 一致性测试要点

| 领域 | 最少需要验证的内容 |
|---|---|
| 推断 | 参数类型由流向推断；只有方法调用时要求标注；流向 any 或 Option[any] 不算依据；局部变量先看流入、再看流向，结果与约束的顺序无关；方法调用处就地确定柔性字面量的类型；空容器成员要求标注；不同类的分支不求共同父类 |
| 泛型 | 显式泛型能够实例化；`has_method` 看不到泛型方法；以 i32 实例化时按 32 位语义运算 |
| SCC | 同一文件和跨文件的互递归都能求解（包括 §11 中 `make_b().g()` 的例子）；不在环上的泛型工具函数不受影响；类型冲突定位到真正的来源 |
| enum | 载荷、命名的返回值、穷尽检查；不会合成匿名的和类型；enum 的值不能原地修改；递归 enum 报错并列出循环路径，而经由 Array、Dictionary 或 class 的递归可以通过 |
| trait | 满足和不满足约束时的编译结果，不依赖 dyn |
| 可空 | `T?` 与 `Option[T]` 等价；`T??` 能区分两层；`!` 断言失败时的诊断；`?.` 整条链短路；成员不做收窄 |
| 存活 | 局部 Node 跨过 await 后，非空仍成立而存活不一定成立；`?.` 遇到已释放的对象时报失效访问 |
| 所有权 | 只被 Object 类型变量持有的 RefCounted 对象仍然存活；下转后所有权不变；对句柄类型使用 `weak` 报错 |
| 共享与写回 | 通过别名做的修改彼此可见；`line.points.append(p)` 能写回属性；显式复制不会暗中做深拷贝；弱引用和手动断环有效 |
| 数值 | 默认设置下 `position += velocity * delta` 不产生警告；各类警告独立配置；整数转换损失默认关，浮点转整数的值域损失仍默认开；`x: u8` 时 `x + 100` 为 u8；`var a: u8 = 300` 报编译错误 |
| 整数转换 | 窄化、同宽变符号、有符号和无符号加宽，包括负数有符号源到更宽无符号目标，均遵循 §7.3；范围内常量通过，越界常量即使显式转换或关闭警告仍报错；传播不被 `var` 阻断；运行时值域可能损失不等于常量错误 |
| 溢出 | 常量表达式溢出报编译错误；显式回绕运算不报错；运行时检测开关有效；检测关闭时解释器和 JIT 的结果一致；跨函数推出的溢出不报编译错误 |
| 数值边界 | §7.5 的表逐项验证；u64 往返（ObjectID 的第 63 位）；越界检查不受溢出检测开关影响 |
| 初始化 | 构造期的成员初始化器引用 self 时报错，`@onready` 初始化器可以引用 self；`@onready` 初始化器通过方法调用读到后面声明的成员时能被检出；零参数 `_init` 的检查；子节点在 `_ready` 中经由信号读取父节点的 `@onready` 成员时，给出可读的诊断 |
| await | 恢复顺序、可重入、实例销毁后恢复、帧清理，都对照目标版本验证 |
| Callable | 已知签名的静态检查；擦除类型的结果不会冒充成已知类型 |
| 动态值 | 普通整数规范化为 i64、浮点规范化为 f64，不保留源位宽；u64 始终带类型装箱，取出时先恢复无符号值再按目标转换；运行时 u64 最大值转回 u64 保值，转 i64 得 −1；基础类型和用户类型的值，包括 Option.None，都能进入 any；Object 继承不变；裸 NIL 读为 any 时报错，读为 Option[any] 时得 None；带类型 Option.None 盒子在 any 内仍为有值状态；嵌套 Option 盒子保留每一层 |
| Variant 映射 | 映射表逐行往返；唯一无载荷分支保留 NIL，冲突的内层载荷装箱；剩余冲突（包括该盒子引起的 ARRAY 冲突）导致外层所有分支装箱；§12.4 的嵌套 Option 往返，外层 None 为 NIL，内层 Option 值装箱，各层 None 可区分；盒子作为 Dictionary 键时按内容比较；编码和解码检查深度；解码检查类型信息、分支、长度和字段 |
| 外部读取与入口转换 | 错误类型、越界外部整数和非空位置缺值时报错；Array::resize 产生的 null 在读取时检查；外部写 NIL 按目标类型得到 None 或报错；复制 Variant 槽不深拷贝 Array/Dictionary 内容；后续外部修改在读取时检查，不属于编码器构造保证；已解码 enum 的值字段独立于编码盒子 |
| 增量编译 | 修改函数体、签名或依赖的 SCC 后，不复用过期的结论 |
| 引擎集成 | 端到端验证：挂载脚本、回调、属性、场景的保存与加载 |
| 诊断 | 报出实际的文件位置、两侧的类型和决定类型的那一行、运行时调用栈；不依赖热重载 |

补全、断点、导出可执行程序等功能，按实现成本分级验收，不必全部作为 alpha 版本的必备项。

## 16. 路线图与反馈

**路线图**

1. 收集公开反馈，冻结一个可测试的最小核心。
2. 构建测试集：盘点可以复用的测试及其许可证；区分沿用的行为、有意改变的行为和新增的能力；覆盖正向、负向、运行时和引擎集成测试。

## 附录 B：考虑过但没有采用的方案

| 方案 | 没有采用的原因 |
|---|---|
| 默认借用、显式 move，或放入容器时自动 move | 脚本场景下标注负担太重；改为共享引用，外部类型服从引擎契约 |
| 追踪式 GC | 改为引用计数、弱引用和手动断环 |
| 普通引用自动让 Node 保持存活 | Node 的生命周期由引擎管理；句柄不延长寿命 |
| 以 HM 作为推断路线，合法时隐式泛化普通函数 | 与“引擎可见的入口”冲突（R2）；改为先定语义（R1–R7），泛型必须显式声明 |
| 从调用方反推函数类型 | 函数类型会随着新增调用而改变，而且动态调用方看不见（R1） |
| 局部变量的多个约束不一致时直接报错（类 Rust） | 真实代码中这类冲突大多是“流入 f64、流向 f32”，报错并不能抓到真正的错误；改为先看流入、再看流向（R4，见调查记录） |
| 局部变量的类型只由初始化式决定（类 Swift、Kotlin、C#） | `var r = 0` 之后再赋值一个 double，会被截断成 0（R4，见调查记录） |
| 抽象的 int，沿着调用链再决定位宽 | 改为一整套定宽类型，没有约束时默认 i32 |
| 默认使用 f32 | 改为默认 f64，用 `f` 后缀表示 f32 |
| 有损隐式转换统一报一种警告 | 精度损失、整数转换损失、浮点转整数的值域损失分别配置；整数转换默认静默截断（§7.3） |
| 仅因单字段载荷编码包含 NIL 就给外层 enum 的所有分支装箱 | 唯一外层无载荷分支保留 NIL，内层载荷装箱；只有仍存在冲突才须给外层全部装箱（§12.4） |
| u64 存入 any 时使用原生有符号 INT，或仅给大数装箱 | any 始终给 u64 装箱，保留无符号数值且表示不随大小改变；已知 u64 API 槽位使用独立的位传输契约（§12.1、§12.3） |
| 裸 NIL 作为 any 的值 | any 非空；Option[any] 用 NIL 表示空缺，存入 any 的 Option 值则使用带类型非 NIL 盒子 |
| 拒绝所有可能有损的运行时整数转换 | 运行时转换具有确定的模运算结果；只有越界常量转换是必须报告的错误（§7.3） |
| 检测关闭时，溢出是未定义行为 | 破坏确定性（帧同步联机、回放）；改为结果确定为回绕 |
| 运行时初始化后冻结的 const | 只保留常量表达式 |
| `T?` 与 Option 作为两个独立的概念 | 泛型代码需要嵌套，两套 API 风格会互相割裂；改为 `T?` 即 `Option[T]` |
| 用 RefCounted 对象给 enum 装箱 | 按身份比较，导致作为 Dictionary 的键时失效；改为只读 Array |
| 把小 enum 位打包进 INT 或 Vector4i | 没有地方存放分支标记，浮点的相等语义也会随表示变化，调试器也看不懂 |
| 本语言自己的容器，跨边界时复制 | 引擎对容器的修改本语言看不到；改为直接使用引擎容器，读取时检查 |
| 自动间接存储的递归 enum | 只省下一个关键字，却换来看不见的堆分配；第一版不支持递归 enum |
| 先建立文件级依赖图，再做推断 | 依赖图要到推断过程中才能知道；改为以声明为单位、按需发现的 SCC |
| 完整的行多态，静态转发任意参数 | 参数包列为后续计划 |
| 热重载与运行中的状态迁移 | 不做 |
