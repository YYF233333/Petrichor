# Petrichor implementation architecture

**Draft · 2026-10-29** · 中文: [architecture.zh.md](architecture.zh.md)

This document records implementation decisions: how the components are split, how values are represented, testing, and the order of work. The [language specification](language-spec.en.md) is authoritative for language rules. When the implementation reveals a problem in the specification, the specification is changed in a separate commit; the implementation does not relax its rules. Engine facts are checked against Godot 4.7.2-stable (commit `ed1daf0`).

## 1. Decisions

- **C++17, godot-cpp, SCons.** The interpreter has to run on iOS and consoles (spec §12.2), and an engine-module build may come later (§1.3). The engine is compiled as C++17 (`SConstruct:916, 921`) and engine modules can only be built with SCons, so this project uses both. Since v10, godot-cpp is versioned independently of Godot and one version can target several Godot versions; this project pins it to a commit and builds it with `api_version=4.7`. This project raises its C++ standard only after the engine does: C++20 brings only conveniences, and the guaranteed tail calls an interpreter may use are compiler extensions, independent of the standard.
- **The target engine is Godot 4.7.** The extension declares 4.7 as its minimum version, and the engine loads extensions whose minimum version is not above its own (`core/extension/gdextension_library_loader.cpp:315-329`), so later engines load the same build too; it is checked only against 4.7.2. Running on them also needs the engine's values to keep the layout this build relies on: a Variant holds its type first and its data 8 bytes on, an object in it as its ObjectID and pointer (`src/runtime/values.h`), and no built-in type takes more bytes than the bytecode reserves for it, which the runtime checks when it loads.
- **Exported games contain only bytecode** (spec §1.3). A `.gdextension` file selects different libraries for the editor and for export templates by feature tags (`gdextension_library_loader.cpp:82-96`): the editor library includes the compiler, the export-template library only the runtime.
- **Registers hold native values according to their static types.** Even where static types are known, GDScript's registers are Variants (`modules/gdscript/gdscript_vm.cpp:536`), its operators run through function pointers on Variants (`:848-862`), and engine method calls take Variant pointers as well (`:2273-2313`). This language uses its fully static types to avoid these costs, which is the main source of being "clearly faster than GDScript" (spec §12.2). For now, engine methods are called by name (§2.6).
- **When run from the editor, the game reads the bytecode the editor has written and does not compile** (§2.4).

## 2. Components

| Component | Depends on | Contents |
|---|---|---|
| compiler | nothing from Godot | lexing and parsing, semantic analysis, scene checks, typed IR, bytecode generation, diagnostics, symbol index |
| bytecode | nothing from Godot | the format of compiled code, its serialization and its verification, shared by the compiler and the runtime |
| runtime | godot-cpp | bytecode loading, the virtual machine, values and type descriptors, tasks, program errors, checks and conversions at the engine boundary |
| adapter | godot-cpp, runtime; the editor library also compiler | the three extension interfaces for the script language, scripts and script instances, resource loading and saving, the export plugin, the editor plugin, the headless command |

### 2.1 compiler

- It includes no Godot headers; the build does not give compiler sources the godot-cpp include paths. Its tests are therefore plain C++ programs that do not start the engine, and it can be used unchanged in an engine-module build.
- External information is obtained through interfaces:
  - the engine API: classes, methods, properties, signals, enums, and the operator table of the built-in types;
  - the project: scenes, resources, autoloads, global classes;
  - the static view of GDScript classes (spec §11.1);
  - binding review data (§10.3), kept as data files in the repository (`src/compiler/binding_metadata.txt`).
  In the editor and in headless mode the adapter implements these interfaces: engine classes come from ClassDB, because the classes of other extensions and the API of newer engine versions are not in the `extension_api-4-7.json` shipped with godot-cpp; scenes come from the scene states the engine reads (SceneState), so text and binary scenes and instances are read as the engine reads them; GDScript classes come from Script's reflection interface. Built-in types (operators, members, methods, constructors) and utility functions are the exception: ClassDB does not describe them and the engine offers an extension no way to list them, so the editor and the tests both use tables generated from the JSON at build time; they do not vary with extensions, and newer engines only add to them. The engine's own nullability metadata (RequiredResult and RequiredParam, spec §10.2) is in the same position: ClassDB's method information leaves it out (`core/object/method_info.cpp:37-51`), so it is generated from the JSON too, merged with the review data; classes of other extensions follow the default rules of §10.2. The tests currently describe engine classes and scenes by hand.
- Pipeline: lexing → syntax tree → semantic analysis (names, types, narrowing, match, generics, interfaces, visibility) → scene checks (§7) → typed IR → bytecode, debug information and class metadata.
- The IR consists of explicit basic blocks and virtual registers; it is not SSA. Every instruction has a type and a source position. Syntactic sugar is expanded when the IR is generated: the early return of `?`, the write-back of chained assignment (§3.6), the suspension points of await, the branches of match, and the suspension of setters before ready (§6.5). Bytecode corresponds almost one to one to the IR, with virtual registers allocated to slots in the stack frame. A field of a struct in a register is a register too, a view of the struct's bytes with no slot of its own, so that reading and writing a field needs neither a copy nor an instruction of its own; whatever reasons about registers, such as reusing slots or finding the slots a suspended coroutine keeps, takes a view as part of the register it views, and a write to it as a partial write of that register. A struct is constructed in a new register once all its fields are evaluated, so that no field read for it is overwritten first.
- Constant expressions (spec §4.5) are computed with each expression as types are checked: the compiler computes scalars and the structure of containers and keeps the parts of engine types as computations, written into the bytecode's table of constants, which the runtime computes once when the class loads (§2.2). The compiler computes as the virtual machine's instructions do, int arithmetic wrapping for one, since the virtual machine computes the same expression in a function body.
- The first version re-analyses the whole project each time, without incrementality. Each phase depends only on its own inputs, so caches can be added later as needed without changing interfaces.
- The syntax tree rests on a lossless token stream: lexing keeps the source text and gives each token's byte offset and length; lines and columns are computed from a table of line starts per file only when reporting, columns counting code points. The syntax tokens the parser reads form one list; comments, backslashes ending a line and invalid characters form another list of tokens (trivia), likewise ordered by offset; Newline, Indent and Dedent have length zero. Merged by offset, the two lists leave only whitespace between tokens and concatenate to the source, and blank lines follow from the offsets. Comments stay out of the syntax tokens so that the parser's lookahead need not skip them; whatever uses comments, formatting, `##` doc comments, telling whether the cursor is in a comment, finds them by offset. GDScript likewise keeps comments apart in a table by line, from which the parser takes doc comments by line (`modules/gdscript/gdscript_parser.cpp:4066-4106`). Each node of the syntax tree records the indices of its first and last syntax token, parentheses included; names and operators record their own token index beside their fields, since the reference table needs the position of every name and a node can have several names (`Combat.Damageable`, `Hit(damage = 3)`). A node the parser synthesizes, such as the if that an `elif` becomes, takes the range of the source it comes from. The token list, the trivia, the line table and the source text make up one source file object, which the syntax tree holds. A diagnostic is a byte range, and each check chooses what it covers: the whole expression, a name or an operator; Godot's interface takes only the line and column of its start (`core/object/script_language_extension.h:322-330`). The ranges that quick fixes edit and formatting likewise work in tokens. A lossless concrete syntax tree (the red-green trees of Roslyn and rust-analyzer) was not adopted: it means rewriting the parser and making the checker read through views, while most formatters build on an AST and tokens (gofmt, zig fmt, Ruff, dart_style), and Biome, which builds on such a tree, still takes comments out and reattaches them to nodes ([`biome_formatter/src/comments.rs`](https://github.com/biomejs/biome/blob/main/crates/biome_formatter/src/comments.rs)). GDScript's parser keeps only the tokens that matter to execution, so the formatter proposed to the engine lost the spelling of literals and parentheses ([godotengine/godot#76211](https://github.com/godotengine/godot/pull/76211)).
- The resolution of names is recorded in a reference table: wherever the checker resolves a name, it records an entry with the position, the identity of the declaration referred to and the role, either declaration or reference. In a `.pet` file the position is a byte range, not token indices, since method and property names in literals (spec §10.4) and the segments of `$"Head/Camera"` are only parts of a string token; in a scene it is the scene's path, a node path, a kind and a key, since scenes are read through SceneState and have no offsets. A declaration's identity consists of a kind, a scope and a name, compares by value and is stable across files: a member of this language is its class's path and its name, a struct field being written `Hit.damage`; a local or parameter is the file's path and the offset of its declaration; a scene node is the scene's path and the node's path; an engine member is the class name and its name; a member of a GDScript class has the same form as one of this language with a different kind. One place in the source can have several entries: when a script is attached in two scenes, `$Head/Camera` refers to the node of each. A name that cannot be resolved, such as a member through a Variant or a dynamic call, is recorded with an unresolved identity that has only the name. The declaration entry of a declaration that overrides or implements another carries the identity of the one it overrides; a rename follows these relations to every declaration involved, and go to definition still reaches the subclass's method; clangd's index (`RelationKind::OverriddenBy`) and clang's indexing library (`SymbolRole::RelationOverrideOf`) record this relation likewise. A table belongs to the check that produced it, that is, to one `.pet` file, and is replaced whole when the file is checked again; references in scenes, method names in signal connections, node paths and keys of exported properties, are written into the table of the script attached in the scene when that script is checked, and a change to the scene makes that script be checked again anyway; checking another script's declarations records nothing. Go to definition looks the table up by position, find references and rename by declaration; a rename checks every place against the current text when it runs and gives up if one does not match; unresolved same-named candidates, and same-named calls in GDScript, are only listed for confirmation (spec §13.3). Completion does not use the table; it takes the type and scope at the cursor. Evidence: clangd, Dart and Swift's IndexStore likewise record every reference when checking, clangd, sourcekit-lsp and gopls all check again against the current state when renaming, and IntelliJ lets non-code files take part in a rename through extension points, which is how JetBrains' Godot plugin treats `.tscn` files ([godot-support](https://github.com/JetBrains/godot-support/blob/master/gdscript/src/main/resources/META-INF/plugin.xml)). GDScript's language server has no such table: to find references it searches every script for the name as text and resolves each place again (`modules/gdscript/language_server/gdscript_workspace.cpp:434-500`), and finds no reference in literals or scenes.
- With syntax errors, diagnostics report only the syntax errors, as GDScript does (`modules/gdscript/gdscript_editor.cpp:150-153`); completion, hover and go to definition run the checker on the recovered syntax tree (the same file, `:3441-3442`). Completion inserts a placeholder identifier at the cursor before parsing, and checks only the member around the cursor. A compile with syntax errors runs the checker as well, discards its diagnostics and generates no IR, so that every feature's handling of the recovered syntax tree stays tested. Recovery works by line: an error discards only the rest of its line, what was parsed is kept, a missing expression or type is filled with an error node whose range is the discarded tokens, and the block after the line is parsed as usual and goes to the line's statement or function, or to an error statement when the line formed none. GDScript likewise parses the block of an `if` whose condition is in error (`modules/gdscript/gdscript_parser.cpp:2366-2373`). Line breaks inside brackets do not count, so an unclosed bracket swallows the line structure after it, and that is the most common state while typing. The lexer first finds the brackets the text never closes, then scans again and takes each as closed at the first line break after it that is followed by a line indented no deeper than the bracket's own and not beginning with a closing bracket, so that `set_process(true)` after `print("a",` at the same indentation is still the next statement; the rule applies only to unclosed brackets and leaves valid files alone. Lines indented deeper can still be read into the bracket, as the body under `func f(` is, so when the parser meets an error inside brackets the line ends at the next line break inside them: the lexer scans again taking it as a real one, and the parser parses again. Ruff's Python parser likewise re-lexes line breaks inside brackets (`re_lex_logical_token` in [`ruff_python_parser/src/lexer.rs`](https://github.com/astral-sh/ruff/blob/main/crates/ruff_python_parser/src/lexer.rs)), but decides by syntax alone, so a next line that can continue what is inside the brackets, such as `set_process(true)` above, is read as an argument. One cause gives one error, reported where the mistake is and in its own words: a bracket that is never closed is reported once at the bracket, and what the parser finds wrong before it is taken as closed is not; nor is anything on a line where the lexer reported an error; a missing comma is reported where it goes, and an extra closing bracket as unmatched. The reference is CPython 3.10's and rustc's messages, which both report an unclosed bracket at the bracket, CPython also suggesting a missing comma ([What's New In Python 3.10](https://docs.python.org/3/whatsnew/3.10.html)). The checker takes an error node as type Error and reports nothing further because of it. The formatter does not touch a file with syntax errors.
- Lints are checks in the checker, reading the typed syntax tree and reported as warnings, sharing diagnostics and `@warning_ignore` with the compiler's warnings (spec §13.2). Quick fixes and automatic fixes are text replacements on token ranges, each marked as applicable automatically or not; applied together, fixes with overlapping ranges are skipped, and the result is checked again.
- The formatter decides itself where comments belong; a comment where the indentation decreases goes to a block by its column. Its acceptance comes in two steps: with all rules removed it reproduces its input byte for byte; then three checks are added: the syntax tree is unchanged, formatting a second time changes nothing, and every comment is kept.

### 2.2 runtime

- Values: int and float take 8 bytes each; the engine's built-in value types are stored in place and copied and destroyed by the engine's rules; String, Array and Dictionary use the engine's types; Variant is one slot type; Option and enums with payloads have their own layouts with a discriminant; a struct holds its fields one after another, each in its own layout, so that a field is a slot inside the struct's, which the verifier finds from the type table rather than from the bytecode's list of slots. `==` of structs is one instruction, which compares the fields by the type table.
- A container whose elements are of a type only this language has (spec §3.8), or are such containers, is an engine container of Callables, each element in an immutable box: a custom Callable created with this library's token (`core/extension/gdextension_interface.cpp:1617-1631`), whose data is the element's type, from a registry by type key that outlives class images, and its value; boxes cannot be called. The engine compares Callables through the box's equal callback (`core/variant/callable.cpp:265-288`, `gdextension_interface.cpp:85-93`), which `has`, `find`, `count`, `erase`, container `==` and Dictionary lookups reach through `hash_compare` (`core/variant/variant.cpp:3351-3355`), so these, and the operations that only move elements, follow this language's semantics by construction. The operator table has no ordering of Callables (`core/variant/variant_op.cpp:731-791`), and a Callable's hash is computed once when it is created (`gdextension_interface.cpp:221-227`); so the box of an element has no hash callback and costs no hashing, while the box of a key, whose content is read-only (spec §3.8), hashes its content when created: values of engine types by the engine's hash, which takes all NaNs and both zeros as equal (`core/templates/hashfuncs.cpp:39-64`), objects by ObjectID, T? by tag and value, struct fields in order, containers by content. The runtime carries out the rest: `sort` through the engine's `sort_custom` with a comparator Callable applying this language's `<`, `bsearch` through `bsearch_custom`, `min`, `max` and `<` of containers with the same comparison, `hash` and `has_all` through the boxes, and the copies inside boxes after the engine's deep copies (`duplicate(true)`, `duplicate_deep`, a deep `slice`). After `resize`, code the compiler emits sets each new element to its default, since only the compiler knows the defaults of a struct's fields; so too for elements that are containers, which the engine would fill in untyped. Which methods change a container comes from the engine's API description; the runtime lists by name those that insert keys, hand them out, or that it finishes. Inserting a key stores a copy read-only at every level, and a key handed out whose type can hold a container is made read-only in place unless it already is; the virtual machine checks `is_read_only()` before every operation that changes a container, since the engine only reports an error there (`core/variant/array.cpp:518`) or writes into a scratch value without one (`array.cpp:104-108`). An instruction boxes a value; conversion from Variant unboxes a box of exactly the type; `Array(hits)` and `Dictionary(d)` encode as spec §10.1 says. The cost is a box per element; escape analysis may later give containers that do not escape a private representation.
- Objects: an object that is not RefCounted is stored as an ObjectID and a pointer and checked for liveness on access (spec §3.3); RefCounted is held by a strong reference; `weak` holds no reference (§3.12). The members of an instance of this language are held by the instance and by every call running on it: when the engine deletes the instance while one of its methods runs (`free()`, `set_script`), the members are only marked freed, using a member or self afterwards is a program error, and the members are destroyed when the last holder lets go.
- Each type has a type descriptor that provides copying, moving, destruction, and conversion to and from Variant (§10.1, §10.8). The compiler emits a slot type table for each stack frame; destruction, moving the frame of a suspending coroutine, and the debugger's display of locals all rely on it.
- The table of constants is computed once, when the class loads: constructors, operations, math functions and fields of engine types through the engine's interface; a scalar computed so is written back into the table, for the instructions that read scalars; containers are made read-only at every level, and every use of a constant reads the same container. A constant that loads a resource loads it only when read by name (spec §4.5).
- Compiled functions are immutable and versioned. Hot reload of a function body replaces the class's function table; running and suspended frames keep using the old version (§12.4).
- Coroutine frames live on the heap and form a tree by ownership, along which cancellation propagates (§9.3). Notice that an object has been freed comes from the runtime's own instance binding: an object can hold several instance bindings with different tokens at once (`core/object/object.cpp:2167-2201`), so the runtime's binding does not conflict with godot-cpp's; whether to report an error is decided in the script language's per-frame callback (§9.7).
- A program error unwinds this language's call stack, releasing locals, back to the engine's call entry, which returns the default value of its type (§8.1).
- Calls to methods of classes of this language do not go through the engine: the virtual machine finds the object's instance of this language, or for a static method the current image of the class's script, finds the method by name, checks that the method's signature is the one the caller recorded when it was compiled, and passes arguments and result in their slots' native layout (§8.1). The scripts of one run are always compiled together (§12.4); only bytecode that was not built together can make the signatures differ, and the call is then a program error. Calls to engine methods are to pass pointers to native values directly to ptrcall, and for now go by name (§2.6); calls coming from the engine pass the entry checks (§10.1).
- The virtual machine can run on any thread and uses no global mutable state that is not protected by a lock (§12.3).
- The runtime uses godot-cpp's types (Variant, String, Object and so on) directly, with no layer in between. They correspond to the engine's own types of the same names: for an engine-module build, the runtime would switch to the types of the engine's headers and the adapter would be rewritten (§2.3), while the compiler and the bytecode can be used as they are (§2.1).
- The first version dispatches with a switch only, so there is one code path to test on every platform. GDScript uses computed goto on GCC and Clang (`modules/gdscript/gdscript_vm.cpp:254-450`); this language's main advantage lies in registers typed by static type, not in dispatch. Each instruction's handler is written once and the interpreter's state is kept in a few local variables, so computed-goto or tail-call dispatch can later be generated from the same definitions; whether to add them is decided by the benchmarks in §4. Switch dispatch stays in any case, since not every toolchain guarantees tail calls, MSVC debug builds for one.
- Native code is generated as spec §12.2 says: one code generator with several backends, used for generation at run time and ahead of time, compiling a function at a time. When it is generated is not decided yet (§7). CPython's JIT is the cautionary tale: it compiles traces, generating code by copy-and-patch, and is only 4–12% faster than the interpreter in 3.15; its authors proposed a method-based frontend in [PEP 836](https://peps.python.org/pep-0836/), the Steering Council found the plan short on maintenance, on how performance would be evaluated and on working with debugging and profiling tools, the PEP was withdrawn on 2026-10-19, and the JIT is to be removed from CPython. So this language's code generation must from the start keep the debugger, the positions of program errors and profiling working with native code (by keeping the mapping to lines and slots, or by running interpreted when debugging), and fix its benchmarks and targets before it is built.

### 2.3 adapter

- It implements ScriptLanguageExtension, ScriptExtension and ScriptInstanceExtension, and forwards property reads and writes, method calls and notifications of instances to the runtime.
- Loading and saving of `.pet` sources and bytecode files.
- Export plugin: it replaces `.pet` with bytecode, creating the remap through `add_file(..., true)` as GDScript does for `.gdc` (`modules/gdscript/register_types.cpp:99-116`).
- Editor plugin: the analysis service (§13.1), error marks in the scene editor, renaming with the scene part and undo (§13.3), compiling before running.
- Headless command: runs the same analysis and exits with a non-zero code on compile errors (§13.1).

### 2.4 Editing, running, export and hot reload

- Editing: the analysis service holds the compiled state of the whole project in the editor process, recompiles when sources or scenes change, and shows diagnostics in the script editor and the scene editor.
- When the editor loads a script, it compiles only the declarations (class header, members, signatures): enough for the reflection of exported properties and methods, but not runnable. At that point the scenes that use the script cannot be loaded, since the engine refuses such a load on the same thread as cyclic (`core/io/resource_loader.cpp:1049-1056`). The full compilation, with function bodies and scene checks, happens outside of loading: checks while editing, saving, the build before running, and export. Compiling only the declarations reads no scenes, so a member typed from them (such as `@onready var camera = $Head/Camera`) is a Variant until the full compilation. Only tool scripts run this language's code in the editor; when they are supported, a full compilation follows the load.
- Running from the editor: the project is compiled before it runs (the editor plugin's `_build`) and the bytecode is written to `.godot/petrichor/`; the game process only reads it. Rationale: the types of `$X` and the like depend on scenes (spec §7), so a game process compiling by itself would analyse all of the project's scenes again, start more slowly, and might reach different results from the editor.
- The headless command writes bytecode to `.godot/petrichor/` as well; tests and CI use it in place of the editor.
- Export: the export plugin puts the bytecode in the exported package (§1).
- Bytecode carries no version number before the first release. A file carries an identifier of its format, a hash of `src/bytecode/` computed at build time, and is read only by builds with the same identifier; the editor library and the export templates built from the same sources therefore agree. The build before running recompiles every script; a script loaded with its source also checks that its bytecode was compiled from exactly that source, by a hash of it, and otherwise asks for a rebuild instead of running stale code.
- Hot reload: when a script is saved, the editor recompiles it and tells the game over the debugger connection, and the game reloads the script from `.godot/petrichor/`. When only function bodies changed, running instances switch to the new code; when declarations changed, the game keeps the code it has and applies no reload until it runs again (spec §12.4).

## 3. Testing

Tests come from three sources, the specification, the engine and real code, and are not derived from the implementation:

- **Specification conformance**: each row of §15 becomes tests. Compile-time checks go into the compiler's tests, which do not start the engine; run-time behavior goes into the engine tests.
- **Engine compatibility**: a Godot test project run in headless mode checks attaching, saving and reloading scripts, calls between GDScript and this language in both directions, and lifecycles: the owner freed during an await, the signal source freed, a signal emitted synchronously followed by another suspension, the same suspension point resumed twice, and GDScript calling this language, which then awaits an external signal.
- **Real code**: the FPS and Ring code of the [second paper migration](surveys/paper-migration-2.en.md) actually runs.

The compiler tests compile sources through one helper, which checks the conventions of §2.1 on each: the token stream is lossless; node ranges nest in order, and a name token's text is the name; the text of each reference in the source is the name of the declaration referred to, and every name the checker resolves has a reference. For a source without errors it also compiles it again with each line cut in the middle, requiring no crash, only syntax errors, and the statements of the other lines still in the syntax tree; when the cut leaves a bracket unclosed, the lines after it indented deeper than its own are exempt (§2.1). Every new feature's tests thus check these conventions too, without separate tests. The messages of syntax errors have cases of their own, typical mistakes made while typing, each with its position and wording (§2.1). The `.pet` files in `tests/engine` are real code, but the compiler tests have no real engine API, so for them only the token stream, the node ranges and the parse after cutting are checked.

Each engine test names the errors it expects, by their text and, for scripts, their place; any other error fails it. The imports the runners start are not checked, since Godot 4.7.2 can crash as an editor exits right after importing (Godot issue #111048).

## 4. Performance

Four groups of benchmarks compare against GDScript, measuring the virtual machine itself and the cost of crossing the engine boundary separately:

| Benchmark | Measures |
|---|---|
| Startup and compilation | cold start, repeated runs, re-running after a code change |
| Pure computation | integer and float loops, arrays, function calls, generics |
| Engine boundary | property reads and writes, engine method calls, Callable, signals |
| Allocation | enums with payloads, closures, coroutine suspension, object creation |

Comparisons use optimized builds, not `dev_build`. These data decide whether native code is generated and which paths to optimize.

So far `benchmarks/` holds six cases of pure computation, each with a GDScript twin computing the same result, which the runner compares. On the official 4.7.2 release, on one Windows machine (2026-10-29), in milliseconds:

| Case | GDScript | This language |
|---|---:|---:|
| int_loop | 34.1 | 21.8 |
| float_loop | 25.9 | 24.4 |
| calls | 78.2 | 18.1 |
| members | 30.2 | 22.0 |
| vectors | 33.9 | 29.5 |
| arrays | 40.9 | 80.0 |

## 5. Order of work

1. **Engine integration**, without the language: the extension loads in the 4.7.2 editor; a `.pet` script can be created and attached to a node, and still works after the scene is saved and reopened; hard-coded behavior responds to `_ready`; properties and methods appear in the inspector and can be called from GDScript; the export plugin replaces the file. Acceptance: a real scene runs in the editor and after export.
2. **Probes**: verify on a running engine the points of the specification that were derived only from source:
   - undo merging with `history_changed` and `MERGE_ALL` (spec §13.3);
   - cross-language await in both directions (§9.8);
   - GDScript's static checking of this language's classes: the types of `new` and of members (§11.3);
   - the runtime's own instance binding receives a callback when the object is freed, without affecting godot-cpp's binding (§9.7).
   If a probe fails, the question goes back to the specification.
3. **Minimal compilation chain**: a subset of the language with `extends Node`, typed members, functions, int and float arithmetic, if and while, calls to engine methods, and `_process`. Acceptance: the script runs attached in a scene, GDScript can call it, a breakpoint stops, and a change to a function body hot-reloads.
4. **First milestone**: the FPS code of the second paper migration actually runs. Features are added as needed, and the corresponding rows of §15 become tests at the same time. The engine tests copy the project and replace each migrated script; the scripts not yet migrated stay GDScript, and the migrated run may only report the errors that the original reports and keep at exit only the resources that the original keeps. Scripts are migrated in the order cloud, impact, hud, audio, weapon, then combat, enemy and player together, so that this language never calls into GDScript and the static view of GDScript classes (spec §11.1) is not needed for this milestone. The last three go together because the enemy recognizes the player by the interface Combat.Damageable, which only this language's classes can implement (spec §3.9): with enemy migrated alone, the enemies would no longer hurt the player, and the tests would not notice. Done: all eight scripts run migrated.
5. **Paying down debt**, before new features: the quick first implementation left behavior that differs from the specification, rules kept in several places, and tests and documents that say something untrue. They are worked through in the order correctness, verification, code, documents; all four groups are done.
6. **Second milestone**: the breakout of Ring in the second paper migration runs with its migrated scripts, as in step 4. Ring is mostly C#, and `Root.cs` starts breakout: it instances the breakout scene, hands BreakoutManager the init message in a Dictionary, and breakout calls its `EndGame()` when it ends (`breakout/Root.cs:77-96`). The engine tests need no .NET: `tests/engine/ring/ring_check.tscn` stands in for `Root.cs` and sends the message that Ring's `main.md` builds; to this language, C#'s `Call()` is the same as a dynamic call from GDScript, a call by name through the engine. Apart from the subclasses of Brick and Enemy, every migrated script uses GDScript classes, so the static view of GDScript classes (spec §11.1) comes first, then inheritance between classes of this language; other features are added as the scripts need them. Done: the fifteen migrated scripts all run in this language.
7. **The rest of the first version's language**: steps 4 and 6 showed on real code that the approach works and meets no trivial blocker, but they cover only the constructs those two projects use. This step implements the remaining language features of the specification's first version, and the corresponding rows of §15 become tests at the same time. It begins by giving the existing syntax and checks what §2.1 sets out: the lossless token stream, the token ranges of nodes, error nodes and the reference table; every feature after that follows the same conventions, and the tools of step 8 build on them. A feature that changes a hot path runs the benchmarks (§4) once and records the cost in its commit message, without optimizing for it: a runtime check written into the specification is a constraint later, and its cost should be known before it is settled. Acceptance: the constructs in the table of the [implementation coverage survey](surveys/implementation-coverage.en.md) are all supported, and the survey is run again.
8. **Tools**: the first-version tools of specification §13.2, renaming with its part in scenes (§13.3) included. They come after the language because, built alongside its features, they would be reworked as the implementation changes; once the language is settled, building them in one go is simpler. Renaming in large projects and teams follows §6.4. Acceptance: each tool that §13.2 lists.
9. **Performance**: the four groups of benchmarks of §4 against GDScript, then the optimizations the data call for, including whether to generate native code (§7). Last, because the constraints come before speed. Acceptance: clearly faster than GDScript (specification §1.1, §12.2).
10. **First public release**: CI builds the editor library and the libraries of the two kinds of export templates for the platforms of §6.3, and exported games run with the official export templates. When the library for the target platform is missing, the engine only warns at export (`editor/export/gdextension_export_plugin.h:161-165`) and fails at run time, so this language's export plugin reports an error at export, and also when a Web export has no extension support. The bytecode format gets a version number (§2.4, §6.1). Acceptance: with no C++ toolchain installed, a project exports to every platform and runs.
11. **After the first version**: mods (§6.1), exporting structs and enums with payloads (§6.2), and the rest of what spec §14.2 lists.

The work of each step not done yet is listed in `BACKLOG.md` at the root of the repository.

## 6. What must be possible later

The four things below come in step 8 or later, but without them real projects either cannot choose this language or get stuck halfway. This section shows that the current design allows them later, and the constraints the implementation must not break until then.

### 6.1 Mods

A game written in this language loads the pack of a mod at run time; the mod's classes extend, call and implement the game's classes and use its scenes; the mod's author does not have the game's sources.

- Loading: a mod's pack is loaded with `ProjectSettings.load_resource_pack` (`core/config/project_settings.cpp:581-585`). The export plugin replaces `.pet` with bytecode through a remap (§2.3), and the engine looks for a `.remap` file at every resource load (`core/io/resource_loader.cpp:1491-1519`), so the remaps of a pack loaded later apply too, and the mod's scripts reach the runtime the same way as the game's. Bytecode names classes of this language by script path (`src/bytecode/module.h:76-82`), with no global class name to register.
- Linking: scripts refer to each other by path and name, and the runtime checks the member layout and signature of the base class at load (`src/runtime/class_image.cpp:50-54, 101`), the signature of a method at a call (`src/runtime/vm.cpp:1102-1103`), and the class of a scene's node where it is used (`vm.cpp:800-813, 879-889`). So a mod compiled against another version of the game, or one that replaces a scene of the game, gets a load error or a program error and never reads the wrong memory. Mods of C# and Java rest on the same checked dynamic linking.
- Format: before the first release, bytecode is read only by builds with the same `src/bytecode/` (§2.4), so a mod must be compiled with the game's build; the first release gives the format a version number, after which the runtime reads mods compiled by compatible versions.
- Declarations: the compiler reads other scripts through ProjectApi's `script_source` (`src/compiler/project_api.h:91`) and checks only their declarations, not their function bodies (`src/compiler/script_classes.h:14-16`). So the game's scripts without their function bodies, shipped with its modding tools, give a mod full checks and completion; they can be generated from the token ranges of the nodes (§2.1). Scenes are read through SceneState, binary ones too (§2.1), so the scenes in the game's pack serve as they are.
- Trust: the verifier refuses damaged and outdated files but trusts the engine signatures recorded in the tables (`module.h:419-427`), so a crafted file can crash the game. A mod written in GDScript can already do anything a script can, so loading a mod is a decision of trust anyway; for untrusted bytecode to be unable to corrupt memory too, the runtime can check those signatures against the engine at load, or the game can use the runtime library with the compiler and compile the mod's sources itself (spec §14.2). Both add to what exists without changing it.
- To keep until then:
  - References between scripts stay by path and name, checked at load or at a call. Optimizations across scripts, such as finding a method once per call site (the performance part of the backlog), happen at load or at the first call, and never compile another script's indices or layout into the bytecode unchecked.
  - Generics (spec §3.10) are compiled so that a type of another module can instantiate a generic without the generic's source: the definition stays in its own module, for instance specialized by the type arguments at load, with native values still in the registers (§1); it is not monomorphized at the use from source. The spec already keeps type arguments at run time (§3.10).
  - The compiler reads other scripts only through its interfaces, which the build already enforces (`SConstruct:76-82`).

### 6.2 Exporting structs and enums with payloads

Members of structs and of enums with payloads can be `@export`ed, edited in the Inspector, and stored in scenes and `.tres` (spec §14.2).

- Storage: at the engine boundary both are encoded as a Dictionary by field name, an enum with payloads also recording its variant's name under the reserved key `"$variant"` (spec §10.1), which scenes and resources store as they store any Dictionary. Saving a scene, the engine takes the properties with STORAGE from the property list and reads them with `get` (`scene/resources/packed_scene.cpp:861-883`); instantiating it, the engine sets them by name (`:494`), the script instance first (`core/object/object.cpp:239-246`), that is through the entry check that decodes them (spec §10.1). Both ways exist, with no change to the engine.
- Editing: the Inspector edits a Dictionary property with its generic dictionary editor (`editor/inspector/editor_properties.cpp:4280-4287`), which already works, only not by type. Panels by type, a struct's fields and a drop-down of an enum's variants, come from an EditorInspectorPlugin that this extension's editor plugin registers (`editor/inspector/editor_inspector.h:356, 360`, `editor/plugins/editor_plugin.cpp:674`), the property's hint string naming the type.
- Rules to settle when it is added: decoding old data that lacks a field added since is now a program error (spec §3.6); stored data should take the field's default, a relaxation and so compatible. Renaming a field rewrites the nested keys in scenes, which needs the scene index to read the values of properties, the same work as renaming exported members in step 8 (the editor part of the backlog).
- To keep until then: once values can be exported, the encoding of §10.1 is a storage format. It encodes by field and variant name, not by position, so adding fields or reordering them leaves old data readable; enums with payloads are implemented in this encoding, and after the first release it does not change in a way that loses old data.

### 6.3 Prebuilt libraries for every platform

Users export to Windows, Linux, macOS, Android, iOS and Web without a C++ toolchain, and later Godot 4.x versions keep working.

- Distribution: the `.gdextension` file lists a library for each platform and architecture by feature tags (`core/extension/gdextension_library_loader.cpp:82-96`), and the export plugin puts the one that matches the export into it (`editor/export/gdextension_export_plugin.h:107-117`). iOS takes a `.dylib`, a `.framework`, an `.xcframework` or a static library, whose registration code the export plugin generates (`:119-137`, `editor/export/editor_export_platform_apple_embedded.cpp:1233-1325`); Android puts the library in `lib/<abi>/` (`platform/android/export/export_plugin.cpp:800-822`); Web needs the export templates with extension support (`platform/web/export/export_plugin.cpp:362-374`, spec §1.3). So a release is a library built for each platform, and godot-cpp has build scripts for all of them (`thirdparty/godot-cpp/tools/`).
- Code: the compiler and the bytecode are plain C++17 (§2.1), the runtime and the adapter use only godot-cpp, `src/` has no conditional compilation by platform, and SConstruct leaves platforms to godot-cpp (`SConstruct:14`). The interpreter generates no machine code (§2.2), so it runs on iOS and consoles, which forbid generating code at run time (spec §12.2).
- Consoles: whether an extension loads on a console is up to the porter. The fallback is building this language as an engine module, which the engine compiles into the export templates of every platform (Godot's `SConstruct:1237`, `modules/SCsub:32-42`); C++17, SCons and a runtime that uses the types named as the engine's were chosen to keep this way open (§1, §2.2).
- Engine versions: the extension declares 4.7 as its minimum, and later versions load the same build (`gdextension_library_loader.cpp:315-329`, §1). What a new version can change is the engine behavior and API that the spec relies on: the former is recorded with line numbers in Appendix A of the spec and re-verified item by item when moving to a new engine commit; the latter shows when the runtime finds methods by name and hash (`src/bytecode/module.h:425-426`), and never makes it call a wrong method silently.
- To keep until then: platform-specific code only through godot-cpp; no correctness that depends on generating machine code; no compiler in the library for exports (`SConstruct:84-89`).

### 6.4 Renaming in large projects and teams

In a project of a thousand scripts and hundreds of scenes that several people change on branches, renaming a member, a method or a node must respond quickly, and should not force anyone to rewrite at once the scenes others are editing.

- Why scenes are rewritten: a scene stores the values of exported properties and the methods of signal connections by name, and instantiating it sets the properties by name (`scene/resources/packed_scene.cpp:494`) and connects by name (`:666, 682`); when a name no longer exists, nobody reads the failed result and the value is dropped silently. So a rename rewrites these keys (spec §13.3). The rewrite is a text replacement on token ranges (§2.1) that touches only the lines using the name, so it conflicts only when someone else changed the same line.
- Without rewriting scenes: the engine gives a property set to the script instance first (`core/object/object.cpp:239-246`), and a call of a connected method by name too (`:800-816`). Both go through this language's instance, so the runtime can accept the name a member had before a rename, declared for instance with the member; a scene is written with the new name the next time it is saved, so scenes migrate when someone edits them anyway, the reference table lists those still using the old name (§2.1), and the old name goes once they all have migrated. In the editor, placeholder instances are now the engine's (`src/adapter/pet_script.cpp:627-628`), which fail for names outside their list (`core/object/script_language.cpp:680-707`); accepting old names takes this language's own placeholder, which the extension interface allows (`core/object/script_language_extension.h:65-70`, `core/extension/gdextension_interface.json:8254-8257`). Declaring old names is a language rule, to be proposed when step 8 does renames.
- Response: checking a script depends only on its source, the declarations of the other scripts it uses (without function bodies, `src/compiler/script_classes.h:14-16`), the scenes that attach it, and for `@owner` the scenes that instance a scene whose root has it (`src/compiler/checker.cpp:5256`). Changing only a function body leaves the declarations as they were, which hot reload already compares (`src/runtime/class_image.cpp:584`), so the scripts that depend on it need no new check; each stage depends only on its inputs (§2.1), so a cache keyed by them changes no interface. Building Ring's 15 scripts now takes 4.6 s, and compiling each script compiles its bases again and lists the scenes again (the editor part of the backlog); keeping what one build has read removes that part.
- To keep until then: checks depend only on the inputs their interfaces give, with no state outside them; the reference table is per file (§2.1).
