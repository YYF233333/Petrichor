# 调查：引擎按名字访问的成员

**2026-11-08** · 关联：[语言规范](../language-spec.zh.md) §4.2、§7.7、§10.4、§10.5；[成员使用调查](member-visibility.md)（语料相同）

## 问题

Godot 在许多地方按名字查找成员，本语言要在其上建立静态引用。本文为两个问题提供数据：

- 按名字访问有哪些途径，各有多少，编译期能否知道名字所指；
- 不带 `pub` 的成员若对一切按名查找都不可见，有多少成员要为此改成 `pub`，能否机械地找出。

## 语料

与[成员使用调查](member-visibility.md)相同：20 个仓库，固定提交，第一方规则也相同。第一方代码 203,720 行，其中 12 个游戏仓库 70,646 行。引擎 API 取自 godot-cpp 随附的 `extension_api-4-7.json`（Godot 4.7.2，`ed1daf0`）。

## 方法

- **途径**分为四类：
  - 代码：字面量写在命名成员的参数上，如 `call_deferred("m")`、`tween_property(obj, "p", ...)`。参数位置整理自引擎 API 中名为 `method`、`property`、`signal` 的参数（`names.py` 中的 `POSITIONS`）。按方法名匹配，不做类型解析；
  - 场景和资源：`.tscn` 的信号连接、动画的属性轨道和方法轨道、`SceneReplicationConfig` 的同步属性、AnimationTree 转换的表达式；
  - 声明：`@export` 变量和 `@rpc` 函数，引擎也按名字访问它们；
  - 项目中的事物：输入动作、组、动画名、着色器参数、主题项和元数据，由引擎 API 的参数名找出。
- **目标**：调用没有接收者，或接收者（或对象实参）是 `self` 时，目标是本脚本。
- **名字的归类**，依次为：
  - 含 `/` 的为“动态”，引擎按实例列出这类属性；
  - 目标是本脚本时，本脚本或第一方祖先声明的为“脚本”，其引擎基类的成员为“引擎”；
  - 其他目标：是某个引擎类的成员名为“引擎”。在仓库中只有一个根声明的为“脚本”，有几个的为“多义”；
  - 其余为“未知”。
- **外部使用**：与成员使用调查相同，即 `.名字` 出现在声明脚本及其子孙以外的第一方脚本中。这里不要求名字唯一。
- 被按名访问、又没有外部使用的脚本成员，在严格可见性下只为引擎才需要 `pub`。

## 结果

### 途径

| 途径 | 全部 | 游戏 | 全部中指向脚本成员的 |
|---|---|---|---|
| 场景信号连接 | 2,211 | 518 | 2,154 |
| `@export` 变量 | 2,276 | 1,270 | 2,276 |
| `@rpc` 函数 | 124 | 104 | 124 |
| 动画属性轨道 | 996 | 478 | 1 |
| 动画方法轨道的键 | 41 | 24 | 18 |
| 同步属性 | 26 | 22 | 9 |
| 代码，目标为本脚本 | 109 | 61 | 57 |
| 代码，目标为其他对象，`get`/`set` 除外 | 613 | 223 | 111 |
| 代码，`get`/`set` 用在其他接收者上 | 1,910 | 1,527 | 259 |
| 代码，无单一目标（`call_group`、`propagate_call` 等） | 41 | 2 | 1 |
| 项目中的事物 | 2,780 | 1,544 | — |

- 动画属性轨道几乎都指向引擎属性：996 条中 939 条，带 `/` 的 53 条，脚本变量只有 1 条。
- 代码中目标为本脚本的名字很少，全部仓库 109 处，每千行 0.5 处。
- 其他接收者上的 `get`/`set` 多是 `Dictionary.get`，其中 849 处的名字不是任何成员。
- 项目中的事物：
  - 主题项 895 处，输入动作 863 处；
  - 动画名 432 处，组 307 处；
  - 元数据 200 处，着色器参数 83 处；
  - 字面量节点路径另有 2,023 处（[场景结构调查](scene-structures.md)）。
- AnimationTree 转换的表达式没有出现。

### 严格可见性下要补的 `pub`

| | 全部 | 游戏 |
|---|---|---|
| 被按名访问、无外部使用的脚本成员 | 3,258 | 1,003 |
| 每千行 | 16.0 | 14.2 |
| 其中场景信号连接的处理函数 | 1,869 | 355 |
| 处理函数中名字以 `_` 开头的 | 1,823 | 351 |
| 其中 `@export` 变量 | 1,236 | 547 |
| 其中 `@rpc` 函数 | 70 | 58 |
| 其中代码中目标为本脚本的名字 | 28 | 18 |
| 其中动画方法轨道的键 | 18 | 13 |
| 其中同步属性 | 3 | 3 |

- 一个成员可以经几种途径访问，所以各项之和略大于总数。其余途径共 51 个，多数是 `get`/`set` 的多义匹配。
- 成员使用调查中，必须写的 `pub` 每千行至少 22.6 个，游戏 30.1 个。严格可见性每千行再加 16.0 个，游戏 14.2 个。
- 处理函数占新增的 57%。其中 98% 以 `_` 开头，作者按 GDScript 惯例把它们当作私有。

### 能否机械地找出

严格可见性下，要补的 `pub` 几乎都能由编译器从它已读取的来源中找出：

- 场景中的信号连接，编译器已经检查（规范 §7.7）；
- `@export` 和 `@rpc` 就是声明本身；
- 代码中的字面量名字，按规范 §10.4 静态解析后即可得到；
- 动画轨道和同步属性在场景和资源中，规范 §7.7 要求解析它们。

找不出的只有两处：无单一目标的位置，全部仓库中只指向 1 个脚本成员；以及其他语言的代码。

### 编辑器和引擎

- 动画编辑器选属性时，只列出 `get_property_list` 中用途含 EDITOR 或 SCRIPT_VARIABLE 的（`editor/inspector/property_selector.cpp:73, 117`）。
- 选方法时只列脚本的方法表（`editor/inspector/property_selector.cpp:176`）。所以不对引擎列出的成员，编辑器无从选择。
- 按名字找不到时，引擎的反应不一。`tween_property` 报错（`scene/animation/tween.cpp:108`），`set_deferred` 则什么也不做（`core/object/message_queue.cpp:277`）。
- C# 的实例字段和属性，以及签名合乎要求的方法，不论访问修饰符都对按名查找可见（`modules/mono/editor/Godot.NET.Sdk/Godot.SourceGenerators/ScriptPropertiesGenerator.cs:117-124`、`ScriptMethodsGenerator.cs:128-133`）。它另为每个类生成 `PropertyName`、`MethodName`、`SignalName` 常量代替字符串。
- 以上引擎源码均在 `ed1daf0`。

## 局限

- 不做类型解析。参数位置按方法名匹配，`get`、`set` 和 `call` 会混入字典和函数值上的调用。
- 外部使用不要求名字唯一，别处的同名成员也算。所以“无外部使用”的数字是下限。
- 动画轨道、同步属性和其他对象上的名字，没有解析到目标节点，只按名字归类。
- 只统计顶层成员，内部类中的写法按外层类解析。

## 对设计的影响

- 按名访问的脚本成员大多来自场景连接、`@export` 和 `@rpc`，编译器都已读取。代码中的字面量名字是少数。
- 现行设计把编译器收集的成员暴露给按名反射（规范 §10.5）。暴露后，任何调用方都能按名字访问它。例如 GDScript 可以 `call("_on_x")` 或 `set("speed", v)`。
- 严格可见性下，每千行多写约 16 个 `pub`，几乎都能由编译器机械地找出。
