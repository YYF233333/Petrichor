# Petrichor Language Specification

**v0.2 draft · 2026-10-25** · 中文: [language-spec.zh.md](language-spec.zh.md)

Petrichor is a statically typed scripting language for medium-to-large Godot 4 projects, replacing GDScript in project code while coexisting with GDScript plugins, delivered as a GDExtension. This document is a draft of its specification, published for comments; the implementation follows the [implementation architecture](architecture.en.md) and does not cover every rule yet. The previous version, v0.1, is kept at git tag `spec-v0.1`.

## 1. Overview

### 1.1 Problem and goals

- Large Godot projects written in a dynamic language are hard to manage. GDScript is bound by historical compatibility and cannot leave dynamic typing behind; and even when every script is statically typed, node paths, signals connected in the editor, animation tracks and resource property names stay dynamic, because the static information in scenes never reaches the scripts. Switching to C# makes language support second-class; the cross-language bridge has pitfalls, some engine capabilities are restricted, and the toolchain's integration with Godot has pitfalls of its own.
- This language is fully statically typed; dynamic values appear only where the engine or third parties impose them (§3.13). Static checking extends to scenes: node paths, signals connected in scenes, animation tracks, exported properties and scene resources are typed, and renames change the scenes too (§7, §13).
- The target users are developers who read and modify code, on projects of medium size and up, where part of the code may be generated by AI. Small projects are better served by GDScript.
- New projects are the main use. Third-party plugins stay in GDScript and need not be migrated (§11).
- Performance should be clearly better than GDScript's; C# is not the target (§12.2).

### 1.2 Relationship to GDScript

- The surface syntax follows GDScript: indentation, `func`, `var`, `extends`, `signal`, `@export`, `$X` and so on. New constructs extend it in the same style (§2).
- **Syntax hard rule**: a construct spelled as in GDScript either behaves as in GDScript or is a compile error with a suggested fix; it never behaves differently in silence. The exception is where GDScript fails at runtime or silently yields a wrong result (a default value, a truncation, waiting forever): there this language raises a program error (§8.1), or produces what the code intended, as setters before ready do (§6.5). Every rule in this document that differs from GDScript satisfies this; where a rule says "as in GDScript", it means the agreement this rule requires.
- This language does not promise to compile GDScript source directly. Migration is guided by compile errors and quick fixes (§13.4).

### 1.3 Delivery

- It is delivered as a GDExtension implementing Godot's script language extension interface (`core/object/script_language_extension.h:304, 391, 441, 497, 655`). The compiler and the bytecode do not depend on the engine, and the runtime uses godot-cpp, whose types correspond to the engine's own, so an engine-module build remains possible later.
- A GDExtension can be installed in the official editor and uses the official export templates. The cost is that Web exports need "Extensions Support" enabled, which uses the dynamically linked export templates (`platform/web/export/export_plugin.cpp:374`, `platform/web/export/export_plugin.h:59-73`); cross-origin isolation headers are needed only when thread support is also enabled (`platform/web/doc_classes/EditorExportPlatformWeb.xml:93-95`).
- Rationale: the [pitfall catalog](surveys/pitfalls.en.md) contains no entry that only a module could fix; what a GDExtension cannot fix needs changes to the engine, which a module cannot make either.
- Source is compiled only in the editor and in headless mode. Exported games contain only bytecode, and the library used by the export templates contains no compiler. Rationale: the types of `$X`, `@parent` and `PackedScene[T]` depend on scenes (§7), so compiling at load time would mean analysing scenes again inside the game and shipping the analyzer to every export platform. GDScript goes no further than tokenizing at export, and parses and compiles at load time (`modules/gdscript/register_types.cpp:99-116`, `modules/gdscript/gdscript_cache.cpp:373-379, 392`).

### 1.4 Conventions

- Rules that define legal programs and required behavior are normative. Rationale, evidence, examples, §15 and Appendix B are not.
- "Evidence" points to the surveys in `surveys/`, each with scripts that reproduce it: [scene structures](surveys/scene-structures.en.md), [cross-branch duplication](surveys/cross-branch-duplication.en.md), [pitfall catalog](surveys/pitfalls.en.md), [property accessors](surveys/property-accessors.en.md), [await signal results](surveys/await-signal-results.en.md), [member visibility](surveys/member-visibility.en.md), [paper migration](surveys/paper-migration.en.md) (a migration under v0.1), [second paper migration](surveys/paper-migration-2.en.md) (two real projects rewritten in this language on paper), [corpus counts](surveys/corpus-counts.en.md).
- Status markers:
  - **[Open]**: not yet decided; listed in §14.3;
  - **[Known limitation]**: not supported in the first version; rules that restrict which programs are legal remain normative;
  - **[Later]**: can be added compatibly later and is not part of the first version.
- A **compile error** is an error the analysis service reports before running, making the program illegal. The only exception is a missing value marked on a scene, which does not block running in the editor (§7.5). **Warnings** and **hints** do not affect legality. A **program error** is the runtime error defined in §8.1.
- Engine behavior cited here was checked against Godot 4.7.2-stable (commit `ed1daf0`), with sources listed in Appendix A. This is the verification baseline, not a statement of supported versions.
- Petrichor is a working name. The source file extension is provisionally `.pet`, and will be fixed together with the final name before the language's first release, because changing it afterwards would change every path in scenes that points to a script. The extension must be short and lowercase, must not clash with extensions Godot already uses (such as `.gd` and `.tscn`), nor with another language in GitHub Linguist or common editors. A script language reports its extension through `get_extension` (`core/object/script_language_extension.h:236`).

## 2. Lexical structure and surface syntax

### 2.1 Files and classes

- A source file is a class, as in GDScript. A file may declare a global class name with `class_name Name`; files without `class_name` are referred to through `preload`. Global names come only from `class_name` (§4.1).
- The class header may contain, in order: class-level annotations, `class_name`, `extends`, `implements`. `extends` and `implements` may be on the same line as `class_name` or on lines of their own:

  ```gdscript
  class_name Player extends CharacterBody3D implements Combat.Damageable
  ```

- A file may declare inner classes (`class Name:`), structs, enums and interfaces, all of which belong to the file's class (§2.4).

### 2.2 Lexical structure

- Indentation, comments, identifiers, literals and operators are as in GDScript, with these changes:
  - New keywords: `pub`, `struct`, `interface`, `implements`, `async`, `None`.
  - A new postfix operator `?` (§8.2). In GDScript `?` is a syntax error (`modules/gdscript/gdscript_parser.cpp:3860-3861`).
  - Prefix `!` remains logical not (`gdscript_parser.cpp:2963-2965`).
  - `null` is an alias of None, with GDScript's meaning everywhere: `x = null` gives a `T?` the empty value, `x != null` is the same as `x != None` and narrows, and passed as a Variant the engine receives NIL. Assigning it to a non-null `T` is a compile error, and the quick fix changes the type to `T?`. A hint suggests writing None in new code. Rationale: `null` occurs 22.2 times per 1,000 lines in the [corpus counts](surveys/corpus-counts.en.md), and making it a compile error would only add mechanical migration work.
- Literals: integers, floats, strings (including triple quotes and the `r` prefix), `&"…"` (StringName), `^"…"` (NodePath), arrays `[…]`, dictionaries `{k: v}` and `{k = v}`, `true`, `false` and `None`, as in GDScript; `None` is the empty value of Option (§3.4). The types of literals are in §3.2 and §10.7.

### 2.3 Annotations

- GDScript's annotations are kept with their meaning: the `@export` family, `@onready`, `@tool`, `@icon`, `@warning_ignore`, `@rpc`, `@static_unload`, `@abstract` (§4.1).
- New class-level annotations: `@parent(T)` and `@owner(T)` (§7.3).
- New member annotation: `@readonly`, only for interface properties (§3.9).
- Annotations precede the declaration and may share its line; `pub` comes after annotations and before `static` (§2.4).

### 2.4 Declaration spellings

- **Structs**: `struct Name:` followed by fields declared with `var`, which may have default values. Construction takes arguments by name only, and fields with defaults may be omitted:

  ```gdscript
  struct Hit:
      var damage: int
      var point: Vector3
      var crit: bool = false

  var h = Hit(damage = 3, point = p)
  ```

- **Enums**: GDScript's brace form, where variants may carry named payload fields. Enums without payloads are as in GDScript. A variant with a payload is constructed with arguments by name:

  ```gdscript
  enum Command { IDLE, MOVE(target: Vector3), ATTACK(target: Node3D, power: int) }

  var c = Command.MOVE(target = Vector3.ZERO)
  ```

- **Interfaces**: an indented block that can declare `var`, `signal` and `func`. A method without a body has no colon, as with GDScript's `@abstract func` (`gdscript_parser.cpp:1773-1774`); a method with a body is a default method. A property is required to be readable and writable; one required only to be readable is marked `@readonly`, as in `@readonly var max_hp: int`. All members of an interface are public:

  ```gdscript
  pub interface Damageable:
      var hp: int
      signal died
      func take_damage(amount: int)
      func is_dead() -> bool:
          return hp <= 0
  ```

- **Implementing interfaces**: the class header writes `implements A, B` (§2.1); they are not folded into `extends`, so the base class and the interfaces are told apart at a glance. An interface extending interfaces is written `interface Combatant extends Damageable, Healable:` (§3.9).
- **pub**: a keyword written after annotations and before `static`, for example `@export pub var max_hp: int`, `pub static func make() -> Player`, `pub signal died`. Structs, enums, interfaces and inner classes are made public with `pub` too, as in `pub interface Damageable:` (§4.2). It is a keyword rather than an annotation because it is written often: at least 22 times per 1,000 lines in the [member visibility survey](surveys/member-visibility.en.md).
- **Placement and naming**: structs, enums, interfaces and inner classes belong to the class of the file that declares them. In that file they are written by name; in other files as `ClassName.Name`, for example `Combat.Hit` or `Player.Command.MOVE(target = p)`. Types shared by several classes go into a class that exists to hold them. [Later] Aliases or `import`.
- **Generics**: type parameters are written in square brackets after the name, consistent with `Array[int]` and as in Python 3.12 (PEP 695); a constraint is written `T: Interface` (§3.10). A file's class declares its type parameters on `class_name`, for example `class_name Cache[K, V] extends RefCounted`; an inner class is written `class Cache[K, V] extends RefCounted:`.

  ```gdscript
  func first[T](items: Array[T]) -> T?:
      return None if items.is_empty() else items[0]

  struct Pair[A, B]:
      var first: A
      var second: B

  enum Tree[T] { LEAF, NODE(value: T, children: Array[Tree[T]]) }

  func weakest[T: Damageable](units: Array[T]) -> T?:
      var best: T? = None
      for u in units:
          if best == None or u.hp < best.hp:
              best = u
      return best
  ```

  At call sites type arguments are usually inferred from the arguments, and are written out when they cannot be, for example `first[int]([])` or `Pair[int, String](first = 1, second = "a")`. `name[...]` looks like a subscript and is told apart by name resolution: when the name is a generic function or a generic type, the brackets hold type arguments; otherwise they are a subscript. In GDScript `[` after an inner class name, the name in `class_name`, an enum name or a function name is a syntax error (`gdscript_parser.cpp:964, 1005-1010, 1602, 1805`), so these declarations do not break the syntax hard rule.
- **Function types** keep the shape of a function declaration without the function and parameter names (§3.11). A GDScript type can only start with an identifier or `void` (`gdscript_parser.cpp:3874-3886`), so `func(...)` as a type is a syntax error.

  ```gdscript
  var on_hit: func(int, Node3D)                 # no return value; -> void may also be written
  var score: func(Enemy) -> float
  var load_level: async func(String) -> Level   # calling it yields Task[Level]
  var filter: (func(Enemy) -> bool)?            # nullable needs parentheses; otherwise ? belongs to the return type
  ```

### 2.5 Statements

- `var`, `const`, `if`/`elif`/`else`, `while`, `for`, `match`, `break`, `continue`, `pass` and `return` are as in GDScript; their rules are in §5.
- `assert(condition, message)` is as in GDScript and is removed in release builds (§8.3).
- There is no form that uses an if/else block as a value; the only conditional expression is `a if c else b` (§5.5).

## 3. Types

### 3.1 Overview

| Category | Types |
|---|---|
| Numbers and booleans | `int` (64-bit), `float` (64-bit), `bool` |
| Strings | `String`, `StringName`, `NodePath` |
| Core value types | `Vector2`, `Vector2i`, `Vector3`, `Vector3i`, `Vector4`, `Vector4i`, `Color`, `Rect2`, `Rect2i`, `Transform2D`, `Transform3D`, `Basis`, `Quaternion`, `Plane`, `AABB`, `Projection`, `RID`, and the `Packed*Array` types |
| Containers | `Array[T]`, `Dictionary[K, V]` (§3.8) |
| Objects | engine classes, classes of this language, global classes of GDScript and C#; non-null `T` and nullable `T?` (§3.3); scene resources `PackedScene[T]` (§7.4) |
| Value types of this language | structs (§3.6), enums (§3.7) |
| Interfaces | §3.9 |
| Standard types | `T?` (Option, §3.4), `Result[T, E]` (§3.5), `Task[T]` and `Settled[T]` (§9), `weak[T]` (§3.12), `ConversionError` (§5.3) |
| Functions | function types (§3.11), `Callable`, `Signal` |
| Dynamic | `Variant` (§3.13) |

### 3.2 Numbers

- The only numeric types are `int` and `float`, both 64-bit, matching Variant (`core/variant/variant.h:252-253`). There are no narrow types for users; fixed-width arithmetic uses wrapping methods and bit operations on `int`.
- Integer literals have type `int`, floating-point literals type `float`.
- An `int` converts implicitly to `float` in assignments, arguments and returns. Converting a `float` to an `int` requires `int(x)` and is otherwise a compile error. Rationale: `var hp = 10` is inferred as int in this language (§4.3) but is untyped in GDScript, where `hp = 2.5` leaves 2.5; implicit truncation would make the result silently differ.
- The result types of operators follow §5.1.
- Numeric boundaries with the engine follow §10.6.

### 3.3 Objects and nullability

- A value of object type `T` always refers to an object; a value of `T?` is an object or None.
- After an object is freed:
  - reading a reference of type `T?` that refers to it yields None, so a `!= None` check, and the narrowing it brings (§5.4), is also a liveness check;
  - a reference of type `T` may still hold the freed object; reading, comparing and passing it do not count as access, and accessing its members is a program error; `==` compares ObjectIDs, so two different freed objects are not equal (§5.2). In debug builds, if the object is an instance of this language or was freed by code of this language, the diagnostic says where it was freed;
  - the exception is where the engine uses the object without checking that it is alive: passing the freed object to an engine parameter declared with an object type, writing it to an engine property of an object type, or giving it to an `Array[T]` whose elements are objects (as in `append`, `erase`, `has`) is a program error. The engine takes the pointer out of the Variant and uses it (`core/variant/variant.cpp:2024-2026`, `core/variant/binder_common.h:58-61`), and a typed Array asks ObjectDB first only in debug builds (`core/variant/container_type_validate.h:89-112`). GDScript hands the object over as it is (`modules/gdscript/gdscript_vm.cpp:2046-2055, 2072`), and the engine may then use another object that took over the same memory. Other parameters declared as Variant are unaffected; `is_instance_valid`, for one, checks liveness first (`core/variant/variant_utility.cpp:1133-1137`);
  - `is` is false for a freed object and `as` yields None, whatever the static type, so a type test is also a liveness test. GDScript fails at runtime here (`modules/gdscript/gdscript_vm.cpp:942-947, 1665-1669`);
  - when the object is freed, or loses its script of this language, while one of its methods runs, the method goes on until it uses a member or self, which is a program error. GDScript reads and writes the freed members here (`modules/gdscript/gdscript_vm.cpp:751`, `modules/gdscript/gdscript.cpp:2066-2084`);
  - after `queue_free()` and until the object is actually deleted at the end of the frame, it still counts as alive: the engine puts it in the deletion queue, which is flushed at the end of each physics step and each process frame (`scene/main/node.cpp:3461-3471`, `scene/main/scene_tree.cpp:666, 735, 1626-1643`). `is_instance_valid` behaves as in GDScript.
- Every read of an object reference of type `T?` performs a liveness query.
- Rationale: in the [corpus counts](surveys/corpus-counts.en.md), `is_instance_valid` appears 3.3 times per 1,000 lines, and 12.8 times per 1,000 lines in phantom-camera; since 4.4 the engine also treats freed objects as false in conditions (PR [#93885](https://github.com/godotengine/godot/pull/93885), `core/variant/variant.cpp:952-953`). Evidence: [pitfall catalog](surveys/pitfalls.en.md) G-07, G-08.

### 3.4 Option

- `T?` is Option: `Some(v)`, where v is a value of T, or None. A value of T is wrapped into a Some implicitly; where it must be written out, use `Some(v)`, for example `Some(None)` in a `T??`. When S is a subtype of T or implements the interface T, `S?` can be used where `T?` is expected.
- Option is a value, and operations on it are methods with the same names as in Rust: `unwrap` and `expect(message)` (both a program error on failure), `unwrap_or`, `unwrap_or_else`, `map`, `and_then`, `or`, `or_else`, `filter`, `ok_or`, `ok_or_else`. There are no `!`, `??` or `?.` operators.
- The only special syntax is postfix `?`: on None the current function returns None (§8.2).
- Null tests use `!= None` and narrowing (§5.4); there is no truthiness.
- Nested Options keep two levels, as in Rust. `T??` is a valid type, mostly produced by generics and containers (§3.8):
  - implicit wrapping adds levels according to the target type: a `T?` value assigned to a `T??` gives a Some containing that value, and the literal None is always the outermost None;
  - `?`, `unwrap`, match and narrowing each remove one level; `.flatten()` merges `T??` into `T?`;
  - `Variant?` works the same way: None means no value, and NIL is a value (§3.13);
  - the rule for handing them to the engine is in §10.1.

  ```gdscript
  var r = enemies.pop_back()   # enemies: Array[Enemy?], r: Enemy??
  match r:
      None: print("empty array")
      var e: print(e)          # e: Enemy?, possibly None
  ```

  Rationale: with one merged level, generic code would behave differently depending on T; for example, `first[T]` with T = `Enemy?` could not tell an empty array from a first element that is None, and a generic cache would take a stored None for a missing entry; a missing JSON key could not be told from null either. This language has no `?.`, so nesting appears almost only in generics and when reading from containers.

### 3.5 Result

- `Result[T, E]` expresses an operation that may fail in an expected way. It is constructed with `Ok(v)` and `Err(e)`; success values are not wrapped implicitly.
- Operations are methods with the same names as in Rust: `unwrap`, `expect`, `unwrap_or`, `unwrap_or_else`, `map`, `map_err`, `and_then`, `or_else`, `ok`, `err`.
- Postfix `?` makes the current function return `Err(e)` on `Err(e)` (§8.2).
- Discarding a Result is a compile error; to deliberately ignore one, write `.ok()`.

### 3.6 Structs

- Structs have value semantics: assignment, argument passing and return copy them. They exist only inside this language.
- Construction takes arguments by name only, and fields with defaults may be omitted (§2.4). [Later] Positional arguments.
- When crossing the engine boundary (signal arguments, Variant, cross-language messages), a struct is encoded automatically as a Dictionary keyed by field name, with String keys so that the encoding survives a JSON round trip; decoding checks the presence and type of every field and descends into containers and nested structs, as in `Dictionary[String, ConsumableState]`. Fields are decoded by the same rules as `T.try_from` (§5.3). Keys that are not fields are ignored, so that a message from a newer sender that carries more fields, or JSON written for several readers, still decodes as long as every field the struct needs is there.
- [Known limitation] In the first version structs cannot be `@export`ed or stored in `.tres`; data edited in the editor uses Resource.
- Methods: a struct can declare `func` and `static func`. Inside methods self is read-only, and assigning to a field of self is a compile error; a method that needs a change returns a modified copy. Rationale: a method that modifies self needs a call site that can be written back, and called on a temporary, on a property read through a getter, or on a loop variable, it would either be an error or silently modify a copy. [Later] Methods that modify self.
- Fields and methods are visible wherever the struct is (§4.2). [Later] A stricter `private`.
- Modification: `s.x = 1` modifies the copy where s lives (a variable, a member or a container element).
  - A chained assignment reads, modifies and writes back along the chain, as GDScript does for `node.position.x = 1` (`modules/gdscript/gdscript_compiler.cpp:1172-1190`): `player.last_hit.damage = 3` writes back through the setter of `last_hit`, and `hits[0].damage = 3` modifies the element in the array;
  - assigning to a field of a temporary is a compile error, for example `get_hit().damage = 3`;
  - loop variables and lambda captures are copies, as with Vector2 in GDScript. Modifying a field of a struct-typed loop variable that is not read afterwards gives a "modifies a copy" warning.
- Copies are shallow: object and container fields copy the reference, as these values do when assigned anywhere else. When an independent container is needed, call `duplicate()` on that field.
- `==` compares field by field, each field by the `==` of its own type (§5.2). Hashing agrees with `==`, and structs can be Dictionary keys; a key is a copy, so later changes to the original do not affect it. A struct that contains an Array or Dictionary field, directly or through nesting, cannot be a key, and using it as one is a compile error, because copies are shallow and modifying the shared container would change the key's hash; Packed arrays are copy-on-write values and objects hash by identity, so neither is restricted. GDScript allows Arrays as keys, and this language keeps that.
- A struct or enum with payloads that contains itself, directly or indirectly, without going through a container (Array, Dictionary) is a compile error whose diagnostic lists the fields of the cycle, because such a value has no finite size. Recursion through a container is allowed, such as `Tree[T]` in §2.4; list-like structures use RefCounted classes. [Later] A spelling like Swift's `indirect`.

  ```gdscript
  struct Hit:
      var damage: int
      var crit: bool = false

      func total() -> int:
          return damage * 2 if crit else damage

  player.last_hit.damage = 3   # read, modify, write back through last_hit's setter
  get_hit().damage = 3         # compile error: modifies a temporary
  for h in hits:
      h.damage = 0             # warning: modifies a copy
  ```

### 3.7 Enums

- Enums without payloads are as in GDScript.
- Payload fields of a variant must be named, as in `MOVE(target: Vector3)`. Naming keeps the encoding independent of field order.
- A match over an enum must be exhaustive or have `_` (§5.6). When a variant is added, the compiler lists every place that does not handle it.
- What the engine sees is in §10.1: an enum without payloads is an int and is shown as a drop-down when exported; an enum with payloads is encoded as a Dictionary keyed by field name, where the reserved key `"$variant"` holds the variant name as a string; for example, `Command.MOVE(target = p)` is encoded as `{"$variant": "MOVE", "target": p}`, and `Command.IDLE` as `{"$variant": "IDLE"}`. `$variant` is not a valid identifier, so it cannot clash with a field name; recording the name rather than an ordinal keeps the encoding independent of the order of variants.
- `==` on an enum with payloads compares the variant first and then the fields one by one; hashing agrees with `==`. Using one as a Dictionary key is restricted as for structs (§3.6).
- Payload fields can be taken out only through match (§5.6), not as `c.target`; so payloads cannot be modified in place, and a new value is constructed instead.
- [Known limitation] In the first version enums with payloads cannot have methods, because the brace form has no place for function bodies, so related functions go in the enclosing class; nor can they be `@export`ed, for the same reason as structs (§3.6).

### 3.8 Containers

- Whatever their internal representation (next item), users see a single `Array[T]` and a single `Dictionary[K, V]`, with the same API as in GDScript. `Array` and `Dictionary` without type arguments have Variant elements, as in GDScript. `Array[T]` and `Dictionary[K, V]` are invariant; for example, `Array[Node2D]` cannot be used where `Array[Node]` is expected, as in GDScript's static checks (`modules/gdscript/gdscript_analyzer.cpp:6379-6393`).
- When elements are representable by the engine, the container is the engine's typed container, shared with the engine. When elements are of a type only this language has (structs, enums with payloads and so on), it uses its own representation; passing it to the engine requires an explicit conversion, written as GDScript's constructor conversion `Array(hits)` or `Dictionary(d)`, whose result is an untyped engine container with the elements encoded as in §10.1, a copy; the opposite direction is `Array[Hit].try_from(v)` (§5.3). Rationale: implicit copying would create pitfalls of the "you modified a copy" kind.
- Access:
  - `pop_front()` and `pop_back()` return `T?`: the engine returns null on an empty array without reporting an error (`core/variant/array.cpp:781-800`);
  - `pop_at(i)` returns T, and an index out of range is a program error, also on an empty array, as for indexing. The engine returns null on an empty array without an error, and reports an error and returns null when the index is out of range on a non-empty one (`array.cpp:802-826`). Evidence: the 14 uses of `pop_at` in the [corpus counts](surveys/corpus-counts.en.md) all remove an element at an index the program computed, and none tests the result for null;
  - `front()` and `back()` return T and are a program error on an empty array, where the engine reports an error too (`array.cpp:354-362`);
  - an out-of-range index is a program error;
  - when T is itself nullable, `pop_front()` and `pop_back()` return `T??`, and the binding layer checks for an empty array first, because the engine returns null in both cases;
  - `Dictionary[K, V].get(k)` returns `V?`, None when the key is missing, matching the engine returning the default for a missing key (`core/variant/dictionary.cpp:178-187`); `get(k, default)` returns V; `d[k]` with a missing key is a program error, where GDScript reports an error too.
- The standard library provides `map`, `filter`, `sort` and similar methods taking typed lambdas on the native containers (§3.11).

### 3.9 Interfaces

- Interfaces are nominal: a class must declare with `implements` which interfaces it implements.
- Interfaces may declare methods, properties and signals, and may have default methods, which read and write state through interface properties.
- A property requirement can be satisfied by an inherited engine property, for example `var global_position: Vector2` by Node2D's property of that name; the type must be the same. A property is required to be readable and writable, and one marked `@readonly` only to be readable: a readable and writable implementation satisfies a read-only requirement, but not the other way round; a `var` of this language is always readable and writable, so an engine property without a setter can only satisfy a `@readonly` requirement. A default method assigning to a `@readonly` property is a compile error. `@readonly` is only for interface properties; anywhere else it is a compile error.
- Members that implement an interface must be `pub` (§4.2).
- Only classes of this language can implement interfaces; foreign objects need an explicit wrapper.
- [Known limitation] The first version has no stateful mixins. Evidence: in the [cross-branch duplication survey](surveys/cross-branch-duplication.en.md), duplication caused by different native base classes is about 4–10 lines per 1,000 lines in most game repositories; judged by reading, 185 of its 353 lines in games could be removed with composition or static functions, and 72 of the 102 lines suited to stateful mixins come from a single project, Ring. Duplication that inheritance could have removed but did not is larger, 4.9 times as much (between unrelated scripts on the same native base) and 8.2 times as much (along one inheritance chain), but it comes mostly from a single repository, tanks-of-freedom-ii.
- An interface can extend several interfaces:
  - a class implementing the child interface also implements each parent, and a value of the child interface can be used where a parent is expected;
  - a child interface may redeclare a parent's method with a covariant return type;
  - when two parents have members of the same name with incompatible signatures, it is a compile error on the child interface;
  - when two parents both provide a default implementation for a method of the same name, the child interface or the implementing class must override it;
  - a cycle of extension is a compile error.

  Evidence: of the 16 classes in gdUnit4 that have only abstract methods, 14 extend GdUnitAssert, which also has only abstract methods, and redeclare its methods with more specific return types; for example, `is_null() -> GdUnitAssert` at `GdUnitAssert.gd:7` is written `is_null() -> GdUnitIntAssert` at `GdUnitIntAssert.gd:7`.
- [Known limitation] In the first version interfaces cannot be generic. Rationale: generic interfaces must settle variance (whether `Source[Enemy]` is a `Source[Node]`) and self-referential constraints such as `Comparable[T]`, and no need was found in the surveyed code; sorting and comparison use lambdas (§3.8). [Later] Generic interfaces, written `interface Source[T]:`.

### 3.10 Generics

- Functions, structs, enums, and RefCounted classes that do not extend Resource may be generic. Node and Resource scripts and autoloads cannot, because the engine provides no type arguments when it instantiates them. Generic classes are not registered in the engine's global class table, so GDScript does not see them, since it cannot give type arguments.
- Constraints are expressed with interfaces, at most one per type parameter in the first version. Type arguments are kept at runtime.
- The spelling is in §2.4.
- Generic methods are not exposed through reflection (§10.5), because the engine and GDScript cannot supply type arguments when calling by name. To use one as a Callable, its type arguments must be fixed, for example `sig.connect(handle[int])`.
- [Later] Several constraints, and classes as constraints, with the same spelling.

### 3.11 Function types and Callable

- A function type records the parameter types, the return type, and whether the function is async; the spelling is in §2.4. A function type without a return type returns void.
- Calls are written `f.call(x)` as in GDScript and checked statically against the function type. Writing `f(x)` gives GDScript's existing error with a fix (`modules/gdscript/gdscript_analyzer.cpp:3741-3745`).
- Whether a function value can be used in a position depends only on types, and lambdas and method values are treated alike:
  - parameters are contravariant and return values covariant; for example, `func(Node)` can be used where `func(Node3D)` is expected;
  - there is no implicit conversion between async and ordinary function types;
  - positions the engine calls accept async functions: signal connections in code and in scenes, and the Callable parameters of engine APIs (such as `tween_callback`). The task runs as a root task, as with async engine virtuals (§9.1, §9.2). Evidence: in the [corpus counts](surveys/corpus-counts.en.md), coroutine methods are used as values 91 times, 60 of them as `connect(name)`.
- [Later] Parameter names in function types; direct calls `f(x)`; passing an ordinary function where an async one is expected.
- Method values (such as `change_weapon` or `_on_hit`) and lambdas have function types; handed to the engine, they become Callables that refer to the method directly rather than by name (§10.5).
- The type of `f.bind(a, b)` is f's function type without its last two parameters, because the engine appends bound arguments after the call's arguments (`core/variant/callable_bind.cpp:141-150`).
- A `Callable` of unknown signature needs an explicit conversion to a function type and is checked on every call, for its arguments and return value.
- Lambdas capture by value, as in GDScript. In a RefCounted class, capturing self is a strong reference (`modules/gdscript/gdscript_lambda_callable.cpp:285-291`) and is not silently made weak; weak capture uses `weak` (§3.12).
- The types of lambdas are inferred by the local rules (§4.6).

### 3.12 Weak references

- `weak[T]` is a typed weak reference: `weak(x)` creates one, and `.get()` returns `T?`.
- To capture self weakly in a closure, write `var me = weak(self)` outside the closure and use `me.get()` inside it.

### 3.13 Variant

- Dynamic values are imposed from outside in only three places: engine APIs declared as Variant; parameters, return values and members left untyped in GDScript plugins (§11.1); and messages from other languages. Variant written in code of this language, and the elements of Array and Dictionary without type arguments (§3.8), are dynamic values too.
- A dynamic value entering static code needs an explicit conversion (§5.3); there are no implicit checks.
- Types are fixed at the source wherever possible: constraints the engine has but does not export are added in this language's binding metadata (§10.3).
- Static values enter a Variant implicitly, by assignment, as arguments and as return values. Structs and enums with payloads are encoded as in §10.1. The exception is containers whose elements are of a type only this language has, which need an explicit conversion, written `Array(hits)` (§3.8).
- A Variant enters static code only explicitly:
  - `v as T`, for objects only, yielding `T?` (§5.3);
  - `T(v)`, GDScript's constructor conversion;
  - `T.try_from(v)`, a strict conversion returning a Result;
  - `if v is T:`, in whose branch locals and parameters narrow to T (§5.4).
- `==` and `!=` use the engine's Variant comparison (§5.2).
- Every other operation is a compile error, and the quick fix inserts a conversion or `if v is T:`: operators, member access `v.x`, method calls `v.f()`, subscripts `v[i]`, `for x in v`. GDScript executes these positions dynamically. Dynamic access by name, where really needed, converts to Object first and then uses the engine's `get`, `set` and `call` (§10.4).
- A Variant includes NIL: `v == None` is true for NIL and for a freed object, as in the engine's operator table (`core/variant/variant_op.h:484-489`), `v is int` is false for NIL, and `v as Node` yields None for NIL. `Variant?` differs from Variant (§3.4); for example, `get("hp")` on a `Dictionary[String, Variant]` is None when the key is missing, and a Some containing NIL for `{"hp": null}`.

  ```gdscript
  var data = JSON.parse_string(text)   # Variant
  data.hp                              # compile error: convert first
  if data is Dictionary:               # data narrows to Dictionary
      var hp = int.try_from(data.get("hp", 100)).unwrap_or(100)
  var n = data as Node                 # Node?
  ```

## 4. Declarations

### 4.1 Classes and inheritance

- Class names use the engine's flat global class table. The compiler checks for duplicates, including clashes with class names of GDScript plugins and C#. [Known limitation] The first version has no namespaces.
- A class may extend an engine class or a class of this language.
- [Known limitation] Cross-language inheritance is not supported in either direction: a class of this language cannot extend a GDScript class, and a GDScript script cannot extend a class of this language (§11.2).
- The signature rules for overriding methods are in §4.6, the visibility rules in §4.2.
- `@abstract` is as in GDScript (`modules/gdscript/gdscript_analyzer.cpp:1533-1552, 3630-3643`, `modules/gdscript/gdscript_parser.cpp:4500-4524`):
  - an abstract method has no colon and no body;
  - a class with abstract methods must be marked `@abstract`;
  - a concrete subclass must implement every abstract method;
  - an abstract class cannot be constructed;
  - calling an abstract method through `super` and marking a static method `@abstract` are compile errors.
- A node in a scene that uses an abstract class is a compile error, reported on that scene. The engine itself does not set abstract scripts on objects either (`core/object/object.cpp:976`); the language reports abstractness to the engine through `_is_abstract` and the global class list (`core/object/script_language_extension.h:132-136, 657-670`).
- A common base class with state is written with `@abstract`; a capability shared by classes with different engine bases is an interface (§3.9). For example, godot-open-rpg's BattlerAction extends Resource and has exported fields and an abstract coroutine `execute`:

  ```gdscript
  @abstract
  class_name BattlerAction extends Resource

  @export var label: String

  @abstract pub async func execute()
  ```

  Evidence: in the [corpus counts](surveys/corpus-counts.en.md), 25 of 28 abstract classes are in gdUnit4, and 17 of the abstract classes declared by a file have only abstract methods, so they can be rewritten as interfaces.

### 4.2 Visibility

- Members without `pub`, including structs, enums, interfaces and inner classes, are visible in the file that declares them, inner classes in that file included, and subclasses may read, write, call and override them; other classes cannot see them.
- Members marked `pub` are visible to all code.
- Overriding keeps visibility: an override of a `pub` member must be `pub`, and an override of a member without `pub` cannot add it.
- Members that implement an interface must be `pub`.
- A type that is not `pub` appearing in the signature of a `pub` member is a compile error.
- A must-assign member (§6.2) without `pub` can be assigned only by scenes (when exported) or by code in its file or subclasses; when none does, it is a compile error marked at the member's declaration.
- Which members the engine, GDScript and C# can access by name is in §10.5.
- Evidence: in the [member visibility survey](surveys/member-visibility.en.md), about 25% of the members whose names could be resolved are accessed from other files. In the [second paper migration](surveys/paper-migration-2.en.md), if subclasses could see only `pub` members, 29 of the 102 `pub` markers would exist only for subclasses.
- [Later] A stricter `private`.

### 4.3 Member variables

- `var` declares a member. With an initializer, the type may be inferred from it by the same rules as for locals: `var speed = 5.0` is float, and `@onready var label = $Label` is inferred from the scene as Label (§7.1). Inferred types appear on hover, in completion and in the property information the engine sees.
- These members must be annotated: those without an initializer, and those whose initializer does not determine a type, such as empty containers and None.
- In GDScript `var hp = 10` is an untyped member; in this language it is inferred as int, and assigning another type afterwards is a compile error, which the syntax hard rule allows.
- Members without an initializer:
  - numbers, bool, String, StringName, NodePath, core value types, containers, `Callable`, `Signal` and enums without payloads start at their default value, as in GDScript;
  - `T?` starts at None, Variant at NIL, and `weak[T]` at a weak reference to no object;
  - a struct starts at its default when every field has a default, and must otherwise be assigned like an object reference;
  - enums with payloads and function types must be assigned;
  - the rules for must-assign members are in §6.2.
- `@export` follows GDScript, and in addition: structs and enums with payloads cannot be exported (§3.6, §3.7); exported scenes are written `PackedScene[T]` (§7.4); exports of non-null object type must be assigned (§7.5).
- `@onready` is in §6.3.

### 4.4 Property accessors

- Setters and getters are written as in GDScript: inline `set(value):` and `get:`, or named `set = f` and `get = g`.
- Inside a property's own accessors, the property name refers to its storage field; elsewhere in the class, reads and writes go through the accessors, as in GDScript.
- Initializers write the field directly, bypassing the setter (§6.1).
- Setters and getters cannot be coroutines.
- The rules for setters that run before ready are in §6.5.

### 4.5 Constants

- `const` is as in GDScript.

### 4.6 Functions

- Function signature types are written by hand, not inferred. Parameters must be annotated, except in overrides (next item) and in lambdas with an expected type (second-to-last item of this section).
- An override of an engine virtual or of a base-class method may omit its parameter and return types; the omitted types are taken from the overridden declaration and shown on hover. Types that are written follow GDScript's override check: the return type may be covariant, parameter types may be contravariant, and extra parameters with defaults may be added (`modules/gdscript/gdscript_analyzer.cpp:1895-1936`); parameter names may differ. For example, delta in `func _process(delta):` is a float (`scene/main/node.h:433-434`). This is not inference: the types are set by the overridden declaration, not by the body. Evidence: the [second paper migration](surveys/paper-migration-2.en.md) has 6 parameter annotations on engine virtual overrides.
- For a function that is not an override, an omitted return type means void; returning a value from it is a compile error, and the quick fix adds the return type.
- Parameters may have default values, as in GDScript.
- Rest parameters:
  - `...args: Array` is as in GDScript; it must be the last parameter and cannot have a default value (`gdscript_parser.cpp:1709-1716`);
  - `...args: Array[T]` is also allowed, and each argument is checked at the call site; GDScript reports typed rest parameters as a compile error (`gdscript_analyzer.cpp:1803-1810`);
  - a bare `...args` is a compile error, and the quick fix adds `: Array`;
  - the method information the engine sees carries `METHOD_FLAG_VARARG`, from which GDScript accepts any number of extra arguments (`gdscript_analyzer.cpp:6052-6055`); the element type is enforced by the entry check (§10.1);
  - there is no spread at call sites, and GDScript has none either (`gdscript_parser.cpp:4344`); an existing array is passed with `callv`. Without a spread form mistakes are easy; for example, Pixelorama's `_debug_msg` passes its whole args as one argument to `_prefix_print`, which then calls `prints(args)` and prints an array instead of space-separated values (`src/Classes/ObjParse.gd:59-66`). [Later] A spread form;
  - evidence: in the [corpus counts](surveys/corpus-counts.en.md), 76 of the 78 rest parameters are in gdUnit4's assertion interfaces, all with Variant elements.
- Calls pass arguments by position, as in GDScript. Arguments by name are used only to construct structs and variants with payloads (§2.4), and to pass must-assign members to `instantiate(...)` and `new(...)` (§6.2).
- Local variables inside functions may infer their type from an initializer. A lambda is code inside a function and is inferred by the local rules: its parameter types come from the expected function type when there is one and must be written otherwise, and its return type is inferred from its body, as in `weapons.map(func(w): return w.name)`.
- A local variable, the variable of a `for` and a `var x` binding in match may not have the name of a local variable or parameter of an enclosing block of the same function; this is a compile error, as in GDScript (`modules/gdscript/gdscript_parser.cpp:1983-1987, 2345-2349, 2599-2600, 4384-4392`). Blocks side by side may each use the same name. Rationale: GDScript code never does this, and allowing shadowing later is a compatible change.
- Coroutines are declared in the signature as `async func`, and so are lambdas (§9.1).

### 4.7 Signals

- Signal parameters must be annotated, for example `pub signal died(cause: String)`.
- `emit` and `connect` are both checked statically: the arguments at the emit, and the parameter count and types of the connected function.
- Connections stored in scenes are checked by the scene model (§7.7).
- Signals of engine classes are typed from ClassDB; unaudited object parameters are treated as non-null (§10.2).
- The result of awaiting a signal is in §9.6.

### 4.8 Static members

- `static var`, `static func` and `_static_init()` are written and timed as in GDScript: when a class is loaded, base classes first, its static members are initialized in declaration order and `_static_init` is called last (`modules/gdscript/gdscript_compiler.cpp:2629-2632`). Static initializers bypass setters too (`gdscript_compiler.cpp:2603-2626`).
- When a class's static initialization reads a static member of another class, that class is initialized first.
- A cycle between static initializations is a program error whose diagnostic lists the dependency chain; cycles that can be determined statically are compile errors. Default or unfinished values are never read. Related GDScript issues: [godotengine/godot#104161](https://github.com/godotengine/godot/issues/104161), [#82141](https://github.com/godotengine/godot/issues/82141), [#104588](https://github.com/godotengine/godot/issues/104588).
- Static initialization cannot await.
- Editing the declaration of a static member is a structural change; hot reload requires a restart (§12.4).
- Rationale: the [corpus counts](surveys/corpus-counts.en.md) have only 188 `static var` and 4 `_static_init`, so contact is rare.

## 5. Expressions and statements

### 5.1 Operators

- The result types of operators follow the engine's operator table, as GDScript's static checks do (`core/variant/variant_op.cpp:212-1033`). For example, `Vector2 * float` is a Vector2, `Vector2i * float` is a Vector2, and `int / int` is integer division. Combinations missing from the table, such as `Vector2 + Vector2i`, are compile errors.
- Mixed `int` and `float` arithmetic promotes to `float`.
- Integer division by zero is a program error.
- The typing of utility functions bound with Variant (lerp, clamp, min, max, abs, wrap and others) is in §10.3.

### 5.2 Comparison

- `==` is typed by the engine's operator table, like the other operators (§5.1); a combination missing from the table is a compile error, for example `hp == "3"` or `Vector2() == Vector2i()`.
- int and float compare numerically, so `1 == 1.0` is true (`core/variant/variant_op.cpp:490-491`). String and StringName compare contents (§10.7).
- Objects compare by identity, that is, by ObjectID (`variant_op.cpp:514`), so two different freed objects are not equal. The engine turns freed objects into null before comparing, so two freed objects are equal in GDScript (`core/variant/variant_op.h:471-477`), which falls under the exception in §1.2. When both types are classes and neither is a subclass of the other, it is a compile error, since the result is always false; comparisons involving interfaces are allowed.
- Option: None equals None; two Somes are equal when their contents are; the operand with fewer levels is first wrapped to the same number of levels, as in `hp == 3` with hp an `int?`, or when comparing a `T?` with a `T??`. Comparing a value that is neither an Option nor a Variant with None is a compile error, since the result is always false; the quick fix changes the type to `T?`, or uses `is_instance_valid(x)` for a liveness check.
- Containers compare element by element as in the engine; a Dictionary compares entry by entry by key, regardless of order. The engine requires compared elements to have the same type (`core/variant/array.cpp:155-158`, `core/variant/dictionary.cpp:255-285`, `core/variant/variant.cpp:3176-3179`), so `[1] == [1.0]` is false while `1 == 1.0` is true. Comparing containers with different element types, such as `Array[int] == Array[float]`, is a compile error, since they are equal only when both are empty.
- When one operand is a Variant, the comparison is evaluated at runtime by the engine's operator table; a combination missing from the table is a program error (`variant_op.cpp:1049-1054`). GDScript reports an error there; when the operand types differ from those of the instruction's first execution, only debug builds check, and release builds get null and continue (`modules/gdscript/gdscript_vm.cpp:793-798, 821-843`). `v == None` is true for NIL and for a freed object (§3.13).
- `!=` is the negation of `==` in every case.
- Structs and enums with payloads compare field by field (§3.6, §3.7).

### 5.3 Conversions

- `x as T` is only for object types, and its result is `T?`: None when the type does not match, as in GDScript (`modules/gdscript/gdscript_vm.cpp:1677-1678`). When the static type of x already is T, the result is T, with a hint that the `as` is redundant. `as` on a freed object yields None for any type (§3.3).
- `as` to a built-in type is a compile error. GDScript converts through the constructor there and reports a failed conversion only in debug builds (`gdscript_vm.cpp:1642-1650`), so the quick fix offers two rewrites:
  - `T(x)`, which keeps that conversion, as in `int("5")` or `int(2.7)`;
  - `T.try_from(x)`, the strict conversion.
- `T.try_from(v)` returns `Result[T, ConversionError]`. It follows the rules for decoding a struct field: the value's type must match T; for `int`, a float that is exactly an integer within the int64 range is accepted (§10.8). `?` propagates the failure, and `.unwrap()` or `.expect(…)` turns it into a program error.
- A downcast that must succeed is written `(x as T).unwrap()`. Evidence: the [second paper migration](surveys/paper-migration-2.en.md) has 16 of them.
- For code that tests membership with `is_in_group` and then downcasts, the quick fix suggests narrowing with `is` instead.

### 5.4 Narrowing

- Narrowing resembles Kotlin's smart casts but applies only to locals and parameters: they narrow after `!= None`, `is` and early returns, and likewise in both branches of the conditional expression `a if c else b` and in the right operand of `and` and `or`. After a local is reassigned, narrowing follows the new value.
- Members do not narrow and must first be read into a local. Evidence: in the [second paper migration](surveys/paper-migration-2.en.md), the locals added for this were 4.4 per 1,000 lines. [Later] Conditional binding (such as `if var t = _tween:`), or narrowing fields without a getter when no call, await or assignment occurs between the check and the use.
- There is no truthiness: conditions, and the operands of `not`, `!`, `and` and `or`, must be bool. With a non-bool x, GDScript's `if x:` and `if not x:` are compile errors, and the quick fix rewrites them according to x's type, as `x != None`, `x != 0`, `x != ""` and so on, with `x == None` and so on for `not x`.
- Non-null does not mean the object is still alive; access still checks (§3.3).

### 5.5 Conditional expressions

- The only one is GDScript's `a if c else b`, where c must be bool.

### 5.6 match

- Every GDScript pattern is kept with its meaning (`modules/gdscript/gdscript_parser.cpp:2487-2711`): literals and constant expressions compare by equality; `var x` binds; `_` is a wildcard; array and dictionary patterns, with `..` inside them; several comma-separated patterns, which cannot bind; and `when` guards.
- New patterns:
  - Enum variants: `Type.VARIANT(field = pattern, ...)`. `var field` is short for `field = var field`. Fields not listed must be covered by `..`, as in dictionary patterns. Patterns nest.
  - Structs: the same form, for example `Hit(damage = var d, ..)`.
  - Built-in constructors: `Ok(var v)` and `Err(var e)` (Result), `Some(var x)` (Option), `Finished(var v)` and `Cancelled(var r)` (Settled, §9.2), without a type prefix and written positionally, as they are constructed.
  - Option also has `None` and `var x`; the value bound by the latter is narrowed to T.

  ```gdscript
  match cmd:
      Command.IDLE:
          stop()
      Command.MOVE(var target):
          walk_to(target)
      Command.ATTACK(target = var enemy, power = 0):
          taunt(enemy)
      Command.ATTACK(var target, ..) when target.is_in_group("bosses"):
          flee()
      Command.ATTACK(..):
          hit()
  ```

- A match over an enum (with or without payloads), a Result or an Option must be exhaustive or have `_`; branches with `when` do not count toward coverage. A match over other types need not be exhaustive, as in GDScript.
- [Known limitation] The first version has no type patterns (use `if x is T`), no match expressions, and no binding in comma-separated patterns. [Later] All three can be added compatibly.

### 5.7 Loops

- `for` is as in GDScript: `for i in n` iterates from 0 to n-1 with i an int; `range(...)`, containers, Strings and the keys of a Dictionary can be iterated.
- The loop variable may be annotated, as in `for i: int in ...`, with the element type or one of its base types; there is no implicit downcast.
- Iterating over a float or a vector is a compile error, and the quick fix uses `range(...)`. GDScript allows it and treats the vector as a range (`gdscript_vm.cpp:3092-3229`); under static typing this is almost always a mistake.
- `while`, `break` and `continue` are as in GDScript.

## 6. Initialization and lifecycle

### 6.1 Member initialization

- Member initializers write the field directly, bypassing the setter, for instance and static members alike, as in GDScript (`modules/gdscript/gdscript_compiler.cpp:2414-2430, 2603-2626`). The initializer gives the first value and the setter handles changes; during initialization there are no observers, and members declared later are not initialized yet.
- Derived state is computed in `_ready` or `_static_init`. When a member has both an initializer and a setter, the compiler gives a hint that initialization bypasses the setter.
- Members without an initializer start at a default value or must be assigned (§4.3).

### 6.2 Must-assign members

- `_init` of Node and Resource scripts cannot take parameters, because the engine always constructs them with zero arguments (`core/object/script_language.h:152`; [pitfall catalog](surveys/pitfalls.en.md) G-02). Constructor parameters are expressed as must-assign members: non-null members without a default.
- A must-assign member must be assigned before its scene has finished becoming ready, by one of:
  - the scene: exported members are provided by the scene (§7.5);
  - the creator: `instantiate(...)` and `new(...)` accept member values by name and assign them before returning, as in `BulletScene.instantiate(speed = 300.0, target = enemy)`. For `PackedScene[T]`, the compiler checks at the call site that every member that must be passed (§7.4) is passed, and leaving one out is a compile error; leaving one out of `new(...)` is not a compile error, and is checked at the times below;
  - an ancestor: an ancestor node in the same scene assigns it in its own `_ready`, provided the scene model can see the assignment, that is, it is written `$Child.target = v` or goes through an `@onready` reference.
- When checks happen:
  - members provided by the scene or the creator are checked when the node becomes ready, before `@onready` initialization;
  - members assigned by an ancestor are checked once the whole scene is ready. Ready propagates synchronously when a node enters the tree (`scene/main/node.cpp:3368-3372`), and per-frame callbacks come from the main loop, so ordinary logic cannot read the missing value;
  - a child reading a member assigned by an ancestor in its own `_ready` is a compile error;
  - reading a member that has not been assigned yet before ready is a program error whose diagnostic names the member;
  - if the configuration is invisible to the scene model (for example assignments in a loop over `get_children()`), the member must be written `T?`.
- Scenes whose path is known only at runtime have only the check at ready.
- Resources have no ready phase: assignments in `.tres` files are checked statically, and resources created with `new()` in code are checked on read.
- RefCounted classes that do not extend Resource use `_init` with parameters as usual; GDScript passes the arguments by position through `new` (§10.1).
- An autoload outlives scenes, so its members that refer to scene nodes can only be `T?`. Where non-null is wanted, make the manager a node in the scene and refer to the other nodes through must-assign exports.
- [Known limitation] The first version has no "non-null member assigned after ready" (like Kotlin's `lateinit`). Evidence: in the [corpus counts](surveys/corpus-counts.en.md), registering a node on an autoload member in `_ready` occurs only 6 times, 5 of them in one project (Ring, one of the subjects of the [second paper migration](surveys/paper-migration-2.en.md)). [Later] Non-null members assigned after ready.

### 6.3 `@onready`

- GDScript's timing is kept: `@onready` initializers run before `_ready`, base class first, each in declaration order (`modules/gdscript/gdscript.cpp:1937-1953`).
- The following are compile errors: combining `@onready` with `@export`; await in an initializer; reading an `@onready` member directly in `_init` or `_enter_tree`.
- Reading an `@onready` member that is not initialized yet through a call is a program error whose diagnostic names the member. Evidence: [pitfall catalog](surveys/pitfalls.en.md) G-04.

### 6.4 Ready order

- Children become ready before their parent, following the engine's order (`scene/main/node.cpp:326-337`); no lifecycle hooks are added.
- When a child reads, in its `_ready`, a member of its parent that is not initialized yet, it is a program error whose diagnostic explains the cause and suggests two rewrites: have the parent configure the child in its own `_ready` (§6.2), or declare the child's `_ready` async, declare `@parent(T)`, and `await get_parent().ready`.
- Such a read is legal when a child is added at runtime under a parent that is already ready, so it is not rejected wholesale at compile time.
- Re-entering the tree does not run `_ready` again, as in the engine (`node.cpp:334-336, 454`). Evidence: [pitfall catalog](surveys/pitfalls.en.md) G-03, G-05.

### 6.5 Setters before ready

- When a scene is instantiated, the engine sets a node's saved properties before adding the node to its parent (`scene/resources/packed_scene.cpp:494, 543`), when the node's children and `@onready` members are not yet available.
- A setter runs immediately as usual. At the first statement that needs the node to be ready, if the node is not ready yet, the setter suspends there and continues from that point once the node is ready:
  - statements that need readiness are determined by static analysis: accessing `@onready` members, `$X` or children, or calling methods of the class that access them, including overrides in subclasses;
  - accesses reachable only while `is_node_ready()` is true do not count, decided by the same rules as narrowing (§5.4): inside an `if is_node_ready():` branch, after `if not is_node_ready(): return`, and on the right of `is_node_ready() and …`. A method all of whose such accesses do not count does not need ready when called. Only `is_node_ready()` counts, because `@onready` members may still be uninitialized while `is_inside_tree()` is true;
  - the position of the suspension point is visible on hover in the editor.
- When the same property is written again before ready, the earlier suspended call is cancelled at once, whether or not the new write suspends. Suspended calls continue after `@onready` initialization and before `_ready`, in the order they were written. If the node is freed before it is ready, the suspended calls are dropped. Once the node is ready, setters no longer suspend.
- Statements before the suspension point run as usual. A setter usually transforms and stores the value before it synchronizes nodes, so a read before ready sees the transformed value. Deferring the whole setter and recording the raw input would make reads before ready see the untransformed input, for example Ring's `Runtime/AVGRuntime/UI/UI.cs:16-35` wraps character names in 【】.
- This is what GDScript code writes by hand as `if not is_node_ready(): await ready`, done by the compiler, so users need no new concept; that line written by hand in a setter is a compile error (§4.4), and the quick fix deletes it. Evidence: the [property accessor survey](surveys/property-accessors.en.md) has 25 setters that wait for ready with `await ready`.
- A property whose value lives only in nodes (no field, with a getter that reads children) is a program error when read before ready, and the diagnostic names the node that is not ready yet. If it must be readable before ready, keep the value in a field.
- A property that was never written does not run its setter at ready, as in GDScript. A hint is given when an exported property's setter synchronizes nodes but its default value never goes through the setter.

### 6.6 Destruction

- No new syntax: `NOTIFICATION_PREDELETE` is still handled in `_notification(what)`, and cleanup related to the scene tree goes in `_exit_tree`, written and timed as in GDScript; the order of destruction follows the engine. Rationale: `NOTIFICATION_PREDELETE` occurs only 40 times in the [corpus counts](surveys/corpus-counts.en.md), 32 of them in gdUnit4.
- The runtime guarantees that a RefCounted object can read and write its own fields and call its own methods during PREDELETE, without taking a new reference to self. In the engine the reference count is already zero at PREDELETE, and taking a new reference fails (`core/object/ref_counted.cpp:94-95`, `core/templates/safe_refcount.h:136-146`, `core/variant/variant.cpp:1104-1108, 2509-2510`).
- In the branch handling PREDELETE, using self as a value (as an argument, stored, returned, compared and so on; `self.x` and `self.f()` do not count) and using await are compile errors. During that time, `weak` references to self return None. Rationale: a RefCounted object that puts self into a value then gets null, and GDScript's self is null there (`modules/gdscript/gdscript_vm.cpp:656-657`); a Node's self passed out is freed right after, and a call site does not show whether the callee keeps it. Evidence: [pitfall catalog](surveys/pitfalls.en.md) G-09.

### 6.7 Reference cycles and leaks

- There is no tracing GC. RefCounted uses the engine's reference counting, and cycles are not freed.
- The compiler warns about evident cycles, with a quick fix that rewrites them to use `weak`:
  - a closure capturing self stored in a member of self, a signal connection of self itself, or a container held by self;
  - two RefCounted classes pointing at each other through fields of strong reference types.
- Nodes are not reference counted. Warnings are given when:
  - a node obtained from `new()` or `instantiate()` is, on some path, neither added to the scene tree nor returned, stored or freed;
  - a node after `remove_child` is neither stored nor freed.
- Debug builds list leaked nodes and objects, with where they were created, on exit.
- Cycles formed indirectly through engine containers or other objects cannot be found by static analysis. Evidence: [pitfall catalog](surveys/pitfalls.en.md) G-10.

## 7. Scene model

### 7.1 Typing nodes

- The compiler collects every scene structure the script is used in, including inherited scenes and edits on instances, and types `$X`, `%X` and `get_node` with a literal path from them.
- If different scene structures give different types, it is a compile error; the path must be assigned to a variable annotated with a common base class or interface, for example `@onready var weapon: Node3D = $Weapon`. Evidence: in the game repositories of the [scene structure survey](surveys/scene-structures.en.md), none of 2,023 literal paths resolves to different types in different structures.
- A path that cannot be found is a compile error, marked on the scene that lacks the node; which scenes need the node is in §7.2.

### 7.2 Structures that differ between scenes

- The following three cases all use existing spellings and need no new declaration.
- **Child nodes required by a base class and provided by inheriting scenes**: checked by how scenes are used, with the same rules as required exports (§7.5).
  - A scene used only as the base of inheritance may lack the node; a scene used as a root or instanced must have it; a scene referenced from nowhere gets only a warning when it lacks the node.
  - The type of `$X` comes from the scenes that have the node.
  - For example, tanks-of-freedom-ii's `base_ground.tscn` lacks the `$"mesh"` used by `tile.gd`; it is preloaded as a placeholder tile, which is a use as a root, so the error is marked on that scene.
  - Evidence: in the [scene structure survey](surveys/scene-structures.en.md), 7 paths in game code that are missing in some structures are nodes that template or placeholder scenes lack.
- **Optional child nodes**: `get_node_or_null(...)` with a literal path is the declaration; its type is `T?`, and scenes lacking the node are not errors.

  ```gdscript
  @onready var trail_right = get_node_or_null("Container/TrailRight")   # GPUParticles3D?
  ```

  When `$X` is missing in some scene that is used, the quick fix changes the access to `get_node_or_null`. Evidence: in the [scene structure survey](surveys/scene-structures.en.md), 8 paths in game code that are missing in some structures use `get_node_or_null`, such as the trails of the two vehicles in Starter-Kit-Racing.
- **Child nodes added at runtime**: not typed by path.
  - `$X` found in no scene is a compile error, even if those scenes are referenced from nowhere; the quick fix suggests storing the node in a typed member when calling `add_child`, for example `var tetromino: Tetromino?`. This rule also catches paths not updated after a rename, for example tps-demo's `door.gd:6` uses `$DoorModel/AnimationPlayer`, while that node is called `DoorModel2` in `door.tscn`.
  - Where a lookup by name is really needed, `get_node_or_null("X")` yields a `Node?`, converted with `as` (§5.3).
  - A literal path of `get_node_or_null` that exists in no scene gets a warning; for a node that really is added at runtime, `@warning_ignore` turns it off.

### 7.3 Upward access

- Autoloads are accessed by their global names, typed as the class of their script (§11.1). Accessing an autoload through a literal path of the form `/root/X` is a compile error, and the quick fix rewrites it to the global name X.
- Parent and owner requirements are written as the class-level annotations `@parent(T)` and `@owner(T)`, placed where `@tool` goes. With a declaration, `get_parent()`, `$".."` and `owner` have type T. Without one, `get_parent()` and `owner` have type `Node?`, as in the engine: having no parent or owner is a normal state of a node, and the engine then returns null without an error (`scene/main/node.cpp:2100-2102, 2296-2298`); `$".."` and `get_node("..")` have type Node, because GDScript reports an error there too when there is no parent. Without a declaration, `get_parent().x` or `owner.x` is a compile error; the quick fix infers the common type of the parent or owner from the scene model and adds `@parent(T)` or `@owner(T)` to the class, or rewrites the call site with `.unwrap()`. Evidence: in the [corpus counts](surveys/corpus-counts.en.md), `get_parent()` on self occurs 174 times, 62 of them accessing a member directly, in 46 files; `owner` has a member accessed directly 49 times, in 21 files. 3 more places handle a missing parent, among them a beehave setter that runs before the node is attached to its parent, where `get_parent()` yields null.

  ```gdscript
  @owner(Combat.Combatant)
  class_name HealthComponent extends Node

  func _ready():
      current_health = owner.init_health
  ```

- The static check happens where scenes place the script. A parent requirement checks the node's parent in the scene, and the outer parent when the scene's root is instanced into another scene, and a mismatch is a compile error marked on that scene; for the main scene the parent is the root viewport, of type Window, which is checked the same way; for other scenes used as a root the parent is known only at runtime, and the check happens only at runtime. The owner is the root of the scene that contains the node; when a scene's root is instanced into another scene, its owner is the root of the outer scene (`scene/resources/packed_scene.cpp:567-570`). A script on the root of a scene used as a root (§7.5) has no owner, and such a scene using a script that declares `@owner` is a compile error marked on that scene.
- At runtime:
  - the parent requirement is checked when the node is attached to a parent (`NOTIFICATION_PARENTED`, `scene/main/node.h:465`); calling `get_parent()` on a node that declares `@parent(T)` while it has no parent is a program error;
  - with `@owner(T)` declared, `owner` is checked on every read to be non-null and to satisfy the requirement; a failure is a program error whose diagnostic names the requirement and the actual owner. Owner is not checked when nodes move: when a node is taken out of its owner's subtree, the engine sets owner to null (`scene/main/node.cpp:391-396, 1781-1783`), and that is a legitimate operation, for example Ring's DeathComponent reads its owner and then moves itself to the foreground layer; owner is also set to null when the owner is freed (`node.cpp:299-302`). Code can also make any ancestor the owner with `set_owner()`, or clear it; a node that is not an ancestor is an engine error that leaves owner null as well (`node.cpp:2271-2294`).
- `get_owner()` and `get_node_or_null("..")` always have type `Node?`; code that declares a requirement uses them to test whether there is an owner or a parent.

### 7.4 Scene resources

- `preload` and `load` with a literal path are typed by the resource's actual contents; a scene yields `PackedScene[T]`, where T is the type of the scene's root node, or the class of its script when it has one.
- Exported scenes are written `PackedScene[T]`, and the editor checks the scene that is filled in. `instantiate()` yields T.
- `PackedScene[T]` is covariant in T; for example, `PackedScene[Boss]` can be used where `PackedScene[Enemy]` is expected.
- Which members `instantiate(...)` must be passed depends on whether the actual scene is known statically:
  - when it is, that is, for `preload`, `load` with a literal path, and constants initialized with them, the must-assign members that the scene does not provide must be passed;
  - for any other `PackedScene[T]`, that is, exports, variables, parameters and return values, the must-assign members of T that are not exported must be passed; exported must-assign members are provided by the scene itself;
  - when a scene becomes a `PackedScene[T]` of the second kind, that is, when it is filled into an export, assigned to a variable or passed as an argument, the must-assign members of the actual class of its root that the scene does not provide may only be must-assign members of T that are not exported; otherwise it is a compile error, marked on the scene that fills in the export, or reported at the assignment. For example, if `Boss extends Enemy` adds a must-assign member `arena` that is not exported, filling boss.tscn into a `PackedScene[Enemy]` is an error, because the call site knows only Enemy.
- `load` with a path known only at runtime yields a Resource, as the engine's signature says, with nullability per the audit in §10.2; for a scene loaded this way, `instantiate()` yields a Node. Converting to a more specific type needs an explicit conversion (§5.3).

### 7.5 Required exports

- Exports of non-null object type must be assigned. Ones that may genuinely be missing are written `T?`.
- The check follows how each scene is used:
  - when a scene is instanced or inherited by other scenes, an assignment at any level of the instance and inheritance chain counts; each instance is checked separately, and a missing value is marked on the scene containing that instance. For example, `crosshair` in player.tscn points to a node that exists only in main.tscn, which assigns it on the instance, so player.tscn itself is not an error;
  - when a scene is used as a root, that is, as the main scene, loaded with `load` or `preload` from a literal path, or assigned to an exported `PackedScene[T]` property, the scene itself is checked; a value the scene does not provide also counts when passed at an `instantiate(...)` call in code as §7.4 allows, and leaving it out is a compile error at the call;
  - a scene referenced from nowhere gets only a warning, because a `load` whose path is known only at runtime cannot be seen.
- Checks happen at three points:
  - while editing, clearing is allowed. The field in the Inspector and the node in the scene tree are marked with a compile error at once, but no operation is blocked, and the mark disappears when a value is assigned again;
  - when running, the game may run: such compile errors marked on scenes do not block running in the editor; a node still missing a value raises a program error when it becomes ready, checked before `@onready` initialization, and the diagnostic names the member, as when player.tscn is run on its own in the editor;
  - when exporting, scenes certain to miss a value are reported as errors through an export plugin, and the export dialog shows a failure whose messages name the scene and the member; warnings do not affect the export. CI blocks with the headless analysis command (§13.1);
  - [Known limitation] the engine's exporter does not stop on errors reported by plugins: no export plugin hook can make an export fail (`editor/export/editor_export_platform.cpp:2568-2576`, `editor/export/editor_export_plugin.h:120-122`), a reported error only makes the export dialog show a failure (`editor_export_platform.cpp:131, 146-148`), the output is still written, and command-line export still exits with code 0 (`editor/editor_node.cpp:1408-1424`).
- When the remote inspector writes null to a non-null member, the entry check fails, which is a program error (§10.1): the write is rejected and the value is unchanged.
- Rationale: clearing and then replacing is a normal step while editing, so non-null constrains the finished scene. Replacing does not even require clearing first, since node references are stored as paths in `.tscn` and resolved during instantiation (`scene/resources/packed_scene.cpp:376-395`).

### 7.6 Shared resources

- The semantics of resource sharing are unchanged; the scene model finds the problems. The compiler knows which resources are shared: resources from `load`, `preload` and exported properties come from the cache (`core/io/resource_loader.cpp:800-810`), and embedded sub-resources in a scene that are not set to "local to scene" are shared by all instances of that scene (`scene/resources/packed_scene.cpp:705-706`).
- Writing a property of a resource known to be shared, or calling a method that modifies it, gives a warning listing where it is shared, with two quick fixes: make it local to the scene, or `duplicate()` it before modifying. Deliberate modification of a shared resource is silenced with `@warning_ignore`. Resources replaced at runtime cannot be tracked and are not warned about. Example: in godot-open-rpg, the CircleShape2D embedded in `interaction_popup.tscn` is not local to scene, the setter at `interaction_popup.gd:30` changes its radius, and in `main.tscn:484-486` only one instance sets radius to 64; by the engine's sharing rules, the dozen or so instances share one shape whose radius is whatever the last setter wrote (inferred, not verified by running).
- `duplicate()` returns the static type of its receiver; the depth of copying is stated with `duplicate_deep(mode)`.
- Reference cycles between `preload`, exported PackedScenes and resources are compile errors, and the quick fix turns one edge into a runtime `load`; the engine returns null there (`core/io/resource_loader.cpp:1049-1056`). Evidence: [pitfall catalog](surveys/pitfalls.en.md) G-19, G-20, G-34.

### 7.7 Connections and paths in scenes

- For signal connections stored in scenes, the scene model checks that the method exists and that its parameters match the signal.
- Property paths in animation tracks, method names in method tracks, and property paths such as `"position:x"` are resolved as static references (§10.4).
- These references take part in rename and find references (§13.3).

## 8. Errors

### 8.1 Program errors

- A program error aborts the entire call chain of this language back to the entry point through which the engine called in. A call to a method declared by a class of this language belongs to the chain, whatever class the receiver is and also through an interface; a new chain begins only where the engine calls in, such as for a signal, a Callable or an engine virtual method. On the way out, held references are released and the error and call stack are logged; when running in the editor, the debugger breaks. The game keeps running.
- Program errors are detected and handled the same way in debug and release builds; the only exception is `assert` (§8.3). Debug builds only add detail to diagnostics and report leaks on exit (§6.7, §12.5).
- If the engine's entry point must return a value, the engine receives the default value of its type.
- Every situation this document calls a "program error" is handled by this rule, including: accessing a freed object (§3.3), a failed `unwrap` or `expect`, an out-of-range index, integer division by zero, reading a member that has not been assigned yet before ready, a failed entry check at the engine boundary (§10.1), and awaiting a cancelled task (§9.2).
- Calls of this language nested more than 1024 deep on one thread are a program error, instead of a stack overflow that crashes the process; 1024 is GDScript's default limit (`modules/gdscript/gdscript.cpp:2870`, `modules/gdscript/gdscript.h:489-490`).
- Rationale: after an error GDScript returns a default value built for the return type in debug builds (`modules/gdscript/gdscript_vm.cpp:3963-3993`) and null in release builds (`:535, 3995`), and the caller continues either way; under static typing this would hand code fake values.

### 8.2 Expected failures

- Expected failures are expressed with Option (§3.4) or Result (§3.5), following Rust's model: Option is an ordinary value for something that may be absent and may be left unhandled; Result reports a failure and cannot be discarded (§3.5).
- The only special syntax is postfix `?`, a short-circuit return:
  - applied to `Result[T, E]`: on `Err(e)` the current function returns `Err(e)`; otherwise it yields T. The current function must return `Result[_, E]` with the same E; a different E is first converted with `map_err`.
  - applied to `T?`: on None the current function returns None; otherwise it yields T. The current function must return `_?`.
  - Using `?` in a function that returns void, or propagating between Option and Result, is a compile error; the two are converted with `ok()` and `ok_or()`.
  - Its precedence makes `await f()?` parse as `(await f())?`.

  ```gdscript
  func load_profile(path: String) -> Result[Profile, Error]:
      var text = read_text(path)?
      return Ok(parse_profile(text)?)
  ```

- Rationale: a short-circuit return changes control flow and needs syntax; everything else transforms values, for which methods suffice, and Rust's documentation applies directly. If optional chaining `?.` were also provided, whether `x?.y` returns from the function or yields None would depend on the type of x.

### 8.3 Assertions

- `assert(condition, message)` is as in GDScript: it is evaluated only in debug builds (runs in the editor and debug exports), and a failure is a program error; in release builds it is removed, and neither its condition nor its message is evaluated (`modules/gdscript/gdscript_compiler.cpp:2181-2207`; for GDScript's handling of failures see `modules/gdscript/gdscript_vm.cpp:3876-3902`).
- Await or postfix `?` in the condition or message is a compile error, because it would vanish with the assertion in release builds.
- The condition must be bool (§5.4); for example, `assert(save_data, "...")` is a compile error whose quick fix changes it to `save_data != None`.
- Checks also needed in release builds use `expect` (§3.4) or an explicit `if`. [Later] An always-on assertion.
- Rationale: GDScript removes assert in release builds, so the syntax hard rule requires the same; in the [corpus counts](surveys/corpus-counts.en.md), the conditions of the 595 asserts are almost all queries, such as `peers.has(peer_id)`, and none has await in its arguments.

### 8.4 Diagnostics

- Compile errors, warnings and hints are reported by the analysis service and marked in the source, the Inspector and the scene tree (§13).
- The diagnostic of a program error gives the location, the members or objects involved, and the call stack. For some program errors this document states what the diagnostic must contain, such as the name of a must-assign member, where a freed object was freed, or the owner requirement and the actual owner.

## 9. Coroutines

### 9.1 async and Task

- Coroutines are declared in the signature as `async func`. A function whose body contains await without the declaration is a compile error. Only engine virtual functions returning void may be declared async; `_init` cannot be declared async. Rationale: construction does not wait for the return value of `_init`, and engine virtuals with return values read them synchronously, so they cannot accept the completion signal returned on suspension (Godot `ed1daf0`, `modules/gdscript/gdscript.cpp:194`, `core/object/make_virtuals.py:1-10, 173-174`).
- The same holds for lambdas: a lambda containing await is written `async func(...)`, for example `button.pressed.connect(async func(): await fade_out())`. GDScript marks such lambdas with nothing (`modules/gdscript/gdscript_parser.cpp:3249-3251, 3752-3753`), and the quick fix adds `async`. Rationale: there is a single rule for whether a function is async, and a suspension point always has async in sight; in the [corpus counts](surveys/corpus-counts.en.md), only 35 of 979 lambdas contain await, 33 of them in gdUnit4's tests.
- Positions the engine calls accept async functions, and the task runs as a root task (§3.11).
- Calling an async function yields a `Task[T]`. The task starts immediately and runs until its first suspension; `await f()` and `await t` yield T. A coroutine returning void yields a `Task[void]`; `void` as a type argument is allowed only for Task, and `Task` without a type argument is a compile error.
- Discarding the result of an async call is a compile error; to deliberately not wait, write `f().detach()`. In GDScript, using the result of a coroutine call as a value is already a compile error (`modules/gdscript/gdscript_analyzer.cpp:3776-3784`), so giving `var t = f()` a new meaning does not violate the syntax hard rule.
- Setters, getters, `@onready` initializers and static initialization cannot await.

### 9.2 How tasks end

- A task ends in one of three ways:
  - **finished**, with its return value;
  - **cancelled**, by `t.cancel()`, by its owning object being freed, or, for `Task.of(signal)`, by the signal source being freed (§9.7);
  - **failed**, by a program error inside the task, including an await that meets a cancelled task or a freed signal source (§9.7).
- Awaiting a cancelled task is a program error. A failure propagates up the await chain to the root task, which is a detached task or a task called by the engine, and cannot be intercepted.
- `await t.settled()` waits for the task to finish or be cancelled, treating cancellation as a value rather than an error, and returns `Settled[T]`: `Finished(v)` or `Cancelled(r)`, where r has the enum type `CancelReason` with the variants `REQUESTED`, `OWNER_FREED` and `AWAITED_FREED`. If the task fails, the failure reaches the waiter as usual, as with `await t`. This is not expressed with Result, because being cancelled is not an error.

### 9.3 Cancellation and ownership

- For a suspended task, `cancel()` immediately disconnects the signal or task it is waiting for, and the task ends as cancelled.
- For a running task (which only happens when its own synchronous code indirectly cancels it), it ends as cancelled at its next await or return, and the return value is discarded.
- For a task that has ended, `cancel()` has no effect. After `cancel()` is called, the outcome is always cancelled.
- Cancellation propagates along ownership: a child task the task starts and awaits directly with `await f(...)` belongs to it and is cancelled with it; awaiting a task value obtained elsewhere with `await` means cancellation only stops the waiting, and that task keeps running. The two forms can be told apart at compile time. For example, if the cutscene `cutscene` is cancelled while stopped at `await walk_to(door)`, `walk_to` is cancelled with it and the character stops.

### 9.4 Release

- A coroutine frame, its locals and suspension point, is released as soon as the task ends; held references are handled as at scope exit, and code after the await does not run. [Known limitation] The first version has no finally or defer.
- A Task object is a RefCounted handle that only holds the result. It is freed when no variable, no waiter and no signal wait of the runtime refers to it any more.
- A suspended coroutine does not keep self alive, as in GDScript (`modules/gdscript/gdscript_vm.cpp:2609-2625`).

### 9.5 Combination and reentrancy

- `Task.of(signal)` wraps a signal as a task; `Task.delay(seconds)` waits for a time; `Task.any(list)` returns the index of the first task to finish and cancels the others by the ownership rule (§9.3); `Task.all(list)` waits for all of them. Tasks started directly in the arguments of `Task.any(...)` or `Task.all(...)` belong to it; for tasks obtained elsewhere, it only stops waiting.
- Reentrancy has no automatic policy; when needed, the old call is cancelled through its handle. [Later] Annotations such as `@restart`. Evidence: [pitfall catalog](surveys/pitfalls.en.md) G-12, G-13; proposals [godot-proposals#8838](https://github.com/godotengine/godot-proposals/issues/8838), [#6243](https://github.com/godotengine/godot-proposals/issues/6243).

### 9.6 Awaiting signals

- A signal can be awaited directly.
- A signal without parameters yields no value; a signal with one parameter yields a value of that parameter's type; awaiting a signal with several parameters is allowed only as a statement. Evidence: in the [await signal results survey](surveys/await-signal-results.en.md), only 1 of 1,356 awaits uses the result of a signal with several parameters. GDScript yields an Array of the arguments there (`modules/gdscript/gdscript_function.cpp:256-274`), so GDScript code that uses such a result is a compile error. [Later] Destructuring the result of awaiting a signal with several parameters.
- A signal's signature is unknown when the static type of the signal expression is only `Signal`, for example a variable or parameter of type `Signal`, a method returning a Signal, or a signal taken from a Variant or an Object. Signals reached through a known class all have known signatures: engine classes from ClassDB, classes of this language from their declarations, and GDScript classes through reflection.
- Awaiting a signal whose signature is unknown yields a Variant shaped at runtime as in GDScript: NIL without parameters, the argument with one parameter, and an Array of the arguments with several. As a statement there is no restriction. Rationale: an unknown signature is a dynamic source in the first place, and the result must be converted explicitly under the rules for Variant before use (§3.13). Evidence: in the [await signal results survey](surveys/await-signal-results.en.md), the result of such an await is used only once, at `godot_dialogue_manager/addons/dialogue_manager/dialogue_manager.gd:1956`, which awaits a two-parameter signal declared in C# through a receiver typed RefCounted. [Later] Signal types with parameter types.

  ```gdscript
  var r = await DialogueManager.Resolved   # receiver is a RefCounted, signature unknown: r is a Variant
  if r is Array and r[0] == id:            # narrowed by the rules for Variant before use
      return r[1]
  ```

### 9.7 Freed objects and suspended coroutines

- When the object a coroutine belongs to is freed, the coroutine is cancelled silently and the references its suspended frame holds are released, as in GDScript (`modules/gdscript/gdscript.cpp:2069-2079`). The runtime cancels an object's coroutines as soon as the object receives PREDELETE. PREDELETE reaches the script instance before Node deletes the children (`core/object/object.cpp:173, 928-931`; `scene/main/node.cpp:308-312`), so a coroutine awaiting one of its own children is cancelled before the child is deleted.
- When an awaited object (a coroutine on another object, or the signal source of another object) is freed before it completes, the waiter is not left suspended forever as in GDScript (`modules/gdscript/gdscript.cpp:2069-2079`, `core/object/object.cpp:2327-2342`). The decision is deferred until the objects pending deletion in the current frame have all been deleted, that is, until the scene tree has flushed its deletion queue and the engine calls the script language's per-frame callback (`scene/main/scene_tree.cpp:735`, `main/main.cpp:5106-5109`):
  - if the waiter's own object has been freed in the meantime, the waiter is cancelled silently (`OWNER_FREED`). For example, when the scene changes, the engine deletes siblings one by one from the last (`node.cpp:308-312`), and a coroutine awaiting a sibling's signal gets no error;
  - otherwise the waiter fails at its await, which is a program error whose diagnostic names the freed object and where it was freed, and the failure propagates up the await chain as usual (§9.2).
- Awaiting with `settled()` gives no error and yields the awaited task's own cancellation reason: `Task.of(signal)` yields `Cancelled(CancelReason.AWAITED_FREED)` when the signal source is freed, and a coroutine on another object yields `Cancelled(CancelReason.OWNER_FREED)` when its object is freed.

  ```gdscript
  # hud.pet: HUD and player are both children of Main
  async func _ready():
      await player.died         # scene change: player is deleted first, then HUD, cancelled silently
      show_game_over()          # player freed alone without emitting died: a program error after the frame
  ```
- The freeing of any object can be observed through the instance-binding free callback that GDExtension exposes (`core/object/object.cpp:2360-2365`). The runtime uses its own binding token, and an object can hold bindings for several tokens at once (`core/object/object.cpp:2167-2201`), so godot-cpp's binding is not affected; this has been verified on a running engine ([probes](../tests/engine/project/probes/probes.gd)). Evidence: [pitfall catalog](surveys/pitfalls.en.md) G-11.

### 9.8 Cross-language await

- Calls to GDScript methods may be awaited. If the runtime receives a `GDScriptFunctionState`, it waits for its `completed` signal (`modules/gdscript/gdscript_function.cpp:369`) and then checks the result against the declared return type. Whether a method is a coroutine is not in its reflection information (`core/object/method_info.h:37-44`), so this cannot be decided at compile time. Without await, the form of the call decides, as in GDScript (`modules/gdscript/gdscript_analyzer.cpp:3776-3784`):
  - called as a statement, with the result unused, a method found at runtime to be a coroutine is no error: the coroutine runs to its first suspension and then continues on its own, as if detached;
  - with the result used as a value, receiving a `GDScriptFunctionState` at runtime is a program error whose diagnostic says that the method is a coroutine and needs await.
  - [Later] Obtaining a `Task` handle for a call of a GDScript coroutine, to await it later.
- While awaiting a `GDScriptFunctionState`, the runtime holds it until `completed` is emitted, and watches the object the call was made on: the receiver, or the target object when calling through a Callable. If that object is freed, or its script is replaced (`script_changed`, `core/object/object.cpp:995`), this is handled as an awaited object being freed (§9.7), and `settled()` yields `Cancelled(CancelReason.OWNER_FREED)`. Rationale: after the coroutine suspends again, the inner state remembers the first state's `completed` signal only by ObjectID (`modules/gdscript/gdscript_vm.cpp:2634-2639`), and the first state leaves the instance's pending list when it resumes (`modules/gdscript/gdscript_function.cpp:329-330`), so it would be freed early if not held; when the instance is destroyed, the engine only clears the suspended states and does not emit `completed` (`modules/gdscript/gdscript.cpp:2069-2079`, `gdscript_function.cpp:343-362`); `GDScriptFunctionState` is an internal class that does not expose its instance, and its `is_valid(true)` is always false once it has resumed (`gdscript_function.cpp:288-307, 337, 364-370`, `modules/gdscript/register_types.cpp:140`), so after the coroutine suspends again the held state cannot tell whether its host has been freed.
- [Known limitation] When a GDScript script is reloaded, the engine clears its suspended functions without emitting any signal (`gdscript.cpp:1487-1506`, `modules/gdscript/gdscript_compiler.cpp:2700`), and coroutines awaiting them stay suspended forever. This happens only when a script is edited in the editor.
- When GDScript awaits a coroutine of this language, the coroutine returns its Task's `completed` signal at its first suspension; GDScript's await accepts any Signal value (`modules/gdscript/gdscript_vm.cpp:2586-2600`). The Task emits `completed(value)` when it finishes, and `completed(null)` when it is cancelled or fails, so a GDScript waiter is never left suspended forever; a separate `cancelled` signal serves code that needs to tell the cases apart.
- The return type that an async method of this language reports to the engine is always untyped Variant (`PROPERTY_USAGE_NIL_IS_VARIANT`), whatever the declared return type, void included; the declared type appears only in documentation and hover. Rationale: method reflection information has no coroutine flag (`core/object/method_info.h:37-44`), so GDScript can only check against the reported return type. If T were reported, every await in GDScript would get the "redundant await" warning (`modules/gdscript/gdscript_analyzer.cpp:3102-3107`), and the `completed(null)` sent on cancellation would be written unchecked into a temporary of type T (`modules/gdscript/gdscript_vm.cpp:2667-2668`, `modules/gdscript/gdscript_byte_codegen.cpp:998-1001`); when T is a value type such as Transform3D, a later instruction that accesses it by type dereferences a null pointer and the process crashes. With Variant, debug builds check the type when the result is assigned to a typed variable (`gdscript_vm.cpp:1433-1444`); release builds do not, as for any other GDScript function that returns Variant.
- Both directions have been verified on a running engine ([probes](../tests/engine/project/probes/probes.gd)): holding the first state yields the result after the coroutine suspends again, and without holding it the result never arrives; when the receiver is freed the coroutine never completes; GDScript awaiting a coroutine of this language gets its result, gets null on cancellation, and assigning that null to a Transform3D variable only stops that function instead of crashing.

## 10. Engine boundary

### 10.1 Types as the engine and GDScript see them

| This language | What the engine and GDScript see |
|---|---|
| `int`, `float`, `String`, classes such as Node | the type of the same name |
| objects `T` and `T?` | that class in both cases; non-null is guaranteed by entry checks |
| nullable values such as `int?` | an untyped Variant |
| `Array[T]` and `Dictionary[K, V]` with engine-representable elements | the engine's typed containers |
| enums without payloads | int; shown as a drop-down when exported |
| structs | Dictionaries keyed by field name, with String keys |
| enums with payloads | Dictionaries keyed by field name, with the reserved key `"$variant"` holding the variant name (§3.7) |
| return values of async methods | untyped Variant (§9.8) |

- GDScript types global classes of other languages through the Script reflection interface (`modules/gdscript/gdscript_analyzer.cpp:789-804, 4278-4319, 6005-6014`), so GDScript checks the instance members (properties, methods, signals) of classes of this language as it checks native classes: the types and arguments of known members are checked, and an unknown method name is, as on a native class, only an unsafe-access warning (`gdscript_analyzer.cpp:3750-3757`). `Player.new(...)` is checked too: the Script base class does not bind `new`, GDScript binds its own (`modules/gdscript/gdscript.cpp:1078`), so this language's Script class binds `new` and reports `_init` as a static method returning the class, and GDScript checks `new` as a static `_init` (`gdscript_analyzer.cpp:5958-5961`). Arguments are passed by position; passing must-assign members by name (§6.2) is available only in this language. These have been verified on a running engine ([probes](../tests/engine/project/probes/probes.gd)). Other class-level access is in §11.3.
- **Entry checks**: wherever a value enters this language from the engine, GDScript or C# (arguments, `set` writes to members, signal arguments, results of await, decoding), it is checked against the declared type, and a failure is a program error. Writes by the remote inspector go through entry checks too (§7.5).
- When an Option is handed to the engine, None is encoded as NIL. So `X?` can be handed to the engine implicitly only when no value of X encodes as NIL; when X is an Option or Variant it is a compile error, and the quick fix offers `.flatten()` or `.unwrap_or(null)`. Otherwise Some(None) would silently turn into None after a round trip through the engine (§3.4).

### 10.2 Nullability of objects in engine APIs

- In engine APIs that the binding metadata (§10.3) has not audited, the nullability of an object type follows the direction of the value:
  - values the engine hands to this language may be null: return values of methods and properties read, typed `T?`;
  - values the engine passes in when it calls this language are treated as non-null: parameters of overridden virtual methods and parameters of engine signals, typed T; a null is reported as a program error by the entry checks (§10.1); a handler can declare the parameter `T?` to accept null without waiting for an audit (§4.6);
  - values this language passes to the engine may be null: method arguments and properties written accept None, and whether a null is valid is up to the engine; for example `set_owner(null)` clears the owner (`scene/main/node.cpp:2273-2281`).
- Audits start with the most frequently called APIs. For return values they have three outcomes:
  - non-null, typed T;
  - null only on misuse, that is, the engine reports an error when it returns null, such as `get_tree()` (`scene/main/node.h:558-561`): treated as non-null, and a null is a program error;
  - possibly null in normal use, such as `get_collider()`, `get_first_node_in_group()` and `get_parent()`: typed `T?`.
  Parameters are audited as well: those that do not accept null are marked non-null; virtual-method and signal parameters through which the engine may pass null are marked nullable, for example Area3D's `body_shape_entered` passes null when the node is not in the tree (`scene/3d/physics/area_3d.cpp:233-234`).
- Rationale: the engine marks return values that are "null only on error" with `RequiredResult` (`core/object/object.h:942-944`), and only about 50 API declarations use it, 29 of them in Tween. Objects the engine passes in are almost never null, and GDScript code does not check them; if they were nullable, every `_input(event)` and every signal handler would have to check first, while the rare null is reported by the entry checks at the boundary instead of travelling on silently.

### 10.3 Binding metadata

- Constraints the engine actually has but does not export are added in this language's binding metadata; metadata the engine already exports is used directly.
- Utility functions bound with Variant (lerp, clamp, min, max, abs, wrap and others) are typed by their arguments: when the arguments have the same type, the result has that type. Mixing int and float is a compile error, and the quick fix turns the integer argument into a float, as in `min(ratio, 1.0)`. Rationale: the engine's min, max and clamp return one of their arguments unchanged (`core/variant/variant_utility.cpp:642-759`), so in GDScript `min(1.5, 1)` is an int, and promoting to float would make the result silently differ; lerp itself requires both arguments to have the same type (`variant_utility.cpp:465-469`).
- Engine APIs that filter by a literal class name are typed by that class, for example `find_children("*", "MeshInstance3D")` returns `Array[MeshInstance3D]`: the engine collects only nodes for which `is_class` holds with that name, or whose script is that global class (`scene/main/node.cpp:2031-2042`).
- Engine APIs that "return null on failure and report the error separately" (such as `FileAccess.open`) are wrapped by standard library functions that return Result.

### 10.4 Member names as strings

- For `connect`, `emit_signal`, `call`, `call_deferred`, `set_deferred`, `has_method`, `Callable(obj, "m")`, `tween_property` and property paths such as `"position:x"`, a literal is resolved as a static reference when the target type is known: the name's existence and the value's type are checked, and it takes part in rename and find references.
- Which parameters are names is marked in the binding metadata.
- A non-literal name is explicit dynamic access.

### 10.5 Members exposed through reflection

- Through reflection (`get_property_list`, `has_method`, and `call`, `get` and `set` by name), the engine, GDScript and C# see only:
  - `pub` members;
  - members the engine must find by name: exported properties, signals, overrides of engine virtuals, methods connected in scenes, and members that code in this language hands to the engine by a literal name, such as `call_deferred("reset")`, `tween_property(self, "current_speed")` and property paths in animation tracks of scenes. The compiler collects the latter.
- All other members are invisible to access by name: referring to them from GDScript is a GDScript compile error, and access from C# through `Call`, and access by a non-literal name from any language, report a missing member at runtime.
- A `pub` member whose type is a container with elements of a type only this language has (§3.8) is not exposed through reflection either. Rationale: reflection could hand over only an encoded copy, and changes to the copy outside would not reach the container, which is what the explicit conversion of §3.8 avoids; where needed, the class provides a method returning the conversion, such as `pub func get_hits() -> Array: return Array(hits)`. Members of struct type are exposed: reading gives an encoded copy and writing decodes it (§10.1), copy semantics as for properties of value types such as Vector3.
- Generic methods are not exposed through reflection, because calls by name cannot supply type arguments; methods the engine must find by name cannot be generic (§3.10).
- A Callable formed from a method value (for example `tween_callback(change_weapon)` or `sig.connect(_on_x)`) refers to the method directly, not by name, and is not affected.
- The debugger sees all members.
- Rationale: members without `pub` are referred to only by their file, subclasses and the literal names the compiler collects, so the tools can find every reference when renaming them.

### 10.6 Numeric boundaries

- Writing to an engine 32-bit float location narrows implicitly, for example `real_t` vector components, which are float in standard builds (`core/math/math_defs.h:143-146`).
- Passing a value to an engine integer parameter narrower than int64 or unsigned (int8, int16, int32, uint8, uint16, uint32, uint64, char32) is range-checked, and an out-of-range value is a program error; a property write is checked against the type of its setter's parameter. The engine itself truncates or wraps there (`core/variant/variant.h:336-353, 411-424`), and so does GDScript. Evidence: the engine API has more than 3,700 such method parameters and about 460 such properties; `collision_layer`, for example, is uint32, and writing -1 makes it 4294967295. [Known limitation] Parameter widths come from the engine API description that comes with godot-cpp; classes of other extensions are not in it, and their parameters are not checked.

### 10.7 String and StringName

- Both directions convert implicitly where needed, as in GDScript; `==` compares contents (`core/variant/variant_op.cpp:196-203, 493, 615`).
- Where StringName or NodePath is expected, a string literal is constructed as that type at compile time, with no runtime conversion. Constructing a StringName from a String needs a lookup under the global table's mutex (`core/string/string_name.cpp:263-285`).
- The `&"x"` and `^"x"` prefixes remain. Runtime conversions on hot paths get a performance hint.

### 10.8 JSON

- The engine parses every number in JSON as a float (`core/io/json.cpp:390-396`). Decoding to `int` accepts a float that is exactly an integer within the int64 range and otherwise reports an error, without truncating.
- The standard library provides encoding and decoding between structs and enums and JSON, `var_to_str` and ConfigFile. Containers whose elements are structs or enums with payloads are first turned into engine containers with `Array(hits)` or `Dictionary(d)` (§3.8).

## 11. Coexisting with GDScript and C#

### 11.1 The static view of GDScript classes

- This language sees GDScript classes and autoloads through reflection:
  - object-typed members, parameters and return values are taken as `T?`;
  - value types are as declared;
  - untyped ones are dynamic values (§3.13).
- Autoload names are global identifiers whose type is the class of their script.

### 11.2 Inheritance

- Cross-language inheritance is not supported in either direction:
  - A class of this language cannot extend a GDScript class. When a plugin requires extending its classes (such as Beehave's ActionLeaf), users hand-write a thin GDScript subclass that calls code in this language; GDScript sees this language's types through reflection, so calls to instance members are still statically checked (§10.1). Evidence: [pitfall catalog](surveys/pitfalls.en.md) C-17.
  - A GDScript script cannot extend a class of this language: when GDScript resolves `extends GlobalClassName`, it parses the base class's file as GDScript (`modules/gdscript/gdscript_analyzer.cpp:469-485`, `modules/gdscript/gdscript_cache.cpp:83-92`) and on failure reports only "Could not resolve super class" (`:483, 489`). The analysis service reports an error explaining this on such a GDScript file.
- Migrating a class therefore requires migrating its GDScript subclasses with it (§13.4). Evidence: in the [second paper migration](surveys/paper-migration-2.en.md), Ring's Brick and Enemy brought 5 subclasses along for this reason.

### 11.3 Cross-language calls and messages

- GDScript and C# can access by name only the members listed in §10.5.
- [Known limitation] GDScript can use classes of this language only through instances and construct them with `new` (§10.1). The following class-level access is not supported; the workaround is to go through an instance method or an autoload's instance method:
  - static methods: GDScript's analyzer accepts `Player.make()`, but at runtime the method is not found, because GDScript and C# dispatch static methods by overriding the engine's internal `callp`, and GDExtension has no matching hook (`core/object/object.cpp:800-826`);
  - enums and constants in a class: they cannot be used in GDScript type annotations (`modules/gdscript/gdscript_analyzer.cpp:935-937`), as `const` values or as `Player.State.IDLE`, because GDScript does not treat constants of other languages as constant expressions (`gdscript_analyzer.cpp:4321-4330`); reading a constant's value works;
  - autoloads written in this language: GDScript types only autoloads written in GDScript (`gdscript_analyzer.cpp:806-826, 4579-4616`), so in expressions such an autoload has type Node, and in a type annotation it silently becomes untyped.
- [Later] Supporting GDScript calls to static methods through a script instance on the Script resource; this needs to be verified on a running engine first.
- Messages to and from C# are expressed as structs, encoded as Dictionaries keyed by field name (§3.6), and decoded and checked at the entry.
- Cross-language await is in §9.8.

## 12. Runtime

### 12.1 Adapter layer

- Creating and freeing instances, reading and writing properties, and calling methods all go through GDExtension's script instance interface.

### 12.2 Performance

- Clearly faster than GDScript; C# is not the target. Most scripts never hit the interpreter's performance limits.
- Native code comes from one code generator with several backends, used both for generating it at run time (a JIT) and ahead of time; it compiles a function at a time and does not trace: the types are known at compile time and need no traced run to be found, and generation ahead of time has no run to trace. iOS and most consoles do not allow generating machine code at run time, so there it can only be generated ahead of time. Evidence: CPython's JIT compiles traces and is only 4–12% faster than its interpreter in 3.15 (geometric mean), and its authors proposed a method-based frontend, for maintainability, in [PEP 836](https://peps.python.org/pep-0836/). [Open] When it is generated: at run time, at export, or both; if only at run time, the interpreter alone must reach the performance goal on iOS and consoles.

### 12.3 Threads

- The virtual machine must run safely on whatever thread the engine chooses, for example background resource-loading threads and the physics thread.
- Data races on shared objects are the user's responsibility.
- [Known limitation] The first version adds no threading API and uses the engine's Thread, WorkerThreadPool and Mutex. Evidence: in the [corpus counts](surveys/corpus-counts.en.md), `Thread.new` occurs only 5 times and `WorkerThreadPool` twice.

### 12.4 Hot reload

- When only function bodies change, they are replaced while running: the next call uses the new code, and suspended coroutines finish on the old version.
- When members, signatures or class structure change, state is not migrated and a restart is requested: the running game applies neither this change nor any later one until it restarts, so that each class has one version in a run; tool scripts in the editor rebuild their instances.
- Rationale: if only instances created afterwards used the new version, a class would have two versions in one run, and code compiled against the old declarations could call new instances; and once a change to declarations has been refused, a script whose only change is a function body may already have been compiled against the new declarations. GDScript switches every instance to the new code and moves old values over by member name without checking their types (`modules/gdscript/gdscript_compiler.cpp:3070-3074`, `modules/gdscript/gdscript.cpp:2038-2064`); under static typing the moved values cannot be trusted.

### 12.5 Debugging support

- It plugs into the engine's debugging UI: breakpoints, stepping, locals and call stacks.
- Debug builds record where instances of this language are freed, and where code of this language frees any object, for the diagnostics on freed objects (§3.3), and list leaked nodes and objects on exit (§6.7).

### 12.6 Standard library

- The standard library does not reimplement what the engine provides; it adds three things:
  - typed wrappers from the binding audit, such as `FileAccess.open` returning Result (§10.3);
  - support for this language's types: encoding and decoding of structs and enums (§10.8), the methods on Option and Result (§3.4, §3.5), and `map`, `filter` and `sort` with typed lambdas on native containers (§3.8);
  - the test runner (§13.2).
- There is no package manager.

## 13. Toolchain

### 13.1 Analysis service

- The analysis service runs in the editor process. External IDEs connect through LSP; the command line and CI run the same analysis headless. The headless analysis command exits with a non-zero code when there are compile errors, including missing-value errors marked on scenes (§7.5).
- Rationale: refactorings across scenes must modify scenes the editor has open, which only the editor can do safely. GDScript's LSP is an editor plugin too (`modules/gdscript/language_server/gdscript_language_server.h:35`, `modules/gdscript/register_types.cpp:167`).

### 13.2 Tools in the first version

- Live diagnostics, with the same analysis in the editor, LSP and command line;
- completion, types on hover, go to definition, and find references, including references in scenes;
- rename including the scene half (§13.3);
- scene checks: `$X`, signal connections, `PackedScene[T]`, parent and owner requirements and required exports, with errors marked in the scene editor;
- quick fixes: inserting inferred types, completing match branches, adding explicit conversions for dynamic values, and the rewrites mentioned throughout this document;
- the debugger (§12.5);
- a built-in test runner: discovery, running and reporting, also headless. Rationale: gdUnit4 and GUT require test classes to extend their GDScript base classes, and cross-language inheritance is not supported.

### 13.3 Refactoring

- Refactorings include their scene half. Mechanical, meaning-preserving edits are applied with the refactoring, previewed and undoable: renamed export property keys, method names in signal connections, animation track paths, and lossless value conversions.
- Edits that need judgment are only reported, with options, and never applied automatically, for example changing a node's type or an existing resource no longer matching a new type.
- Rationale: without this, renaming an exported member silently loses the values saved in scenes: loading does not check whether `node->set` succeeded (`scene/resources/packed_scene.cpp:494`), and saving writes only properties in the node's current property list (`packed_scene.cpp:860-869`).
- When a node is renamed or moved in the scene editor:
  - the `$X`, `%X` and literal `get_node` paths that refer to it in scripts of this language are updated automatically, in the same undo step as the editor's own updates of NodePath properties and animation tracks in the scene (`editor/docks/scene_tree_dock.cpp:2143-2248, 2250-2401`);
  - this is done in the `history_changed` signal that the editor emits after committing its action, by creating an action with the same name and the merge mode `MERGE_ALL`, which merges into the action just committed and keeps its operations (`editor/editor_undo_redo_manager.cpp:298`, `core/object/undo_redo.cpp:97, 116-117`). Operations cannot be added while the editor's action executes: when a node is moved the editor emits no signal inside the action (`scene_tree_dock.cpp:2535-2677`), and committing leaves the action before executing it (`undo_redo.cpp:313-332`). The new action takes the root of the edited scene as its context, which puts it in the same undo history (`editor/editor_undo_redo_manager.cpp:63-105, 149-156`); the signal is handled synchronously, within the 800 ms that merging requires; the action name is translated, so it is read from the history. This approach has been verified on a running engine ([editor checks](../tests/engine/project/addons/petrichor_checks/plugin.gd));
  - there is no preview, and the changed places are listed in the output panel afterwards;
  - non-literal paths, and scripts attached in other scenes where the same path still refers to another node, are only reported, not changed, with a quick fix to update the path.

### 13.4 Migration

- Migration is guided by compile errors and quick fixes. Mechanical edits, such as adding `pub`, adding parameter types, rewriting truthiness tests and adding `.detach()`, can be done by quick fixes. Evidence: in the [second paper migration](surveys/paper-migration-2.en.md), 197 of 230 edits were mechanical.
- Before a class is migrated, its GDScript subclasses are listed, with the option to migrate them together (§11.2).

### 13.5 Later

- [Later] Formatting; refactorings such as extract method, change signature and pull members up to a base class; deeper profiler integration; documentation generation; generating GDScript forwarding shells for GDScript plugin classes that require inheritance.

## 14. First-version scope and open questions

### 14.1 Known limitations

- Exported games cannot load scripts from source at run time (§1.3).
- `_init` and overrides of non-void engine virtuals cannot be declared async (§9.1).
- Structs cannot be `@export`ed or stored in `.tres` (§3.6); enums with payloads cannot have methods or be `@export`ed (§3.7).
- There are no stateful mixins, and interfaces cannot be generic (§3.9).
- There are no namespaces (§4.1).
- Cross-language inheritance is not supported in either direction (§4.1, §11.2).
- GDScript cannot call static methods of classes of this language or use their enums and constants as types or constant expressions, and autoloads written in this language are untyped in GDScript (§11.3).
- match has no type patterns, no match expressions, and no binding in comma-separated patterns (§5.6).
- There is no "non-null member assigned after ready" (§6.2).
- Coroutines have no finally or defer (§9.4).
- When a GDScript script is reloaded, coroutines awaiting its suspended functions stay suspended forever (§9.8).
- The engine's exporter does not stop the export on errors about values certain to be missing (§7.5).
- No threading API is added (§12.3).

### 14.2 Compatible later additions

- A runtime library that includes the compiler, for projects that need to load scripts from source at run time, at the cost of compiling at load time (§1.3);
- aliases or `import` (§2.4);
- positional arguments for struct construction, struct methods that modify self, `private` for struct members, and value-type recursion without a container (§3.6);
- generic interfaces, written `interface Source[T]:` (§3.9);
- several constraints on a type parameter, and classes as constraints (§3.10);
- parameter names in function types, direct calls `f(x)`, and passing an ordinary function where an async one is expected (§3.11);
- a stricter `private` visibility (§4.2);
- a spread form at call sites (§4.6);
- conditional binding, or narrowing fields without a getter when no call, await or assignment occurs between the check and the use (§5.4);
- type patterns, match expressions, and binding in comma-separated patterns (§5.6);
- non-null members assigned after ready (§6.2);
- an always-on assertion (§8.3);
- reentrancy annotations such as `@restart` (§9.5);
- destructuring the result of awaiting a signal with several parameters, and Signal types with parameter types (§9.6);
- obtaining a `Task` handle for a call of a GDScript coroutine (§9.8);
- GDScript calls to static methods of classes of this language (§11.3);
- the tools listed in §13.5.

### 14.3 Open questions

- When native code is generated: at run time, at export, or both (§12.2).

## Appendix B: Alternatives considered but not adopted (non-normative)

| Alternative | Why not adopted | Current rule |
|---|---|---|
| Delivery as an engine module (v0.1) | The pitfall catalog has no item only a module could fix; a GDExtension works with the official editor and export templates | §1.3 |
| Narrow integer types such as i32 and u8 (v0.1) | The largest migration cost ([paper migration](surveys/paper-migration.en.md)); scripts rarely care about the performance of numeric types | §3.2 |
| Inferring function signatures (v0.1) | Signatures are contracts and should not change with the body | §4.6 |
| A JIT that compiles traces | The types are known at compile time, which gives the specialization that tracing a run would; generation ahead of time has no run to trace, so the two could not share one code generator | §12.2 |
| Inner blocks shadowing the locals of outer ones, as in C++, Rust and Swift | GDScript forbids it, so migrated code never does it; the restriction can be relaxed compatibly later | §4.6 |
| Cross-language inheritance at the language level | Depends on GDScript's internal implementation | §11.2 |
| Optional chaining `?.`, defaulting `??`, postfix `!` | Combined with Result's short-circuit return, the meaning of `x?.y` would depend on the type of x; methods suffice for Option | §3.4, §8.2 |
| A Swift-style `try` covering a whole expression | Which subexpressions are unwrapped would depend on types; Rust's postfix `?` is more direct | §8.2 |
| Chaining Results with `?.` as well | When the two types nest, one operator cannot say which layer it handles | §8.2 |
| A separate `apply:` block in a property for the code that must wait until the node is ready | Makes users think about when and how often logic runs; automatic suspension can be done by the compiler | §6.5 |
| Recording only a setter's raw input before ready | A setter that transforms and then stores its value (such as one adding 【】 around a character name) would be read untransformed before ready | §6.5 |
| `@late` (like `lateinit`) | The code that needs it is uncommon; a parent configuring a child is covered by the ancestor-assignment rule | §6.2 |
| Subclasses seeing only `pub` members | In the [second paper migration](surveys/paper-migration-2.en.md), 29 of 102 `pub` markers existed only for subclasses | §4.2 |
| A `@public` annotation for the public marker | It is written often, at least 22 times per 1,000 lines in the [member visibility survey](surveys/member-visibility.en.md) | §2.4 |
| Top-level types of a file becoming global names | Breaks "a file is a class" and needs a second global name table | §2.4 |
| Intersection types for interfaces, such as `@owner(Node2D & Combatant)` | A new concept; letting engine properties satisfy interface property requirements is enough | §3.9 |
| A tracing GC, or closures capturing self weakly by default | Would silently differ from GDScript | §3.11, §6.7 |
| Checking owner when nodes move | Taking a node out of its owner's subtree is a legitimate operation | §7.3 |
| Unreferenced scenes with missing values also counting as export errors | A `load` whose path is known only at runtime cannot be seen, so it cannot be concluded that the scene is unused | §7.5 |
| Strict checking for `as` to built-in types | Would silently differ from GDScript's constructor conversion | §5.3 |
| All object types in unaudited engine APIs being nullable | Virtual-method and signal parameters the engine passes in are almost never null, and this would make every handler check first; the rare null is reported by the entry checks | §10.2 |
| Promoting utility functions with mixed int and float to float | GDScript returns the argument unchanged, so the result would silently differ | §10.3 |
| `pop_front()` on an empty array being a program error | The engine returns null there without an error, so it would silently differ | §3.8 |
| `pop_at` returning `T?` as `pop_back` does | Real code uses `pop_at` to remove an element at a known index and does not test the result for null; `T?` would make every use unwrap it, while an index out of range is itself the error | §3.8 |
| Awaiting a multi-parameter signal yielding an Array, or destructuring | Real code almost never uses such results; destructuring can be added later | §9.6 |
| Using an if/else block as a value | Duplicates the conditional expression | §5.5 |
| A separate declaration for child nodes required by a base class, optional ones, and ones added at runtime | Checking by usage and `get_node_or_null` already cover the three cases; new declarations would only add concepts | §7.2 |
| Reflection handing over an encoded copy of a container member whose elements are of a type only this language has | Changes to the copy outside would not reach the container, which the explicit conversion of §3.8 avoids | §10.5 |
| Requiring types written in an override to match the overridden ones exactly | Stricter than GDScript, and rejects the covariant return types of fluent interfaces such as gdUnit4's | §4.6 |
| Merging nested Options into one level (as Kotlin does) | Generic code would behave differently depending on T; a None stored in a container could not be told from a missing value | §3.4 |
| Lambdas without async, inferred from the body or the expected type | Deciding whether a function is async would take several rules, and lambdas and method values could be passed to different places | §9.1 |
| Allowing `_init` and overrides of non-void engine virtuals to be async | Construction does not wait for initialization to finish; synchronous engine calls cannot obtain the eventual coroutine result | §9.1 |
| Async methods reporting their declared return type to the engine | Every await in GDScript would get a warning; the null sent on cancellation, written into a temporary of a value type, would crash the process | §9.8 |
| After a hot reload that changes declarations, letting instances created afterwards use the new version | A class would have two versions in one run, and code compiled against the old declarations could call new instances; the main use is only tuning objects that keep being created | §12.4 |
| After a hot reload that changes declarations, migrating state by member name as GDScript does | Members may have changed type; under static typing the moved values cannot be trusted | §12.4 |
| A compile error for `free()` and `set_script()` on self | Neither really occurs in the [corpus counts](surveys/corpus-counts.en.md); indirect cases, such as a handler freeing the emitter or a callee freeing its caller, cannot be detected before running, so the runtime check is needed anyway | §3.3 |
| Refusing keys that are not fields when decoding a struct | A message from a newer sender that carries more fields, or JSON written for several readers, would fail at the entry, though every field the struct needs is there | §3.6 |
