# Design notes and trade-offs

中文: [design-notes.zh.md](design-notes.zh.md)

This non-normative companion collects three parts moved out of the [language specification](language-spec.en.md): full designs for features after the first version, detailed rationales and corpus counts behind individual sections, and alternatives considered but not adopted. The language specification is authoritative for language rules; engine citations are listed in [engine-facts.en.md](engine-facts.en.md).

## 1. Post-v1 designs

### 1.1 User-defined generics (spec §2.4, §3.10)

- GDScript has no user-defined generics, so migrated code (including FPS and Ring) does not use them; because their spellings are compile errors in the first version, adding them later is compatible.
- **What may be generic**: functions, structs, enums, and RefCounted classes that do not extend Resource. Node and Resource scripts and autoloads cannot declare type parameters, because the engine provides no type arguments when instantiating them. Generic classes are not registered in the engine's global class table, so GDScript does not see them, since it cannot supply type arguments.
- **Spelling**: type parameters are written in square brackets after the name, matching `Array[int]` and Python 3.12 (PEP 695); a constraint is written `T: Interface`. A file's class declares type parameters on `class_name`, as in `class_name Cache[K, V] extends RefCounted`; an inner class writes `class Cache[K, V] extends RefCounted:`. In GDScript, `[` after an inner class name, the name in `class_name`, an enum name or a function name is a syntax error ([engine-facts.en.md](engine-facts.en.md)), so these declarations respect the syntax hard rule.

  ```gdscript
  func first[T](items: Array[T]) -> T?:
      return None if items.is_empty() else items[0]

  struct Pair[A, B]:
      var first: A
      var second: B

  enum Tree[T] { LEAF, NODE(value: T, children: Array[Tree[T]]) }

  func weakest[T: Damageable](units: Array[T]) -> T?:
      var best: T? = None
      for u in units:
          if best == None or u.hp < best.hp:
              best = u
      return best
  ```

- **Type arguments and inference**: at call sites type arguments are usually inferred from the arguments, and must be written out when they cannot be (as in `first[int]([])` or `Pair[int, String](first = 1, second = "a")`), or else `var x = first([])` is a compile error. `name[...]` shares its shape with subscripting and is disambiguated by name resolution: when the name resolves to a generic function or generic type, the brackets hold type arguments; otherwise they are a subscript.
- **Constraints and runtime retention**: constraints use interfaces, initially at most one per type parameter (unsatisfied constraints are compile errors), extendable later with the same spelling to multiple constraints, class constraints, and generic interfaces `interface Source[T]:` (spec §3.9). Type arguments are kept at runtime (architecture §6.1).
- **Reflection and Callables**: generic methods are not exposed through reflection (spec §10.5), because the engine and GDScript cannot supply type arguments when calling by name; methods the engine must find by name cannot be generic. Using a generic method as a Callable requires fixing its type arguments (as in `sig.connect(handle[int])`), and is a compile error when they cannot be determined.

### 1.2 Setters that wait for ready (spec §6.5)

- The [property accessor survey](surveys/property-accessors.en.md) found 25 setters that wait for node readiness with `await ready`. In the first version setters run immediately and accessing an `@onready` member or child before ready is a program error; this can later be relaxed compatibly so the compiler suspends automatically (whether to adopt it is an open question in `BACKLOG.md`):
  - at the first statement that needs the node to be ready, if the node is not ready yet, the setter suspends there and continues from that point once ready;
  - statements needing readiness are determined by static analysis: accessing `@onready` members, `$X` or children, or calling methods of the class (including overrides in subclasses) that access them;
  - accesses reachable only while `is_node_ready()` is true do not count, judged by the narrowing rules (spec §5.4): inside `if is_node_ready():`, after `if not is_node_ready(): return`, and on the right of `is_node_ready() and …`. Calling a method all of whose such accesses are guarded does not need readiness either. Only `is_node_ready()` counts, because `@onready` members may still be uninitialized while `is_inside_tree()` is true;
  - the suspension point is shown on hover in the editor;
  - when the same property is written again before ready, the earlier suspended call is cancelled at once, whether or not the new write suspends. Suspended calls resume after `@onready` initialization and before `_ready` in write order, and are dropped if the node is freed before ready; once ready, setters no longer suspend;
  - statements before the suspension point run immediately: setters normally transform and store the value before synchronizing nodes, so reads before ready see the transformed value. Deferring the whole setter and recording only the raw input would expose untransformed values before ready, as in Ring's `Runtime/AVGRuntime/UI/UI.cs:16-35`, which wraps character names in 【】;
  - users learn no new concept; handwritten `await ready` in a setter stays a compile error whose quick fix deletes it.

## 2. Section rationales and corpus evidence

### §1–§2 Delivery, lexical structure and surface syntax

- **GDExtension and bytecode-only exports (§1.3)**: the [pitfall catalog](surveys/pitfalls.en.md) has no item that only an engine module could fix; what a GDExtension cannot fix requires engine changes that a module cannot make either. Because the types of `$X`, `@parent` and `PackedScene[T]` depend on scenes (§7), compiling source at load time would mean re-analyzing scenes inside the game and shipping the analyzer to every export platform.
- **Preloaded scripts as classes (§2.1)**: in the [corpus counts](surveys/corpus-counts.en.md), 207 of 351 preloads of `.gd` files initialize constants, used in the same file with `new()` 54 times, in other calls 124 times, for other members 134 times, after `is` 69 times and as a type 46 times; 69 preloads are followed directly by `.new()`.
- **`null` alias and single-line quoted strings (§2.2)**: `null` occurs 22.2 times per 1,000 lines in the [corpus counts](surveys/corpus-counts.en.md), so making it a compile error would only add mechanical migration work. Multi-line single- or double-quoted strings occur 97 times in the corpus, 95 of them in `godot_dialogue_manager`'s tests; forbidding them reports a missing closing quote on its own line instead of swallowing following code.
- **No `@tool` in the first version (§2.3)**: running scripts in the editor requires full compilation on load plus instantiating and reloading in the editor, while 211 of the 326 `@tool` files in the [corpus counts](surveys/corpus-counts.en.md) are in plugin repositories and 58 in game repositories (31 of those in `godot-open-rpg`).
- **`pub` as a keyword (§2.4)**: written at least 22 times per 1,000 lines in the [member visibility survey](surveys/member-visibility.en.md), too frequent for a `@public` annotation.

### §3 Types

- **No implicit `float` to `int` (§3.2)**: `var hp = 10` is inferred as `int` in this language (§4.3) but is untyped in GDScript, where `hp = 2.5` leaves `2.5`; implicit truncation would silently yield a different result.
- **Object nullability and freed objects (§3.3)**: in the [corpus counts](surveys/corpus-counts.en.md), `is_instance_valid` appears 3.3 times per 1,000 lines (12.8 in `phantom-camera`); since Godot 4.4 the engine also treats freed objects as false in conditions ([godotengine/godot#93885](https://github.com/godotengine/godot/pull/93885)). See [pitfall catalog](surveys/pitfalls.en.md) G-07, G-08.
- **Two-level nested Options (§3.4)**: merging `T??` into `T?` makes generic code vary with `T` (`first[T]` on `Array[Enemy?]` could not tell an empty array from a `None` first element, and a generic cache would treat a stored `None` as a miss), nor could a missing JSON key be told from `null`. Without `?.`, nesting appears almost only in generics and container reads.
- **Read-only `self` and default operations on structs (§3.6)**: mutating methods require a write-back target, so calls on temporaries, getter results or loop variables would either fail or silently mutate a copy. Ignoring unknown keys on decode lets messages from newer senders or multi-reader JSON decode cleanly. Default `==`, `<` and hashing work out of the box as in a scripting language.
- **Enums (§3.7)**: engine enums are open because the engine produces out-of-range values (such as `Key` combined with modifier bits) and adds enum values in later 4.x releases on which the same build runs (architecture §6.3). In the [corpus counts](surveys/corpus-counts.en.md): `int` cast to enum with `as` occurs 10 times and `INT_AS_ENUM_WITHOUT_CAST` is ignored 4 times; enum names are used as Dictionaries 38 times and aliased 3 times; 8 of 258 enums have no value 0.
- **Containers (§3.8)**: untyped-view writes and lookups of incompatible values are program errors because the engine skips failed writes and continues, while lookups and `assign()` truncate `1.5` to `1`. Passing containers of language-specific types to the engine requires explicit `Array(hits)` so copies are never mutated by mistake. All 14 `pop_at` uses in the [corpus counts](surveys/corpus-counts.en.md) remove an element at a computed index without testing for null. Dictionary keys are copied and deep-frozen on insert because Dictionary caches each key's insertion hash and `make_read_only` cannot be undone: mutating a key in GDScript makes the entry unreachable under both old and new contents, while freezing the caller's container would make it permanently read-only.
- **Interfaces and no stateful mixins (§3.9)**: in the [cross-branch duplication survey](surveys/cross-branch-duplication.en.md), duplication across different native bases is ~4–10 lines per 1,000 lines in most games; 185 of its 353 lines in games can be removed by composition or static functions, and 72 of the 102 lines suited to stateful mixins come from Ring alone; duplication along the same native base is 4.9x and 8.2x larger (mostly in `tanks-of-freedom-ii`). In `gdUnit4`, 14 of 16 abstract-only classes extend `GdUnitAssert` and redeclare its methods with covariant return types (e.g. `is_null() -> GdUnitAssert` at `GdUnitAssert.gd:7` narrowed to `-> GdUnitIntAssert` at `GdUnitIntAssert.gd:7`). Generic interfaces are deferred so variance and self-referential constraints are not fixed without demand from real code.
- **Function types and lambdas (§3.11)**: in the [corpus counts](surveys/corpus-counts.en.md), coroutine methods are used as values 91 times (60 in `connect(name)`); none of the 961 lambdas in methods assigns to an outer local, while the 15 that assign through a member or subscript mutate objects or containers; 18 of 979 lambdas are named, and none has parameter defaults.

### §4 Declarations

- **Classes, `@abstract` and inner classes (§4.1)**: in the [implementation coverage survey](surveys/implementation-coverage.en.md), 4.9% of files use bare engine-base constants. In the [corpus counts](surveys/corpus-counts.en.md): 25 of 28 `@abstract` classes are in `gdUnit4`, and 17 file-level abstract classes have only abstract methods (rewritable as interfaces, unlike `godot-open-rpg`'s `BattlerAction`, which combines exported fields with an abstract coroutine); 192 inner classes appear across 121 of 2,800 files (37 in 19 game files), 7 nested in another inner class, 10 with `extends` at the start of the body, and 168 of 175 uses through an autoload in `godot-open-rts` (such as `Constants.Match.Units.PROJECTILES`). Resolving enclosing static functions and variables in inner classes matches Java, C# and Kotlin while preserving every name GDScript resolves.
- **Visibility (§4.2)**: in the [member visibility survey](surveys/member-visibility.en.md), ~25% of members whose names could be resolved are accessed from other files. In the [second paper migration](surveys/paper-migration-2.en.md), 29 of 102 `pub` markers would exist only for subclasses if subclasses could not see non-`pub` members.
- **Constants (§4.5)**: vector components (`real_t`) differ between single- and double-precision builds and transcendental functions such as `sin` vary in the last digit across math libraries, so engine-typed constants and float math functions are evaluated once when the class loads while compile-time checks rule out every value error. In the [constant-expressions survey](surveys/constant-expressions.en.md), 2,920 of 3,094 constants need no computation, 141 are scalar computations and 33 need the engine; all 7 constants in annotation arguments are literals, no enum value uses a constant, and none of the excluded forms appears.
- **Functions and rest parameters (§4.6)**: the [second paper migration](surveys/paper-migration-2.en.md) omits parameter types on 6 engine virtual overrides. In the [corpus counts](surveys/corpus-counts.en.md), 76 of 78 rest parameters are in `gdUnit4`'s assertion APIs. Without call-site spread it is easy to pass an array as a single argument by mistake, as Pixelorama's `_debug_msg` does when calling `_prefix_print` (`src/Classes/ObjParse.gd:59-66`). Forbidding local variable shadowing matches GDScript and can be relaxed compatibly later.
- **Static members (§4.8)**: the [corpus counts](surveys/corpus-counts.en.md) have 188 `static var` (29 uninitialized class-typed, such as `static var instance: DMPlugin`) and 4 `_static_init`. For GDScript's static initialization order and cycle issues see [godotengine/godot#104161](https://github.com/godotengine/godot/issues/104161), [#82141](https://github.com/godotengine/godot/issues/82141), [#104588](https://github.com/godotengine/godot/issues/104588).

### §5–§7 Expressions, lifecycle and scene model

- **Expressions and narrowing (§5.1–§5.4)**: `godot-open-rts` tests members with `"hp" in unit` 16 times. The [second paper migration](surveys/paper-migration-2.en.md) has 16 `(x as T).unwrap()` downcasts, and adds 4.4 locals per 1,000 lines because members do not narrow.
- **Lifecycle and destruction (§6.2–§6.7)**: for the underlying engine pitfalls see [pitfall catalog](surveys/pitfalls.en.md) G-02, G-03, G-04, G-05, G-09, G-10. In the [corpus counts](surveys/corpus-counts.en.md), registering a node on an autoload member in `_ready` occurs 6 times (5 in Ring), and `NOTIFICATION_PREDELETE` occurs 40 times (32 in `gdUnit4`).
- **Scene typing and differing structures (§7.1–§7.2)**: in the game repositories of the [scene structure survey](surveys/scene-structures.en.md), none of 2,023 literal paths resolves to different types across structures; among paths missing in some structures, 7 are template or placeholder scenes lacking a node (such as `tanks-of-freedom-ii`'s `base_ground.tscn`, preloaded as a placeholder tile while lacking `$"mesh"` used by `tile.gd`) and 8 use `get_node_or_null` (such as the trails on two vehicles in `Starter-Kit-Racing`). Rejecting `$X` missing from all scenes also catches stale paths after renames, such as `tps-demo`'s `door.gd:6` reading `$DoorModel/AnimationPlayer` when `door.tscn` names it `DoorModel2`.
- **Upward access and shared resources (§7.3, §7.6)**: in the [corpus counts](surveys/corpus-counts.en.md), `get_parent()` on self occurs 174 times (62 accessing a member directly across 46 files; 3 handling null, including a `beehave` setter running before the node is parented), and `owner` has a member accessed directly 49 times across 21 files. `owner` is checked on read rather than when nodes move because reading `owner` and then reparenting out of its subtree, as Ring's `DeathComponent` does, is legitimate. For unintended sub-resource sharing see `godot-open-rpg`'s `interaction_popup.tscn` (an embedded `CircleShape2D` not marked local to scene, mutated at `interaction_popup.gd:30` while one instance in `main.tscn:484-486` sets radius 64); for resource cycles see [pitfall catalog](surveys/pitfalls.en.md) G-19, G-20, G-34.

### §8–§13 Errors, coroutines, engine boundary and toolchain

- **Program errors and assertions (§8.1–§8.3)**: after an error GDScript returns a constructed default in debug builds and `null` in release builds while letting the caller continue, handing statically typed code fake values. Postfix `?` is not paired with `?.`, whose behavior on `x?.y` would depend on whether `x` is Option or Result. In the [corpus counts](surveys/corpus-counts.en.md), the 595 `assert` conditions are almost all pure queries, none contains `await`, and none of the 539 messages relies on eager evaluation when the assertion passes.
- **Coroutines and signals (§9.1–§9.7)**: in the [corpus counts](surveys/corpus-counts.en.md), only 35 of 979 lambdas contain `await` (33 in `gdUnit4` tests). For reentrancy and freed-awaiter pitfalls see [pitfall catalog](surveys/pitfalls.en.md) G-11, G-12, G-13 and proposals [godot-proposals#8838](https://github.com/godotengine/godot-proposals/issues/8838), [#6243](https://github.com/godotengine/godot-proposals/issues/6243). In the [await signal results survey](surveys/await-signal-results.en.md), only 1 of 1,356 awaits uses the result of a multi-parameter signal, and only 1 uses the result of an unknown-signature `Signal` (`godot_dialogue_manager` `:1956`, awaiting a two-parameter C# signal on a `RefCounted` receiver).
- **Engine boundary (§10.2–§10.6)**: Godot marks only ~50 APIs with `RequiredResult` (29 in `Tween`); objects passed into virtual methods and signals are almost never null, so treating unaudited incoming parameters as non-null with entry checks avoids boilerplate null checks in every `_input` and signal handler. The engine API has over 3,700 method parameters and ~460 properties narrower than `int64` or unsigned (for example `uint32` `collision_layer`, where `-1` wraps to `4294967295`).
- **Coexistence, threads and toolchain (§11.2, §12.3, §13.2–§13.4)**: for cross-language inheritance see [pitfall catalog](surveys/pitfalls.en.md) C-17; in the [second paper migration](surveys/paper-migration-2.en.md), Ring's `Brick` and `Enemy` brought 5 subclasses along, and 197 of 230 migration edits were mechanical. In the [corpus counts](surveys/corpus-counts.en.md), `Thread.new` appears 5 times and `WorkerThreadPool` twice, and real code mostly indents bracket continuation lines one level rather than the style guide's two. The GDScript formatter draft stalled partly because GDScript's parser discards literal spellings and parentheses ([godotengine/godot#76211](https://github.com/godotengine/godot/pull/76211)). A built-in test runner is included because `gdUnit4` and `GUT` require extending their GDScript base classes.

## 3. Alternatives considered but not adopted

| Alternative | Why not adopted | Current rule |
|---|---|---|
| Delivery as an engine module (v0.1) | The pitfall catalog has no item only a module could fix; a GDExtension works with the official editor and export templates | §1.3 |
| Narrow integer types such as i32 and u8 (v0.1) | The largest migration cost ([paper migration](surveys/paper-migration.en.md)); scripts rarely care about the performance of numeric types | §3.2 |
| Inferring function signatures (v0.1) | Signatures are contracts and should not change with the body | §4.6 |
| A JIT that compiles traces | The types are known at compile time, which gives the specialization that tracing a run would; generation ahead of time has no run to trace, so the two could not share one code generator | §12.2 |
| Inner blocks shadowing the locals of outer ones, as in C++, Rust and Swift | GDScript forbids it, so migrated code never does it; the restriction can be relaxed compatibly later | §4.6 |
| Cross-language inheritance at the language level | Depends on GDScript's internal implementation | §11.2 |
| Optional chaining `?.`, defaulting `??`, postfix `!` | Combined with Result's short-circuit return, the meaning of `x?.y` would depend on the type of x; methods suffice for Option | §3.4, §8.2 |
| A Swift-style `try` covering a whole expression | Which subexpressions are unwrapped would depend on types; Rust's postfix `?` is more direct | §8.2 |
| Chaining Results with `?.` as well | When the two types nest, one operator cannot say which layer it handles | §8.2 |
| A separate `apply:` block in a property for the code that must wait until the node is ready | Makes users think about when and how often logic runs; automatic suspension can be done by the compiler | §6.5 |
| Recording only a setter's raw input before ready | A setter that transforms and then stores its value (such as one adding 【】 around a character name) would be read untransformed before ready | §6.5 |
| `@late` (like `lateinit`) | The code that needs it is uncommon; a parent configuring a child is covered by the ancestor-assignment rule | §6.2 |
| Subclasses seeing only `pub` members | In the [second paper migration](surveys/paper-migration-2.en.md), 29 of 102 `pub` markers existed only for subclasses | §4.2 |
| A `@public` annotation for the public marker | It is written often, at least 22 times per 1,000 lines in the [member visibility survey](surveys/member-visibility.en.md) | §2.4 |
| Top-level types of a file becoming global names | Breaks "a file is a class" and needs a second global name table | §2.4 |
| Intersection types for interfaces, such as `@owner(Node2D & Combatant)` | A new concept; letting engine properties satisfy interface property requirements is enough | §3.9 |
| A tracing GC, or closures capturing self weakly by default | Would silently differ from GDScript | §3.11, §6.7 |
| Assigning captured variables as GDScript does, with a warning | The assignment would change neither the variable outside nor the next call, the opposite of what it reads as; no lambda in the corpus does it | §3.11 |
| A call of a function value of this language beginning a new chain, as a Callable the engine calls does | The caller would go on with the default value of the return type, a fake value, while a direct call of the same method aborts it | §8.1 |
| Checking owner when nodes move | Taking a node out of its owner's subtree is a legitimate operation | §7.3 |
| Unreferenced scenes with missing values also counting as export errors | A `load` whose path is known only at runtime cannot be seen, so it cannot be concluded that the scene is unused | §7.5 |
| Strict checking for `as` to built-in types | Would silently differ from GDScript's constructor conversion | §5.3 |
| All object types in unaudited engine APIs being nullable | Virtual-method and signal parameters the engine passes in are almost never null, and this would make every handler check first; the rare null is reported by the entry checks | §10.2 |
| Promoting utility functions with mixed int and float to float | GDScript returns the argument unchanged, so the result would silently differ | §10.3 |
| `pop_front()` on an empty array being a program error | The engine returns null there without an error, so it would silently differ | §3.8 |
| `pop_at` returning `T?` as `pop_back` does | Real code uses `pop_at` to remove an element at a known index and does not test the result for null; `T?` would make every use unwrap it, while an index out of range is itself the error | §3.8 |
| Awaiting a multi-parameter signal yielding an Array, or destructuring | Real code almost never uses such results; destructuring can be added later | §9.6 |
| Using an if/else block as a value | Duplicates the conditional expression | §5.5 |
| A separate declaration for child nodes required by a base class, optional ones, and ones added at runtime | Checking by usage and `get_node_or_null` already cover the three cases; new declarations would only add concepts | §7.2 |
| Reflection handing over an encoded copy of a container member whose elements are of a type only this language has | Changes to the copy outside would not reach the container, which the explicit conversion of §3.8 avoids | §10.5 |
| Requiring types written in an override to match the overridden ones exactly | Stricter than GDScript, and rejects the covariant return types of fluent interfaces such as gdUnit4's | §4.6 |
| Merging nested Options into one level (as Kotlin does) | Generic code would behave differently depending on T; a None stored in a container could not be told from a missing value | §3.4 |
| Lambdas without async, inferred from the body or the expected type | Deciding whether a function is async would take several rules, and lambdas and method values could be passed to different places | §9.1 |
| Allowing `_init` and overrides of non-void engine virtuals to be async | Construction does not wait for initialization to finish; synchronous engine calls cannot obtain the eventual coroutine result | §9.1 |
| Async methods reporting their declared return type to the engine | Every await in GDScript would get a warning; the null sent on cancellation, written into a temporary of a value type, would crash the process | §9.8 |
| After a hot reload that changes declarations, letting instances created afterwards use the new version | A class would have two versions in one run, and code compiled against the old declarations could call new instances; the main use is only tuning objects that keep being created | §12.4 |
| After a hot reload that changes declarations, migrating state by member name as GDScript does | Members may have changed type; under static typing the moved values cannot be trusted | §12.4 |
| A compile error for `free()` and `set_script()` on self | Neither really occurs in the [corpus counts](surveys/corpus-counts.en.md); indirect cases, such as a handler freeing the emitter or a callee freeing its caller, cannot be detected before running, so the runtime check is needed anyway | §3.3 |
| Refusing keys that are not fields when decoding a struct | A message from a newer sender that carries more fields, or JSON written for several readers, would fail at the entry, though every field the struct needs is there | §3.6 |
| Compile errors for `sort`, `min`, `max`, `hash` and the like on containers whose elements are of a type only this language has | GDScript code calls them, and migrated code would have to be rewritten; the runtime carries them out with the operations of this language | §3.8 |
| Leaving container fields out of a struct's hash, or giving structs `==` and hashing without `<` | Which fields take part is the user's choice, not the implementation's; out of the box, the defaults work together, and struct methods can redefine them later | §3.6 |
| Forbidding structs with container fields as Dictionary keys | GDScript allows containers as keys; read-only copies keep the stored hash valid | §3.8 |
| Making the original read-only when it becomes a key | `make_read_only` cannot be undone, so the caller's container, and anything else holding it, could never be changed again | §3.8 |
| `min()` and `max()` returning `T?`, as GDScript's null on an empty array would suggest | The null is a value the element type does not have, which GDScript hands on in silence; the program error says where an empty array was not expected | §3.8 |
| The compiler computing every constant, operations on engine types included | Vector components are float or double depending on how the engine is built, and bytecode compiled once can fix only one of the results; the compiler would also rewrite the engine's operations | §4.5 |
| Computing constants with the engine at compile time | The compiler would depend on the engine, and compiler tests could either not test constants or need the computation written again in the test stub | §4.5 |
| Computing every constant when the class loads | Annotation arguments and enum values would have no value at compile time, and errors such as `10 / 0` would wait until loading | §4.5 |
| Strings in single or double quotes that span lines, as in GDScript | A missing closing quote would be reported far away; the corpus has 97 such strings, 95 in the tests of one repository | §2.2 |
| Inner classes resolving, of the classes enclosing them, only constants, enums and inner classes, as GDScript does | GDScript's restriction is a by-product of its lookup; static members need no instance, and Java, C# and Kotlin let nested classes use them by name | §4.1 |
| Static variables of object types without an initializer starting as None, as in GDScript | A non-null type has no None value; `T?` is written where an empty value is needed | §4.8 |
| Untyped containers converting implicitly to typed ones, as in GDScript's static checks | In GDScript this succeeds at runtime only when the container is exactly of that type, so the implicit conversion hides a check that always happens at runtime; an explicit `is` spells it out | §3.8 |
| Skipping a write of a value that does not fit the element type through an untyped view, as the engine does | The program goes on without the value it meant to write; for lookups, the engine also truncates 1.5 to 1 | §3.8 |
| `as` making a value in a Variant that is not an object a program error, as GDScript's debug builds do | `as` is a conversion that may fail and is None when the type does not match; `v is Node` is false there as well | §5.3 |
| A literal that goes into a Variant typed by its elements too | An empty literal has nothing to be typed by, so `d[k] = []` would need a type; with elements it would be a typed container, into which writing a value of another type through a Variant is then a program error, while GDScript allows it | §3.13 |
| Checking cycles between static initializations of different classes at compile time | It would need to know what the initialization of other files reads; such a cycle is reported every time a run loads those classes | §4.8 |
