# Petrichor 实现架构

**草案 · 2026-10-29** · English: [architecture.en.md](architecture.en.md)

本文记录实现层面的决定：组件划分、值的表示、测试和推进顺序。语言规则以[语言规范](language-spec.zh.md)为准。实现中发现规范有问题时，单独提交修改规范，不在实现中放宽规则。引擎事实对照 Godot 4.7.2-stable（提交 `ed1daf0`）核对。

## 1. 已定的选择

- **C++17、godot-cpp、SCons。** 解释器要在 iOS 和主机上运行（规范 §12.2），以后还可能改为引擎模块（§1.3）。引擎用 C++17 编译（`SConstruct:916, 921`），引擎模块只能用 SCons 构建，所以本项目也用这两者。godot-cpp 从 v10 起独立于 Godot 编号，一个版本可以面向多个 Godot 版本；本项目把它固定在某个提交，以 `api_version=4.7` 构建。引擎提高 C++ 标准之前，本项目也不提高：C++20 只带来写法上的方便，解释器可能用到的强制尾调用是编译器扩展，与标准无关。
- **目标引擎是 Godot 4.7。** 扩展声明的最低版本是 4.7，引擎加载最低版本不高于自身版本的扩展（`core/extension/gdextension_library_loader.cpp:315-329`），所以之后版本的引擎也会加载同一个构建；但只对照 4.7.2 核对过。要在这些版本上运行，引擎的值还须保持本构建依赖的布局：Variant 先存类型，数据从第 8 字节起，其中的对象存为 ObjectID 和指针（`src/runtime/values.h`）；各内置类型占用的字节不超过字节码为它预留的，运行时在加载时检查这一点。
- **导出的游戏只含字节码**（规范 §1.3）。`.gdextension` 按功能标签为编辑器和导出模板选择不同的库（`gdextension_library_loader.cpp:82-96`）：编辑器用的库包含编译器，导出模板用的库只含运行时。
- **寄存器按静态类型存放原生值。** GDScript 即使在静态类型已知时，寄存器也是 Variant（`modules/gdscript/gdscript_vm.cpp:536`），运算经函数指针在 Variant 上进行（`:848-862`），调用引擎方法时也传 Variant 指针（`:2273-2313`）。本语言用全静态类型省掉这些开销，这是“明显快于 GDScript”（规范 §12.2）的主要来源。引擎方法目前按名字调用（§2.6）。
- **从编辑器运行时，游戏读取编辑器写好的字节码，自己不编译**（§2.4）。

## 2. 组件

| 组件 | 依赖 | 内容 |
|---|---|---|
| compiler | 不依赖 Godot | 词法和语法分析、语义分析、场景检查、带类型的 IR、字节码生成、诊断、符号索引 |
| bytecode | 不依赖 Godot | 编译结果的格式、序列化和校验，compiler 与 runtime 共用 |
| runtime | godot-cpp | 字节码加载、虚拟机、值和类型描述、任务、程序错误、引擎边界上的检查和转换 |
| adapter | godot-cpp、runtime；编辑器用的库还依赖 compiler | 脚本语言、脚本和脚本实例三个扩展接口，资源的加载和保存，导出插件，编辑器插件，无界面命令 |

### 2.1 compiler

- 不包含 Godot 的头文件，构建时编译器的源码看不到 godot-cpp 的头文件路径。因此它的测试是普通的 C++ 程序，不必启动引擎；改为引擎模块时它也可以原样使用。
- 外部信息经接口取得：
  - 引擎 API：类、方法、属性、信号、enum、内置类型的运算符表；
  - 项目：场景、资源、autoload、全局类；
  - GDScript 类的静态视图（规范 §11.1）；
  - 绑定审核的数据（§10.3），作为数据文件放在仓库中（`src/compiler/binding_metadata.txt`）。
  在编辑器和无界面模式中，这些接口由 adapter 实现：引擎类来自 ClassDB，因为其他扩展的类和更新版本引擎的 API 都不在 godot-cpp 附带的 `extension_api-4-7.json` 中；场景来自引擎读出的场景状态（SceneState），所以文本和二进制场景、实例都按引擎的理解读取；GDScript 类来自 Script 的反射接口。内置类型（运算符、成员、方法、构造函数）和工具函数是例外：ClassDB 不描述它们，引擎也没有让扩展列举它们的接口，所以编辑器和测试都使用构建时从这个 JSON 生成的表；它们不随扩展变化，更新版本的引擎只会增加。引擎自己的可空性元数据（RequiredResult 和 RequiredParam，规范 §10.2）也是这样：ClassDB 的方法信息不带它（`core/object/method_info.cpp:37-51`），所以同样从 JSON 生成，并与审核数据合并；其他扩展的类按 §10.2 的默认规则处理。测试中的引擎类和场景目前由测试手写。
- 流程：词法 → 语法树 → 语义分析（名字、类型、收窄、match、泛型、接口、可见性）→ 场景检查（§7）→ 带类型的 IR → 字节码、调试信息和类的元数据。
- IR 由显式的基本块和虚拟寄存器组成，不是 SSA。每条指令都有类型和源码位置。语法糖在生成 IR 时展开：`?` 的提前返回、链式赋值的写回（§3.6）、await 的挂起点、match 的分支、就绪前 setter 的挂起（§6.5）。字节码与 IR 基本一一对应，虚拟寄存器分配为栈帧中的槽位。寄存器中 struct 的字段也是寄存器，是 struct 字节上的视图，没有自己的槽位，所以读写字段既不复制也不需要专门的指令；凡是推理寄存器的处理，例如复用槽位、找出挂起的协程要保留的槽位，都把视图当作它所视的寄存器的一部分，把写视图当作对那个寄存器的部分写入。struct 在所有字段求值之后构造到新的寄存器中，所以为它读取的字段不会先被覆盖。
- 常量表达式（规范 §4.5）在类型检查时随每个表达式求出：编译器算出标量和容器的结构，引擎类型的部分保留为运算，写进字节码的常量表，由运行时在类加载时算一次（§2.2）。编译期的算法与虚拟机的指令相同，例如 int 的回绕，因为同一表达式在函数体中由虚拟机计算。
- 第一版每次都重新分析整个项目，不做增量。各阶段只依赖自己的输入，以后可以按需加缓存，不改接口。
- 语法树建在无损的 token 流上：词法分析保留原文，给出每个 token 的字节偏移和长度；行列只在报告时由每个文件的行首表换算，列按码点计。解析器读取的语法 token 是一列；注释、行尾的 `\` 和非法字符是另一列 token（trivia），同样按偏移排列；Newline、Indent、Dedent 长度为零。两列按偏移合并后，token 之间只剩空白，拼接即是原文，空行由偏移得出。注释不放进语法 token 一列，所以解析器的前瞻不必跳过它们；用到注释的地方，格式化、`##` 文档注释、判断光标是否在注释中，都按偏移查找。GDScript 同样把注释另存为按行号的表，解析器按行号取文档注释（`modules/gdscript/gdscript_parser.cpp:4066-4106`）。语法树的每个节点记下首尾语法 token 的下标，括号算在节点之内；名字和运算符在各自的字段旁记下自己的 token 下标，因为引用表需要每个名字的位置，而一个节点可以有多个名字（`Combat.Damageable`、`Hit(damage = 3)`）。解析器合成的节点，如 `elif` 变成的 if，取它所来自的源码的范围。token 表、trivia、行首表和原文合为一个源文件对象，由语法树持有。诊断是字节区间，每处检查选择它指向的部分：整个表达式、名字或运算符；Godot 的接口只取起点的行列（`core/object/script_language_extension.h:322-330`）。快速修复的编辑区间和格式化同样以 token 为单位。没有采用无损的具体语法树（Roslyn、rust-analyzer 的 red-green 树）：它要重写解析器，检查器也要改为经视图读取；而格式化器大多建在 AST 和 token 上（gofmt、zig fmt、Ruff、dart_style），建在这种树上的 Biome 同样要把注释取出来重新挂到节点上（[`biome_formatter/src/comments.rs`](https://github.com/biomejs/biome/blob/main/crates/biome_formatter/src/comments.rs)）。GDScript 的解析器只保留与执行有关的 token，向引擎提交的格式化器因此丢失了字面量的写法和括号（[godotengine/godot#76211](https://github.com/godotengine/godot/pull/76211)）。
- 名字的解析记在引用表中：检查器在每个解析名字的地方记下一条，含位置、所指声明的标识和角色，角色分声明和引用。位置在 `.pet` 中是字节区间，不是 token 下标，因为字面量中的方法名和属性名（规范 §10.4）以及 `$"Head/Camera"` 的各段只是字符串 token 的一部分；在场景中是场景路径、节点路径、种类和键，因为场景经 SceneState 读取，没有偏移。声明的标识由种类、作用域和名字组成，按值比较，跨文件稳定：本语言的成员是类的路径加成员名，struct 的字段写作 `Hit.damage`；局部变量和参数是文件路径加声明的偏移；场景节点是场景路径加节点路径；引擎成员是类名加成员名；GDScript 类的成员与本语言的形式相同而种类不同。同一处源码可以有多条：脚本挂在两个场景中时，`$Head/Camera` 指向两个场景各自的节点。解析不出的名字，例如经 Variant 的成员和动态调用，记为只有名字的未解析标识。覆盖或实现另一声明的声明条目带上被覆盖者的标识，重命名沿这些关系找全所有相关的声明，跳转到定义仍到子类的方法；clangd 的索引（`RelationKind::OverriddenBy`）和 clang 的索引库（`SymbolRole::RelationOverrideOf`）同样记下这一关系。表属于产生它的那次检查，即一个 `.pet` 文件，重新检查时整份替换；场景中的引用，即信号连接中的方法名、节点路径和导出属性的键，在检查挂载该场景的脚本时写入这个脚本的表，场景改变时这个脚本本来就要重新检查；检查其他脚本的声明时不记录。跳转到定义按位置查表，查找引用和重命名反查；重命名执行时按当前文本核对每一处，对不上就放弃；未解析的同名候选，以及 GDScript 中的同名调用，只列出供确认（规范 §13.3）。补全不用这张表，取光标处的类型和作用域。依据：clangd、Dart 和 Swift 的 IndexStore 同样在检查时记下每处引用，clangd、sourcekit-lsp 和 gopls 在重命名时都按当前状态重新核对，IntelliJ 经扩展点让非代码文件参与重命名，JetBrains 的 Godot 插件就这样处理 `.tscn`（[godot-support](https://github.com/JetBrains/godot-support/blob/master/gdscript/src/main/resources/META-INF/plugin.xml)）。GDScript 的语言服务器没有这张表，查找引用时在每个脚本中按文本搜索名字，再逐处重新解析（`modules/gdscript/language_server/gdscript_workspace.cpp:434-500`），字面量和场景中的引用都找不到。
- 有语法错误时，诊断只报语法错误，与 GDScript 相同（`modules/gdscript/gdscript_editor.cpp:150-153`）；补全、悬停和跳转在恢复后的语法树上运行检查（同一文件 `:3441-3442`）。补全在光标处插入一个占位的标识符再解析，只检查光标所在的成员。编译有语法错误时同样运行检查器，丢弃它的诊断，不生成 IR，所以每个特性对恢复后的语法树的处理始终受到检验。恢复以行为单位：出错时只丢弃本行余下的 token，已解析的部分保留，缺少的表达式和类型由错误节点填补，范围是被丢弃的 token；行后的块照常解析，挂到本行的语句或函数上，本行未形成语句时挂到一条错误语句上。GDScript 同样在 `if` 的条件出错后照常解析它的块（`modules/gdscript/gdscript_parser.cpp:2366-2373`）。括号内的换行不起作用，所以未闭合的括号会吞掉其后的行结构，而这正是边输入边编辑时最常见的状态。词法分析先找出文本始终没有闭合的括号，再扫描一遍，在其后第一个“下一行缩进不深于括号所在行、且不以闭括号开头”的换行处视为它已闭合，所以 `print("a",` 之后同一缩进的 `set_process(true)` 仍是下一条语句；这条规则只作用于未闭合的括号，合法的文件不受影响。缩进更深的行仍可能被读进括号，例如 `func f(` 下的函数体，所以解析器在括号内出错时，本行止于括号内的下一个换行：词法分析把它当作真正的换行重新扫描，解析器再解析一遍。Ruff 的 Python 解析器同样重新扫描括号内的换行（[`ruff_python_parser/src/lexer.rs`](https://github.com/astral-sh/ruff/blob/main/crates/ruff_python_parser/src/lexer.rs) 的 `re_lex_logical_token`），但只凭语法决定，下一行能接在括号内的内容之后时，如上面的 `set_process(true)`，就被读成实参。一个原因只报一条错误，报在错处，用错误本身的说法：始终没有闭合的括号在开括号处报一次，解析器在它闭合之前发现的问题不再报；词法分析已报错的行，解析器不再报；漏掉的逗号报在应有逗号的地方；多出的闭括号报为不匹配。参照的是 CPython 3.10 和 rustc 的报错，二者都在开括号处报未闭合的括号，CPython 并提示漏掉的逗号（[What's New In Python 3.10](https://docs.python.org/3/whatsnew/3.10.html)）。检查器把错误节点当作类型 Error，不因它再报错。格式化器不处理有语法错误的文件。
- lint 是检查器中的检查，读带类型的语法树，作为警告给出，与编译器的警告共用诊断和 `@warning_ignore`（规范 §13.2）。快速修复和自动修复是 token 区间上的文本替换，各自标明能否自动应用；一起应用时跳过区间重叠的修复，应用之后重新检查。
- 格式化器自己决定注释的归属，缩进减少处的注释按列号归入所在的块。验收先做到去掉所有规则时逐字节原样输出，再加三项检查：语法树不变，第二次格式化不再改动，注释全部保留。

### 2.2 runtime

- 值：int、float 各占 8 字节；引擎的内置值类型就地存放，按引擎的规则复制和析构；String、Array、Dictionary 使用引擎的类型；Variant 是一种槽位类型；Option 和带载荷的 enum 使用自己的布局，带判别字段；struct 把字段依次存放，每个字段按自己的布局，所以字段就是 struct 槽位内的一个槽位，verifier 从类型表而不是从字节码的槽位列表得出这些槽位。struct 的 `==` 是一条指令，按类型表逐字段比较。
- 元素是本语言独有类型的容器（规范 §3.8），或元素是这种容器的容器，是元素为 Callable 的引擎容器，每个元素装在不可变的盒子里：盒子是用本库的 token 创建的自定义 Callable（`core/extension/gdextension_interface.cpp:1617-1631`），数据是元素的类型和值，类型取自按类型键登记、比类映像活得久的登记表；盒子不能调用。引擎经盒子的 equal 回调比较 Callable（`core/variant/callable.cpp:265-288`，`gdextension_interface.cpp:85-93`），`has`、`find`、`count`、`erase`、容器的 `==` 和 Dictionary 的查找经 `hash_compare` 走到这里（`core/variant/variant.cpp:3351-3355`），所以这些操作，以及只移动元素的操作，由构造保证按本语言的语义进行。运算表中没有 Callable 的大小比较（`core/variant/variant_op.cpp:731-791`），Callable 的哈希在创建时算一次（`gdextension_interface.cpp:221-227`）；所以元素的盒子没有 hash 回调，不花哈希的时间，键的盒子内容只读（规范 §3.8），创建时哈希其内容：引擎类型的值用引擎的哈希，它把所有 NaN 和正负零各视为相等（`core/templates/hashfuncs.cpp:39-64`），对象按 ObjectID，T? 按标记和值，struct 按顺序哈希字段，容器按内容。其余的由运行时完成：`sort` 经引擎的 `sort_custom`，用一个按本语言 `<` 比较的比较器 Callable，`bsearch` 经 `bsearch_custom`，`min`、`max` 和容器的 `<` 用同样的比较，`hash` 和 `has_all` 经盒子计算，深复制（`duplicate(true)`、`duplicate_deep`、深的 `slice`）在引擎之后复制盒子内部。`resize` 之后由编译器生成的代码把每个新元素设为默认值，因为 struct 字段的默认值只有编译器知道；元素是容器时也这样，引擎只会填入无类型的容器。哪些方法修改容器取自引擎的 API 描述，运行时按名字列出插入键、交出键以及要由它完成的方法。插入键时存入每一层都只读的副本，交出的键在类型可能含容器时，若尚未只读就地设为只读；虚拟机在每个修改容器的操作之前检查 `is_read_only()`，因为引擎在这里只报错（`core/variant/array.cpp:518`），或不报错地写入一个临时值（`array.cpp:104-108`）。一条指令把值装箱；从 Variant 转换时拆开类型完全相同的盒子；`Array(hits)`、`Dictionary(d)` 按规范 §10.1 编码。代价是每个元素一个盒子；不逃逸的容器以后可以由逃逸分析换成私有表示。
- 对象：不是 RefCounted 的对象存为 ObjectID 和指针，访问时检查是否存活（规范 §3.3）；RefCounted 持有强引用；`weak` 不持有引用（§3.12）。本语言实例的成员由实例和正在它上面运行的调用共同持有：引擎在方法运行中删除实例（`free()`、`set_script`）时只把成员标记为已释放，之后访问成员或 self 是程序错误，最后一个持有者退出时才析构成员。
- 每种类型有一个类型描述，提供复制、移动、析构以及与 Variant 的相互转换（§10.1、§10.8）。编译器为每个栈帧生成槽位的类型表，析构、协程挂起时搬移栈帧、调试器显示局部变量都依据它。
- 常量表在类加载时求值一次：引擎类型的构造、运算、数学函数和字段经引擎的接口计算；算出的标量写回常量表，供读取标量的指令使用；容器逐层设为只读，同一个常量的每次使用读到同一个容器。加载资源的常量只在被按名字读取时加载（规范 §4.5）。
- 编译好的函数不可修改，带版本。只改函数体的热重载替换类的函数表，正在运行和挂起的栈帧继续使用旧版本（§12.4）。
- 协程的栈帧放在堆上，按归属组成树，取消沿树传递（§9.3）。对象被释放的通知来自运行时自己的实例绑定：一个对象可以同时持有多个标识不同的实例绑定（`core/object/object.cpp:2167-2201`），所以运行时的绑定与 godot-cpp 的绑定不冲突；是否报错在脚本语言的每帧回调中判定（§9.7）。
- 程序错误沿本语言的调用栈展开，释放局部变量，回到引擎的调用入口，由入口返回该类型的默认值（§8.1）。
- 对本语言类的方法的调用不经过引擎：虚拟机找到对象上本语言的实例，静态方法则找到类的脚本当前的镜像，按名字找到方法，比较方法的签名与调用方编译时记下的是否相同，再按槽位的原生布局传递参数和结果（§8.1）。同一次运行中的脚本总是一起编译的（§12.4），只有不是一起构建的字节码会使签名不同，这时调用是程序错误。调用引擎方法时，应把原生值的指针直接传给 ptrcall，目前按名字调用（§2.6）；从引擎进入时做入口检查（§10.1）。
- 虚拟机可以在任意线程上运行，不使用没有锁保护的全局可变状态（§12.3）。
- 运行时直接使用 godot-cpp 的类型（Variant、String、Object 等），不经过中间层。它们与引擎内部的同名类型对应，改编为引擎模块时，运行时要换用引擎头文件中的类型，adapter 要重写（§2.3），编译器和字节码可以原样使用（§2.1）。
- 第一版只用 switch 分派，所有平台只有一条代码路径需要测试。GDScript 在 GCC 和 Clang 上用 computed goto（`modules/gdscript/gdscript_vm.cpp:254-450`），本语言的主要优势在按类型存放的寄存器，不在分派。每条指令的处理只写一次，解释器的状态集中在少数局部变量中，以后可以从同一份定义生成 computed goto 或尾调用分派，是否加入由 §4 的基准决定。switch 分派无论如何都要保留，因为并非所有工具链都保证尾调用，例如 MSVC 的 debug 构建。
- 原生代码按规范 §12.2 生成：一个多后端的代码生成模块，运行时生成和事先生成都用它，以函数为单位编译。生成时机暂不决定（§6）。CPython 的 JIT 是前车之鉴：它以 trace 为单位，用 copy-and-patch 生成代码，到 3.15 只比解释器快 4–12%；作者在 [PEP 836](https://peps.python.org/pep-0836/) 中提出改为按方法编译，指导委员会认为这份计划在维护、性能的评估方法以及与调试和性能剖析工具的配合上都说得不够，PEP 于 2026-10-19 撤回，这个 JIT 将从 CPython 中移除。所以本语言的代码生成从一开始就要让调试器、程序错误的位置和性能剖析在原生代码下可用（保留与行号和槽位的对应，或在调试时改用解释器），并在动手之前定好基准和要达到的目标。

### 2.3 adapter

- 实现 ScriptLanguageExtension、ScriptExtension 和 ScriptInstanceExtension，把实例的属性读写、方法调用和通知转给 runtime。
- `.pet` 源码和字节码文件的加载与保存。
- 导出插件：用字节码替换 `.pet`，与 GDScript 替换为 `.gdc` 时一样，经 `add_file(..., true)` 生成重映射（`modules/gdscript/register_types.cpp:99-116`）。
- 编辑器插件：分析服务（§13.1）、场景编辑器中的错误标记、带场景部分的重命名和撤销（§13.3）、运行前的编译。
- 无界面命令：运行同一套分析，有编译错误时以非零退出码结束（§13.1）。

### 2.4 编辑、运行、导出和热重载

- 编辑：分析服务在编辑器进程中持有整个项目的编译结果，源码或场景改变时重新编译，诊断显示在脚本编辑器和场景编辑器中。
- 编辑器加载脚本时只编译声明（类头、成员、签名），足以提供导出属性和方法的反射信息，但不能运行：这时不能加载使用这个脚本的场景，引擎把同一线程上的这种加载当作循环加载拒绝（`core/io/resource_loader.cpp:1049-1056`）。带函数体和场景检查的完整编译在加载之外进行：编辑时的检查、保存、运行前的构建和导出。只编译声明时不读场景，所以由场景定型的成员（如 `@onready var camera = $Head/Camera`）这时是 Variant，完整编译后才有类型。编辑器中只有 tool 脚本会运行本语言的代码，支持 tool 脚本时，在加载后补一次完整编译。
- 从编辑器运行：运行前编译（编辑器插件的 `_build`），字节码写入 `.godot/petrichor/`；游戏进程只读取它。理由：`$X` 等的类型取决于场景（规范 §7），游戏进程自己编译就要重新分析整个项目的场景，启动变慢，也可能与编辑器得出不同的结果。
- 无界面命令同样把字节码写入 `.godot/petrichor/`，测试和 CI 用它代替编辑器。
- 导出：导出插件把字节码放入导出包（§1）。
- 首次发布前字节码不设版本号。文件带有其格式的标识，即构建时对 `src/bytecode/` 计算的哈希，只有标识相同的构建才读取它；因此由同一份源码构建的编辑器库与导出模板一致。运行前的构建会重新编译所有脚本；带着源码加载的脚本还会用源码的哈希检查字节码是否正是由这份源码编译的，不是则要求重新构建，而不运行过时的代码。
- 热重载：保存脚本时编辑器重新编译，经调试连接通知游戏，游戏从 `.godot/petrichor/` 重新加载该脚本。只改了函数体时，运行中的实例换用新代码；声明有变化时，游戏保留原来的代码，并且直到重新运行都不再应用任何重载（规范 §12.4）。

## 3. 测试

测试来自规范、引擎和真实代码三个方面，不从实现反推：

- **规范一致性**：§15 的每一行写成测试。编译期的检查放在 compiler 的测试中，不启动引擎；运行时的行为放在引擎测试中。
- **引擎兼容**：一个以无界面模式运行的 Godot 测试项目，检查脚本的挂载、保存和重新加载，GDScript 与本语言之间双向的调用，以及生命周期：await 期间所属对象被释放、信号源被释放、信号同步发出后再次挂起、同一个挂起点被恢复两次、GDScript 调用本语言后本语言再等待外部信号。
- **真实代码**：[第二次纸面迁移](surveys/paper-migration-2.zh.md)中的 FPS 和 Ring 代码真正运行起来。

编译器测试经同一个辅助函数编译源码，它对每段源码检查 §2.1 的约定：token 流无损；节点的范围依次嵌套，名字 token 的原文等于名字；每条文本引用的原文等于所指声明的名字，检查器解析的每个名字都有一条引用。对没有错误的源码，它还把每一行从中间截断后再编译，要求不崩溃、只报语法错误、其他行的语句都还在语法树上；截断留下未闭合的括号时，括号所在行之后缩进比它深的行不在此列（§2.1）。这样每个新特性的测试同时检验这些约定，不靠另写。语法错误的报错另有一组用例，取边输入边编辑时的典型错误，逐条写明位置和措辞（§2.1）。`tests/engine` 中的 `.pet` 文件是真实代码，但编译器测试没有真实的引擎 API，对它们只检查 token 流、节点的范围和截断后的解析。

每个引擎测试都写明它预期的错误：错误的文字，脚本的错误还有位置；出现其他任何错误都算失败。运行器启动的导入不做检查，因为 Godot 4.7.2 的编辑器在导入后立即退出时可能崩溃（Godot issue #111048）。

## 4. 性能

与 GDScript 比较四组基准，分别测量虚拟机本身和跨引擎边界的开销：

| 基准 | 测量内容 |
|---|---|
| 启动与编译 | 冷启动、重复运行、修改代码后重新运行 |
| 纯计算 | 整数和浮点循环、数组、函数调用、泛型 |
| 引擎边界 | 属性读写、调用引擎方法、Callable、信号 |
| 分配 | 带载荷的 enum、闭包、协程挂起、创建对象 |

比较使用优化过的构建，不用 `dev_build`。是否生成原生代码、优化哪些路径，由这些数据决定。

目前 `benchmarks/` 中有六个纯计算的基准，每个都有一个计算相同结果的 GDScript 版本，由运行器比较两者的结果。在官方 4.7.2 发行版上、一台 Windows 机器上（2026-10-29），以毫秒计：

|---|---:|---:|
| int_loop | 34.1 | 21.8 |
| float_loop | 25.9 | 24.4 |
| calls | 78.2 | 18.1 |
| members | 30.2 | 22.0 |
| vectors | 33.9 | 29.5 |
| arrays | 40.9 | 80.0 |

## 5. 推进顺序

1. **引擎接入**，不含语言：扩展在 4.7.2 的编辑器中加载；能新建 `.pet` 脚本并挂到节点上，保存场景后重新打开仍然有效；一段写死的行为响应 `_ready`；属性和方法出现在检查器中，可以从 GDScript 调用；导出插件替换文件。验收：真实场景在编辑器中和导出后都能运行。
2. **探针**：在运行的引擎上验证规范中只由源码推出的几处：
   - 撤销合并：`history_changed` 加 `MERGE_ALL`（规范 §13.3）；
   - 跨语言 await，两个方向（§9.8）；
   - GDScript 对本语言类的静态检查：`new` 和成员的类型（§11.3）；
   - 运行时自己的实例绑定在对象释放时收到回调，不影响 godot-cpp 的绑定（§9.7）。
   探针不成立时，回到规范讨论。
3. **最小编译链**：语言的一个子集，包括 `extends Node`、带类型的成员、函数、int 和 float 的运算、if 和 while、调用引擎方法、`_process`。验收：脚本挂进场景运行，GDScript 能调用它，断点能停下，修改函数体能热重载。
4. **第一个里程碑**：第二次纸面迁移中的 FPS 代码真正运行。功能按需要加入，§15 中对应的行同时写成测试。引擎测试复制该项目，逐个替换已迁移的脚本，尚未迁移的仍是 GDScript；迁移后的运行只能报告原项目自己也报告的错误，退出时仍占用的资源也只能是原项目也占用的。迁移顺序为 cloud、impact、hud、audio、weapon，最后 combat、enemy 和 player 一起迁移，使本语言始终不调用 GDScript，这个里程碑不需要 GDScript 类的静态视图（规范 §11.1）。最后三个放在一起，是因为 enemy 靠接口 Combat.Damageable 识别玩家，而只有本语言的类能实现接口（规范 §3.9）：单独迁移 enemy 时，敌人不再能伤到玩家，测试也察觉不到。已完成：八个脚本都以迁移后的版本运行。
5. **偿还技术债**，先于新特性：快速完成的第一版实现留下了与规范不符的行为、在多处重复的规则、说法不实的测试和文档。按正确性、验证、代码、文档的顺序逐项处理，四组都已完成。
6. **第二个里程碑**：第二次纸面迁移中 Ring 的 breakout 以迁移后的脚本运行，做法同第 4 步。Ring 的主体是 C#，breakout 由 `Root.cs` 启动：它实例化 breakout 的场景，用 Dictionary 把初始化消息交给 BreakoutManager，breakout 结束时调用它的 `EndGame()`（`breakout/Root.cs:77-96`）。引擎测试不需要 .NET：`tests/engine/ring/ring_check.tscn` 代替 `Root.cs`，发出 Ring 的 `main.md` 构造的消息；对本语言来说，C# 的 `Call()` 与 GDScript 的动态调用一样，都经引擎按名字调用。除了继承 Brick 和 Enemy 的子类，迁移的脚本都用到 GDScript 类，所以先做 GDScript 类的静态视图（规范 §11.1），再做本语言类之间的继承；其余特性按脚本的需要加入。已完成：迁移的 15 个脚本都以本语言运行。
7. **补齐第一版的语言**：第 4、6 步在真实代码上验证了做法可行、没有琐碎的阻碍，但只覆盖这两个项目用到的写法。这一步实现规范第一版其余的语言特性，§15 中对应的行同时写成测试。开始时先按 §2.1 为已有的语法和检查改出无损的 token 流、节点的 token 范围、错误节点和引用表，之后每个新特性同时满足这些约定，第 8 步的工具建在其上。改动热路径的特性各跑一次基准（§4），把代价记进提交说明，不为它优化：写进规范的运行时检查是以后的约束，定下之前要知道它的代价。验收：[实现覆盖调查](surveys/implementation-coverage.zh.md)表中的写法都得到支持，重跑调查。
8. **工具链**：规范 §13.2 的第一版工具，包括带场景部分的重命名（§13.3）。放在语言之后，因为与语言特性同时做，工具会随实现反复调整；语言定型后一次做成更简单。验收：§13.2 所列的每项工具。
9. **性能**：§4 的四组基准与 GDScript 比较，再按数据做相应的优化，包括是否生成原生代码（§6）。放在最后，因为先满足约束才谈得上快。验收：明显快于 GDScript（规范 §1.1、§12.2）。

各步尚未做完的具体工作列在仓库根目录的 `BACKLOG.md` 中。
